## Trigger and resulting behavior

When an idle check says busy, this worker releases its claim. If cancelled later during busy acknowledgement or cooldown, R3 dispatched another release. Since inbox.release checks only session/ID/state=processing, another helper sharing the same inbox could have claimed the row between those releases. The second release could return the new owner's claim to received. The two TS3 reports concern distinct hosts and do not establish a shared inbox or this incident cause.

The worker now keeps a local release_task per claimed item. The busy path creates it once and awaits it under shield. Cancellation recovery reuses that same task, whether pending or completed; it creates one only if no release has been initiated. No second release is dispatched after the successful busy release. Tracking a task rather than only a post-await boolean also covers cancellation while the first synchronous release is still in flight. Storage exceptions are not converted into success or retried. Later process_inbound_message/injection behavior is unchanged and never automatically requeued by this guard.
