# 参考资料 · 未采纳方案：PG + RLS 的配套要求

> 业主 2026-08-24 裁定（SpecDoc C.3）：**受控仓储 API 单点，不做 RLS，不做每租户独立库。**
> ⇒ 本件所述**一律不生效**，仅供日后若改裁时取用。

> ⚠️ **为什么从 SpecDoc 移出来**（业主 2026-08-25）：**没有采纳的东西不该出现在规范正文里。**

**RLS 不是「自动的机制」，它自己也需要一套纪律。配错即失效。**

| 必做 | 说明 |
|---|---|
| `ALTER TABLE ... FORCE ROW LEVEL SECURITY` | **表 owner 默认可绕**，不 FORCE 即无效 |
| **每事务 `SET LOCAL`** | 用会话级 `SET` 会把租户上下文泄漏给下一个借用连接者，**且恰在高并发下才暴露** |
| 最小权限 runtime role，**不得带 `BYPASSRLS`** | —— |
| **缺 context 默认拒** | 漏设即泄漏 |
| 所有关联表与间接查询策略 | 含 view / `SECURITY DEFINER` 审查 |
| 跨租户 admin 独立角色 | —— |
| **负测** | 必须有「越权查询被拒」的测试 |


## 原 E.3 中的三条条件性核验项（同样不生效）

| # | 核验项 |
|---|---|
| 1 | **若裁 PG+RLS**：所有租户表已 `FORCE ROW LEVEL SECURITY` |
| 2 | **若裁 PG+RLS**：runtime role 不带 `BYPASSRLS`，且为最小权限 |
| 3 | **若裁 PG+RLS**：租户上下文用 `SET LOCAL`（事务级），非会话级 `SET` |
