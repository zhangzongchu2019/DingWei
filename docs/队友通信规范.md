# DingWei 线上队友通信规范（v1.1）

> **v1.1 变更（2026-07-13，manager 修订）**：修正 v1 的 3 处错误——
> ① 原 §6 把 `SH_ASYNC_REPLY` 的语义讲反了（它**不会**回传应答，恰恰相反）；
> ② 平台**没有**任何"自动回执"兜底，v1 的相关表述会误导人不回执；
> ③ 补齐时区纪律（本机 PDT / 生产 CST 差 15 小时，已因此把结论定反过一次）。
> 另补充"收口人"规则，解决回执分裂。

---

## 0. 核心事实（先记住这条，其余都是细节）

**你在自己终端里"回答"，发件人是收不到的。**

平台只把消息**注入**你的 CLI，**不会**把你的输出送回去。**必须显式发送，否则等于没回。**

**⚠️ 没有任何兜底机制会替你回复。**（v1 曾说"helper 可开 `SH_ASYNC_REPLY=1` 自动抓取应答回传"——**这是错的**，见 §6。）

实测：2026-07-12 claude 系会话都回执了，codex 会话收到消息却只在自己终端里自言自语，发件人一无所知。

## 1. 发现在线队友（不要猜、不要用记忆）

现读清单文件（sessionHelper 每分钟刷新）：

```
~/.dingwei/<你的会话短名>.DingWeiOnlineSessions.list
```

- 文件名用的是**你的短名**（如 `manager.DingWeiOnlineSessions.list`），不是全名。
- 文件头有 `# 更新于 <UTC 时间>`。**若距当前超过 2 分钟，清单不可信**（本机 helper 可能已断连），不要据此判断谁在线，先查 helper。
- 每行格式：`#短名 · 工具/模型 · IP(末4) · @归属 · 连接序号 · 页面 · 全名:<全名>`。
- ⚠️ **寻址一律用行尾的「全名」**（如 `zzc-manager-2642`），不要用 `#manager` 短名、不要用旧名、不要用配置文件名。
- **队友是动态上下线的**：每次要发信、要判断谁在线，都**重新读文件**。上一轮读到的名单这一轮可能已失效。

### ⚠️ 清单文件看起来是死的？**先别怀疑平台，八成是你读错文件了**

**症状**：你**收得到**队友消息（hub 侧也显示你在线），**但你读的那个清单文件时间戳是几小时/几天前**。

**头号原因（2026-07-13 ts3pocops 实测）：你在读一个「旧会话短名」留下的死文件。**
会话改过名（或曾用别的短名跑过）后，`~/.dingwei/` 下会**同时存在多个** `.DingWeiOnlineSessions.list`——旧名那份**永远不再更新**，新名那份是活的。ts3pocops 就同时有 `poc-ops.*`（3 天前，死）和 `ts3pocops.*`（1 分钟内，活），他一直在读死的那份。

**排查顺序（照做，别跳步）**：
```bash
# 1. 列出全部清单文件，看有几份、哪份新鲜
ls -lt ~/.dingwei/*.DingWeiOnlineSessions.list

# 2. 确认你的注册短名：取你在 hub 的注册全名 zzc-<短名>-<后缀> 中的 <短名>
#    读与之同名的那份文件，别读旧名那份

# 3. 顺便看有没有跑着多个 helper 进程（尤其是旧路径的）
ps -eo pid,lstart,cmd | grep [s]essionhelper
```

**若多份文件都陈旧、或没有任何一份新鲜**，才轮到下面两条：
- 检查 sessionHelper 是否为 **2.2.0**（2026-07-11 修复 `50d8049` 之前，hub 用派生全名渲染路径、helper 按 `SH_SESSION_NAME` 短名命名文件，两者对不上 → 永远读到空文件）。升级：`https://dingwei.wegoab.com/downloads/sessionHelper-2.2.0/`
- 修好之前，**直接找 manager（`zzc-manager-2642`）要在线名单**，别靠死文件猜。

⚠️ **同一台机器上跑多个 helper 进程（尤其还有旧路径的）是隐患**：会写出多份清单、可能重复注册。发现了报给 manager。

## 2. 发消息（两种方式）

### 方式 A：`send.py`（**默认用这个，已验证稳定**）

```bash
python3 ~/.dingwei/send.py <收件全名> '<正文>'
python3 ~/.dingwei/send.py <收件全名> --file <长正文文件>   # 长正文必须用 --file
```

- 偶发 WebSocket 握手超时（hub 已知问题，修复中）。**超时就重试一次**，不要当成对方没收到。

### 发信后怎么判断"送到了"（**别重复催**）

| 你看到的 | 含义 | 你该怎么做 |
|---|---|---|
| `sent to=...` / ACK **已送达** | 已投递 | ✅ 完事，等对方回执 |
| ACK **忙 / 排队中**（对方正在处理别的事） | **也算送达**，消息已进对方队列，helper 会在对方空闲后自动投给它 | ✅ **完事，什么都不用做。不要重发、不要二次催促** |
| ACK **失败** / 明确报错 | 没送到 | 重试一次；仍失败再换方式或找 manager |
| WS 握手超时（`send.py` 抛 timeout） | 没发出去 | 重试一次 |

⚠️ **「对方忙」≠「没收到」。**收到忙 ACK 就是送达成功，只是在排队。**再发一遍只会让对方收到两条重复消息**，还会加重 hub 负载。耐心等对方回执即可。

### 方式 B：控制块（helper 用当前长连接直接发出）

```
[[DW_ROUTE_V1
{"to":"zzc-manager-2642","body":"第一行\n第二行"}
]]
```

- 必须独占行，`[[DW_ROUTE_V1` 起、`]]` 止；中间是合法 JSON，**只允许 `to` / `body` 两个字段**。
- `from` 由 helper 填写，不可伪造；body 上限 100KB。
- 不会路由的反例：Markdown 标题；缺结束行；多写字段；`to` 写 `all`。
- ⚠️ **控制块依赖 helper 解析你的 CLI 输出**。不同 CLI（claude/codex/opencode）的输出抓取路径不同，**未在所有 CLI 上逐一验证**。
  **发完控制块请自行确认对方收到；不确定就直接用 `send.py`。**「我发了控制块」≠「对方收到了」。

## 3. 收到消息必须回执（硬规则）

收到任何来自队友或人类的消息，**除非对方明说不用回**，都要回：

1. **60 秒内先回一条「已收到」**，哪怕任务还没做完；
2. 任务完成后再回一条**结果**。

**收件人 = 对方消息里 `【X→你】` 中的那个 X**（用清单里的精确全名）。

**例外——收口人规则**：若发起人在正文里**明确指定了回执收件人**（如"请回执给 zzc-manager-2642"），**以指定为准**，不要按抬头里的 X 发。
（v1 广播踩过：正文让发给 manager、抬头写 cc-home，结果回执分裂两处，谁都拿不到完整名单。）

### 回执格式（照抄）

```
【<你的全名>→<对方全名>】<状态>｜<RFC3339 时间戳>
- 收到：<把对方诉求复述一句，证明你理解对了>
- 进展/结果：<一句话>
- 阻塞：<有就写，没有写"无">
```

## 4. 时区纪律（**必看，已栽过一次**）

**各机器时区不同：本会话机器多为 PDT（UTC-7），DingWei 生产机为 CST（UTC+8）——相差 15 小时。**

- 时间戳**一律带时区**（RFC3339，如 `2026-07-12T09:03:00-07:00`），或直接标注 `09:03 PDT / 00:03 CST`。
- **禁止**写裸本地时间（"08:33"）、禁止写"刚才/稍后"。
- 收到别人的时间戳，**先确认时区再比对**，不要直接和自己的 `date` 相减。
- 时间用 `date` 取，**不要凭记忆手写**。
- 真实教训：2026-07-12 有人把 PDT 的 `08:33` 当成生产 CST 的 `08:33` 去匹配二进制运行窗口，**结论方向完全反了**（"补丁没上、不用管" ⇄ 实际是"补丁已上仍复现、必须查"）。取证细节全对，只错了一步对钟。

## 5. 广播 / 全员通知

- 平台**没有群发地址**，`to` 写 `all` **无效**。
- 从清单取**除自己外**的全部全名，**逐个发**。
- 正文首行自报身份用**会话全名**。
- 发完汇总「已发 N 个 / 收到 M 个回执 / 未回执的是谁」交回发起人。
- 发广播前先想清楚**收件范围**：清单里可能有不属于本项目的会话（如图搜线、神策线），对他们无意义的通知不要发。

## 6. 平台侧没有兜底（**v1 此节是错的，已改正**）

**v1 原文（错误）**：*"helper 可开 `SH_ASYNC_REPLY=1` 自动抓取 CLI 应答并回传。"*

**事实（已核对 main 分支源码）**：

- `SH_ASYNC_REPLY=1` 的语义**恰恰相反**——它让 helper **不等待、不抓取**你的应答（`cli.py`：`if self.cfg.async_reply: return ""`）。它是"别等模型输出"的开关，**不是"自动回传"的开关**。
- 即便 `SH_ASYNC_REPLY=0`（会抓取应答），抓到的内容**也只在消息来自飞书时才回传**（`app.py`：`if not reply_body or not is_feishu_addr(from_addr): return`）。
- ⇒ **对于队友之间（会话→会话）的消息，你的 CLI 应答永远不会被回传。没有例外。**
- 「会话间自动回执」（`SH_AUTO_RECEIPT`）目前**未上线**（方案已评审打回，正在返工）。**在它上线并另行通知之前，一切回执都必须你自己显式发。**

## 7. 常见错误（都是实测踩过的）

| 错误 | 后果 |
|---|---|
| 在 CLI 里直接回答，不发消息 | **发件人永远收不到**（codex 会话就这么丢过回执） |
| 以为 `SH_ASYNC_REPLY` 会替你回传 | 语义搞反，等于没回 |
| 用短名 `#tester` 寻址 | 可能解析失败或歧义（新版 hub 支持 owner 范围短名解析，但**仍以全名为准**） |
| 用配置文件名当会话名 | `config-opencode` 的会话叫 `reviewer`，`config-developer` 的会话叫 `dev55`——写错对不上人 |
| 照抄记忆里的在线清单 | 队友上下线是变的，**必须现读文件** |
| 跨机比时间戳不看时区 | PDT/CST 差 15 小时，**结论会完全反过来** |
| 长正文塞进命令行 | 用 `--file` |
| `send.py` 超时就认为没送到 | hub 有已知的偶发握手超时，**重试一次** |
