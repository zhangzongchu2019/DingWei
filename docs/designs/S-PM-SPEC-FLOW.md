# S-PM-SPEC-FLOW（一页设计，待审）

基线：integration/spec5ff-r37，29e63f9963dedcc32010ca89265d78ba12664bf2。只描述产品设计，不含实现或上线授权。目标是让 PM 无需显式“创建”即可起草、借 Agent 结构化补全，并让审查与任务拆解绑定到确切修订。

## PM 流程与状态

打开“新建”后，首次输入经约 700 ms 节流自动建立一份可变工作草稿；后续自动保存只更新这同一工作草稿，不制造不可变修订。每次写入带 expected_version 与 content_sha256 做 CAS。冲突时服务端保留本地提交字节和当前服务端字节两份并显示差异；用户选择恢复／合并后再提交，绝不静默覆盖。首存前浏览器本地保留恢复副本，页面显示“保存中／已保存”。

只有三类显式动作会把工作草稿固化为不可变修订：①接受 Agent 的一条或多条建议并应用到结构化区；②转给他人审查；③审查完成。每次固化均在同一事务内核对工作草稿版本与 SHA，写入修订并更新工作草稿基准；转审接收者完成已钉定修订时不重复造版，重放只返回原结果。点击“Agent 协助”本身不固化修订：请求绑定当时的工作草稿 version＋content SHA、spec、编辑者、实际 Agent 与 request_id。回信仅在该工作草稿仍匹配时有效；编辑后旧结果标为过期，须重新协助。转审后接收者的协助则绑定已固化修订 SHA。

| 流程状态 | 可执行动作及转移 |
| --- | --- |
| 草稿／编辑中 | 当前编辑者编辑并自动保存同一可变工作草稿；可请求 Agent 协助，逐条接受／忽略。接受会将所选建议写入结构化区并固化新修订，忽略只追加决定记录、不固化修订。当前编辑者可自行点“审查完成”：须对当前工作草稿 SHA 重新运行 Agent 协助，且对本轮每条建议与审查问题明确表态。若接受项改变结构，接受动作先固化新修订并使该轮结果过期，须对新 SHA 重跑；只有当前轮仍绑定当前 SHA 且所有条目均有决定时，才固化当前内容并把审查完成绑定到该修订 SHA。转给他人审时先固化工作草稿，再钉修订号与 SHA。 |
| 审查中（已转交） | 原编辑者与 owner 不得改正文；指定接收者只读，可对钉定修订运行 Agent 协助、逐条表态，然后“审查完成”或“退回（附异议）”。完成要求本轮协助绑定该修订 SHA 且全部建议和问题均有接受／不接受记录。接收者不能编辑或应用建议；任何需改正文／结构的建议只能退回。 |
| 退回／编辑中 | 退回原因和逐项意见追加留档，回到原编辑者并解锁；自动保存继续更新工作草稿。应用修改或接受建议时按三类固化动作产生新修订；旧协助与审查决定只作历史。再次转审先固化再重新协助。owner 可撤回审查并交还原编辑者，但不得替接收者完成审查。 |
| 审查完成 | 完成状态绑定已固化的当前修订 SHA。页面直接提供“定稿并进入拆解”按钮；当前编辑者／owner 可触发现有 final＋splitting 门，一次操作按现有规则定稿并进入拆解，不新增流程。转审接收者不能定稿或拆解。 |

旧 final spec 不追写新历史：已存在任务和拆解保持；旧 final 标成 legacy 历史态。新建拆解必须有当前修订审查完成标记；未标记的旧 spec 须派生新修订后走新流程，不能静默补标。

## 数据与 Agent 协议

SQLite schema_migrations 建议新增 0064_console_spec_flow.sql（落地前核最新号）。新增可变工作草稿记录（expected_version、content_sha256、正文与结构化区；冲突时保存两份待处理字节），不可变 revision 只由上述三类动作写入。revision 增 source_refs_json（来源 URI／版本／SHA／定位）和 norm_anchors_json（规范、版本、章节／条款及引用摘要）；spec 流程绑定表记录状态、原编辑者、审查接收者、返回目标、锁定 revision／SHA；Agent run 与条目表记录类别（验收标准、来源引用、规范锚点、审查问题）、候选、绑定的工作草稿 version／SHA 或修订 SHA、实际 Agent、期限；另设只追加的逐项表态与审计事件。已有单锚字段保留并按一项 legacy anchor 读取；新修订 SHA 覆盖新增结构字段。

“Agent 协助”复用 R8 认证请求／回信通道、PG 当前成员／active 身份锁、SQLite CAS 和提交前重核；一次请求返回上述全部候选类别。Agent 只能提案，不写工作草稿／revision、不作人类决定或定稿。当前编辑者接受一项提案时显示差异、在 CAS 事务中应用到工作草稿并固化为新修订；相应旧 run 立即过期，须对新 SHA 重新协助。请求重放返回原结果；旧 SHA、改派、撤权、超时或伪造身份拒绝。接收者权限只限对本次钉定修订协助及完成／退回；所有正文／结构写入口（含旧 API、MCP、D1、clarification 转换）由服务端统一拒绝，不能只隐藏按钮。

## 权限、旧流程与兼容

| 主体 | 草稿／编辑 | 审查中 | 定稿／任务门 |
| --- | --- | --- | --- |
| 当前编辑者 | 编辑、自动保存、Agent 协助、逐项接受／忽略；对当前修订自行审查完成；指定并转审 | 只读；可由 owner 撤回后恢复编辑 | 审查完成后可触发既有 final＋splitting 门 |
| 指定接收者 | 无正文权限 | 只读、逐项表态、审查完成或附异议退回 | 不可定稿、拆解或改派他人 |
| owner | 建草稿、指定接收者、撤回／归档并审计；仅当前编辑者身份才可写正文 | 不可越权改正文或替审；可撤回 | 可按既有权限触发 final＋splitting；仍须当前修订审查完成绑定门 |

D1 模板六项必填、实际责任接受、完整档风险门不被 Agent 建议代替；接受模板建议可填结构字段，但不能伪造签收或 D1 回执。S-SPEC-CLARIFICATION 仍是指定 revision 下的追加讨论；答复不改正文、不自动满足审查。把 clarification 提炼进 spec 必须由编辑者显式接受为新修订，并重新 Agent 协助。

迁移只增表／列和门控，旧 revision／链接／历史 review 可读；旧 helper 未协商 spec_assist_v1 不收新信封，旧 Hub 不支持新写协议时不发请求。新流程按能力门启用。回滚先关新写入口并冻结带 flow 记录的 spec 写入，保留新增表和审计；旧 Hub 可只读基础 spec／旧修订，但不得对有新流程数据的 spec 写入或拆解。不得删迁移、压平修订或用旧二进制可写回滚。

手机端沿用 Console 响应式页面：390／820 px 单列编辑、自动保存状态、逐条接受／忽略、差异冲突与审查动作可触控（目标至少 44 px），不依赖 hover；弱网结果未知时用原 request_id 查询，不盲目新建或覆盖。

## 验收与撤修计划（设计阶段，未运行）

- 首次输入建立一份工作草稿；连续自动保存只更新该草稿、不增加不可变修订；CAS 冲突保全两边字节；撤 CAS 或本地恢复后红。
- 接受建议、转审、审查完成各只固化一次且可幂等重放；忽略不固化。协助绑定工作草稿 version／SHA，编辑后旧 run 过期；转审后绑定不可变修订 SHA。撤任一绑定／幂等门指定红。
- 作者自行审查完成要求当前 SHA 的新协助与所有条目明确表态；缺任一条件拒绝。接收者只能完成／退回且所有服务端写路径拒绝其修改。
- 审查完成后直接显示“定稿并进入拆解”；仍须现有 final＋splitting 门，接收者不能定稿；无审查绑定时即使 final/splitting 也不能新建任务。
- 退回恢复原编辑者并留异议；转交、自动保存、Agent 回信并发仅一个 CAS 成功；旧任务与 legacy final 不被迁移误删／误改。
- D1 未接受责任、clarification 误写正文、旧 helper／Hub 不识别新能力均失败关闭；迁移前后旧读兼容、回滚保留新数据且无旧版写入。
- 手机／平板 390／820 px、长正文、无 hover、弱网保存冲突与恢复浏览器门。
