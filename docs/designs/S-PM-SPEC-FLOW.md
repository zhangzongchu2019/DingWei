# S-PM-SPEC-FLOW（一页设计，待审）

基线：integration/spec5ff-r37，29e63f9963dedcc32010ca89265d78ba12664bf2。只描述产品设计，不含实现或上线授权。目标是让 PM 无需显式“创建”即可起草、借 Agent 结构化补全，并让审查与任务拆解绑定到确切修订。

## PM 流程与状态

打开“新建”后，首次输入经约 700 ms 节流自动建立草稿并保存；后续保存均以 expected_revision + content_sha256 CAS 追加不可变修订。无需点创建。页面显示“保存中／已保存”。首存前浏览器本地保留恢复副本。遇 CAS 冲突时保留本地与服务端两份并显示差异；用户选择继续编辑为新修订或放弃本地副本，绝不静默后写覆盖。

| 流程状态 | 可执行动作及转移 |
| --- | --- |
| 草稿／编辑中 | 当前编辑者修改和运行 Agent 协助；每条建议可逐条接受或忽略。接受将建议写入结构化区并 CAS 追加新修订；忽略只追加决定记录。任何正文或结构化内容变化都会使旧 Agent 结果不再满足审查门，需对新当前修订重跑。编辑者转审时钉接收者、修订号和 SHA。 |
| 审查中 | 原编辑者与 owner 均不能改正文；接收者只读，可对钉定修订运行 Agent 协助、逐条表态，然后“审查完成”或“退回（附异议）”。接收者接受了需改正文/结构的建议时只能退回，不能直接应用；完成要求本轮协助绑定当前 SHA 且所有建议和问题均有接受/不接受记录。 |
| 退回／编辑中 | 退回原因和逐项意见追加留档，回到原编辑者并解锁；修改产生新修订，旧协助和审查决定仅作历史，再次转审必须重新协助。owner 可撤回审查回原编辑者，但不得替接收者完成审查。 |
| 审查完成／final | 审查完成只标记某个当前 revision/SHA，不自动定稿。之后沿用现有人类 finalization；任务拆解要求 review_complete 与现有 state=final AND task_state=splitting 同时满足。final 继续不可编辑。 |

旧 final spec 不追写新历史：已存在任务和拆解保持；旧 final 标成 legacy 历史态。新建拆解必须有当前修订审查完成标记；未标记的旧 spec 须派生新修订后走新流程，不能静默补标。

## 数据与 Agent 协议

SQLite schema_migrations 建议新增 0064_console_spec_flow.sql（落地前核最新号）。只追加：revision 的 source_refs_json（来源 URI/版本/SHA/定位）和 norm_anchors_json（规范、版本、章节/条款及引用摘要）；spec 流程绑定表（状态、原编辑者、审查接收者、返回目标、锁定 revision/SHA）；Agent 协助 run 与条目表（类别：验收标准、来源引用、规范锚点、审查问题；原始候选、run 修订/SHA、实际 Agent、期限）；独立追加的逐条表态记录（decision、理由、主体、时刻）及审计事件。已有单锚字段保留并按一项 legacy anchor 读取；旧修订不改写，新修订 SHA 覆盖新增结构字段。

“Agent 协助”复用 R8 的认证请求／回信通道与 PG 当前成员/active 身份锁、SQLite CAS 和提交前重核；一次 console_spec_assist_request/result 绑定 spec、revision、SHA、request_id、当前编辑者、实际 Agent 与 deadline，返回上述全部候选类别。Agent 只能提案，不直接写 revision、作人类决定或定稿。每次接受由当前编辑者对一项提案显示差异后单项提交为新修订；请求重放返回原结果，旧 SHA、改派、撤权、超时或伪造身份拒绝。接收者权限仅限对本次钉定修订作协助决定及完成/退回；任何正文/结构写入口（含旧 API、MCP、D1、clarification 转换）均由服务端统一拒绝，不能只靠隐藏按钮。

## 权限、旧流程与兼容

| 主体 | 草稿/编辑 | 审查中 | 定稿/任务门 |
| --- | --- | --- | --- |
| 当前编辑者 | 编辑、自动保存、Agent 协助、逐项接受/忽略、指定并转审 | 只读；可由 owner 撤回后恢复编辑 | 不能代接收者标审查完成 |
| 指定接收者 | 无正文权限 | 只读、逐项表态、审查完成或附异议退回 | 不可定稿、拆解或改派他人 |
| owner | 建草稿、指定接收者、撤回/归档并审计；仅当前编辑者身份才可写正文 | 不可越权改正文或替审；可撤回 | 仍须通过当前 final + splitting 与审查修订绑定门 |

D1 模板六项必填、实际责任接受、完整档风险门不被 Agent 建议代替；接受模板建议可填结构字段，但不能伪造签收或 D1 回执。S-SPEC-CLARIFICATION 仍是指定 revision 下的追加讨论；答复不改正文、不自动满足审查。把 clarification 提炼进 spec 必须由编辑者显式接受为新修订，并重新 Agent 协助。

迁移只增表/列和门控，旧 revision/链接/历史 review 可读；旧 helper 未协商 spec_assist_v1 不收新信封，旧 Hub 不支持新写协议时不发请求。新流程按能力门启用。回滚先关新写入口并冻结带 flow 记录的 spec 写入，保留新增表和审计；旧 Hub 可只读基础 spec/旧修订，但不得对有新流程数据的 spec 写入或拆解。不得删迁移、压平修订或用旧二进制可写回滚。

手机端沿用 Console 响应式页面：390/820 px 单列编辑、保存状态、逐条接受/忽略、差异冲突与审查动作可触控（目标至少 44 px），不依赖 hover；弱网结果未知时用原 request_id 查询，不盲目新建或覆盖。

## 验收与撤修计划（设计阶段，未运行）

- 首次输入自动落草稿；刷新可恢复。并发编辑 CAS 冲突两边字节保全；撤 CAS 或本地恢复后红。
- 一次协助四类结果齐全；真实来源 Agent、当前 SHA、超时、重放校验。逐条接受只新增一版且写入对应结构；忽略不改版；内容改后旧 run 不能完成审查。撤身份/SHA/幂等门各指定红。
- 审查中接收者经 UI/API/MCP/旧路径均不能写；未经当前修订新协助或有未表态项不能完成；退回恢复原编辑者并留异议；transfer、自动保存、Agent 回信并发仅一个 CAS 成功。撤任一服务端写门指定红。
- review_complete 缺失时即使 final/splitting 也不能新建任务；具备修订匹配标记仍须现有 final+splitting；旧任务与 legacy final 不被迁移误删/误改。
- D1 未接受责任、clarification 误写正文、旧 helper/Hub 不识别新能力均失败关闭；迁移前后旧读兼容、回滚保留新数据且无旧版写入。
- 手机/平板 390/820 px、长正文、无 hover、弱网保存冲突与恢复浏览器门。
