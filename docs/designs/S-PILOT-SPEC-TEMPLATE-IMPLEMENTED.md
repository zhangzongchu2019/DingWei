# D1 implementation: light PRD → spec

Approved light design: `28af2a0eabf795476c9ea9328ccc967cf5bea40d`. This is the fourth candidate in the approved pilot sequence, based on D3 `48befea2bfbd8cbe0685f35be5a8c5fbbfad4576`; it does not replace the separately approved 0.2.3.6 upgrade artifact. No deployment, seat change, live PRD request or business action is included.

The Specs workspace exposes “试点：PRD → spec 模板” in its navigation, opening `/console/spec-templates` from an embedded workspace at the top level. Its three steps are: fix a traceable source and bounded scope; expand six fields per requirement/case and obtain actual principal receipts; confirm the immutable version. Unknowns stay in the pending pool with field paths. Multi-person review is explicit; a single person uses a separate reviewing Agent. The same person may accept execution and business-signoff responsibility, but this does not record actual execution, test success or final business signoff. Any new draft version requires new receipts. Withdrawal appends history and blocks subsequent gates. No automatic CLI wake/execution is added by D1.

Source import accepts only typed Feishu/Lark document identities. The separately authorized provider connector adapter remains unconfigured: a link-only request yields `pending_config`, never a simulated successful import. The usable fallback is a human-authorized manual export, labelled as such, with source revision/time and server SHA. There is no arbitrary URL GET, redirect, borrowed cookie or datad path. Imported text is data, never instructions. The page provides structured templates and the original STOCK sample; it does not claim automatic semantic PRD extraction by a model. The PM supplies and confirms the extracted requirements.

`pilot-spec-light/1` produces deterministic Spec Kit artifacts: constitution, spec, independent reviewer checklist (all unchecked), contract JSON and structural missing-field analyze JSON. The analyze result is not an independent semantic audit or a claim that external SpecDoc rule evaluation ran. STOCK retains all 13 original IDs, only `B06-applied-lost` has budget 1, all other budgets are zero; every result starts NOT_RUN. Selecting this scaffold is not selecting the pilot's real first scope or verifying all 49 cases.

Light mode does not require full SpecDoc fields. Production/security flags, including the corresponding seven-attribute declarations, force full mode. Full mode additionally requires valid attribute enums, rule version/IDs, six content faces, analyze/contract/probe/human-review references, a named human review receipt and either explicit absence of action authorization (not valid for production actions) or specific scope/purpose/source/expiry. These are recorded external gate references and a scoped human review, not fabricated external security approval or action permission. The explicit invited human accepts their own review role; no unrelated platform-admin role is invented. Parent full mode cannot be silently bypassed by a light child. Downgrading a successor needs owner confirmation of a new revision with a reason and risk-clearance reference. All responses still say execution_authorized=false and business_signed_off=false.

Confirm creates an editing spec; actual R8 review callback, human issue handling and finalize are still required. The actual spec pre-reviewing Agent cannot be any declared execution Agent. In single-person mode it must be one of the actually accepted reviewing Agents; different entries may still name different task reviewers, which R9 enforces per linked criterion. A whole-spec R8 review is distinct from later task-case review. Final parent revision/SHA and source remain pinned. Normal/R8 revisions and legacy derive retain mandatory template enrollment; lack of a new matching binding fails closed. Templates use random unreachable legacy edit-capability hashes, not a digest of public plan fields.

Final specs cannot be rewritten. A change derives an exact historical copy at successor revision 1, then appends actual changed revision 2. An impact record blocks old-scope tasks. D3 `confirm_change` gains optional `new_spec_id`: only an owned, nonarchived, direct derived successor with a real current revision of at least 2 is accepted. Same-spec newer-revision behavior remains. Both paths retain original spec/review history and do not move old tasks onto latest text. The end-to-end regression uses real derive/append operations, not SQL invention of a final revision.

For opted-in templates, proposal creation starts only planned/proposed; task start/resume/complete, reassignment and old driver/legacy status entrances recheck the contract. Execution must enter R9's explicit grouped assignment and match the accepted per-criterion execution/review principals. Existing unenrolled specs retain their old behavior. Task actor/group permissions remain the current PG-authorized R9 permissions; historical responsibility receipts do not grant future permissions or business signoff. D2 remains the single blocker input/wake mechanism.

Authorization uses actual human Console cookies or dedicated Agent bearer credentials, never both. PG locks current actor/owners/proposed principals through the bounded SQLite operation, with final checks and a template advisory key. SQLite rechecks the discovered immutable reference/version. Agents can list/read only their current explicit invitations and accept/withdraw their own execution/review responsibilities via `dw_spec_template`; no source raw text, plan edit, human confirm, full human review or business signoff is exposed. Current role removal revokes access. No task/group right follows from a template invitation. Lists/parents/sources use bounded keyset pages.

Storage is additive SQLite `schema_migrations` entry `0060_pilot_spec_template.sql` (the older draft reservation 0057 was never used): ten source/template tables and D3's successor reference column. PG schema and runtime dependency lock are unchanged. The old r32.1 binary is tested for startup/read preservation only. It does not enforce D1/D2/D3 gates; freeze pilot writes before any rollback. Dropping new tables/columns after real adoption loses consent/source/impact records and is not an operational rollback plan. The migration failure test uses only disposable local DBs.

Hub/helper candidate version remains 0.2.3.7 from the pilot batch. MCP exposes 21 tools. Old helpers fail safely and need a separate authorized upgrade to see the new tool. No change to the approved oaagent 0.2.3.6 package, runtime lock, image, host firewall or rollout source is made.
