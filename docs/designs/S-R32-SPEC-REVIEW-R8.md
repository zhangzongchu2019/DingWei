**状态与交接定稿（闭合审查166320df两项）。** review请求允许editing/review→review+pending，回信后仍review；criteria允许editing/review→原状态+pending→原状态+awaiting_confirmation，确认才变revision n+1、editing。final、archived、editing_closed或下游引用锁定均不得发criteria/确认；取消、超时、失败不追加修订、不伪造通过gate，保持当时spec状态（预审已置review则留review），旧数据留档。确认必须再核上述状态和revision/SHA，任一漂移409；重放同确认幂等返回已创建revision，不再append。criteria生成新修订的fresh-review标记由0056旁表记录，finalize存储门校同revision的受信Agent回信及人确认，不能经旧人工接口补一个伪gate绕过。

活动请求交接在原 `POST .../workflow/transfer` 增可选 `cancel_request_id,expected_revision,expected_content_sha256`，页面显示“取消当前请求并转给”并要求显式确认；未传精确活动id的普通transfer仍409。只允许仍为当前编辑人的active人类发起；先验证target有效/非本人及expected锚，再在**同一个SQLite事务**把匹配pending或awaiting_confirmation置cancelled、作废待确认候选/未发outbox（终态留审计）、释放请求锁、执行原transfer设置目标编辑人与editing/review状态。任一步失败整事务回滚，不能先取消后发现target无效；确认权不转移，接收人须选本人在线Agent发新请求/新id。旧发起人不能确认/编辑；旧Agent既不能读请求快照也不能新写结果，迟到WS/HTTP回信409，重复投递不复活。取消后端点拿到已发正文无法撤回，但不能再凭旧授权获取数据或落库。

并发计划：pending期间cancel-and-transfer vs回信、awaiting_confirmation期间cancel-and-transfer vs确认，用事务屏障覆盖两种顺序。取消先提交则回信/确认409、无gate/无新revision；回信先提交则取消CAS409、原gate保留，刷新后走普通transfer；确认先提交则交接锚过期409、新修订只建一次，刷新后普通transfer。不得静默取消一个已经完成的请求或转错revision。补editing/review两起点→待确认→n+1 editing→fresh预审→人确认→final完整正例；final/archived/锁定负例，旧gate仍可查但对n+1无效，stale-confirmation/旧编辑人/跨owner Agent/late reply负例。撤状态门、旧gate隔离、原子取消交接、锚CAS各须命中指定红（不能被别门抢红）。

**身份、范围和重放。** 选择范围沿用现有 presplit 的 owned-Agent 列表与 active owner 身份投影，本批不扩大为任意在线跨用户 Agent；transfer 后由新编辑人选其可用 Agent。请求行绑定不可变 `request_id`（随机128位以上）、kind、spec_id、revision/SHA、发起人 principal、Agent ID、认证 endpoint、generation、created_at/deadline、Hub boot generation。WS 回包从实际 sessionClient 解析 Agent；MCP HTTP 从 dedicated Agent bearer 解析，拒 cookie/混合认证；都调用同一接收器，禁止信任 Body/From/Meta 自报身份，拒不存在/停用/换身份端点。请求快照最多1MiB，回包最多128KiB、issues最多100条、criteria最多100条且每条cases最多100项，拒超限不截断；关联字段全部匹配且 pending 才能消费；同 Agent 同 payload 摘要的重发返回原结果，不再写 gate/revision，异 payload 或已取消/超时/旧代次返回409，其他 Agent 403。人类接口不因 request_id 获得额外权力。列表/获取请求只向该请求当前认证 Agent 返回，状态读取失败关闭，先选后读及 PG 锁内再次检查 Agent、状态、编辑人、revision，补改派/transfer 竞态格；另保留跨owner Agent拒绝格（组长已采纳owned范围）。

**超时和投递。** 等回包180秒（含投递），criteria 回包后的人工确认15分钟；使用服务端 UTC，测试注入时钟。发送前要求在线且已协商 `spec_review_v1`，离线409 `agent_offline`，旧 helper409 `helper_upgrade_required`，发送失败502并终止；请求发出后掉线不无限排队，180秒到期明确 `timed_out`。GET/所有写入均先在事务内惰性到期，另周期扫尾；Hub 重启把旧 boot 的 pending/awaiting_confirmation 明确置 failed，释放锁，迟到回包拒。请求创建与待发 outbox 同事务，发送器仅在deadline内重取已绑定且仍协商能力的在线会话；绝不向未协商的新连接补送；gate/候选写入与请求终态、审计同 SQLite 事务；掉回复可按同 client_request_id 查原结果，不自动新建。终态原因在页面可见；可靠投递 ACK 只代表收到，不代表业务完成，不延长期限。重复投递只处理一次。

**helper / MCP 通道。** 新增 `dw_spec_review_requests`（本人请求的有界列表/按id获取）和 `dw_spec_review_reply`（kind+request_id+revision+结构化 issues 或 criteria/cases）；MCP→本机 IPC→固定 Hub HTTP `GET /api/agent/console/spec-review-requests`、`POST /api/agent/console/spec-review-requests/{id}/result`，15秒 HTTP 超时，不重定向、不接受目标URL/凭据参数，不把 bearer 交给 CLI。helper 只在完整版本具备此通道时宣告 spec_review_v1；Hub 只有向该能力会话下发两个新请求类型，不把它们降级成普通消息。新版 helper 将合法 Hub 系统请求作为“人显式请求的 spec 分析”展示，正文为待分析数据，不允许据其执行命令；回包经专用工具，不自动 finalize。不认识/未协商类型安全忽略或仅本地提示升级，不注入用户指令、不自动回信；Hub 拒 Agent 伪造新系统类型。driver 与 desktop 共享分类和来源校验，processed/delivered ACK 语义及 R9 dw_inbox 本地已读保持。Hub/root/helper/MCP 文档与版本断言同步 `0.2.3.6`（R9 为0.2.3.5），不升级运行中 helper；真旧0.2.3.5对照证明不收到新信封，直接兼容输入安全格独立验证。

**与 R9 授权的交互。** 此请求是限时特定 spec 快照分析授权，不是任务指派，不赋予 dw_task_list/update、任务确认或普通 spec 写权；R9 仍以当前角色+PG成员锁逐次核权。R8 owned-Agent 用 PG active Agent/owner 与当前人类编辑人核权，普通读写事务 FOR SHARE 期间做 SQLite 请求CAS/落库，提交前再核；不声明跨库原子提交。回包若 Agent/owner吊销或transfer编辑人改变即拒，标请求失败/释放，后台 reconciliation补漏；PG错误拒读写，不退化无锁。PG释放/响应丢失的提交不确定回 outcome_unknown，按原 request_id 查状态；不能假称已回滚。R8不凭R9旧任务指派绕过当前身份；R9接口不因处于R8锁定而新增写权限。
