## §0 本件的定位与边界

### 0.1 三份材料各管什么

| 件 | 回答的问题 | 变了要做什么 |
|---|---|---|
| **SpecDoc** | **该怎么做**（规则、判据、门） | 走 §4.6 准入 + 评审 |
| **原型** | **人看到什么**（入口、字段、交互） | 走 §25.3 查阅入口的展示要求 |
| **本件（架构设计）** | **系统由什么构成、怎么落到机器上** | 走 **§25.3 架构评审**，L3 |

🔴 **本件不重复 SpecDoc 的规则，只锚不述。** 凡属规则的一律写 `§X`，不抄原文。
理由是这一轮刚踩过的坑：**两处写同一条规则必然漂移**，第二处会成为错的事实源。

### 0.2 抽象层原则（业主定）

> **架构描述停在能支撑理解与决策的抽象层。**
> 抽象层记录的不是「实现是什么」，是「**你据此该怎么做**」。

⇒ 本件**不画**真实 IP、主机名、端口全集、代理链细节。
业主原话：「实现了从 A 城到 B 城的集群，但对研发来说理解为同一套机制，
至于实际数据在哪里如何存储，不影响开发测试就可以了。」
⚠️ 那些内容属 **D0 · `restricted`**（§11.4a），不落本件（§22.4 S0 亦不落任何文档）。

### 0.3 🔴 现状 / 目标 / 差距 三分，不得混写

架构文档最常见的失败是**把「想要的」写成「有的」**。本件每个要素强制标注：

| 标记 | 含义 |
|---|---|
| ✅ **现状** | 代码里已有，本件写作时实测过 |
| 🎯 **目标** | SpecDoc 已定但代码未实现 |
| ⚠️ **差距** | 现状与目标的距离，**须有承接的子 spec** |

⇒ **凡标 🎯 者，不得作为「系统已具备」对外陈述**（同 E.4 #58：断言作用域不得大于实际覆盖）。

### 0.4 本件自身的门

**本件尚未过架构评审 ⇒ 不得作为施工依据**（§25.3）。
与 SP7a「形态已定为受控仓储 API」是两回事：**形态定了，设计未过审**。

# 第一部 · 业务架构

## §1 业务实体与关系

```
  人（企业 IM 身份）
   └─→ 租户（业主级隔离域，隔离主体）        ← §21.1 三级映射
        ├─→ 项目（D3 归属域）
        │    └─→ 任务 / node（执行单元）
        └─→ 会话 / Agent（执行主体，持 token）

  横切三类资产（共用归属域轴 D0–D3 与晋升链）： ← §11.2
    知识条目 · skill（过程性记忆） · MCP
```

**一个人可在多个租户有身份**（§21.1）—— 这条决定了很多东西：
周报「人视图」须按 `(人 × 租户)` 出（§20.1）、跨租户读须 §22.1c capability（SA-10）。

## §2 业务主链：从需求到知识沉淀

```
  ① 需求提出
      └─→ ② spec 起草（五个必备面，§4.7.1）
            └─→ ③ 准入硬门（§4.6.2，机器判）
                  ├─不过─→ 【待完善池】（带结构化缺项原因）──回炉──┐
                  │                                                  │
                  └─过──→ ④ 人审（§4.6.4）──不过─→ 【待完善池】──────┘
                              └─过─→ 【待认领开发任务池】
                                        └─⑤ 认领（此后正文不得再改，§4.7.3 #3）
                                              └─⑥ node 派发（不可变快照，§11.6）
                                                    └─⑦ 门（§7 门禁纪律）
                                                          └─⑧ 收口（§8.2 四交付物）
                                                                └─⑨ 知识沉淀（§12/§13）
                                                                      └─⑩ 复盘（§9.2）
```

**三处是这条链的承重点，其余都可调**：

| # | 承重点 | 为什么 |
|---|---|---|
| 1 | **③④ 之间机器与人的分工** | §4.6.4：机器决定「是否值得占用人审」，**不决定「是否需要人审」** |
| 2 | **⑤ 认领后 spec 冻结** | 否则「认领的是 A、做的是 B」，而 `acceptance` 是按 A 生成的 |
| 3 | **⑥ 派发快照不可变** | 修订 node 不依赖 worker 记忆（§11.6）；快照可变则复现不可能 |

## §3 角色与职责边界

| 角色 | 决断什么 | **不**决断什么 |
|---|---|---|
| 业主 | 产品定义 · 资源投入 · 跨域裁定 | 工程实现选型（§28 · 本席自裁范围） |
| 平台级 ops | D0 资产 · 平台域基线（§24）· 企业统一资源（VPN 等） | 租户内业务优先级 |
| 业务线 ops | D1 资产 · 其辖下租户分发 | 平台基线 |
| 租户级 ops | D2 资产 · 该租户周报定稿 | 跨租户读（须 §22.1c） |
| 项目管理方 | D3 资产 · 任务收口 | spec 准入判定 |
| 门方（reviewer） | checklist 打勾（§4.1，**reviewer-owned**） | 自己执行被审的活（§7.2） |
| implementer | 执行 | **不得自签门 PASS**（§7.2） |

🔴 **同一人可兼多角，但同一件事上不得既是执行者又是门方**（§5.8 · E.1 #3）。

## §4 业务边界：明确不做的事

| 不做 | 理由 |
|---|---|
| 不引入新流程引擎 | §4.5：保留 `mcsd` 的调度语义与契约 |
| 不做评级 / 评分卡 | §4.6.1：打分制一定退化成主观，且综合评分会把一票否决项平均掉 |
| 不做每租户独立库 | C.3：跨域读是常规高频动作，独立库把它变成 N 库扇出 |
| 不做 RLS | C.3 业主裁：成本考虑；残余面由代码评审把关（§22.2c） |
| 不把审批拆成多入口 | §25.1：单一 typed 待决队列 |

## §8 现状拓扑（抽象层，不含主机标识）

```
   企业 IM / 渠道                    浏览器
        │                              │
        ▼                              ▼
   ┌──────────────────────────────────────────┐
   │  nginx（统一入口 · 反代 · 认证）          │  ✅ deploy/nginx-dingwei.conf
   │   /dingwei/  /dingwei/ws/  /schedule/    │
   └───────────────────┬──────────────────────┘
                       ▼  127.0.0.1（不暴露裸端口）
   ┌──────────────────────────────────────────┐
   │  workpulse（主体进程）                    │  ✅ systemd: workpulse.service
   │   admin · portal · view · m8 · bus …     │     + workpulse-livez.timer 探活
   └───┬─────────────┬──────────────┬─────────┘
       ▼             ▼              ▼
   mcsd          dingwei-datad   feishu-fanout / fcs
   （调度）       （派发·PG）      （出站·渠道凭据）
```

✅ **实测要点**：
- nginx 反代到 **`127.0.0.1`**，公网访问一律经 nginx，**裸端口不可达**
- systemd 管进程 + 独立 livez timer 做探活
- `docker-compose.yml` 仅含 `workpulse` / `workpulse-data` 两项，**非全量编排**

⚠️ **差距**（v0.2 改写，乙域 terra AD-SA-02：原文只点了「缺什么」，没写成**可验约束**）：

#### 8.1 🔴 trusted principal 端到端链（SP1 承接）

现状：nginx 是 HTTP 基础认证，给不出 per-session principal，与 §21.1「审计与授权挂在**人**身上」冲突。

> ⚠️ **原文只写「须换成能带 principal 的认证」——不够。**
> 「换个认证方式」是形态描述，**验不了**。P1 要的是**一条端到端可信链**，
> 中间任一段允许旁路，换什么认证都白搭。

| # | 可验约束 | 锚 |
|---|---|---|
| 1 | **只有认证器 / 验证器可注入身份**；其余组件一律不得构造 principal | §7.1 P1 |
| 2 | **edge 处剥除调用方自带的身份 / tenant 头**（不是「忽略」，是**删除**，防下游误信） | §22.1a |
| 3 | **连接层 → 派发信封 → Receiver 全程同一个已验证 per-session principal**，不得中途重建或降级 | §7.1 P1 · §11.6 |
| 4 | **伪造 principal 负测：拒绝** | §22.2a #3 |
| 5 | 🔴 **链未就绪时 fail-closed**：**mutating 操作与状态观测一律拒**，不得「先放行，认证随后补」 | §22.2a #1 |

#### 8.2 🔴 环境属性的可信来源与执行点

现状：环境分层（研发测试 / 沙盒 / 生产）未在部署件中显式表达，而 §22.4 的凭据放宽
「须以环境属性为条件显式声明」。

> ⚠️ **原文只写「环境属性须可判，不能靠约定」——判据对，但没说【谁来判、判了给谁用】。**
> 一个没有可信来源的环境属性，等于把放宽条件交给了调用方自述。

| # | 可验约束 | 锚 |
|---|---|---|
| 1 | 环境 profile / 服务身份**由部署件声明、服务端取得**，属**受控来源** | §22.4 |
| 2 | 🔴 **凭据签发与放宽策略必须实际使用它**——声明了却不用于判定，等于没有 | §22.4 |
| 3 | 🔴 **客户端 / 普通应用不得自报环境** | §22.1a（同「不得取自客户端」） |
| 4 | **缺失或不匹配 ⇒ 默认不放宽**（fail-closed） | §22.4 |
| 5 | 验收须有**部署配置 ＋ 负测**：伪造环境属性请求放宽，须被拒 | §22.2a #3 |

🔴 **实测发现的一处名字冲突，须在 SP7a 之前定掉**：
表名 **`task`** 在 **`board`（SQLite）** 与 **`datad`（PG）** 两处**各自建过一次**。
两处 schema 不同、生命周期不同，却叫同一个名字。
⇒ **收编进统一仓储包时会正面撞车**：同名不同义，仓储层无法用一个类型承载。
须先定「哪个是权威 `task`、另一个改名或改归属」，**不能等到迁移时再发现**（同 E.3 #47b「权威定义唯一」）。

## §12 🔴 SP7a 的主要工作量：把存量收编进仓储包

**C.3 已裁：受控仓储 API 单点，强制租户上下文。** 收编对象按优先级：

| # | 对象 | 现状 | 收编要点 |
|---|---|---|---|
| 1 | `internal/datad/pgstore.go` | 直接开 3 个 PG DSN | PG 侧是跨租户数据主场，**先收它** |
| 2 | `internal/fanout/{spool,inspool,admin}.go` | 直接开 SQLite + 满篇裸 SQL | 出站含租户数据，**泄漏面直接** |
| 3 | `internal/mcs/board` | 独立 SQLite + 自带 schema | board 是执行主干，改动风险高，**放在有 conformance suite 之后**（§4.5） |
| 4 | `internal/store` | 已是仓储形态 | 补 `TenantCtx` 与迁移 runner |

**验收判据**（§22.2c · §22.2a，机器可判）：

**甲组 · 收口是否完成**
- 仓储包外 `sql.Open` 处数 **恒为 0**（现为 8）
- 未被仓储包引用的表数 **恒为 0**
- 漏传 `TenantCtx` **编译失败**（负测须存在）

**乙组 · 隔离是否成立**（v0.2 补，乙域 terra AD-SA-01）

> 🔴 **甲组只证明了「收口」与「缺 context 被拒」，证不了「持【有效】`TenantCtx` 的跨租户请求被拒」。**
> 而后者才是隔离本身 —— 一个规规矩矩传了 A 租户 `TenantCtx` 却去读 B 租户资源的调用，
> 甲组三条**一条都拦不住**。本席原表把「入口收口」当成了「隔离达成」，
> 与 SA-10「限制输出冒充授权」、PB-01「不泄漏存在性冒充拒绝」是同一个滑坡的第三次。

**跨租户读须【四项同时】验（§22.2a #3）**：

| # | 断言 | 为什么不能省 |
|---|---|---|
| 1 | **PEP 在 selector / 资源解析【之前】拒绝**；仓储查询 spy 计数 **＝ 0** | 与 #2 **独立验**，否则漏掉「**先查了再拒**」——对外拒了，但查询已落到库上，跨租户读实际发生过 |
| 2 | 调用语义为 **deny**；**禁 200 / 禁成功空集合** | 「成功的空集合」把 fail-closed 降格成一次看似成功的查询（§22.2a #2a） |
| 3 | 目标**存在与不存在**的响应不可区分——**状态码 · 响应体 · 时延**三者皆同 | 任一维可区分，存在性即已泄漏（时延维机器不易判 ⇒ E.4 #64 人审） |
| 4 | **最小化拒绝审计存在**（源 principal · 派生 tenant · 请求 op · capability/policy 判定 · 时刻） | §22.2a #2b；且内容须最小化，**不得回显判定器输入**（§22.5 #5） |

⚠️ **#1 与 #2 必须分开验**，这是本组的骨：只验 #2 会让「先查再拒」通过验收。

⚠️ **不可回滚风险**：SP7b（领域 schema 迁移与 cutover）按 §0.3 **由各领域 spec 自己交付**，
不作统一前置——因为 SP2/SP3/SP5 都会定义各自的领域模型，统一前置会造成循环阻塞。
