## §2 需求与诊断

### 2.1 业主需求

1. 有 spec 限制的文档交付
2. 有严格流程约束的项目推进
3. 每个环节都有明确的、**经评审的**交付物
4. 明确的项目拆分任务
5. **一旦进入项目开发，驱动的是流程引擎，而不是 Agent**
6. 开发环节**分等级**：什么条件下必须架构评审 / 设计评审 / 代码评审即可；测试同理（用例评审、执行结果评审）
7. 要和产品经理对接，需要一套**产品定义规范**
8. 平台要能**接入知识库与业务流程**，便于项目快速理解、分析、开展工作
9. **上下文分层管理机制**：基础环境上下文 + 项目知识库 + 版本上下文 + 任务上下文，逐层晋升
10. （可独立推进）需要**能直接与 Agent 交互的 web 界面**——平台一出问题，人就无法与 Agent 交互，尤其 ops-Agent

### 2.2 诊断

业主判断：

> 现在靠 coordinator 来管理，很容易丢失上下文后任务丢失、环节丢失、交付物丢失，造成项目损失。

**机理：状态只存在于消息流里，没有权威账。** 任何人要知道"现在到哪了"，都得重读历史消息重建；上下文一截断就重建不出来。

**环节丢失的精确机理**：现有契约中里程碑分段是**人填的**（§4.2 C2.1）。填的人一旦丢上下文，那一段就不存在了，**且事后无从发现**——因为没有"本该有这一段"的依据。

### 2.3 本次讨论期间的真实样本

- 本席 2026-08-23 05:4xZ 发出三版功能清单（614 行）。
- coordinator 05:16Z 的 ack 引用的仍是上一版（583 行单份），并将「安全缺口 `2d642f1` **仍待核**」转呈业主。

- 由本席主动纠偏追回。

**丢的不是消息，是"这条结论现在处于什么状态"。** 文档质量不是问题——**问题是状态存在文档里，就没有机制告诉任何人哪份是当前的。**

## §3 代码现状盘点

### 3.1 已实现且严密：执行管道

**流程引擎 `internal/mcs/mcsd`（灰度线，882 行）** —— 形态正是「引擎驱动，不是 Agent 驱动」。
`mcsd/daemon.go` 包注释自述：

> 文件库 Board + Takeover(epoch+1) + Renew 循环（活调度者必须能续期）；调度循环：**ReadyNodes → 择人 → Send 记账 → Deliver 外呼**；池满入缓冲，有闲回灌；reconciler 定时 Sweep（过期降级 / timeout 注记 / #15 兜底 / redeliver 候选）；回执入口（processing/terminal → guarded 写 + 归还 worker）

**Agent 在此模型中是 `pool.Worker`**（`internal/mcs/pool/pool.go:35`），接口仅 `ID / Health / Caps / Deliver / Stop`；
`DriverAdapter.Spawn()` 注释：「抽象『起一个新 worker』。生产=各 CLI 驱动」。
→ **Worker 是可随时 Spawn、随时 Stop 的子 CLI 会话句柄**，被引擎拉动，不能自主决定做什么。

**投递语义（`dispatch/dispatch.go`，119 行）**：记账先行 → 再外呼（崩在中间 = `dispatched` 无回执 → redeliver 收敛）；
worker 判死 → `Reassign(gen+1)` → 重派；CAS 不过则归还 worker 零副作用；池满 → 有界缓冲。

**数据模型（`board/schema.sql`）**：

| 表 | 关键字段 |
|---|---|
| `task` | `status ∈ {planning,running,done,failed,partial}`、`critical_path_len`、`result_version` |
| `node` | `seq`、`deps`、`acceptance`、`result_ref`、`status ∈ {pending,ready,dispatched,running,done,blocked,failed}`、`generation`、`assigned_agent`、`attempt`/`max_attempt`、`sla_deadline`、`blocker_reason`、`context_budget` |
| `task_role` | `role ∈ {designer,implementer,tester,qa_owner}` + `who` + `cli` + `llm` + `promoted` |
| `role_exemption` | 豁免落账（`task,who,reason,granted_by`），注释：「可审计，不可匿名突破」 |
| `node_request` | `expected_state` + `outcome ∈ {pending,uncertain,applied,cas_miss,rejected}` |
| `task_request` | `op ∈ {create_task, initial_plan, append_revision}` + `body_hash` |
| `owner_op` | `op ∈ {owner_takeover, owner_override}` + `idempotency_id` + `owner_principal` 守卫 |
| `board_event` | `cursor` 单调自增 |

`blocker_reason` 是**六值枚举**：`starved / dep_failed / timeout / retry_exhausted / awaiting_input / delivery_unresolved`。

**自检机制**：reconciler `SweepReport.StrayPromoted` / `StrayRecovered`，注释「**本应恒空，>0 = 主路径缺陷告警**」。

**知识库地基（`internal/datad/kb.go`，161 行，trunk 线）**：
`KBProvider` 接口**冻结**（`Query(q, topK) []KBHit` / `Ingest(doc KBDoc)`）；首 provider = `fsgrep`（文件目录 + 全文子串检索，零新依赖）；
注释留有升级位「**向量库 provider 接口不变后批插入**」；`KBDoc{Source, Content, Meta}`；原子写 + 路径穿越防护；
写权纪律：「**ingest=coordinator（知识策展归管理域）；query=全员**」。

**直连通道地基（`tools/sessionhelper/sessionhelper/sidecar.py`，173 行，三血脉完全一致且接线均在）**：见 §10。

### 3.4 一句话结论

> **管道严密，判据缺席。**
> 「谁能写、什么时候能写、并发怎么办」管得极严；「写的内容对不对」完全不管。
> **执行席自报一句 `ok=true`（`result_ref` 可为空），node 立刻 done，同一事务里后继全部提升到 ready。**
> **谁判断？执行席自己。谁校验？没有。**

## §5 定义层：产品定义规范

### 5.1 选型：Spec Kit（已裁定）

优于 OpenSpec 的三点：

1. **`constitution.md`** —— 唯一的「项目治理原则」载体，产品定义规范该住的地方
2. **`/speckit.checklist`** —— 生成质量检查清单，直接落成 `node.acceptance`（当前死字段）
3. **`/speckit.analyze`** —— 跨制品一致性检查，是**环节丢失的输入端检测器**

正向信号：`/speckit.taskstoissues` 证明「tasks 出到外部工单系统」是该工具支持的模式；`tasks → board node` 适配器是同一类接缝。

> ⚠️ **v1.1 更正**：v1.0 写「constitution 是 advisory 不是 enforced，不设硬门」。**该表述不准确，予以更正**（本席 §13-6 实读 spec-kit v1.0.1 得出）。

**实际情况比 v1.0 评估的严谨得多**：

- `templates/plan-template.md:39-41` 有显式闸：`## Constitution Check` + `*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*`——**前后各检一次**
- `plan-template.md:106-113` `Complexity Tracking`：**违规必须书面论证**（`Violation | Why Needed | Simpler Alternative Rejected Because`）
- `templates/checklist-template.md` 写死：checklist 是 **reviewer-owned**，只有 reviewer 能打 `[x]`；IMPLEMENT 命令**读 checkbox 当 gate 且不得修改标记**

> 最后一条与本纲领 §7.2「门方 ≠ 执行者、implementer 不能自签门 PASS」**是同一条纪律**。

**准确表述**：Spec Kit 有明确的闸与违规论证机制，且 checklist 所有权与标记语义已写死；
但其强制力在 **agent 侧**（由 slash command 指令约束），**没有外部系统拦截**——agent 若不遵守，无物阻止。
故仍属 §5.3 的「自律型」，**但自律的纪律设计值得直接沿用，不必重新发明**。**硬门仍须落在 board。**

另两项可直接复用（§13-6 实读）：
- constitution 有**语义化版本 + Ratified / Last Amended 日期**，且真实实例头部有 **SYNC IMPACT REPORT** 块，
  记录「版本变更 / bump 理由 / 新增章节 / **逐个复核了哪些下游模板并打 ✅** / 遗留 TODO」——
  **这就是 §7.5 自检通则的同构实现，建议直接沿用该格式。**
- 仓内有完整扩展体系（`EXTENSION-API-REFERENCE` / `RFC-EXTENSION-SYSTEM` / `presets`）→
  **§6 分级层可实现为 Spec Kit 扩展**，让 D2 与 D3 合为一条链，PM 在同一工具内完成「填属性 → 看到该走哪些评审」。

### 5.2 三个外部件的定位

| 工具 | 定位 | 采用 |
|---|---|---|
| Spec Kit | 定义层载体 | ✅ 主选 |
| OpenSpec | 更轻的替代 | 备选 |
| Superpowers | 单 agent 执行纪律（TDD 红绿、四阶段调试） | 可选，加分项非地基 |

### 5.3 为何外部件补不了保障层

**三者全是「agent 自律型」**——靠 agent 遵守流程，不靠系统强制。

> **自律型工具的约束存在于 agent 的上下文里；上下文一丢，约束跟着一起丢。**
> **本纲领要求约束存在于上下文之外。**

对照：board 的 `node` 存在 SQLite 里，DAG 走不通就是走不通，与谁记不记得无关。

### 5.4 流程引擎：不引入新的（已裁定）

`mcsd` 做的恰是通用引擎做不了的部分——agent 择人、worker 判死换代重派、记账先行→外呼的崩溃切点、per-段门方授权矩阵、执行席≤2。

| 候选 | 判断 |
|---|---|
| Temporal | mcsd 已自做 durable 语义，引入=重写 dispatch 层 |
| Camunda/Zeebe | 最贴分级审批流但 JVM 重；人工任务模型 ≠ agent worker |
| Argo Workflows | 面向 CI/批处理，无门禁与角色授权 |
| **保留 mcsd** | ✅ |

**唯一引入的外部件：DMN 决策表**（可脱离 BPMN 引擎单用）——「输入属性 → 输出决策」的标准化表格，**PM 可自维护**。用它的决策表，不用它的执行引擎。

## §6 分级层

### 6.1 属性表

#### 6.1.1 设计目标：不是「描述准确」，是「两个人填出来一样」

> ⚠️ **v1.1 更正**：v1.0 写「两个人填出来一样」是**唯一**判据。该表述**过强**，予以放宽。
> 评审方指出：兼容性含**语义变更**（不只 endpoint/字段增删）；migration 不必在固定目录；
> 「影响几个顶层包」不等于「影响几个服务」；在产路径与回滚成本需 **owner/ops 的事实**才能填。
> 这些属性**当下无法做到两人必然一致**，有的甚至事后才知。

**修订后的判据（两条并列）：**

1. **可重复判定** —— 同一份 spec，同一角色的两个人，依同一份判定说明，应得同一结果。
2. **可由产物反证** —— 声明与最终产物不符时，**机器能查出来**（见 §6.1.3②）。

第 2 条是第 1 条的兜底：**主观性无法完全消除，但可以被事后反证约束。**

> **仍然成立：宁可粗（三档枚举），不可细（十档打分）。打分制一定退化成主观。**

#### 6.1.1a 属性的填写归属（v1.1 新增）

v1.0 隐含「属性全由 PM 填」，**不成立**——技术与发布属性 PM 无从判断。修订为**三方分填**：

| 类别 | 填写方 | 属性 |
|---|---|---|
| 产品属性 | **PM** | 外部契约变更（业务语义层）、价值优先级 |
| 技术属性 | **tech（设计者/实现者）** | 数据模型变更、影响范围、外部契约变更（接口层） |
| 发布属性 | **ops / owner** | 在产影响、回滚成本、安全面 |
| 全部 | **机器** | 事后反验，不符即告警并强制升级 |

**分级仍不由执行者单方决定**（§6.2.6 不变）：执行者可补技术属性，但**不得下调**已声明的风险档；下调须走门方或调度者。

#### 6.1.2 起点草案（7 个属性）

**A 类 —— 影响面（错了会波及多远）**

| 属性 | 取值 | 判定依据 |
|---|---|---|
| `外部契约变更` | 无 / 兼容新增 / **破坏性变更** | 是否改 endpoint、字段、枚举值 |
| `数据模型变更` | 无 / 加列加表 / **改列删列改语义** | `migrations/` 有无新文件、何种类型 |
| `影响范围` | 单模块 / 跨模块 / **跨服务** | 改动涉及几个顶层包 |

**B 类 —— 风险（错了有多难收拾）**

| 属性 | 取值 | 判定依据 |
|---|---|---|
| `在产影响` | 不影响 / 灰度可回滚 / **直接影响在产** | 是否进在产部署路径 |
| `回滚成本` | 重启即回滚 / 需回滚数据 / **不可回滚** | 有无不可逆动作 |
| `安全面` | 否 / **是** | 是否触及鉴权、授权、密钥、身份 |

**C 类 —— 规模**

| 属性 | 取值 | 用途 |
|---|---|---|
| `预估节点数` | 数字 | 超阈值强制先做拆分设计 |

#### 6.1.3 两条纪律

**① `安全面` 必须是独立维度，不能被"改动小"稀释。**
五行的改动若动了鉴权，它就是高风险。揉进综合评分会被平均掉——这是最典型的漏网方式。

**② 每个属性须有「事后可机器验证」的对应物。**
声明「数据模型变更=无」但交付物 diff 中出现 migration → **自动告警并强制升级**。
**这是分级不能被绕过的关键**，也是 §7.5 自检通则的一个实例（计数器：「属性声明与产物不符」应恒为 0）。

### 6.2 分级 × 环节矩阵

#### 6.2.1 环节数不固定——这是分级有意义的前提

业主设想稿中的 8 列（文档执笔 / 文档评审 / 开发设计 / 代码评审 / 测试用例 / 用例评审 / 测试执行 / 交付验证）是**中等级别的典型形态**。低级别更少，高级别追加「架构评审」。

> **如果列固定，就等于所有任务同一套流程，分级即无意义。**

**UI 影响（须在看板实现前知晓）**：看板需处理**变长列**——低级别任务在某些格子是 **N/A**，不是"未完成"。

#### 6.2.2 级别是标签，门按属性直接算

| 做法 | 评价 |
|---|---|
| (a) 先算总级别 L1/L2/L3 → 再查"L几要过哪些门" | 会失真 |
| **(b) 每个属性独立映射到"必须加哪些门" → 取并集** | **采用** |

理由：`安全面=是` 应强制加代码评审（且门方须为安全角色），但不一定需要架构评审；
`外部契约=破坏性` 应强制架构评审，但对测试深度要求未必更高。合成粗级别会丢掉这种区分。

> ⚠️ **v1.1 更正**：v1.0 写「L1/L2/L3 只是**并集规模**的简称」。**按数量命名会让风险语义漂移**——
> 一个门数多但全是低风险门的任务会被叫成 L3。评审方指出此点，接受。

**修订：L1/L2/L3 按「触发的最高风险档」命名，不按门的数量命名。**
即：任一属性命中**破坏性/不可回滚/安全面=是**这类高风险取值 → L3；仅命中中风险 → L2；全无 → L1。
**级别仍只供人沟通，不参与计算**；计算走并集。

#### 6.2.2a 并集法的必备规则（v1.1 新增，评审方要求）

采用并集法必须同时规定以下五项，否则规则会失控：

| # | 规则 | 说明 |
|---|---|---|
| 1 | **DMN hit policy = COLLECT / UNION** | 多条规则同时命中时取并集而非首条，须在决策表上显式声明 |
| 2 | **基础必过模板** | 无论属性如何，恒必过的最小环节集（如：实现 → 代码评审 → 测试执行）。并集在此基础上追加 |
| 3 | **规则优先级与冲突消解** | 两条规则对同一环节给出不同门方时如何裁决（建议：取更严者，即更高权限角色） |
| 4 | **可解释输出** | 每次判定必须输出 `{命中的 rule id, 规则表 version, reason}`，供事后复核与申诉 |
| 5 | **允许跨属性组合规则** | 单属性映射不足以表达「破坏性变更 ∧ 直接影响在产」这类叠加风险，须支持组合条件 |

第 4 项尤其重要：**分级结果必须可解释、可追溯到规则版本**，否则「为什么这个任务要走架构评审」无法回答，
执行方会把它当成随机负担而设法规避。

这正是 DMN 决策表的形状：多输入列 → 多输出列 + hit policy + 规则版本。

#### 6.2.3 映射表（起点草案）

| 属性取值 | 强制追加的环节 |
|---|---|
| 外部契约 = **破坏性变更** | 架构评审 + 用例评审 + 交付验证 |
| 外部契约 = 兼容新增 | 文档评审 |
| 数据模型 = **改列/删列/改语义** | 架构评审 + 交付验证（含回滚演练） |
| 数据模型 = 加列/加表 | 文档评审 |
| **安全面 = 是** | 架构评审 + 代码评审（**门方必须是安全角色**） |
| 在产影响 = **直接影响在产** | 交付验证 + 执行结果评审 |
| 回滚成本 = **不可回滚** | 架构评审 + **业主签署**（升 C3 决策链） |
| 影响范围 = 跨服务 | 架构评审 |
| 以上皆否 | 只留基础环节 |

#### 6.2.4 三档典型形态

| 级别 | 环节 | 典型场景 |
|---|---|---|
| **L1** 代码评审即可 | 实现 → 代码评审 → 测试执行（3 node） | 内部重构、修 bug、日志改进 |
| **L2** 设计评审 | + 文档执笔 → 文档评审 → 测试用例 → 用例评审（7 node） | 新增内部功能、加列 |
| **L3** 架构评审 | + 架构评审 → 交付验证（含回滚演练）→ 业主签署（9-10 node） | 改对外协议、删列、动鉴权 |

#### 6.2.5 门方也是矩阵的输出列

核心纪律：**门方 ≠ 执行者**（gate-3 矩阵本就防此）。

| 环节 | 门方 |
|---|---|
| 代码评审 | 不能是该 node 的 implementer；`安全面=是` 时**必须**为安全角色 |
| 交付验证 | `qa_owner` |
| 架构评审 | 调度者或指定架构角色 |
| 业主签署 | 业主 principal（C0.1 校验，非自述） |

#### 6.2.6 最容易被绕过的地方

**分级不能由执行者自己填**，否则全是 L1。

> ⚠️ **v1.2 更正**：v1.1 此处仍写「属性由 PM 在 front-matter 里填，不由执行方填」，
> **与 v1.1 新增的 §6.1.1a 三方分填直接冲突**（评审方指出）；且「front-matter」已被 §13-6 更正为
> `**Key**: value` 头块。两处一并改。

**修订后的规则（与 §6.1.1a 一致）：**

1. 属性按 §6.1.1a **三方分填**：PM 出产品属性 / tech 出技术属性 / ops·owner 出发布属性，
   填在 `spec.md` 已有的 **`**Key**: value` 头块**（非 YAML front-matter，见 §13-6）。
2. **执行者不得单方定级**：可补技术属性，但**不得下调**任何已声明的风险档；下调须走门方或调度者。
3. 叠加 §6.1.3② 机器交叉验证——**声明与产物不符即告警并强制升级**。

三条合起来，分级才是「保障」而非「自觉」。

### 6.3 与产品经理的推进方式

**第一次会：只定属性表。** 7 个左右，每个 2-3 档，逐个问「两个人会不会填出不一样的答案」——填不一样的当场砍掉或改写。
**第二次会：填映射表。** 拿属性表逐行问「这个取值出现时，什么评审必须做」。
**不要在这两次会里定各环节的 acceptance 内容**——那是 `/speckit.checklist` 的事，混在一起会开不完。

## §7 执行层

### 7.1 判定模型三层：能机器判的绝不交给人

#### 层一：结构闸（不需要判断，靠 schema 让违规不可能发生）

| 改动 | 位置 |
|---|---|
> ⚠️ **v1.1 重要更正**：v1.0 曾把本层写成「四项局部改动」，并估「改动面不大」。**该估计错误，予以撤回。**
> 评审方指出并经本席复核：**这至少是一次 board 状态机设计变更 + 数据迁移 + 回归窗**，不是四个改点。

**唯一可独立先落的一项**：`Terminal(done=true)` 前置 `result_ref != ''`。
它不改状态集、不动 fan-out，只加一条准入校验——可作为独立小 commit，风险最低。

这层的性质仍成立（**违规不可能发生，不存在「谁来判断」**），但其**代价**远高于 v1.0 的估计。

#### 层二：机器校验（客观、可复算、自动跑）

C2.2 回执五要素中，**四个机器可验**：

| 要素 | 自动验 |
|---|---|
| 件（路径或 commit 40hex） | ✅ 存在性可查 |
| sha256（"最终态当场算，报后不改"） | ✅ 可复算比对 |
| 行数 + 字节（wc -c 口径） | ✅ 可复算 |
| 自测结果（命令 + 摘要） | ✅ 命令可重跑 |
| 门结果（PASS/FAIL + 失败最小复现） | ❌ 需要人 |

契约作者即此设计——sha256 特意写「报后不改，改=重报」正为可复算。
→ **「交付物合格」约八成可自动判，门方只判剩下两成**，同时解决「门方成为瓶颈」。

#### 层三：人 / Agent 评审（主观）

只剩「这东西对不对、够不够好」。由该段**指定门方**出 PASS|FAIL，FAIL 必须带**失败最小复现**。

### 7.1a 执行层的上线前置（v1.1 新增，来自 P2 契约与评审）

以下三项是 P2 契约已定的**硬前置**，纲领 v1.0 遗漏，须纳入执行层前置与验收：

| # | 前置 | 契约出处 | 现状 |
|---|---|---|---|
| **P1** | **hub per-session principal 必须可信** | C0.1 / C5 5.0 | ❌ **未实现**——`internal/m8/*.go` 中 principal **零命中**。契约规定其未就绪时**一切 mutating op + 心跳/状态观测全部 fail-closed，仅放行只读查询 + warn/盘点**。→ **它是「上线启用」critical path 的最前置项；但不阻塞 board 状态机的离线设计与实现，二者可并行** （v1.2 按评审方意见更正措辞——v1.1 写「排期最前置项」易被读成「其余全部停等」） |

### 7.2 谁来判断：纪律已定，只需接线

- 门方是 **per-段指定的 principal**，不是角色
- **implementer 不能自签门 PASS**
- **执行席不得自行收口**（收口 = 调度者唯一关闭权）

- **身份用 per-session principal，不信信封自述 `from`**

### 7.3 未达成时的处理

| 情形 | 机制 |
|---|---|
| 重试耗尽 | `retry_exhausted` → blocked |
| 超时 | `sla_deadline` + reconciler `TimeoutAnnotated` |
| 依赖失败 | `dep_failed` → 下游 blocked |
| 无人可派 | `starved` |
| 投递悬空 | `delivery_unresolved` → redeliver 收敛 |
| 等人输入 | `awaiting_input` |
| 需决策 | C2.5 升级链 → 调度者 → 判属产品决策则按 C3.1 格式升业主 |
| 卡死无解 | `owner_override`（**指令须唯一映射到白名单 op，不得自由文本直写**）/ `owner_takeover` |

**C3.1 关键决策请求格式**：`决策项 / 选项(a,b,c…) / 各选项影响一行 / 调度者建议+理由 / 不拍时的默认行为与时限`。一次一批，禁流式追问。

### 7.4 门 FAIL 的回流（已裁定：`append_revision`）

设计已埋两处伏笔（**均为 schema/注释级，非可用实现**——`task_request` 表 Go 侧零写入，见 §3.2）：`task_request.op` 含 `append_revision`；
`dispatch.SetOriginHint()` 注释「修订节点建图时由上层调用，把**原产出 node 的最后执行 worker** 继承给修订 node」。

→ **门 FAIL → 建修订 node → 优先派回原 worker**。

### 7.5 自检通则（纲领级纪律）

reconciler 的 `StrayPromoted` / `StrayRecovered` 注释：「本应恒空，>0 = 主路径缺陷告警」。

> **立为通则：每加一条流程约束，同时加一个「本应恒为 0」的计数器。**
> 否则约束失效了没人知道——这正是「环节丢失造成项目损失」最隐蔽的一种。

已识别应设的计数器：属性声明与产物不符数（§6.1.3②）、KB 条目基线锚失配数（§8.6）、`result_ref` 空而 done 数、门方=执行者数。

## §8 上下文分层管理与知识库

### 8.1 四层上下文

| 层 | 名称 | 内容 | 变更频率 | 载体 | 写入时机 |
|---|---|---|---|---|---|
| **K0** | 基础环境上下文 | Agent 身份/寻址/通信纪律/Git 身份/凭据纪律/工作区约定 | 极低 | `/opt/agent-context/` | 平台变更时人工 |
| **K1** | 项目知识库 | 产品定义、架构与拓扑、代码位置、业务全流程、前代系统、坑清单、优化与预案、版本志 | 低 | datad `KBProvider`（每项目一 namespace） | **版本收口时晋升** |
| **K2** | 版本上下文 | 本版本目标/范围/决策记录/变更摘要/已知问题 | 中 | 版本库（git + board task 聚合） | **任务收口时晋升** |
| **K3** | 任务上下文 | 派发信封 + node 的 acceptance/deps/result_ref/门结果 | 高 | board 台账（task / node / board_event） | 实时 |

### 8.2 晋升机制：完成即晋升，晋升是流程的一个环节

> **晋升不是"额外要写的文档"，而是某个 node 的交付物。**

- 任务的最后一个 node（交付验证）的交付物之一 = **任务摘要** → 写入 K2
- 版本收口（调度者唯一权）的产出之一 = **版本摘要** → `Ingest` 到 K1

因为它们是 node 交付物 / 收口产出，所以**受 §7.1 判定模型约束**：
没有摘要 = `result_ref` 空 = **不能 done**。

**这一条是整个机制成立的关键。** 否则又退回「记得写文档」，而这正是当前失效的根因。

### 8.3 装载：每次派发灌什么

派发信封 =

| 层 | 灌法 | 理由 |
|---|---|---|
| K0 | **全量** | 稳定前缀，可吃 prompt caching |
| K1 | **按需切片**（`KBProvider.Query(q, topK)`） | 全量会撑爆——图搜那种知识库尤其 |
| K2 | 当前版本摘要**全量** | 量小 |
| K3 | 本任务**全量** | 就是派发信封本体 |

**K1 必须是检索式的，不能全量灌。** `KBProvider` 的 `Query(q, topK)` 正为此设计。

### 8.4 项目知识库的条目类型（通用模板）

由业主给的两个实例抽象为八类，每个项目建 KB 时照此建：

| 条目类型 | dingwei 示例 | 图搜 3.0-poc 示例 |
|---|---|---|
| 1 产品定义 | 平台产品定义 | 3.0-poc 产品定义、主要功能介绍 |
| 2 架构与拓扑 | hub / VS / renderer 分层 | 系统拓扑图 |
| 3 代码位置 | 仓库、包、关键文件 | 涉及服务清单、代码位置 |
| 4 业务流程 | 消息路由 / view / 调度 | 业务全流程介绍 |
| 5 前代系统与迁移 | —— | 原 2.0 实现方案、主要问题、解决手段 |
| 6 坑清单 | 研发过程主要坑 | 遇到的坑清单 |
| 7 优化与预案 | —— | 可能的优化点、运维预案 |
| 8 版本志 | 历届版本简介 | 历届版本简介 |

`KBDoc.Meta` 承载 `{project, type, version, baseline_anchor, updated_at}`，供 query 按项目与类型过滤。

### 8.5 写权纪律

`datad/kb.go` 已定：**ingest = coordinator（知识策展归管理域）；query = 全员**。

按 §8.2 晋升机制收紧：

- **K1 的 ingest 仅由「版本收口」原语触发**（调度者唯一关闭权已保证这点）
- 人工订正走独立 curation 流程，**落审计**

### 8.6 防知识库腐坏

**失败模式**：写进去的内容过期了没人知道——比没有知识库更危险，因为它会误导。

**机制**：每个 KB 条目带 `baseline_anchor`（commit 40hex 或 blob sha256）+ `updated_at`。
条目所描述的代码位置若已变化（**锚失配**），标记为「可能过期」并计数。
——这是 §7.5 自检通则的又一实例。

### 8.7 与 Spec Kit 的对接点

Spec Kit 的 archive（`changes/archive/<日期-变更名>/`）是 **K2 → K1 晋升的自然触发点**。

## §9 任务上下文的装载与隔离

### 9.1 每任务清空上下文：可行，且引擎已是这个形状

`DriverAdapter.Spawn()` 抽象即「起一个新 worker」，`Worker` 是「单个子 CLI 会话的句柄」，有 `Stop()`。
**新 Spawn = 新上下文。** `node.context_budget` 字段（虽为死字段）表明设计者已想过按节点给上下文预算。

### 9.2 灌入什么：C2.1 派发信封已给出定义

派发信封 = 任务上下文的定义，且**自带完整性判据**（「缺任一字段 = 无效派发，执行小组拒接」）。
→ **有台账才能灌，灌了才能清**；本机制与 §4 架构互为因果。

### 9.3 与亲和机制的张力及解法

`SetOriginHint` 的设计目的是靠 worker 记忆支持返工，与清空方向相反。
但 `dispatch.go` 注释已指路：亲和「**仅 pick 权重，非正确性依赖**」。

> ⚠️ **v1.1 更正**：解法的**原则成立，但当前实现下不成立**——评审方指出并经本席复核：
> **没有可重灌的账。** `node` 只存 `body` / `acceptance` / `result_ref`；
> `gate_result` 只是审计事件且载荷仅 `{kind, segment, line}`（**只有首行文本**，见 §3.1a）；
> `SetGateKeeper` 门方映射也仅在内存。**「靠台账重灌」目前无账可灌。**

**前置条件（新增，必须先建）：不可变派发快照（immutable dispatch snapshot）**

修订 node 要摆脱对 worker 记忆的依赖，派发时必须持久化一份**不可变快照**，至少含：

| 字段 | 用途 |
|---|---|
| `envelope_ref` | 该次派发的完整信封引用（C2.1 全字段） |
| 原交付物锚 | 上一轮 `result_ref` + sha256（**锚，不是路径**） |
| **完整 FAIL evidence + 失败最小复现** | C2.2 已要求门方 FAIL 时提供，但**当前未持久化** |
| `acceptance` 锚 | 判据的 commit/blob sha256（判据一改锚即变，防悄改判据） |
| 规则版本 | 分级规则表 version（§6.2.2a 第 4 项） |
| 上下文版本 | K0/K1/K2 各层装载时的版本（§8） |

> **解法（修订后）：不靠 worker 记忆，靠不可变派发快照重灌。**
> 亲和退化为纯性能优化的结论**不变**，但它现在有了一个明确前置：**快照必须先建**。
> 修订 node 的派发信封带上「上次 FAIL 的门结果 + 失败最小复现」（C2.2 本就要求 FAIL 带最小复现）。
> 亲和退化为纯性能优化（省一次 Spawn），不承担正确性。

与原设计意图一致，非对抗。

### 9.4 真正的收益（比"专注"更重要）

- **可重放** —— 同一 node 派给谁，上下文都一样
- **可审计** —— agent 当时看到了什么，事后查得出
- **可诊断** —— 做错了能区分「信息不全」与「判断失误」

第三条尤其关键：现在出问题只能归因到"agent 不行"，因为没人知道它当时看到了什么。

### 9.5 连续性与隔离的分工

`internal/m5`（B-lite continuity）与 `internal/mcs/rotation` 在做会话延续，方向与"每任务清空"相反。**二者不矛盾，但须分清适用面**：

> **连续性保「同一 node 执行过程内」的韧性（崩了要能续上）；隔离管「node 之间」的边界。**

若如此切分，两笔投资都不浪费。**但 rotation 按会话轮换的逻辑需重新界定它管什么**（见 §11.2）。

### 9.6 markdown 的分界线

markdown 出现在三处，性质完全不同：

| 位置 | 谁写 | 是否权威 | 是否存档 |
|---|---|---|---|
| **输入端**：spec / checklist | 人（PM） | 是（定义层权威） | ✅ 进 git |
| **中间**：派发信封 | **引擎生成** | 否 | ❌ 用完即弃 |
| **输出端**：交付物本身 | agent | 是（交付物权威） | ✅ 进 git，由 `result_ref` 指向 |

**流程状态不得存在 markdown 里**，因为：判不了分级（自由文本无结构化属性）、没有 CAS（并发即冲突）、DAG 强制不了、没有单调游标（`board_event.cursor` 可查谁在何时改了什么，git 记录不了「当时 node 处于什么态」）。

> **分界线：「会变的状态」进台账，「要评审的内容」进 git。**

`acceptance` 是边界情况——既是文本（要评审）又是判据（要被引用）。解法用 C2.1 已有的两个字段：
**内容**放 git 的 `checklist.md`（可 diff、可评审）；**`node.acceptance` 只存引用**（文件路径 + 锚点 + sha256）。
判据一改 sha256 即变，**无法悄悄改判据来让交付物通过**。

**文件量级**：中间信封生成不落盘；输入端每变更一份 spec + checklist；输出端即交付物本身。审计记录用 `board_event`，不用 markdown。

## §15 本席的方法层缺陷（v1.2 新增，必须公开记录）

到 v1.2 为止，本席已犯**同一个方法错误三次**：

| # | 错误 | 由谁发现 |
|---|---|---|
| 1 | grep 范围限定 `internal/mcs/board/*` 包内 → 断言「门禁在引擎里根本不存在」 | **评审方**（本席在 §13-4 证据文件里还二次确认了同一错误结论） |
| 2 | 见 `node_request`/`task_request`/`owner_op` 三表存在 → 断言「C0.3 幂等键已实现」 | **评审方** |
| 3 | 「Spec Kit constitution 是 advisory」——据命令名与文档描述推断，未读模板 | 本席自查（§13-6） |

**共同形状：用「存在性证据」推出「行为性结论」。**
表存在 ≠ 契约闭合；符号不在某目录 ≠ 功能不存在；命令名 ≠ 强制力。

**为何自审补不上**：范围划错时，再自查也只是在同一个错误范围里重跑一遍，结论必然一致、必然错。
三次里两次由他审抓出，正是 §14「两独立穿透」通则的实证依据。

**本文写作纪律（自 v1.2 起）**：
凡形如「X 已实现 / X 不存在」的断言，必须附**行为级证据**（谁调用、调用几次、写入点在哪、测试覆盖哪条），
不得仅凭表结构、目录 grep 或命名推断。已按此标准重写 §3.2。
