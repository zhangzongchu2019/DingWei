# D3 Feishu outbound startup opt-in (r34 candidate)

`DW_PILOT_QUESTION_FEISHU_ENABLED` defaults **off**. Only a trimmed value `1` enables it; unset, `0`, `true`, malformed values are off. The Hub reads it once during startup; changing the environment requires a **Hub restart**. This file is implementation documentation, not a deployment/enablement GO.

When off, startup does not wire `QuestionSender`. The worker also requires the immutable startup flag, even if an internal test/caller injected a sender. Eligible not-attempted notices stay `pending_config`, reason `DW_PILOT_QUESTION_FEISHU_ENABLED_disabled`; Console questions, task blockers, reminder registration and other platform Feishu messages continue normally. Identity revocation/supersession still cancels obsolete notices; an already-dispatching/unknown notice remains uncertain and is never reset for retry. No migration, PG schema, helper, lock or Feishu wire changes.

When on, the existing real-gateway, HTTPS public origin, active account/current binding and personal open_id checks remain mandatory. Fake/Stub/nil still do not get a D3 sender. Pending **unsent, still authorized** notices may send after startup opt-in, including due reminders: the runbook must inventory the pending queue and identities before enabling. Sent/unknown notices never get blindly replayed; provider acceptance is not human reading/signoff.

`DW_SPEC_CLARIFICATION_FEISHU_REPLY_ENABLED` is a **separate inbound switch**, implemented by the spec clarification work, not by this small patch. D3 does not read it, and enabling inbound must not implicitly enable D3 outbound; enabling D3 outbound must not enable inbound. Both can be off independently. This patch does not claim that the future inbound route already exists or is tested end to end.

For the approved future batch, prodops records the desired outbound and inbound settings separately in the execution sheet, plus current queue inventory, account bindings and exact build source. Apply/start/observe only under that batch's GO. To stop D3 outbound, set this flag to `0`/unset and restart the approved Hub build; Console answers remain usable. An in-flight provider call can already have occurred before process shutdown, so preserve receipts/unknown states and do not resend. Returning to old r33 alone loses this switch and can resume uncontrolled outbound: retain the gated binary or independently freeze the old sender/worker before any old-binary rollback. The owner approval to enable real clarification replies does not turn on an environment key by itself.

Regression plan: closed flag with a current binding means no send and explicit pending reason; opened flag/current binding sends once; Console read still works; Fake/Stub and ordinary gateway messages retain their previous behavior; environment changes are ignored until a fresh startup configuration; inbound/outbound combinations stay independent; uncertain dispatch never becomes retryable. The evidence report records actual tests/mutations separately, including any failures/skips.
