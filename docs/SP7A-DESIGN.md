# SP7a 设计短件 —— 受控仓储包的形状与 `TenantCtx` 落法

> 取件坐标一律现取：件版本/锚/指纹见 `docs/DELIVERY-STATUS.md`，判据实数见 `scripts/repo-boundary-gate.sh` 输出。
> 🔴 **本件依据架构设计 A§12 作【设计依据】** —— 该件只过架构评审，用例评审与交付验证未过，
> **不得据以做交付验收**。验收依据是 SpecDoc §22.2c / §22.2a（生效件）。

## 一、仓储包的形状（已落地，`internal/repo`）

### 1.1 三个类型，职责不重叠

| 类型 | 职责 | 为什么这样切 |
|---|---|---|
| `TenantCtx` | 携带租户身份／系统身份／待租户化占位 | 上下文进**类型**，不进参数列表（§22.2c #2） |
| `Pool` | 持有裸库句柄，暴露受控查询面 | 句柄**不导出、不返回**（§22.2c #1 两半） |
| `Tx` | 回调式事务包装 | `*sql.Tx` 无从逃出包外；见 1.3 |

### 1.2 `TenantCtx` 的三种取值必须互不冒充

```
零值            → 缺上下文 → 一律 ErrNoTenant 拒（§22.2c #4 fail-closed）
SystemCtx()     → 本就无租户语义（建表 · 迁移 · 健康检查）→ 须【显式取】
PendingTenantCtx(reason) → 本该有租户，但领域表还没有租户列 → 须带理由
```

🔴 **为什么必须有第三种**：SP7a 收编时领域包还没有租户概念。若把这些调用点一律填 `SystemCtx()`，
判据一照样达标，却会留下一批「看起来已收编、实则全是系统调用」的点 ——
**用「与租户无关」冒充「已做隔离」**，即已归纳的「安全属性互相冒充」。
⇒ 另立 `PendingTenantCtx`，把债做成**可清点**的：`grep dtx()` 即知还欠多少处，随 SP7b 逐个归零。

### 1.3 「无可用零值」的准确表述（不夸大）

Go 里**没法**让一个 struct 的零值无法编译。本设计做到的是分开的两条：

| # | 做到了什么 | 机制 |
|---|---|---|
| ① | **漏传是编译错误**（§22.2c #2 明确要求「不是运行期错误」） | 所有查询入口以 `TenantCtx` 为**必填形参**，少传实参编译不过 |
| ② | **零值不可用** | 零值一律 `ErrNoTenant`，绝不退化为「当作系统调用放行」 |

⚠️ 把 ② 说成「零值编译错」是**不实的**。此处钉死，免得后来者据此写出过强的验收断言。

### 1.4 事务为什么是回调式

`InTx(ctx, t, opts, func(Tx) error)`，不提供「返回一个 Tx 让调用方自己 Commit」的形态 ——
后者会让 `*sql.Tx` 逃出包外，直接违反 §22.2c #1 后半句。

🔴 **`CommitErr` 的存在理由**（这是本设计最容易被后人删掉的一处）：
`AssignGeneration` 有三处「写审计 + 提交 + **仍返回业务错误**」——审计属 fail-closed，拒绝也必须留痕。
若只提供「返回错误＝回滚」，改写会**静悄悄丢掉审计行**，而调用方看到的错误一模一样。
⇒ 先加 `CommitErr` 精确表达该语义，再动那段代码，不是反过来。这正是 §4.5「不得以重写为由丢弃既有语义」。

## 二、租户过滤的注入位（位已留，过滤未实现）

注入点在 `Pool.Exec/Query/QueryRow` 内部**单点**（§22.2c #3：调用方不得自带 `WHERE`）。

⚠️ **现在注不进任何东西**：领域表没有租户列。领域 schema 按 §0.3 归 **SP7b，由各领域 spec 自交**，不作统一前置。
🔴 因此当前**只能表述为「正常路径已收敛，异常路径由评审把关」，不得表述为「租户隔离已实现」**（§22.2c 开篇原文）。
— 此结论**与业主对 SP7a 完工判据的裁定无关**，无论怎么裁都成立。

## 三、剩余三对象的收编方案

| 序 | 对象 | 方案 | 前置 |
|---|---|---|---|
| 2 | `internal/fanout`（`spool` 持句柄；`inspool`·`admin` 有建表与裸 SQL） | 同 pgstore：句柄换 `*repo.Pool`，查询走受控面，建表走 `SystemCtx()`；三文件均在收编面内 | 无，**可立即开工** |
| 3 | `internal/mcs/board` | 🔴 **须待 conformance suite**（§4.5）。收编时一并做 `board.task → board_task` 改名（§5.6a 名已裁，A§21 #12） | suite 不存在 ⇒ **不得开工** |
| 4 | `internal/store` | 已是仓储形态；补 `TenantCtx` 与**迁移 runner**（SP7a 三项能力之一，尚未实现） | 无 |

**`board.DB()` 的处置**：它是判据二当前唯一的一处。属 board 面 ⇒ 判据二**长期停在 1**，
状态口径为「已知长期非零、非未完成」（coordinator 已归口背书）。**不放宽、不挪进允许清单**，
留在闸的每次打印里 —— 比藏进清单诚实。

## 四、本设计【做不到】什么

| # | 做不到 | 由谁兜底 |
|---|---|---|
| 1 | 拦住不经仓储包的路径（迁移脚本 · 报表 · 手工 psql · 测试夹具外的直连） | 代码评审（§22.2c 开篇已声明本方案不杜绝跨租户泄漏） |
| 2 | 保证「执笔不得自决放宽允许清单」 | **仓侧保护**（CODEOWNERS／受保护分支／签名 manifest+CI 验签）—— 已上呈，未落地前那是纪律不是闸 |
| 3 | 识别 import alias、跨行调用、未列入的新库 | 代码评审；真闭合须换 Go AST 实现 |
| 4 | §22.2c #5 三类越权负测中的**伪造 tenant／跨租户读** | 造不出真负例（领域表无租户列，另一个租户在数据模型上不存在）⇒ 随 SP7b 补 |

🔴 第 4 条尤其不得含糊：**当前只具备「缺 context 默认拒」一类负测**，
不得被引为「§22.2c #5 三类负测已具备」。
