# 耗时成因与测试调度

原测试全部串行。`store_test.go:testpool` 每次调用 `pgtest.Pool(t)`，后者启动独立 tools/pgtest 进程、初始化和启停真实 PG，逐次登记关池、停库、目录与残留断言。表驱动的每个独立夹具均重新执行这条链：SoftHoldReplay 有 8 个场景，NodeDown 有多条操作／回滚分支，RefreshCredResume 有 7 个场景，备份校验也分别建库。主耗时来自这些生命周期顺序累加。少数 5ms／10ms 的条件轮询和 300ms 的竞争反例等待不是慢用例的共同路径，本单保留不动；不把睡眠删掉换取虚假提速。

只在 185 个顶层测试入口加入 parallelHostedTest。内嵌 PG 模式通过 t.Parallel 调度，最多 6 个顶层夹具所有者并发；名额在 t.Cleanup 中最后释放，因此其所有子例和原 PG 收尾仍在名额内。每次 testpool 仍获得独立实例，不共享表、数据、连接池或业务假件，不并行化同一夹具的子场景。6 的上限避免依机器默认 -parallel 值同时起数十／数百个 PG；调用方更小的 -parallel 仍受 Go 原生调度约束。

显式 HUB_TEST_PG_DSN 可能是一个共享测试库，继续原来的串行执行，不新增跳过或放宽断言。工具首次冷缓存构建使用按进程命名的临时产物；testpool 通过 sync.Once 让第一个完整夹具先完成，后续调用只复用已准备好的工具二进制，仍各起独立 PG。没有修改 pgtest 产品辅助包或 tools/pgtest。

对所有原测试文件做还原比较：去掉每个顶层新增的一行调度调用，以及 testpool 的工具首次准备逻辑，其余字节与基线相同。185 个原测试主体及全部断言保留，新增辅助没有 Test 前缀，不改变顶层数量。原始基线 hosted >300 秒构成串行调度的性能反例；前后全仓相同 JSON 口径验证性能门，不提高测试超时来满足判据 a。

并行测试的单例 Elapsed 包含等待名额的时间，不能把其总和当包墙钟；性能判据使用包级 pass 事件的 Elapsed。三轮耗时使用每轮首个顶层 run 到该轮第 185 个顶层 pass 的 UTC 差。
