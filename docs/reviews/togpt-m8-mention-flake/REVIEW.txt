Finding
-------
TestCrossMemberMentionRoutesToTargetSessionAndRepliesToSource opened two
websockets then immediately dispatched a cross-member mention.  A client-side
websocket upgrade completes before HandleSessionWS publishes the session in
Hub.sessionClients: publication happens after the onboarding frame.  The test
therefore sometimes asserted delivery before its target had satisfied the
normal routing precondition.  This repair waits for the concrete, observable
Hub registration condition for both source and target.  It does not extend a
sleep and changes no product code or routing semantics.

S-M8-FIXTURE-RACES follow-up
-----------------------------
Snapshot UTC: 2026-10-15T01:50:00Z

The coordinator grouped four fixtures under the same registration-readiness
issue: the cross-member mention/reply fixture above, the four routing-flow
fixture, and TerminalViewCookie's terminal-state fixture.  The latter two
also treated successful client websocket upgrade as if it implied server-side
runtime publication.  That is not guaranteed: onboarding is written before
`sessionClients` is published, and terminal-view setup reads the terminal
installed by that registered handler.

This follow-up therefore adds three `waitSessionOnline` preconditions:

* both `home` and `developer` before TestSessionAddressingFourFlows sends;
* `home` before TestTerminalViewCookiePersistsAndRestoresUnlock opens its
  terminal view;
* the previously delivered two waits remain in the cross-member mention
  fixture.

All waits use the existing observable Hub registration condition.  No timeout
was extended and no product routing, delivery, terminal, or persistence code
changed.
