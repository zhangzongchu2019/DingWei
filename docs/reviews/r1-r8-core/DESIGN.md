## Boundaries and provider contract

internal/changeflow is independent of network and SQLite. The pure classifier consumes immutable normalized diff/labels and parsed rules. A Service consumes a Provider and transactional Store. Provider.WithAccess must validate a controlled instance/repository/MR and exact coordinate, current individual user's permission for the requested action, and preserve that fence through the callback/commit. Actions read/detect/ack/result/advance/tool/comment are independent; service-account access and platform role do not imply repository access. Reader.Read returns a complete, canonical immutable Snapshot for exactly the requested coordinate, including actual current MR head. Every nested approval, PM, committee, task, applicability and release fact must have been verified to belong to that Snapshot coordinate; wrapping an unrelated fact in a requested coordinate violates the adapter contract. Unknown sets use Known=false, never an empty success default. Current effective review/PM records must be unambiguous; duplicates block.

The mutation reads facts before validation and again within the storage transaction before commit, and rejects any intervening snapshot change. The provider fence must remain valid through that transaction, including ACL validity. This contract is deliberately stronger than simply caching a prior Git API response; real adapters need a reviewed consistency/revocation design and integration evidence. No distributed Git/R9/R7 atomicity is claimed by this fake-provider test cut.

GitHub and GongFeng types are fail-closed stubs returning ErrUnavailable; they never use tokens or make network calls. Real webhook/periodic discovery, host/MR identity mapping, source/ACL completeness, approval policies, R7/R9 bridge, comment reconciliation and credentials remain external gates. Hub.ChangeEvidence is a startup-only dependency and nil by default; default APIs return 503, with no fake data or fake runtime adapter. R7 SpecConfirmations wiring/default remains unchanged (503). A configured trusted core service provides the separate Console entry, GET/POST API and explicit actions. No deployment/production write is implemented or performed.

## Rules selected for this core review

Platform defaults are embedded from internal/changeflow/default_risk_paths.yaml. Repository extension bytes must be fetched by the future provider from openspec/risk-paths.yaml at the exact target commit; ParseRules verifies their Git blob SHA. Schema: version: 1 and rules entries with id/category/paths/keywords. Seven exact category labels are fixed. Default and repository rules are an additive union; duplicate IDs, unknown fields, multiple YAML documents, aliases/anchors, bad categories and unsafe patterns are rejected. A repository cannot silently disable platform defaults.

Paths are canonical relative paths, case-sensitive. * and ? stay in a segment; ** spans segments, and **/ permits zero segments. Traversal, absolute paths, backslashes, controls, and []/{} glob constructs are rejected. Both rename sides participate. Keywords are case-folded literal matches; ASCII word edges prevent substring lookalikes, Chinese phrases match literally. Only added lines parsed from complete unified hunks are scanned; removed/context/header text is excluded. Binary files retain path/label classification and have no textual patch. Incomplete/truncated/invalid input returns unavailable, not zero hits. Matching does not fetch, write, read a clock or emit source lines. Hits include category/rule/source/path/new-line-number only.

Rule identity binds matcher semantics, captured default-table hash, repository Git blob and parsed entries; mutable entries with an old version are rejected. Limits include 16KiB repository YAML, 256 file diffs / 4MiB patches, per-file 2MiB, bounded rules/terms, and a 64MiB keyword-comparison work budget. Exceeding a limit is unknown, never a silent partial result. These executable schema/matching/limit choices are proposed as the reviewable first-cut contract, not a claim that prior R1-A01..04 external assumptions are resolved.

## Reminder and delivery

The coordinate includes provider, instance, repository, stable MR/PR identity, change directory and complete commit. One stable reminder per coordinate contains immutable input revisions. Same canonical input does not create another revision; a newly hit commit has a separate reminder. Labels/rules changing at one commit append a revision and update the original MR/Console reminder. Exact hit-set changes (including decreases and zero) clear that revision's knowledge; unchanged sets preserve the original acknowledgement reference/time. Owner changes produce a new revision and cannot inherit another owner's acknowledgement. Old revisions, knowledge and merge provenance remain visible. Unknown input never clears previous risk. A stale revision acknowledgement is rejected even before a replacement detection is saved.

The Console projection is saved with the revision. Comment delivery is separately authorized; a failed/unknown write does not erase Console state or create a merge/phase gate. UpsertComment must update the same ReminderID, use its per-revision OperationKey, and reconcile unknown writes by that key before any further physical write. Fake tests model a committed write with a lost response and prove a retry does not physically write twice. Attempts/status/location/time are retained; delivered channels are not rewritten on replay. No exactly-once behavior for an actual Git host is claimed. Structured comments never contain added source lines/patches or credentials.

## Lifecycle and evidence

Only adjacent explicit transitions on the exact current head are accepted. Ordinary SPEC_APPROVED requires complete current-head required reviews and all explicit same-head PM responses (agree/disagree/modify retained as such). No R7 call/confirmation is required for ordinary changes. Exact committee-review label OR the provider-verified positive proposal flag adds a valid authorized same-SHA R7 confirmation. Risk, author and platform identity do not infer committee scope. Prerequisites are rechecked cumulatively for later transitions.

ACCEPTANCE requires a nonempty complete task set, done flags and per-ID actor/summary/commit/handoff evidence, with verified applicability for a different execution commit. ARCHIVED requires a nonempty complete scenario set, a latest four-state result per ID, evidence, no FAIL, and reasons for NOT_RUN/NOT_APPLICABLE. Result corrections append and reference the latest old result; no history is overwritten. Tested commits, actor and server UTC are retained. RELEASED requires a verified successful release ID, exact coordinate/commit, report reference and requested environment. Previously recorded environment facts are derived from immutable advance events, separately from a provider's current release snapshot. Tasks/strict/archive/merge tools record their own facts and never change a phase.

Unknown, revoked or stale facts block and never get substituted by an old green state. Console reads reauthorize per user, label historical versions explicitly, show risk freshness, stage/blockers, review/PM/committee/task facts, scenario counts/reasons/evidence, and recorded release environments. Text is rendered with textContent; source diffs/rules are not returned. Failed writes invalidate the displayed snapshot until reread; current permissions are never obtained from cached UI state.

## R45 migration ledger

0069_changeflow_evidence.sql follows the unchanged 0067 legacy freeze and 0068 confirmation migrations. It adds a coordinate-keyed JSON aggregate with a monotonic CAS revision and 8MiB limit. State, reminder revisions, results, operations, tool records and advance audit are committed as one row in one SQLite transaction; failed validation/second read/CAS/SQL commit rolls back the entire mutation. Prefix guards reject modifications/removal of prior results/events/tools/reminder history and already-recorded knowledge/merge facts. No legacy rows, confirmation facts or historical rule data are backfilled or rewritten. Migration replay and reopen persistence are tested. Future database adapters must implement the same transactional/CAS contract.
