## 0. 一句话结论

**五个客户端，没有一个需要 PTY。** 有服务端协议的四家（claude / codex / opencode / codebuddy），多轮会话与打断都是**协议原生能力**；trae 与 kiro 没有协议通道，是本批客户端里的**成本大户**——而它们恰恰是本次需求的主角。

## 2. 测试方法

对每个客户端，依次回答三个问题：

1. **能不能不用 PTY 驱动？**（管道 / 协议 / 库内嵌）
2. **多轮会话支持吗？上下文保持吗？**（喂第二条消息，看它记不记得第一条）
3. **在 Windows 上是否同样成立？**（同一套代码路径跑一遍）

判定标准一律以**可观测的副作用**为准（文件真的被创建、协议帧真的返回），不以"进程没报错"为准。

## 3. 逐个客户端实测过程与结果

### 3.1 claude 2.1.207 —— ✅ 全项通过（唯一端到端全通的）

**驱动方式**：`-p --input-format stream-json --output-format stream-json --replay-user-messages`

**Linux 单轮**（含工具调用）：

```
[回放 user]  Create a file named proto.txt...     <- --replay-user-messages = 协议级送达 ACK
[工具调用]   Write {'file_path': ...}
[工具结果]   File created successfully at: ...
[assistant]  DONE
[RESULT]     is_error=False turns=2 ms=4483       <- 协议级完成边界
proto.txt 内容 = protocol-ok                       <- 副作用真实发生
```

**Linux 多轮（关键验证）**：同一进程连喂两帧，第二帧考记忆——

```
[第0次回答] OK
[RESULT #1] is_error=False session=cc9563fd
[第1次回答] banana                                 <- 准确答出第一轮让它记的词
[RESULT #2] is_error=False session=cc9563fd        <- 同一 session_id，上下文保持
```

**Windows 真机**：同一套命令，`win-proto.txt` = `win-protocol-ok` **真的创建**。

**结论**：送达确认（ACK 帧）、完成边界（`result` 帧）、多轮上下文、工具事件流——**全部由协议提供**。`is_idle` 靠 1.2s PTY 静默猜忙闲的做法，在此彻底失去存在理由。

### 3.2 codex 0.144.3 —— ✅ 协议最强（LLM 端到端受限于 key）

**驱动方式**：`codex app-server`（JSON-RPC over stdio）

**握手实测（Windows 真机，无需认证）**：

```json
{"id":1,"result":{"userAgent":"probe/0.144.3 (Windows 10.0.26200; x86_64)...",
 "codexHome":"C:\\Users\\dev\\.codex","platformFamily":"windows","platformOs":"windows"}}
```

**协议能力**（由 `codex app-server generate-json-schema --out <DIR>` 导出的 JSON Schema 实证，非文档推测）：

```
Thread/startRequest       开会话        Turn/startRequest       发一轮消息
Thread/resumeRequest      恢复会话      Turn/interruptRequest   打断当前轮
Thread/readRequest        读历史        Turn/steerRequest       轮进行中「转向」插话
Thread/forkRequest        分叉会话      Thread/injectItemsRequest  注入条目
Thread/rollbackRequest    回滚          Thread/listRequest      列会话
ApiKeyLoginAccountParams  ← 支持自带 API key
```

**`Turn/interrupt` + `Turn/steer` 正是我们用 Ctrl-C 和「外部消息抢占输入框」硬凑的两件事**——在 codex 里是协议原生能力。

**未验部分**：LLM 端到端。codex 走 OpenAI 协议，而本次可用的 DeepSeek key 只暴露 `/anthropic` 端点，无法完成真实推理调用。**协议通道本身已验证**（握手 + schema 导出均在 Windows 上成功）。

**接入注意点（实测踩到）**：`app-server` **要求 stdin 保持打开**。用 `type req.json | codex app-server` 这种"喂完即关"的管道，进程直接退出、一个字节都不回。必须长驻进程 + 持续写 stdin。

### 3.3 opencode 1.17.18 —— ✅ 协议通过（人机同看最干净）

**驱动方式**：`opencode serve --port --hostname`（headless HTTP 服务端）

**Windows 真机实测**：serve 监听成功，`GET /config` → **HTTP 200**，返回正常 JSON：

```json
{"$schema":"https://opencode.ai/config.json","command":{},"plugin":[],"username":"dev","mode":{},"agent":{}}
```

**会话接口**（由服务端自曝的 OpenAPI `/doc` 实证）：

```
POST   /api/session                        建会话
POST   /api/session/{id}/prompt            发消息（多轮）
GET    /api/session/{id}/message           读消息历史
GET    /api/session/{id}/event             事件流（SSE）      <- view 可直接渲染事件，不必转发 PTY 字节
POST   /api/session/{id}/interrupt         打断
POST   /api/session/{id}/compact           压缩上下文
GET    /api/session/{id}/history /context  历史与上下文
POST   /api/session/{id}/permission/...    工具授权
```

**未验部分**：LLM 端到端（未配 provider）。

**⚠️ 安全问题（实测发现）**：`serve` **默认无鉴权**，启动时自曝警告 `OPENCODE_SERVER_PASSWORD is not set; server is unsecured`。不设该密码，**本机任意进程都能操纵会话**。接入时必须配置。（注：本次尝试用 `-u ":password"` 的 Basic 认证访问返回 401，正确的鉴权头格式待确认。）

### 3.4 codebuddy 2.116.0 —— ⚠️ 协议可行，但**不能自带 key**（硬阻塞）

**协议帧完整**（实测）：`system/init` → `system/status` → `assistant` → **`result`**（带 `is_error` / `errors[]` / `num_turns` / `usage`），完成边界明确。它是 Claude Code 的同构分叉，slash 命令里也有 `remote-control`。

**但模型路由走腾讯云网关，BYO-key 这条路是死的**——三次尝试的证据链：

1. `ANTHROPIC_*` 环境变量：**完全不认**，报 `Authentication required. Please use /login`
2. 改用它自己的 `CODEBUDDY_BASE_URL` / `CODEBUDDY_API_KEY` 指向 `https://api.deepseek.com/anthropic`：模型认了（`model=deepseek-v4-pro`），但报 `404 Server error (proxy: 1.1 -> https://api.deepseek.com)`——**`/anthropic` 路径被吃掉**
3. 起本地改写代理（把 `/v1/*` 补回 `/anthropic/v1/*`）并把 base_url 指向 `http://127.0.0.1:8899`：**本地代理零请求**，报错却变成 `(target: http://127.0.0.1:8899)`

第 3 条是决定性的：**base_url 是在服务端被解释的**——腾讯的网关当然连不到我们机器的 localhost。（该本地代理已单独验证可用：手工 curl 直接从 DeepSeek 拿到正常回包。）

**结论**：接入 codebuddy 必须用 codebuddy 账号 `/login`。多轮能力因此**未能实测**（推测与 claude 一致）。

**落盘格式（附带查明）**：`~/.codebuddy/projects/<cwd-slug>/<uuid>.jsonl`，目录布局与 claude 一致，**但 schema 不同**：

```
claude    : {"type":"assistant", "message":{"role":"assistant","content":[{"type":"text",...}]}}
codebuddy : {"type":"message", "role":"assistant", "content":[{"type":"output_text",...}], "status":"incomplete"}
```

→ 走 `SH_CLAUDE_PROJECTS_ROOT` 捷径会**定位到文件但 parse 出 0 条事件**，表现为"注入未被 CLI 接收"，极易误判为网络问题。

### 3.5 trae（bytedance/trae-agent）—— ⚠️ 能跨平台，但**没有多轮会话**

> **需求歧义警告**：`trae.ai` 卖的 **Trae IDE 是桌面 GUI，没有 CLI，接不进 helper**。本次测试的是 [bytedance/trae-agent](https://github.com/bytedance/trae-agent)（Python / MIT / 命令 `trae-cli`）。

#### ① 无 PTY 驱动 —— ✅ 通过（Linux + Windows 真机）

它**完全没有流式/JSON 接口**（grep 全空），只有 `run`（一次性）和 `interactive`（REPL）。但 simple console 用的是裸 `input()`（`simple_console.py:197`），**普通 stdin 管道即可驱动**。

**Linux**：`Success ✅ / Steps 5`，`hello.txt` = `pipe-ok`
**Windows 真机**：`Success ✅ / Steps 10`，`hello.txt` = `win-pipe-ok`

**同一套代码路径、同一个补丁、同样的结果。这直接证伪了"Windows 必须重做 PTY 层"。**

跨平台的底子也是好的：依赖无 POSIX-only 包（唯一 `pexpect` 在 docker 模式，非必经路径，且 pexpect 自身守卫了 `sys.platform != 'win32'`），`bash_tool.py:41-59` **上游已分支处理 Windows**（走 `cmd.exe /v:on`）。

#### ② 多轮会话 —— ❌ **不支持，且默认第 2 轮必挂**

这是本次最重要的负面发现，分三层：

**第一层：设计上就没有会话记忆。** `agent.run()` 每次都调 `new_task()`，把 `_initial_messages` 清空重建（`trae_agent.py:122`）。**trae 的 interactive 不是"一个有记忆的会话"，而是"一个任务启动器"**——问它第二句，它完全不记得第一句。

**第二层：真 bug —— 第 2 个任务必然 400 失败。**

- `AnthropicClient.message_history` 挂在**客户端实例**上（`anthropic_client.py:28`）
- `chat()` 默认 `reuse_history=True`，往上追加（`:65-66`）
- `base_agent.py:216` 调用时**没传该参数**，且任务开始时**无处重置**

实测第 2 轮报错：

```
400 - messages.10: `tool_use` ids were found without `tool_result` blocks
      immediately after: call_00_MlXzVfl5gAbalxQwZhd23916
```

`messages.10` 说明请求里有 11+ 条消息——第 1 轮的**残缺历史**（有 `tool_use` 无配对 `tool_result`）泄漏进了第 2 轮，服务端直接拒绝。

**第三层：DeepSeek 端点上还有 thinking 块不兼容。** 打上补丁 2 后两个任务都能跑，但第 2 轮仍 `success=False`：

```
400 - The `content[].thinking` in the thinking mode must be passed back to the API
```

trae 的 anthropic 客户端重建历史时丢掉了 `thinking` 块，而 DeepSeek 要求原样回传。**此项 provider 相关**，官方 Anthropic key 未必出现。

#### ③ 接入 trae 需要的三个补丁 / 一个设计

| # | 问题 | 处理 |
|---|---|---|
| 补丁 0 | `docker` / `pexpect` 被 `base_agent.py:12` 无条件导入但**不在 pyproject 依赖里**（trae 的打包 bug） | 手动补装 |
| 补丁 1 | `anthropic_client.py:76-94` 把 `str_replace_based_edit_tool` / `bash` **硬编码成 Anthropic 服务端内置变体**（`text_editor_20250429` / `bash_20250124`），非官方端点报 `400 unknown variant` → 编辑与执行能力全废 | 改走自定义 `input_schema`（其余工具本就如此）。**已验证有效** |
| 补丁 2 | 跨任务 `message_history` 不重置 → 第 2 轮必挂 | `new_task` 后 `set_chat_history([])`。**已验证有效** |
| 设计 | 无会话记忆 | 走 `EmbedDriver`（库内嵌），**由 helper 自己维护对话历史**，每轮前灌进它的公开方法 `set_chat_history()` |

**代价**：接入 trae = 维护一个 trae fork（或把补丁提上游）+ 自己实现会话记忆。**这是需要拍板的长期成本。**

#### ④ 一处更正

此前记录"trajectory 是 session 级单文件"——**错了**。实际是**后一个任务把前一个任务的 trajectory 整个覆盖**（`save_trajectory()` 用 `open(path,"w")` 全量重写，`trajectory_recorder.py:226`）。第 1 轮的记录在第 2 轮开始时即消失。这对 reader 设计影响很大：**不能用字节偏移 tail**。

### 3.6 kiro —— ❌ 未能实测（卡 AWS Builder ID）

- Linux x86_64 要求 **glibc ≥ 2.39**；本机 2.39（Ubuntu 24.04.4），**刚好达标、零余量**
- **必须 AWS Builder ID 登录**才能运行 → 本次无法实测任何一项
- 文档明确：headless 模式 **"No mid-session user input is possible"**，`--no-interactive` 是纯一次性，**不支持持久会话**
- 但**每轮对话落 SQLite**（mac 上 `~/Library/Application Support/kiro-cli/data.sqlite3`），且有 `--resume` / `--resume-id <SESSION_ID>` / `--resume-picker`
  → 与 opencode 的 `opencode_db` 模式同构，现有 `OpenCodeDBReader` 机制可照搬

**生死线（仍未验）**：`--no-interactive` 能否配 `--resume-id`？
- **能** → 用"一次性调用 + resume"拼出伪多轮，绕开 PTY
- **不能** → 每条消息都是无上下文的独立提问，kiro 只能退回 PTY

## 5. 附带交付：Windows 虚机 Chrome 故障修复

排查中发现该 Windows 客户机 Chrome 无法访问任何网页，一并定位并修复。

**两个症状，一个根因**：

| 现象 | 检查结果 |
|---|---|
| DNS 解析 | ✅ 正常（`172.30.0.1` → `www.baidu.com` = `157.148.69.151`） |
| TCP 80 直连 | ✅ 通 |
| HTTP 请求 | ❌ 失败 |
| **系统代理** | **`ProxyEnable=1`，`ProxyServer=106.55.199.210:8080`** |
| 该代理 TCP 8080 | ✅ 端口开着 |
| 该代理实际转发 | ❌ **应用层已死**（走代理 `HTTP=000`，直连 `HTTP=200` 仅 44ms） |
| 直连 HTTPS | ❌ 也失败 → `schannel: CRYPT_E_REVOCATION_OFFLINE (0x80092013)` |

**根因链**：那个"TCP 通但不干活"的半死代理 → ① Chrome 读系统代理 → 网页全废；② **schannel 校验证书时要拉 CRL/OCSP，该请求也走系统代理** → 拉不到 → **HTTPS 全部失败**（即使 curl 用 `--noproxy` 绕过代理连接本身）。

**处置**：`ProxyEnable=0`。复测 HTTP 200 / HTTPS 200 / `Invoke-WebRequest` 200，**用户已确认 Chrome 恢复正常**。

**回滚**：`Set-ItemProperty -Path "HKCU:\...\Internet Settings" -Name ProxyEnable -Value 1`

> 建议确认那个代理 `106.55.199.210:8080` 是否应彻底废弃——"TCP 通但应用层死"的半死状态最具迷惑性。
