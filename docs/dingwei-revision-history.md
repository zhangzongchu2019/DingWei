## 一、架构设计（`dingwei-architecture-design.md`）

### A§0.0 门状态表述的四次失同步

本节的「已过的门 / 可否作为施工依据」是**状态性表述**，随门结果变化；历史上四次未随门状态同步：

| 次 | 形态 |
|---|---|
| 1 | 原型「正在评审中」写进正文，门结束后未改 |
| 2 | A§0.0 头部表格块已改，同节保留段未回头看，两处直接打架 |
| 3 | 头部与保留段同步后，正文另有 4 处同义现状断言（「目前一个都没过」「无有效结果」「不得展开施工」「设计未过审」）未随门结果同步 |
| 4 | 本节曾把草案期的限制写成当前结论（称首要开工件不是 SP7a），被生效与新 verdict 证伪 |

**根因**：改了一处没回头搜同一断言的其余出现点。
🔴 第 3 次那 4 处**不是 PAT 短语，`status-consistency-check` 抓不到** —— **闸过 ≠ 全清**。
⇒ 已立的对策：门状态与各件版本**一律指 `docs/DELIVERY-STATUS.md`，正文不写**。

### A§0.1 「只锚不述」口径的一次撤回

原写「凡属规则的**一律**只写 `§X`，不抄原文」——那是**绝对断言**，而本件实际做不到
（A§3 / A§4 / A§9 / A§13 四处存在规范性复述）。
🔴 **同一份文件里一句立绝对、一句给例外，读者按哪句判都能自证。**
⇒ 原句撤回，口径改为 A§0.1a 的三档表（架构不变量可一句话摘要＋锚；规则正文禁成条复述；判据与阈值一律指锚）。

### A§0.1 「不自报 § 引用数」的由来

正文曾写「53 个 § 引用」——手写值，内容改过之后即不成立，被实算证伪。
⇒ 计数型表述不写死数量（同 E.3 #36）；现值由 `scripts/arch-refcheck.sh` 实算产出，不写进正文。

### A§0.2 抽象层口径的一次收窄

原口径写宽，导致同一份文件内部对撞：A§8 写了 `127.0.0.1` 与反代路径，与本节自禁冲突；
而清查后判定 `127.0.0.1` 属**架构关系（回环）**、非真实部署标识。
🔴 **两说都对，是口径写宽了。** ⇒ 收窄为 A§0.2 的允许/禁止两列表，判据为
「这个值换一台机器部署还成立吗」。

### A§3 / A§4 / A§9 / A§13 的四次压缩

四节原各自复述了 §5.8 / §21 / §23 / §22.4 / §26.4.4 / §5.2 / §0.3 的**规则正文**
（角色×权限矩阵 · 各条裁定的理由 · 凭据级别对照表 · schema 变更分级）。
⇒ 按 A§0.1a「规则正文禁成条复述」删去，只留**规则对系统构成提出的要求**，理由指锚。

### A§6.1 映射表的单向漏检

原表只列「各 SP 承载在哪」，没反过来查「每个包归谁」，14 个包无归属。
🔴 **单向映射看着齐，反查即漏。** ⇒ 映射表须双向闭合：正查每个 SP 有承载，反查每个包有归属。

### A§6.2 「只给结论不给命令」

正文曾只给实测数字、不给产出它的命令 —— 那等于要求评审方**信任执笔方的测量**；
而执笔方在同轮已被实测证伪两次（`internal/view` 当作包依赖 · 手写 § 引用数）。
⇒ 每个实测数字附产出命令，使无仓访问的评审方可判断该数字怎么来的、并在取得访问后逐条复算。

### A§8.3a 「依赖 ≠ 路径」

原写「ops 紧急面必须有独立于边缘层的可达路径」——**自造，且有害**。
§25.4.2 原文即为「浏览器 → Nginx → `127.0.0.1` sidecar」；§25.4.2a 要求的是
**不消费平台令牌、不访问平台应用层**，Nginx 只做固定会话的转发。
🔴 **「不依赖 X」被读成了「不经过 X」** —— 一个是故障传播关系，一个是网络路径。
⚠️ 且推错的方向恰好**扩攻击面**：真去建第二入口，它就绕过了 edge 的剥头 · 日志遮蔽 · TLS · 限流 · 路由隔离，
而第二入口自身的认证 / 固定 `target_session` / 能力收窄 / 审计 / 网络暴露面**一条都还没定义**。
⇒ 采纳现行 SpecDoc 设计（A§8.3a 五条约束）。

### A§12 「入口收口」曾被当成「隔离达成」

原表把甲组三条（建库调用集恒零 · 未被仓储包引用的表恒零 · 漏传 `TenantCtx` 编译失败）当作隔离判据。
🔴 **甲组只证明收口，证不了隔离**：持**有效** `TenantCtx` 跨租户读，甲组三条**一条都拦不住**。
⚠️ 这是同一个滑坡的第三次（前两次：限制输出冒充授权 · 不泄漏存在性冒充拒绝）。
⇒ 增设乙组四项，且 ①②**须分开验** —— 只验②会让「先查了再拒」通过验收。

### A§15 worked example 的一次重算

初版给「跨模块 / 灰度可回滚 / 需回滚成本」各安了一条规则 ID，而 §5.6 从未为这三种取值定义强制追加环节
—— 那是照着「看起来该有」补的，规则表里没有那些 ID。
🔴 **规则表没有的行，样例里不能有** —— 补了就是在样例里悄悄扩规则。
⇒ 改为「无命中」；**一个不能被独立重跑的样例，不构成可重复判定的证据。**

## 二、SpecDoc（`dingwei-platform-specdoc.md`）

### §0.3 子 spec 编号由 `S0–S8` 改为 `SP0–SP8`

起因是自查发现 **`S` 系同词异义**：子 spec 编号与 §22.4 的**凭据分级**（S0–S2）在同一份文档里并存。
最刺眼的一对是「**S1** 是其余全部子 spec 的共同前置」与 §23.5「触及 **S0/S1** 者仍须按对应层级审批」
—— 同一 token，一处分册号、一处凭据级。
⚠️ §11.4a 当时已写「与凭据分级不是同一套」，说明**已察觉 `S` 有歧义**，
却只去澄清它与 `visibility` 的关系，**没意识到它同时还和子 spec 编号撞了** —— 看到一个面，没看到另一个面。

### §0.3 依赖环与子 spec 覆盖

曾把 SP7 整体前置于 SP2/SP3/SP5 以为可消环 —— 不成立，环仍在，只是换了个说法。
另曾遗漏 §1–§4、§23、§24、§28、§29 无人认领，由此增设 SP0 与 SP8 并重画依赖图。

### §0.4 本节四次失同步

本节曾长期写「单一 Markdown / 无 checklist / 第 1、2 项仍欠」，而 `specs/` 已落地、三域 checklist 已产出
—— **同一当前状态两存**。根因是建了 `specs/` 却没回头改本节：**「改了没同步引用点」**。
⚠️ **不是未实现，是已实现而文档没跟上。**
第 3 项曾判「已闭」，后撤回为「部分闭合」。

### §4.5 board 口径的三次收窄

① 曾写「board / mcsd 整体重建」，与本节「保留 mcsd」直接冲突；
② 收窄为「board 存储层与状态机重写」，但所列证据（SQLite 单写者 · 无 migration runner ·
C0.1 未实现 · 幂等键未闭合）只支持**存储层与身份层重建**；
③ 再收窄为「存储层重写；状态模型按新契约重构」——
**证据只支持它所支持的那一层**，不得据以推出更大的结论。

### §5.4a 新权威表与既有 §5.6 的对撞

新表初版**自造了与 §5.6 不同的门集**（`R-DM-02` 曾写代码评审而 §5.6 是文档评审；
`R-CON-01`、`R-PROD-01` 亦各差两项），造成**同一输入两个门集**。
🔴 根因是**加了新权威表却没与既有表对撞** —— 属「合并未对撞」，
且撞的是**自己刚写的表**与**已过多轮评审的旧表**。⇒ 已按 §5.6 为准逐行改回。

### §11.4b 标题条数的一次机器化失败

标题曾写「四条硬性」而表内五行。试图机器化（`head-count` 规则比对「标题所载数量 vs 紧随其后的表行数」）
**失败并撤回**：实跑 6 处命中全部误报 —— 章节号「12.4」被读成「4 条」等。
🔴 判定「标题里这个数指不指这张表」属语义，机器分不出 ⇒ 归 E.3 #36 人审。
⚠️ **本类缺口最终是用眼睛看出来的，不是闸抓出来的。**

### §22.2c / C.3 → C.3a 存储选型的重裁

原裁定（2026-08-24）为「受控仓储 API 单点，不做 RLS，不做每租户独立库」，
排除独立库的核心论据是**运维成本**，其展开为「跨域读是常规高频动作」。
2026-08-25 业主裁定「企业之间不允许任何交流」「D1→D0 晋升关闭」后，**该前提不复存在**，
成本论据随之失效；而原裁定在安全轴上本就承认「只有物理隔离接近杜绝」。
⇒ 重裁为 C.3a（一企业一 PG 库 ＋ RLS 兜人层）。**非否定原判断，是其前提变更后的必然结果。**

### 附录 E.5 计数的一次自相矛盾

曾写「去重后的约束条数」，与本件自定的「计数型表述不写死数量」自相矛盾，已删。
🔴 与「输出精度超过实取精度」同一毛病：**计数亦属可验证值，不得手写。**

### 导出函数：注释与代码相邻对撞

导出改稿的 `out` 对象上方注释论证「内嵌一个上一版的哈希，看着精确其实是过期值」，
**紧接着的下一行就内嵌了两个过期版本号**（`依据SpecDoc版本:'v3.13', 原型版本:'v1.13'`，彼时实为 v3.23/v1.19）。

🔴 属「**刚立的规矩在下一段自破**」，且是最短距离的一例 —— **相邻两行**。
⚠️ 后果不是不好看：任何经此导出的改稿都**天然挂错基准**，收件方按它去比对，
比的是几个版本之前的文本。**这正是「各方评审基准不同」在工具侧的成因。**

⇒ 现改为不写死任何版本，只留一句「基准以导出时仓库的 git 锚与 DELIVERY-STATUS 为准」。
