## §1 要解决的问题（业主原述）

**① 作业无痕**
> 通过平台通讯通知实现了协同，但也带来了作业无痕，即：除非翻看聊天记录，无法知道交付物的产生过程。

**② 消息风暴**
> 过往实践中一个任务如果出现了 3 个评审、4 个 Agent 以及 coordinator，相互之间就会出现大量无效、过期消息，
> 导致时间浪费、token 浪费。

**业主给出的方向**：收敛到参与者；**尽量限制压缩 coordinator 的转发功能**，也能减少其拖沓冗长与浪费。

---

## §2 根因：三件事被混在同一条消息流里

| 混在一起的 | 应有形态 |
|---|---|
| **控制面**（改状态：建单/提交/评审/收口） | 结构化、受权限矩阵约束、**需要推送** |
| **记录面**（讨论、澄清、过程） | 自由文本、**只需留痕，不需推送** |
| **转发面**（coordinator 把 A 的话转给 B） | **本身是放大器**——每次转发既复制内容又引入版本漂移 |

于是：记录面被当成通知推给所有人 → **风暴**；控制面状态只存在消息里、无权威账 → **无痕**
（与纲领 §2.2 同一根因）；转发面把前两者**乘以参与人数**。

> **本轮实证**：本纲领评审一轮内出现三次版本错位，**全部发生在转述环节**。
> coordinator 每次转述都善意且准确，仍然漂移。**不是人的问题，是「转述」这个动作本身有损耗。**

### 3.2 租户是外层硬边界，fail-closed

**可见性 = `tenant` ∧ `task_role`**，两级：

| 层 | 判据 | 性质 |
|---|---|---|
| **外层：租户** | Agent / 任务 / 帖子所属租户 | **硬边界，默认拒绝，fail-closed** |
| **内层：参与者** | C5.1a role×op 矩阵（`task_role` 成员 / per-段指定门方 / 调度者） | 租户内的作用域收敛 |

原提案（v0.1–v0.4）只设计了内层。**外层为本版新增。**

### 3.3 解封阶梯收敛到租户内

§4.3 的阶梯硬门中「业主解封」= **该租户的业主**。升级链在租户内终止，
**不存在平台级超级业主**。这比跨租户升级更干净。

### 3.4 ops 的归属：两类并存（业主 2026-08-23 裁定，原 F7 已闭合）

业主原话：

> ops-Agent 有两类：**系统平台级的 ops**，和**租户级的 ops**。要看具体业务，一般来说
> **生产系统、平台运维、公共资源**都是平台级的 ops 工作；**业务模块开发、测试环境**等都由租户级 ops 自行解决。

→ **F7 的答案不是「租户 or 特殊角色」二选一，而是两类并存、按职责域划分。**

| | **平台级 ops** | **租户级 ops** |
|---|---|---|
| 归属 | **不属于任何业务租户** | **租户内的一个 capability / 职责域**（v1.4 更正——**不是 `task_role` 的一个枚举值**，见下） |
| 职责 | 生产系统、平台运维、**公共资源** | 业务模块开发、测试环境 |
| 边界约束 | 见 §3.4a（权限按面切） | 受正常 `tenant ∧ task_role` 约束 |

> ⚠️ **v1.4 更正（评审方建议）**：v1.1–v1.3 写「租户级 ops 是租户内的**一个角色**」，措辞会被读成扩 `task_role`。
> **本席复核：`board/schema.sql:28` 的 `task_role.role` 是四值 CHECK 枚举
> `('designer','implementer','tester','qa_owner')`，其中无 ops。**
> 扩枚举 = schema CHECK 变更 = 撞上纲领 §7.1 第 14 项那套尚不存在的迁移机制。
> → **租户级 ops 应落为 tenant-scoped capability / 职责域，不直接扩 `task_role`。**
> **是否扩枚举另立项**（列为 F11）。

#### 3.4a 关键推论：权限按**面**切，不按**人**切

**平台级 ops 的权限是分面的，不是「更高」**：

| 权限面 | 平台级 ops |
|---|---|
| **基础设施面**（重启服务、改配置、处置公共资源） | **高** |
| **跨租户数据面**（**备份 / 恢复 / 全库迁移**——v1.4 从基础设施面移出：**一份全库备份含所有租户业务数据**） | **默认无**；须走独立受控 service role + 审批 + 时限 + 审计 |
| **租户业务数据面**（读租户的任务内容、帖子流、交付物） | **默认无** |

**理由**：平台级 ops 修的是基础设施，不是租户的业务内容。
若默认给它全租户业务读权，**多租户隔离在最有权限的那个主体上就破了**——
而它恰恰是跑得最频繁、最容易被复用的主体。

**此思路平台已有先例**：`internal/datad/pgstore.go` 的 `OpenPGPools(dsn, assignDSN, gcDSN)`
——**三池分权**，注释明写「常规应用池对 assignment/首果账**无写权**」。**权限按面切已是既有实践。**

**确需读租户业务数据时**（如排查某租户 board 损坏）：走**受限 + 落账 + 有时限的临时授权**，
仿 C2.6 `role_exemption` 既有口径——**「可审计，不可匿名突破」**。不得常设。

#### 3.4b 若采用 PG RLS：完整角色分离（v1.4 重写）

> ⚠️ **v1.4 更正**：v1.1–v1.3 此处只写「**不得带 `BYPASSRLS`**」，**必要但远不够**。
> 更难堪的是：**v1.3 的 §7.3 里本席自己写了「§3.4b 只写了不得带 `BYPASSRLS`，漏了 owner 绕过」，却没去改 §3.4b。**
> 即**在修正记录中标注了某处有漏，却没把那一处同批修掉**（详见 §12.3）。

**PG 中能绕过 RLS 的三类主体**：`superuser`（永远绕）、`BYPASSRLS` 角色、**table owner（默认绕）**。

**必须的角色分离**：

| 角色 | 属性 | 用途 |
|---|---|---|
| **object-owner / migration owner** | **无登录**（`NOLOGIN`） | 持有表对象、执行 DDL；不用于运行期 |
| **运行期平台 ops 角色** | **非 superuser、非 `BYPASSRLS`、非 table owner** | 日常平台运维 |
| **跨租户 service role** | 独立、受控 | 仅在确需跨租户时启用（见下） |

**表侧配套**：租户表**启用并 `FORCE ROW LEVEL SECURITY`**；
**tenant context 每事务 `SET LOCAL`**（非会话级 `SET`，防连接池泄漏）；**缺失默认拒**。

**跨租户能力（DDL / 备份 / 恢复）走独立受控 service role 或离线流程**，
**不给日常平台 ops 常设数据读权**；其使用须**审批 + 时限 + 审计**。

> ✅ **v1.5 补入 prodops 实测先例**：本队 datad 已在做——
> **`datad_user` / `assign` / `gc` 三角色实测 `rolsuper=f`、`rolbypassrls=f`**。
> 即「运行期角色不带 bypass」**不是理论建议，是本队生产既有实践**。
>
> ⚠️ **同时纳入 prodops 的反向约束**：
> **必须配套【受控 bypass 通道】（备份 / 审计 / 迁移专用角色），否则运维被 RLS 锁死。**
>
> 值得指出：**prodops（ops 视角）与主审 chatgpt56（安全视角）独立收敛到同一处**——
> 后者要求「DDL/备份/恢复走独立受控 service role，不给日常平台 ops 常设数据读权」。
> 两者合起来即完整方案：**日常角色无 bypass + 专用角色可控 bypass + 审批·时限·审计**。

> ⚠️ **评审方点破的一条，本席原分类是错的**：
> **备份不是「无业务数据读取」。** 一份全库备份包含所有租户的业务数据。
> **不能被「基础设施」这个标签掩盖。** §3.4a 的权限分面表须据此修正——
> 备份/恢复属**跨租户数据面**，不属基础设施面。

**F7'（临时授权流程）必须列为【上线前置】，而非普通 TODO。**

#### 3.4e break-glass 必须拆两类（v1.4 新增）

> ⚠️ **v1.4 更正**：v1.1–v1.3 写「break-glass sidecar 主要服务平台级 ops」，
> **与 §3.4a「平台 ops 对租户业务数据默认无权」直接冲突**（评审方抓出）。
> **sidecar 能看到并输入 tenant Agent 的会话，它天然是业务数据面**，不是基础设施面。

| 类型 | 能力 | 授权 |
|---|---|---|
| **infra-only break-glass** | 进程状态 / 健康检查 / 重启。**不读会话内容** | 平台级 ops 常设 |
| **tenant-content break-glass** | 读/写租户 Agent 会话 | **该租户业主批准，或紧急双授权**；**限定 tenant + session**；**只读优先**；**时限**；**全量审计** |

> **核心原则：平台故障不能自动扩大数据权限。**
> 「平台挂了」是可用性事件，不是授权事件。

**租户级 ops 使用 break-glass 同样受 `tenant ∧ capability` 约束**，不因其是 ops 而豁免。

#### 3.4c 公共资源 = 平台域，与 §8 知识层的 K0 对齐

业主把「公共资源」划归平台级 ops。它既不属于某租户，也不是纯基础设施——是**第三类**。

**与纲领 §8 的 K 分层正好对齐**：

| 层 | 域 | 维护方 | 可见性 |
|---|---|---|---|
| **K0 基础环境上下文** | **平台域** | **平台级 ops** | **全租户只读** |
| K1 项目知识库 / K2 版本 / K3 任务 | **租户域** | 租户内（含租户级 ops） | 租户内，受 `tenant ∧ task_role` |

同属平台域的还有：公共 spec 模板、分级规则表（§6 分级层）的**基线版本**。
租户可在其上派生自己的版本，但**不得改平台域基线**。

> ⚠️ **v1.4 新增（评审方建议）：K0「全租户只读」之前，必须先做内容分级与脱敏。**
> K0 当前实际内容（`/opt/agent-context/`）含**主机 IP、会话全名、部署拓扑**等——
> **直接开放给全租户即泄漏。**
>
> **只允许**：公共环境规则、通用模板、平台纪律。
> **不得含**：路径中的敏感拓扑、租户标识、secret、主机与会话可识别信息。
>
> **平台基线的派生与同步机制由 F7'' 闭合**——在 F7'' 与本条脱敏完成前，**K0 不得开放全租户只读**。

#### 3.4d 对既有设计的三处影响

| 处 | 影响 |
|---|---|
| **§5.3 出站闸** | ⚠️ **v1.4 更正**：v1.1–v1.3 写「跨租户广播是平台级 ops 的**白名单通道**」。**白名单落法错误，见 §5.4** |
| **§6 摘要 agent** | 仍**必须租户内**。平台级 ops 不得用它跨租户读业务帖子流 |
| **纲领 §10 break-glass sidecar** | ⚠️ **v1.4 更正,见 §3.4e** —— v1.1–v1.3 写「主要服务平台级 ops」，**与「平台 ops 默认无租户业务读权」自相矛盾** |

### 3.5 spec 拆子 spec：现在就该预留维度

即使跨租户协同暂不实现，**模型不应假定单租户**。建议现在预留：

## §4 帖子流

### 4.1 基础原语可复用，**帖子载体仍需新建**

**搜索范围＝`internal/mcs/board/` 全包 + `internal/mcs/route/`**：

| 需要的 | 现成的 | 出处 |
|---|---|---|
| append-only 帖子流 + 单调读游标 | **`board_event`**：`cursor INTEGER PRIMARY KEY AUTOINCREMENT` | `board/schema.sql` |
| 帖子的「主题」单位 | **`node`**（一个任务的一个环节） | 同上 |
| 内层可见性与发言权 | **C5.1a role×op 矩阵** | `route/route.go:55-80` |
| 审计写入（强制记 actor，禁匿名事件） | `insertEvent` / `AuditEvent` | `board/board.go`、`board/audit.go` |

> ⚠️ **v1.3 更正**：v1.0–v1.2 的小节标题写「载体已存在，不需新建」，**与 §9 第 2 项「帖子正文载体需新建」自相矛盾**（评审方抓出）。
> **`board_event` 是审计事件流，不是帖子存储**——帖子的阈值计数、正文、封存、RLS 策略、读游标都需要独立的 `node_post`。
> 可复用的是**基础原语**（cursor 形态、actor 强制、node 主题单位），**不是载体本身**。

**需新建**：`node_post`（独立表）、租户维度（§3.1）、reader 游标台账（§4.5）、封存与 digest（§4.6）。

### 4.2 帖子数是**分歧探测器**，不是话痨指标

业主判断：

> 当帖子数量累积到 20、30 个时候，这里的讨论就说明是效率很低的、非常浪费 token 的……
> 当出现这类问题时，**一般是对产品定义和架构设计的理解出现了偏差、做了不同的裁剪，导致差异出现**。
> 此时大概率需要业主干预了。

→ **帖子数是「定义层出了问题」的可观测代理。**
反复讨论不收敛通常不是沟通技巧问题，是上游**产品定义或架构裁剪不一致**——
而那恰恰只有业主能裁（纲领 §5 定义层、§6 分级层）。

> **本节目标不是限流，是让定义层的分歧尽早浮出水面并强制升到能裁的人那里。**

### 4.3 阶梯硬门

| 阈值（每 node 每轮） | 动作 | 解封权 |
|---|---|---|
| ≤ 20 | 正常 | —— |
| **> 20** | **三段式封锁（见下）** | **调度者可解封（首次），并须同时向业主预警（§4.4）** |
| **> 40** | **三段式封锁** | **仅该租户业主可解封** |

> ⚠️ **v1.3 撤回**：v1.0–v1.2 写「禁发帖 + **禁读帖**」。**禁读已撤回。**
> 评审方一句决定性反驳：**「已灌入上下文无法追回，不能真正止 token」**——
> **token 在注入时就花掉了，事后禁读追不回来。本席把闸加在了错误的位置。**
> 更糟的是它没达成业主的目的（止住浪费），却附带伤了**可追溯、崩溃恢复、新成员接手、参与者核对摘要**四项。

**修订为三段式**：

| 段 | 动作 | 说明 |
|---|---|---|
| **① 停注入** | **停止自动推送 / 上下文注入，冻结 reader cursor** | **这才是真正止血的一刀**——它止的是**注入**，不是**读取** |
| **② 禁新帖** | 拒绝新增 post | 阻止分歧继续扩散 |
| **③ 保留受限只读** | 固定 digest / snapshot；按需**单次**读取或 break-glass；**带预算与审计** | 保住可追溯、崩溃恢复、新成员接手、核对摘要 |

**新接手者至少可读封锁前的不可变快照。** 调度者 / 业主 / 摘要服务的读权豁免仍保留。

**为何用原始计数而非「有效帖数」**：有效性是主观判断，两人数不出同一结果，
违反纲领 §6.1.1「可重复判定」。**原始计数的价值恰在于客观、不可辩。**

**封锁的作用域豁免**：

| 主体 | 触门后 |
|---|---|
| 该 node 的执行席 / 门方 / 其他 `task_role` 成员 | **停注入 + 禁新帖 + 受限只读**（非全禁） |
| **调度者（解封权人）** | 保留读权（写权仍受 C5.1a 约束） |
| **该租户业主** | 保留读权 |
| **摘要 agent（只读）** | 保留读权——它正在产出解封决策所依赖的摘要 |

**解封必须产出裁定物，不得只是放行**：

| 解封层级 | 必须产出 |
|---|---|
| 调度者（>20） | ① **分歧点陈述**：争的是什么、双方各自的裁剪、调度者的裁定或「判属产品决策，升业主」<br>② **同时向业主发预警**（§4.4） |
| 业主（>40） | **C3.1 格式决策记录**；且**裁定结果须回写定义层**（spec / constitution / 分级规则） |

> **不回写定义层的解封，等于给同一个 bug 反复续命。** 第 21–40 条帖子会重复第 1–20 条的争论。

**开放性讨论的豁免须落账**（业主：「开放性讨论问题除外」）：
建 node 时可标记为**开放讨论型**（阈值放宽或不设）；**豁免必须落账** `{node, 标记人, 理由, 时间}`，
仿 C2.6 `role_exemption` 的既有口径——**「可审计，不可匿名突破」**；
**不得由执行方自行标记**（同纲领 §6.2.6：执行者不得单方降低约束）。

### 4.4 首次解封必须向业主预警

业主指示：

> coordinator 第一次解封时，需要将消息解封通知到业主，预警，方便业主直接干预。

**为何必需**：若只在 40 才通知，**业主第一次知情时分歧已烧掉两倍配额**。
20 那一档的价值不只是「让调度者处理」，更是**让业主有机会早期直接介入**——
因为根因通常是产品定义/架构裁剪不一致，**那是只有业主能裁的东西**，
调度者在那里往往只能「判属产品决策」再回到业主手上，白烧一轮。

**这不是新增义务，是既有义务的具体化。** 契约 C3.3 已确立：
> **知情义务（反向）：调度者对业主 = 事后 flag 制。**

本条给该义务一个**明确触发点与规定载荷**。

| 项 | 要求 |
|---|---|
| **触发** | 调度者执行首次解封（>20）时，**同一事务内写 `notification_outbox`**；**提交后异步投递** |
| **格式** | 沿用 **C3.1 决策请求格式**，但**默认行为明确为「不拍则调度者裁定生效、工作继续」** |
| **载荷** | 必须携带 §4.3 的**分歧点陈述全文**——**通知要带实质，不能只说「已解封」** |
| **性质** | **预警（FYI-actionable），非阻断**；业主可介入亦可不理 |
| **可否推翻** | 可。业主走 C6 `owner_override` 或直接重裁并回写定义层 |

> ⚠️ **v1.3 更正**：v1.0–v1.2 写「**同一事务内发出**」。**对外部消息不可能原子**（经典 dual-write 问题），评审方抓出。
> 改为 **outbox 模式**：同事务写 `notification_outbox` → 提交后异步投递 → 状态区分 **`enqueued` / `delivered` / `acked`**。
> **本仓已有同构先例**：`board/schema.sql` 的 `result_outbox(result_key, task_id, origin_addr, payload_ref, state ∈ {pending,acked}, attempts, next_retry_ts)`。**按同构写，不自造。**
> （本席在 §4.5 引用过 outbox 作先例，却没把它用到通知上——一致性失误。）

**第二次触门（>40）的通知须回指首次预警**：
带上**稳定的 `warning_id`**，而非时间文本（v1.3 更正——时间文本不是稳定引用）。
**40 不应表现为突发事件**——它是首次预警未奏效的可预期后果；回指让业主校准
「是调度者的裁定没解决问题，还是我当初该介入而没介入」。

**配套计数器**（纲领 §7.5 自检通则）：
- **「发出首次预警后仍走到 40」的比例** —— 持续偏高说明**要么调度者裁定没真正消解分歧，要么预警没被读**
- **「预警载荷缺分歧点陈述」次数** —— 应恒为 0（结构闸应直接拒绝空载荷解封）

### 4.5 读取：游标增量，由引擎推送，Agent 不轮询

**业主质疑（成立）**：若 Agent 每次扫全帖，10 条帖子被读 10 次即 O(n²)，**比推送更贵**。

**解法三步**：

1. **Agent 完全不轮询、不主动读。**
2. `mcsd` 派发 node 时，把该 node 帖子流的**增量**（`WHERE cursor > 该 principal 上次读到的位置`）
   打包进**派发信封**——接上纲领 §9.2「派发信封 = 任务上下文的定义」。
3. 成本上界为 **O(成功覆盖的 post-recipient 对 + 重投开销)**。

> ⚠️ **v1.3 撤回**：v1.0–v1.2 宣称「每条帖子被每个相关方读**恰好一次**」。**已撤回。**
> **本席在同一份稿里自相矛盾**——引用过 `dispatch.go` 的「记账先行→外呼，**至少一次投递 + 执行点恰一次**」，
> 却把 delivery 的 **at-least-once** 与 execution 的 **exactly-once** 混为一谈。
> cursor 在外呼前推进会**丢帖**，在外呼/ACK 后推进会**重复**；重试、崩溃、并发 worker 必然触发。

**修订：写目标上界，不宣称 exactly-once。保证 at-least-once + dedupe。**

| 机制 | 要求 |
|---|---|
| **delivery / outbox** | 冻结 `[from, to]` 区间 + `delivery_id` |
| **游标推进** | **ACK 后**以 **CAS 单调推进** |
| **并发控制** | 同 principal **并发租约** |
| **消费侧** | 按 `post_id` / `delivery_id` **幂等去重** |
| **未 ACK** | 可重投 ⇒ **at-least-once + dedupe**，不宣称恰读一次 |

**该模式平台自身契约已确立**：`tools/sessionhelper/sessionhelper/contract.py:51`
> `cursor` — 单调游标。消费方持久化它；helper 重启后用它续读（见 `events(since=...)`）。

**一处关键差异，对本方案有利**：`SessionEvent.cursor` 由 driver 填，
而 `claudeDriver` **不填**（`claudeDriver.py:190` `replayable_events=False`）——这是 view 页分页不成立的原因
（见 `design-view-pagination-tail-anchor-v0.2.md` §4 方案 B）。
而 **`board_event.cursor` 由数据库生成，不依赖任何 driver** —— **故论坛可走，view 页分页不可走。**

**协调者成本与帖子数解耦**：摘要 agent 读增量产出摘要 → 协调者**只读摘要不读原帖** → 成本 O(摘要数)。

**需新建**：游标不能存在 Agent 记忆里（纲领 §9.1 每任务清空上下文，Agent 记不住读到哪）。
需台账表 `node_reader_cursor(tenant, node_id, principal, last_cursor)`。

> ⚠️ **v1.5 更正**：v1.3–v1.4 写「游标维度**已定为** `tenant + node + principal`，**不用** session/device」。
> **提前钉死了唯一维度，已撤回。** 且本席把「session 维度会随清空丢失」当成「principal 维度足够」的理由——
> **那只否定了一个候选，没有证明另一个充分**（§15 第 5 条，从局部证据外推）。

**修订为条件式**：

| 前提 | 维度 |
|---|---|
| 该 principal **保证单活消费者** | `tenant + node + principal` **足够** |
| 同 principal 允许**多设备 / 并发 worker** | **须再有稳定 `consumer_id` 或消费组语义** |

**职责边界（本席原文写模糊了）**：
**cursor 是「读进度」，不是「投递账」。**
投递 attempt 仍须由 **`delivery_id` / outbox / ACK** 管理，**不可由共享 cursor 替代**。

**维度选择随「是否单活消费者」这一前提，列为待裁（F14）。**

### 4.6 三层封存 + digest

业主要求：环节结束应关闭该环节论坛，防篡改、保可追溯、可复盘。**同意，并建议做得更硬**：

| # | 措施 | 理由 |
|---|---|---|
| 1 | **自动封存**：`execution done ∧ verdict ∈ {not_required, **pass**, **fail**}`；**`pending` 不封**。**顺序：先落 FAIL evidence / gate result，再算 digest**（v1.6 更正，见 §4.6b） | **不靠人记得去关**（纲领「靠机制不靠记忆」）。手动关闭必有人忘 |
| 2 | **封存时算 digest**，写入 node 终态记录 | 见下方**威胁模型**——v1.3 已收窄该条的承诺 |
| 3 | **返工天然不污染** | 门 FAIL 走 `append_revision` 建**新 node**（纲领 D4），新 node 有新帖子流 |

#### 4.6b 封存条件必须含 `fail`（v1.6 更正）

> ⚠️ **v1.6 修正一处设计缺陷**：v1.3–v1.5 把封存条件写为 `execution done ∧ verdict ∈ {not_required, pass}`。
> 评审方指出：**这会让「门 FAIL 的 node」永远不封**——旧失败 node 的帖子流长期可写、digest 永不生成，
> **恰恰是最需要留证的那类记录反而没有留证**。

**错因（本席自查）**：`{not_required, pass}` 是**纲领 Q7 的 DAG eligibility 条件**——
它回答的是「**能不能让下游继续**」。本席把它**照搬**成封存条件，
而封存回答的是另一个问题：「**这个 node 是否已不再被工作**」。

**门 FAIL 的 node 已经不再被工作**——按纲领 D4，返工走 `append_revision` 建**新 node**。
所以它**应当封存**，而且比通过的更需要封：**失败证据是复盘的主要材料。**

**修订后的封存条件**：

| verdict | 是否封存 | 说明 |
|---|---|---|
| `not_required` | ✅ 封 | 无需评审的环节，执行完即定案 |
| `pass` | ✅ 封 | 通过 |
| **`fail`** | ✅ **封**（v1.6 新增） | **已不再被工作；返工另起新 node** |
| `pending` | ❌ **不封** | 尚在等评审，工作未结束 |

**顺序要求（评审方补，本席原稿未定）**：
> **先落 FAIL evidence / gate result，再算 digest。**
> 否则 digest 不覆盖失败证据，等于把最关键的那部分留在保护范围之外。

#### 4.6a 威胁模型（v1.3 新增，原「防篡改」承诺已收窄）

> ⚠️ **v1.3 撤回**：v1.0–v1.2 称封存 digest 能做到「**改了能发现**」。**该承诺过强，已收窄。**
> 评审方指出：**digest 与数据同在一个可写 DB，能改帖的人通常也能改 digest**——
> 它只能发现**非协同损坏**，**不能防恶意篡改**。

**修订表述**：**「篡改可检测（限定威胁模型）」**，而非「防篡改」。

**须明确的威胁模型与最低配套**：

| # | 措施 | 作用 |
|---|---|---|
| 1 | **封存后 DB 权限 / trigger 拒 `UPDATE`/`DELETE`** | 阻断常规写路径 |
| 2 | **digest 覆盖 `tenant`/`node`/`seq`/`actor`/`ts`/`content` 的规范序列** | 防止只改内容不改元数据的局部篡改 |
| 3 | **外部或更高权限锚定 + 定期核验** | **唯一能对抗「改帖者亦可改 digest」的一层** |

**未做到第 3 项前，本方案对恶意篡改的防护为零**，只覆盖非协同损坏与误操作。

**digest 选型（业主授权本席定）**：**整流 sha256**，算前用 `internal/jcs` 做规范序列化。

- 需求是「**整段不可篡改**」，不是「只验第 7 条没被改」；Merkle 的局部验证当前**无消费方**
- **升级路径干净**：将来若需局部验证，可在保留 sha256 基础上追加 Merkle root
- `internal/jcs`（trunk，312 行）已实现 **RFC 8785(JCS) 整数子集**，
  「object 键序 / 字符串转义 / 结构序列化与 RFC 8785 逐字一致，由官方向量钉死」——**直接复用，不自造**

**三层封存，对应纲领 §8 晋升链**：

| 帖子流层级 | 封存时机 | 晋升产物 |
|---|---|---|
| **node 帖子流** | **`execution done ∧ verdict ∈ {not_required, pass, fail}`**；`pending` 不封 | → 环节小结 |
| **task 帖子流** | 任务收口（C5.1a：调度者唯一关闭权） | → 任务摘要 → **K2** |
| **version 帖子流** | 版本收口 | → 版本摘要 → **K1** |

> 「环节结束后还想讨论怎么办」有答案：**属于上一层**。node 封了 task 层还开着，task 封了 version 层还开着。
> 既不会无处可说，也不会污染已封存的下层。

### 5.2 发版**不做成新 op**

业主：「发版是否只有三态呢？我只是提到了可能性，并没有钉死，需要业务分析。」**同意，且建议换落法。**

纲领 **D1 已裁定：8 个环节落成 node 模板，而非扩展 `task_role`。发版同理**——
它是**一类 task 的 node 模板**，不是新 op：

| 发版环节（示意，待业务分析定） | 用既有 op 承载 |
|---|---|
| 提请发版 | `new`（建发版 task）或该 node 的 `status` |
| 发版评审 / 审批 | **`gate_result`**（门方=发版审批人） |
| 灰度 / 观察期 | `status` + `gate_result` |
| 全量 | `gate_result` |
| 回滚 | `reject` 或控制 op `stop` / `resume` |
| 收口 | `close`（调度者唯一关闭权） |

> ⚠️ **v1.3 撤回**：v1.0–v1.2 宣称「**零 C1 变更、零重两签**」。**该断言已撤回，改为条件式。**

> `reject`/`stop`/`resume` 也**不天然等于回滚执行**。

**修订：按有无外部副作用拆两层**

| 层 | 内容 | 落法 |
|---|---|---|
| **编排层**（无外部副作用） | 发布计划 / 审批 / 验证 / 观察 | ✅ node 模板 + 既有状态 op |
| **执行层**（有外部副作用） | **实际 deploy / rollback** | ❌ **不可塞进既有 op**。须由**结构化、授权、幂等、可审计的执行 capability / adapter** 承载 |

- 若该 capability **已在 C1 外部**且只回 `result_ref` ⇒ 可零 C1
- 否则**仍可能新增契约语义** ⇒ 须重两签

**模板本身亦须版本化 + schema 校验**——它是数据，但不是免审的数据。

> ⚠️ **v1.3 撤回本席自己给出的「一般化教训」**。
> 原文：「能落在数据上的，不要落在契约上」。
> 评审方点破其危险：**「不能把改变权限或副作用的数据当免审捷径」**。
> 该教训取到极端，就成了「**把危险的东西塞进数据以跳过评审**」的口子——
> 这与本席同日在纲领评审中**拒绝把 §15 第 6 例夹带进 v1.7** 是同一条原则，**本席却在此处自开后门**。
>
> **修订后的表述**：
> **无外部副作用的编排数据可落模板；凡改变权限或产生外部副作用者，
> 不得以「是数据」为由免审。模板须版本化 + schema 校验。**

### 5.4 `platform_notice`：独立 capability，不做白名单（v1.4 新增）

> ⚠️ **v1.4 撤回**：v1.1–v1.3 把「跨租户广播」作为**平台级 ops 的泛化白名单**放进出站闸例外。
> 评审方指出：**这是以白名单旁路契约语义**——与本提案 §5.2 被撤回的
> 「把改变权限或副作用的数据当免审捷径」是**同一个错误模式，本轮第三次**。

**改为独立的结构化 capability**：

| 要素 | 要求 |
|---|---|
| 发起主体 | **可信平台 principal**（非"平台 ops 这个身份"泛指） |
| 受众 | **明确 audience / tenant set**，不得隐式全体 |
| 内容 | **模板 + schema 校验**，**正文自由消息仍不得跨租户** |
| 授权 | **审批或双签** |
| 幂等 | **幂等键** |
| 限流 | **速率限制** |
| 可纠正 | **撤回 / 更正引用** |
| 投递 | **outbox delivery 状态**（`enqueued`/`delivered`/`acked`，同 §4.4） |

> **它不在现有 `stateOps` 六类中，属新增契约语义** ⇒ **须按 C1.3 重两签 + 出站闸一并立项**，
> **不得以白名单旁路。**

**落地节奏（v1.3 按评审方建议改）**：
> **F6 先裁 L1「metadata-only」试点** → **计量误拒率与旁路率** → 再决定是否升 L2/L3 硬门。
> **不可跳过计量直接上硬门**——例外清单是开放的，直接硬化会锁死未列出的合法通道。

**coordinator 保留职责**：派工、收口（唯一关闭权）、升业主决策、应急。**不含内容中继。**

## §6 摘要 agent

| 维度 | 建议 | 理由 |
|---|---|---|
| **触发** | **事件驱动，不定时轮询**：node 进终态 / 触门(>20) / 距上次摘要已积累 N 条新帖 | 定时轮询在无事时空跑烧 token |
| **模型** | **廉价模型** | 任务是「读增量帖，抽取进度/阻塞/需支援」——**是抽取不是推理** |
| **输入** | **仅增量帖**（游标区间）+ node 结构化头（`acceptance`/`deps`/门方） | 不喂全帖历史，否则回到 O(n²) |
| **输出** | **结构化**：`{tenant, node_id, cursor_range, 进度一句话, 阻塞项[], 需支援[], 分歧点[], 建议升级?}` | 结构化才能被看板消费、被校验 |
| **租户** | **必须租户内** | 跨租户读即泄漏。它用廉价模型、跑得频繁、读很多帖，**是易被忽略的泄漏面** |
| **是否入帖子流** | **不入**，单独存 `node_digest` | **入了会推高帖子计数、触发硬门**——而摘要恰是解封决策的依据。**工具不该污染它测量的东西** |
| **是否入账** | **不写权威状态机、不授权；但作为【非权威 observation ledger】持久化** | v1.3 更正——v1.0–v1.2 写「绝不入账」，与「单独存 `node_digest`」**字面冲突**（`node_digest` 本身就是持久观察账）。依据仍是 C5 gate-5：LLM 判读不授权 |
| **输入信任级** | **按不可信数据隔离** | **帖子是 agent 写的文本，可能嵌入针对摘要器的提示注入**（v1.3 新增，本席原稿完全漏了）。摘要服务 principal 须 **tenant + node 最小只读** |

**质量校验**（补「摘要错了谁发现」这个洞）：

> ⚠️ **v1.3 修正两处**（评审方）：

1. ~~「摘要说无阻塞、随后触门/`blocked`」计数器~~ —— **不是零误报指标**，状态可能在摘要**之后**合法变化。
   **改为：按 `cursor_range` 截止时刻的结构化事实对账**，而非与后续状态比。
2. **关键决策不得只依赖摘要**：解封决策时调度者**必须能看原帖**（§4.3 已保证读权豁免）。**摘要是加速器，不是唯一依据。**
3. ~~「可复算：重跑核对」~~ —— **可复算 ≠ 可复现**。**LLM 非确定性，重跑得到的是另一个输出。**
   **改为存证 + 引用校验**：

| 存证项 | 校验项 |
|---|---|
| `input digest` | **覆盖率**（增量区间是否全被处理） |
| `prompt` + `schema` + `model` + `version` | **引用存在性**（`post cursor citations` 指向的帖子是否真实存在） |
| `output digest` | **结构化事实一致性**（摘要断言与台账事实是否冲突） |
| `post cursor citations` | —— |

**提示注入防护同构先例**：契约 C5 gate-5 对 LLM 判读已有同款纪律——
「**判读输入隔离（canonical 首行，非原始 body），不得成提权路径**」。摘要器按同构处理，**不自造**。

## §7 存储选型

### 7.1 先撤回本席 v0.3 的一处论断

v0.3 §3.7a 曾写「200+ Agent、50~100 并行任务会让 SQLite 单写串行成为吞吐瓶颈」。**该论断撤回。**

业主给出实际量级：**50~100 TPS、并发写 50~100**。

> ⚠️ **v1.3 再修正**（评审方补充，本席接受）：
> 撤回「必成瓶颈」是**对的**；但 v1.2 写的「**该量级对 SQLite WAL 不构成瓶颈**」
> **仍是一个未实测的性能结论**——受**事务长度 / fsync / 磁盘 / 读聚合**影响。
>
> **本席等于把一个未实测论断，换成了相反方向的另一个未实测论断。**
>
> **修订表述**：**不能仅凭该数量判定是否瓶颈，须 benchmark。**
> 这才符合撤回的理由本身（§15 第 3 条：过头与不足是同一缺陷的两个方向）。

**错因**：本席从「`SetMaxOpenConns(1)` 单写串行」这一**结构事实**，推到「会成为吞吐瓶颈」这一**性能结论**，
**中间隔着一个本席没有的数字**。属纲领 §15 第 3 条（**反向亦须节制**）所指的「偏严」方向错误——
与 migration runner 那次（评审方判定未推过头）是同一形状的两个方向。

### 7.2 现状（搜索范围＝`go.mod` + 全仓 `*.go`/`*.sql`）

| 事实 | 出处 |
|---|---|

### 7.3 存储权衡（v1.3 由「推荐」改为「权衡表」）

> ⚠️ **v1.3 撤回**：v1.0–v1.2 称「多租户已定 ⇒ 租户隔离须靠 RLS 这一**机制**，不可用更便宜的换」，
> 并以此作为裁 F2' 的首要依据。**该论断夸大，已撤回。**

**RLS 不是「自动的机制」——它自己也需要一套纪律**（评审方列举，本席全认）：

| 洞 | 说明 |
|---|---|
| **表 owner 默认可绕** | 须 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`。**本席 §3.4b 只写了不得带 `BYPASSRLS`，漏了 owner 绕过** |
| **连接池 `SET tenant` 泄漏** | 用 `SET`（会话级）而非 `SET LOCAL`（事务级），租户上下文会泄漏给下一个借用者。**且恰在高并发下才暴露——正是本提案的目标场景** |
| `SECURITY DEFINER` / view | 可绕过策略 |
| 漏设 tenant context | 默认放行即泄漏 |

**采用 RLS 的最低配套**：最小权限 runtime role / `FORCE RLS` / **每事务 `SET LOCAL` 认证 tenant** /
**缺 context 默认拒** / 所有关联表与间接查询策略 / 跨租户 admin 独立角色 / **负测**。

> **结论：本席在 §7.3 画的「机制 vs 纪律」二分，比本席宣称的软。**

**三方案权衡（不单凭 RLS 裁 F2'）**：

| 方案 | 隔离强度 | 代价 |
|---|---|---|
| **PG + RLS** | 强，但**依赖上述整套配置纪律**；配错即失效 | 需 PG 运维（业主已表示 ops 可接）；关联查询与跨租户分析能力最好 |
| **SQLite 每租户独立 DB** | **物理隔离，某种意义上更硬**——不存在「忘了设 context」这种失效模式 | 跨租户分析与运维代价高（N 份库的备份/迁移/聚合） |
| **受控仓储 API** | 应用层单点，可测 | 仍是代码，仍需纪律；但收敛到单点比散落各处强 |

**CHECK 迁移这条也须收窄**：v1.0–v1.2 称「PG CHECK 可改 ⇒ §7.1 第 14 项显著变轻」。
**PG 可改 ≠ 零成本**；`NOT VALID` **只是延迟旧数据校验**，不是免除。该条改为「**成本较低，非消失**」。

**仍倾向 PG**，但理由降级为「**重要理由之一**」，且**不足以单独裁定 F2'**——须结合运维能力、
跨租户分析需求、benchmark（§7.1）综合裁。

### 7.4 更便宜的选项，如实摆出

**留 SQLite + 加只读连接池**：WAL 下读不阻塞写，`SetMaxOpenConns(1)` 是**代码选择**不是 SQLite 限制。
加只读池即可解决理由 3，改动极小。

→ 它解决「看板抢串行点」，**不解决租户隔离与 CHECK 迁移**。
**但按 §7.3 的修正，SQLite 每租户独立 DB 也是一种机制隔离**（且不存在「忘设 context」这种失效模式），
故本条 **v1.3 起不再作为「PG 不可替代」的论据**，只作为三方案之一的成本参考。

### 7.5 不建议分裂存储

「board 用 PG、帖子用 Mongo」看似合理（帖子是文档型），但：封存要把 digest 写进 node 终态 → **跨库事务**；
触门判定要读帖子计数 + 写 node blocker → **又是跨库**；多一套运维。
**PG 的 JSONB/TEXT 完全能承载帖子正文且可索引。一家就够。**

### 7.5a 迁移窗口：现在最便宜（v1.5 新增，prodops 实测）

**prodops 实测**：`mcsd` / `board` **生产无落地**——**无进程，`/data/mcshub/board.db` = 0B**。

| 含义 | 说明 |
|---|---|
| **迁移影响面接近零** | 纲领 §7.1 第 14 项的主要成本是「既有库迁移」；**board 无存量数据 ⇒ 该成本项当前近乎不存在** |
| **但真实成本仍在，只是换了地方** | prodops 指出真成本在 **§7.6 并发语义重论证**——`SetMaxOpenConns(1)` 的线性化假设在 PG **不自动成立**。这正是本席 §7.6 所写，**现由 ops 视角独立确认** |

> **排期含义：迁移窗口现在最便宜，越晚越贵。**
> board 一旦承接真实任务并积累数据，成本会从「接近零」跳到
> 「造完整迁移能力 + 迁存量 + 双写 / 回滚」。
>
> **⇒ 本席建议 F2' 的裁定【提前】**，不要等分级层与帖子流设计完再定存储——
> **存储终态定得越早，后面所有 schema 设计越省事。**

**prodops 建议「先做 §7.6 + bypass 设计再开工」，本席赞同**，并补一句：
§7.6 是**逐个 guarded 原语重新论证**，不是配置项。board 的正确性靠 CAS + 单写串行这一组合；
换 PG 后 CAS 还在，但「单写串行」要换成行级锁 + 隔离级别，**每个原语都要单独证明其线性化点仍成立**。
**这块工作量比建库大得多，且无法并行压缩——是当前迁移路径上唯一的硬骨头。**

### 7.6 迁移时必须重新论证的一点

SQLite 现在是**拿序列化换线性化**（注释：「串行化=线性化点」）。
**PG 上这个保证不自动**，要靠行级锁 + 隔离级别（RC + `SELECT ... FOR UPDATE`，或 SERIALIZABLE）重做。
**必须逐个 guarded 原语重新论证，不能假定 SQL 照搬就对。** 这是迁移工作量的真实所在，比建库大得多。

### 12.1 第 8 次同类错误：搜索键 ≠ 断言概念

纲领 §15 记录过 7 次「**证据的搜索范围 < 断言的作用域**」，范围维度依次是：
包目录 → schema 表 → 命令名与文档 → 单个文件 → 单个符号 → 自己的验证工具 → 新建标题的命名空间。

**第 8 次是新维度：按字面 key 搜索（`tenant`），而断言的是概念（隔离边界）。**

### 12.3 第 9 次：在修正记录里标注了「某处有漏」，却没修那一处

v1.3 的 §7.3 中，本席**亲手写下**：

> 未修则该修正记录本身即为未闭合项。**

### 12.6 第 11 次：**条件复用未验证语义匹配**

v1.3–v1.5 的封存条件 `verdict ∈ {not_required, pass}`，是本席从**纲领 Q7 的 DAG eligibility 条件**
**照搬**过来的。两者回答的是**不同问题**：

| 条件 | 回答的问题 | 正确取值 |
|---|---|---|
| DAG eligibility | 能不能让**下游继续** | `{not_required, pass}` ✅ |
| **封存** | 这个 node **是否已不再被工作** | `{not_required, pass, **fail**}` |

**照搬的后果**：门 FAIL 的 node **永不封存**——帖子流长期可写、digest 永不生成，
**最需要留证的那类记录反而没有留证。**

**与前十次的关系**：前十次是「**证据的搜索范围 < 断言的作用域**」；
这次是「**一个条件被验证过的适用范围 < 本席使用它的范围**」。
**同一族（超出已验证的作用域使用），新维度（条件的语义用途）。**

**操作化**：复用一个已有条件 / 判据 / 枚举时，必须先问
**「它当初是为回答哪个问题而定的？我现在要回答的是不是同一个问题？」**
——不能因为「取值集合看起来对」就复用。

### 12.5 第 10 次:**复述点 ≠ 依赖点** —— §15 第 4 条本身有盲区

本轮评审方抓出两处（⑤ L2「仅 `stateOps` 六类」、⑥ 三层封存表「node 进终态」），
**都是本席改了一处、没同步另一处**。加上此前三处（§3.4b、§11 第 3 条、v1.0 SYNC 历史行），
**同一子模式在本文档内已出现 5 次**。

**但这两处与前三处不同，且暴露了纪律本身的问题**：

纲领 §15 第 4 条写的是「修正一处事实时，**必须全文搜索该事实的所有【复述点】**」。
而 ⑤⑥ **不是复述**：

| 处 | 它说了什么 | 与被改事实的关系 |
|---|---|---|
| L2 行 | 「仅承载 `stateOps` 六类」 | **不复述**「taxonomy 有六项」，而是**依赖**它 |
| 三层封存表 | 「node 进终态」 | **不复述**封存规则，而是**应用**它 |

**它们用的是完全不同的词汇**，本席按被改断言的原文去 grep，**必然搜不到**。

> **教训：改一个事实，要搜的不只是「谁重复说了它」，还有「谁的正确性依赖于它」。**
> **依赖点比复述点难找——因为它们不共享词汇。**

**操作化**：改动一处事实后，问的不该是「**哪里还写了这句话**」，
而应是「**什么地方的正确性依赖于这个事实**」。

**归类判断**（供评审方裁）：本席认为这**不是新纪律，而是 §15 第 4 条「复述点」这一措辞的
【范围澄清】**——该词字面排除了依赖点，属定义偏窄，应读作「复述点 + 依赖点」。
按评审方既定裁定「错误值得记，不等于纪律需要加」，本席**不新增第 6 条**，
建议**修订第 4 条的措辞**。若评审方认为这已构成新语义、须另行入纲领，请指出。
