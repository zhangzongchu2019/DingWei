- **状态**：⏳ 待设计评审（shenceclaude）→ 通过后方可开工
- **变更等级**：**D（bug 修正）** —— 无协议变更，`B` 不跳，**不需要客户端升级**

---

## 1. 问题

**会话间消息（session→session）是全团队协作的主通道，却跑在最弱的一条路上。**

| 路径 | 队列 | 持久化 | 满了怎么办 | helper 重启 |
|---|---|---|---|---|
| 飞书 → 会话 | SQLite（按会话隔离） | ✅ | 有 ACK 三态 | 不丢 |
| **会话 → 会话** | **内存 deque（100）** | **❌** | **静默丢最老的** | **全丢** |

发件人拿到的 `sent` 只代表 **hub 收下了**，不代表对方 helper 收下了，更不代表注入了 CLI。

**成因（非取舍，是历史沿革）**：
- 可靠投递（`e8a18be`，2026-07-11）是为「飞书→会话」做的，产品目标是让人在飞书聊天里看到回执（`notifyDeliveryQueued` → "消息已接收，前面还有 N 条待处理"）。`SourceType` 硬编码 `"feishu_inbound"`。
- 会话间的内存 buffer 是为修 **recv_loop 卡死**加的（`buffer_if_busy` 注释：*"#4 recv_loop hang fix"*），**不是为可靠性设计的**。
- 两条独立演进，从未统一。

---

## 2. 目标与非目标

### 目标
1. 会话间消息获得**持久化、串行注入、幂等去重、忙时 ACK**。
2. **不需要客户端升级**（helper 侧零改动）。
3. ACK 语义统一：**确认「helper 收到」，而非「CLI 执行完」**。

### 非目标（明确不做）
- **网页终端 `/view` 不走队列。** 它是**交互字节流**不是消息；且**人的抢占权必须能绕开队列**——CLI 卡死时要靠 `Ctrl-C` 救它，若排队则会被回「CLI 忙，已排队」，把唯一的救命手也锁死。
- 本期不动 `SetMaxOpenConns(1)`（单独立项）。

---

## 3. 关键事实（已核实，勿重复论证）

**helper 侧无需任何改动**：
- 当前所有 helper 均已声明 `delivery_ack_v1` 能力（`app.py:267`）。
- `is_delivery()` / `accept_delivery()` / SQLite inbox / `delivery_worker_loop`（串行 claim）/ busy ack / 按 `delivery_id` 幂等（`INSERT OR IGNORE`）—— **全部现成**。
- hub 侧已有能力门控：`if ackInbound && h.sessionSupportsDeliveryACK(c) && h.Repo != nil { …delivery… }` **else** `c.write(ctx, env)`（老路径回落）。
  ⇒ **未声明能力的老 helper 自动回落，不会被打挂。**

**唯一的闸门**：`hub.go:2361 / 2382`
```go
h.routeToSession(ctx, …, env, from.Kind == addressFeishu)
//                             ^^^^^^^^^^^^^^^^^^^^^^^^^^ 会话间永远 false
```

**已核实无副作用**：
- `AckMessage(SourceMessageID)` 拿会话间 ID 去 `UPDATE message WHERE id=?` → **更新 0 行，无害 no-op**。
- `notifyDeliveryQueued` 的排队回执带 `no_mirror`+`system` → helper 的 `recv_loop` 直接 `continue` 丢弃 → **不注入 CLI、不刷屏**。

## 4. 改动（全部在 hub）

### 4.1 【必做】包装：会话间纳入可靠投递

`hub.go:2361 / 2382`：`ackInbound` 由 `from.Kind == addressFeishu` 改为对会话间也成立（**仍受 `sessionSupportsDeliveryACK` 门控**）。

### 4.2 🔴【必做】30 分钟硬过期 —— 不改就是丢消息，比现状更糟

`internal/store/sqlite.go:1345-1347`，`ClaimSessionDelivery` 开头：
```sql
UPDATE session_delivery SET state='dead', last_error='delivery_expired'
WHERE key_id=? AND session_name=? AND state NOT IN ('processed','dead','cancelled')
  AND (attempts>=12 OR created_at <= now-30min)
                       ^^^^^^^^^^^^^^^^^^^^^^^
```
**任何非终态消息，创建超过 30 分钟即判 `dead` 丢弃。**

- busy 会 `attempts-1`（T9 的修复），**撞不到 12 次上限，但撞得到这 30 分钟。**
- 对飞书勉强合理（人发的指令放 30 分钟也过期了）。
- **对会话间是致命的**：agent 跑长任务是常态 —— **reviewer 2026-07-13 当天忙了 1 小时以上**。
- ⇒ **不改就丢消息，比现在的内存队列还糟**（内存队列至少 helper 活着就一直留着）。

**修法（待评审拍板）**：
- 方案 a：`busy`/`queued` 状态**不参与**创建时间过期，只保留 `attempts>=12`（但 busy 会减 attempts，等于无上限 —— 需另设"投递失败"上限，与"CLI 忙"区分）。
- 方案 b：过期时长按来源区分（飞书 30min，会话间大幅延长 / 不过期）。
- 方案 c：过期改为「**自最后一次 ACK 起**」计时，而非自 `created_at` 起 —— CLI 一直在回 busy ack，说明 helper 活着且持有消息，不该过期。
- **manager 倾向 c**，请评审给结论。

### 4.3 【必做】busy → 终态，hub 停止重投

`hub.go:2989-2991`：
```go
} else if state == "busy" {
    UpdateSessionDeliveryBusy(id, reason, now+15s)   // state 置回 'queued'
    scheduleSessionDeliveryDrain(c, 15*time.Second)  // 15 秒后重发
}
```
⇒ **CLI 忙 1 小时 = 240 次无意义重投 + 240 次 SQLite 写**，而 hub 是 `SetMaxOpenConns(1)`（2026-07-13 已实测：DB 争用会把 WS 升级拖到 **3.75s**）。

**按张宗楚拍板的 ACK 语义**：
> **helper 回 `ack-injected` 或 `ack-busy(已入队)` 之一，都表示消息已到达 helper，hub 无需再投。**

⇒ busy 应置为一个**不再进入 claim 队列**的状态；由 **helper 自己**在 CLI 空闲后注入（helper 本地已有 `release()` + 循环重试）。

### 4.4 【必做】`SourceType` 区分来源

`hub.go` `EnqueueSessionDelivery` 里 `SourceType: "feishu_inbound"` 是硬编码 ⇒ 会话间也写成 `feishu_inbound`，**审计与排查时来源全错**。

### 4.5 【待定】排队回执要不要给发件人

现在 `notifyDeliveryQueued` 的回执会被 helper 丢弃（`no_mirror`）⇒ **发件人不知道对方忙**。
- 保持现状：安静，但发件人无感知。
- 改为可见：发件人知道"对方忙，已排队"，但会增加消息量。
- **产品决定，请评审给意见。**

## 5. 验收判据（tester）

1. **持久化**：tester → manager 发消息，manager 的 CLI 忙时，消息**落进 `~/.dingwei/sessionhelper_inbox-manager.db`**（不再只在内存）。
2. **重启不丢**：消息入队后 **kill 并重启 manager 的 helper**，消息**仍被投递**（这是现状做不到的）。
3. **🔴 长忙不丢**：CLI 持续忙 **> 30 分钟**，消息**不得被判 `dead`**。（这是本次最关键的回归项 —— 直接对应 4.2。）
4. **串行**：连发 5 条，**逐条按序注入**，不并发、不乱序。
5. **幂等**：hub 重投同一 `delivery_id`，**不得重复注入**。
6. **忙时 ACK**：CLI 忙时发件方收到 busy ACK，且**每个发件人只收一次**（不是每条一次）。
7. **老 helper 回落**：未声明 `delivery_ack_v1` 的 helper **仍能正常收发**（走 `c.write` 老路径）。
8. **飞书不回归**：飞书 → 会话的原有行为**完全不变**。
9. **溢出**：内存 deque 路径废弃后，确认**不再有 `[busy_buffer] drop oldest`**。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| **会话间消息量 × 每条一次 SQLite 写**，叠加 `SetMaxOpenConns(1)` | 消息是人/agent 节奏（低频）。**上线后必须盯 `session handshake timing` 埋点**（2026-07-13 已上线）。若 WS 升级耗时上涨 → 立即回滚并把 `SetMaxOpenConns(1)` 提级。 |
| 4.2 改错 → 消息永不过期，队列无限增长 | 必须有**兜底上限**（区别于"CLI 忙"的真实投递失败次数）。评审重点。 |
| 4.3 改错 → busy 后没人再投，消息永远卡住 | helper 侧**自己**有 `release()` + 循环重试；需在测试项 3 中验证。 |
