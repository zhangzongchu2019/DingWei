# 第一部 · 总则

## §1 总纲

**整个系统是产品定义驱动、流程保障的。**（业主原话，本件第一原则）

由此派生三条：

| # | 原则 |
|---|---|
| 1 | **一旦进入项目开发，驱动的是流程引擎，而不是 Agent。** |
| 2 | **约束必须存在于上下文之外。** 存在于上下文里的约束，上下文一丢就跟着丢。 |
| 3 | **靠机制，不靠记忆。** 每加一条流程约束，同时加一个**可观测的失效探测手段**（§29 四类之一：恒零计数器 / 趋势指标 / 建成核验 / 评审检查）。 |

## §2 实现路径

### 2.1 不受现有代码约束

本规范的实现**不必基于现有 DingWei 平台代码**；现有实现不满足需要时**可新开发**。（业主裁定）

### 2.2 根因：现有平台的建模中心是通信，不是项目/任务管理

| | |
|---|---|
| **现有平台** | 消息是一等公民，任务/项目是消息的附属账 |
| **本规范要求** | **项目 / 任务 / 交付物是一等公民，消息是它们的投影** |

这不是加字段能改的，是把主外键关系倒过来。可指认的事实：

- `store/migrations/0008_projects.sql` 的 `project` 表全部字段为通知路由 + 取证配置，无 spec / 里程碑 / 阶段 / 交付物 / 验收 / 任务关联
- `datad` 的 `task` 表归属维度是 `owner_session`（会话），且**无 `project_id`**
- `board/schema.sql:11` 的 `task` 表含 `origin_envelope_id`——任务的身份锚是消息的身份
- project / task 台账 / task DAG 分处三个库，零外键

### 2.3 保留 / 重建分界

> **凡建模的是「消息如何可靠传到」的，保留；凡建模的是「工作如何被定义、被验收、被追责」的，重建。**

| 组件 | 处置 | 依据 |
|---|---|---|
| provision 分发通道 | **保留** | 安全模型扎实：hub 只下发数据不下发指令；5 道闸；版本号只在 `ack(ok=true)` 后推进 |
| sessionhelper sidecar | **保留** | 实测补 2 处腐点后 5/5 端点可用 |
| `internal/store/` 迁移框架 | **保留复用** | 已到 migration 0031，可作迁移基座 |
| `datad` | **schema 级重构** | 全包无租户维度、无 RLS；表结构是单租户模型 |
| admin 后台 | **重建管理面** | 无角色模型；且「租户」一词已被占用为 API-key 归属空间（`registered_service` 表） |
| **`mcsd` 调度语义** | 🔴 **保留**（与 §4.5 一致） | 其承担的是通用引擎做不了的部分：agent 择人、worker 判死换代重派、记账先行→外呼的崩溃切点、per-段门方授权矩阵、执行席≤2 |

# 第二部 · 定义层与分级层

## §3 四层架构

```
  定义层（Spec Kit：spec / constitution / checklist）
      ↓ 产品定义
  分级层（属性表 → DMN 决策表 → 必过环节并集）
      ↓ 该走哪些门
  执行层（board DAG + mcsd 派发 + 门禁）
      ↓ 交付物 + 门结果
  保障层（台账、封存、晋升、自检计数器）
```

## §4 定义层：产品定义规范

### 4.1 选型：Spec Kit

采用 Spec Kit 作为产品定义规范的载体。三项直接使用：

| 件 | 用途 |
|---|---|
| `constitution.md` | 项目治理原则的唯一载体 |
| `/speckit.checklist` | 生成质量检查清单 → 落成 `node.acceptance` |
| `/speckit.analyze` | 跨制品一致性检查 = 环节丢失的输入端检测器 |

沿用其两项设计，不重新发明：

1. **`Constitution Check` 前后各检一次**（`plan-template.md`）；违规须书面论证（`Violation | Why Needed | Simpler Alternative Rejected Because`）
2. **checklist 是 reviewer-owned**，只有 reviewer 能打 `[x]`，IMPLEMENT 命令读 checkbox 当 gate 且不得修改标记——**与 §7.2「implementer 不能自签门 PASS」是同一条纪律**

### 4.2 Spec Kit 及三个外部件的性质：它们是平台级 skill

Spec Kit / OpenSpec / Superpowers 的约束住在 agent 上下文里、由斜杠命令承载、无外部系统拦截
——**按 §14.1 判据，它们是 skill，不是机制**。

**由此的硬性要求**：

| # | 要求 |
|---|---|
| 1 | 三者按平台级 skill 治理（§15、§16），不另设「外部件引入」流程 |
| 2 | 🔴 **Spec Kit 及其模板列入 immutable 名单第一批**（§16.5）——它同时满足**平台级 + 承载纪律 + 影响授权判据** |
| 3 | **硬门仍须落在 board。** 自律型工具不承担门禁 |

### 4.3 spec 是授权凭据

spec 中可写**预授权**（§23.2）。因此：

- spec 的**评审带安全权重**：凡含跨边界数据访问声明的 spec，其评审门方**必须包含有权批准该访问的角色**
- spec 查阅入口**必须显示**：版本 / 评审状态 / 所含预授权条目及作用域 / 生命周期状态（研发测试期有效 / 已因上线 `expired`）

### 4.4 spec 拆分

一份 spec 可拆多个子 spec。数据模型**必须预留** `parent / child` 维度与跨租户引用位置。

### 4.5 流程引擎：不引入新的

**保留 `mcsd`**——不引入任何外部流程引擎替代它。
唯一引入的外部件是 **DMN 决策表**（用其决策表，不用其执行引擎），供 PM 自维护分级规则。

> ⚠️ **与 §2.3 的关系（v2.3 澄清，原两处冲突）**：
> **「保留 mcsd」指保留其调度语义与契约；「重写 board」指重写其存储层与状态机实现。**
> 二者不矛盾。v2.2 及以前把 §2.3 写成「board / mcsd 整体重建」，与本节直接冲突，**已改正**。
>
> **且「整体重建」的证据本不充分**：所列依据（SQLite 单写者、无 migration runner、
> C0.1 未实现、幂等键未闭合）支持的是**存储层与身份层重建**，**不支持调度逻辑重建**。
>
> 🔴 **v2.5 再次收窄（复审指出）**：v2.3–v2.4 仍写「board 存储层**与状态机**重写」。
> **上述证据只证明存储实现须换，不能单独证明状态机算法应整体重写。**
> 门 verdict 独立化等确会改变状态模型，但那是**契约驱动的重构**，不是「因为旧的不行」。
>
> **修订表述**：**board 存储层重写；状态模型按新契约重构；
> 既有并发与代际语义（CAS、`generation`、迟到结果处置、fan-out、reconciler 谓词）
> 须由 conformance suite 先固化，再逐项判保留或替换。**
> **无 conformance suite 之前，不得以「重写」为由丢弃任一既有并发语义。**

## §4.6 spec 准入检查（v3.0 新增）

### 4.6.1 不设评级，不产总分

> **理由取自本规范自身**：§5.1「宁可粗，不可细。**打分制一定退化成主观**」；
> §5.2「**安全面必须是独立维度，不得被『改动小』稀释**」——**综合评分正是把一票否决项平均掉的机器**。

⇒ 设计为 **① 硬门（pass/fail，不加权）＋ ② 参考项（不否决）＋ ③ 人审触发规则**，**不产出任何总分**。

### 4.6.2 硬门 —— 不满足即拒收，不进人审队列

| # | 检查项 | 机器判据 |
|---|---|---|
| 1 | 属性头块七项齐全，取值在枚举内 | 字段存在性 + 枚举匹配 |
| 2 | 分级结果可复算：`rule_ids` ＋ 规则表 version 齐 | §5.4 规则 4 |
| 3 | **预授权条目具体**：范围/用途/时限三字段非空，且无禁用词（可能 · 视情况 · 相关 · 适当 · 如有必要） | §23.2 第 6 条 |
| 4 | 父 / 子 spec 引用可解析 | §4.4 |
| 5 | 交付物锚格式合规（commit 40hex / sha256 64hex） | 正则 |
| 6 | `/speckit.analyze` 跨制品一致性零冲突 | §4.1 |
| 7 | 每条硬性约束有对应探测手段登记 | 附录 E 同构 |

> **为什么要有一票否决**：§6.1 已定「交付物合格约八成可自动判，**门方只判剩下两成**」——**门方是瓶颈资源**。
> 让门方去审一份属性头块都没填全、预授权写着「可能需要读取相关数据」的 spec，
> **是把瓶颈资源花在机器能挡的事上**。**硬门不是为了严，是为了不浪费人审。**

### 4.6.3 参考项 —— 不否决，供门方定深度

判据可机器验证的属性比例 · `acceptance` 的可执行性 · spec 声明的变更是否都有对应测试用例设计 ·
预授权条目数与其范围宽窄。

⚠️ **不加权、不合成总分。** 用途是**告诉门方该盯哪里**，不是替门方下结论。

### 4.6.4 🔴 不得因「机器项全过」而免人审

| # | 理由 |
|---|---|
| 1 | **规范已有明文**：§5.4 规则 2「基础必过模板」含代码评审，任何级别不可省。**spec 不应比代码宽松** |
| 2 | 🔴 **免人审会把检查项变成攻击面**：一旦「过检查项即免审」，就会出现**为过检查项而写的 spec**——字段填齐、禁用词避开、锚格式合法，而实质是空的 |

> **正确关系：机器决定「是否值得占用人审」，不决定「是否需要人审」。**
> **检查项判的是形状，人审判的是「是不是那么回事」。**

**人审深度与门方人选由检查结果决定**：

| 条件 | 人审形态 |
|---|---|
| 硬门有任一不过 | **不进人审** · 退回补齐 |
| 硬门全过 ＋ 无预授权 ＋ 属性无高风险档 | 文档评审（单门方） |
| 硬门全过 ＋ 含预授权条目 | 文档评审，**门方须含有权批准该访问的角色**（§4.3） |
| 硬门全过 ＋ `安全面=是` | **架构评审 ＋ 门方必须是安全角色** |
| 硬门全过 ＋ `回滚成本=不可回滚` | 架构评审 ＋ **业主签署** |

### 4.6.5 唯一的免人审通道：非语义修订

类比 §24.2a，但**「非语义」必须机器可判，不得自述**。**下列各条须【同时】满足**（不写死条数，增删以本表为准）：

| # | 判据 |
|---|---|
| 1 | diff 不触及**属性头块** |
| 2 | diff 不触及**预授权条目段** |
| 3 | diff 不触及 `acceptance` 段 |
| 4 | diff 不触及任何含「必须/禁止/不得/须/唯一/只有/fail-closed」的行**及表格规则行**（附录 E.0 五形态） |
| 5 | **分级结果重算后不变** |
| 6 | 该 spec **不在 immutable 名单内** |
| **7** | 🔴 **diff 不触及上述受保护行【所引用的】任何对象**（v3.1，SA-01） |

**除【依赖闭包】条外，其余各条只保护「行文本」**，不保护**被引用的东西**。可在不碰任何受保护行的前提下，
改其引用的**规则表目标 · 枚举含义 · 术语定义 · 例外条件 · 禁用词表 · 链接目标 · immutable 名单**
—— 受保护的「必须」行一字未动，**实际约束已被放宽**，且规则 ID 与版本可保持不变。

**⇒ 免审判定须建立在【依赖闭包】上**：解析受保护行所引用的全部对象，
将其纳入同一次 diff 判定。**无法建立完整闭包 ⇒ 一律按语义修订处理。**

**任一不满足 ⇒ 按语义变更处理。存疑即按语义变更（fail-closed）。**
**且非语义修订仍须落账** —— 免的是评审，不是记录。

## §5 分级层

### 5.1 属性表判据

| # | 判据 |
|---|---|
| 1 | **可重复判定**——同一份 spec、同一角色的两个人，依同一份判定说明应得同一结果 |
| 2 | **可由产物反证**——声明与最终产物不符时机器能查出来 |

**宁可粗（三档枚举），不可细（十档打分）。打分制一定退化成主观。**

### 5.2 属性（起点 7 项）与填写归属

| 类 | 属性 | 取值 | 填写方 |
|---|---|---|---|
| A 影响面 | `外部契约变更` | 无 / 兼容新增 / **破坏性** | 业务语义层=PM，接口层=tech |
| | `数据模型变更` | 无 / 加列加表 / **改列删列改语义** | tech |
| | `影响范围` | 单模块 / 跨模块 / **跨服务** | tech |
| B 风险 | `在产影响` | 不影响 / 灰度可回滚 / **直接影响在产** | ops / owner |
| | `回滚成本` | 重启即回滚 / 需回滚数据 / **不可回滚** | ops / owner |
| | `安全面` | 否 / **是** | ops / owner |
| C 规模 | `预估节点数` | 数字 | tech |

**两条硬性纪律**：

1. **`安全面` 必须是独立维度，不得被「改动小」稀释。** 五行改动若动了鉴权，它就是高风险。
2. **每个属性须有事后可机器验证的对应物。** 声明「数据模型变更=无」而交付物 diff 中出现 migration → **自动告警并强制升级**。

### 5.3 门按属性算，级别只是标签

**每个属性独立映射到「必须加哪些门」→ 取并集。** 禁止先算总级别再查门。

L1/L2/L3 **按触发的最高风险档命名**，不按门数量命名；**级别只供人沟通，不参与计算**。

### 5.4 并集法的五项必备规则

| # | 规则 |
|---|---|
| 1 | DMN hit policy = **COLLECT / UNION**，须在决策表上显式声明 |
| 2 | **基础必过模板**：恒必过的最小环节集（实现 → 代码评审 → 测试执行），并集在此之上追加 |
| 3 | **冲突消解按 §5.5 四步**（禁止「取更严者」） |
| 4 | **可解释输出**：每次判定输出 `{命中 rule id, 规则表 version, reason}` |
| 5 | 允许**跨属性组合规则** |

### 5.5 冲突消解四步

**输出取要求集合的合取，不取「更严的那一条」**——责任域不同的评审互补而非可替代。

| 步 | 规则 |
|---|---|
| 1 | 同 gate、同责任域 → 按**稳定 gate key** 去重 |
| 2 | 同 gate、不同责任域 → **要求并存**，或升级为 **multi-sign** |
| 3 | 仅当存在预定义 **subsumption / precedence 表**时，才允许高覆盖低 |
| 4 | 无法比较 → **fail-closed，升调度者裁定**（不猜、不默认取严、不默认取宽） |

单调膨胀由**稳定 gate key** + **subsumption 表**控制；gate catalog 是有限集。

### 5.6 映射表（起点）

| 属性取值 | 强制追加的环节 |
|---|---|
| 外部契约 = 破坏性 | 架构评审 + 用例评审 + 交付验证 |
| 外部契约 = 兼容新增 | 文档评审 |
| 数据模型 = 改列/删列/改语义 | 架构评审 + 交付验证（含回滚演练） |
| 数据模型 = 加列/加表 | 文档评审 |
| **安全面 = 是** | 架构评审 + 代码评审（**门方必须是安全角色**） |
| 在产影响 = 直接影响在产 | 交付验证 + 执行结果评审 |
| 回滚成本 = 不可回滚 | 架构评审 + **业主签署** |
| 影响范围 = 跨服务 | 架构评审 |
| 皆否 | 只留基础环节 |

### 5.7 环节数不固定

低级别更少，高级别追加架构评审。**若列固定，分级即无意义。**
看板必须处理**变长列**——低级别任务的某些格子是 **N/A**，不是「未完成」。

### 5.8 门方是矩阵的输出列

| 环节 | 门方 |
|---|---|
| 代码评审 | 不得是该 node 的 implementer；`安全面=是` 时**必须**为安全角色 |
| 交付验证 | `qa_owner` |
| 架构评审 | 调度者或指定架构角色 |
| 业主签署 | 业主 principal（C0.1 校验，非自述） |

### 5.9 防绕过

1. 属性**三方分填**，填在 `spec.md` 的 `**Key**: value` 头块
2. **执行者不得单方定级**：可补技术属性，**不得下调**任何已声明的风险档；下调须走门方或调度者
3. 叠加 §5.2 第 2 条机器交叉验证

# 第三部 · 执行层与保障层

## §6 判定模型三层：能机器判的绝不交给人

| 层 | 性质 | 内容 |
|---|---|---|
| **一 · 结构闸** | 违规不可能发生，不存在「谁来判断」 | schema / 状态机约束 |
| **二 · 机器校验** | 客观、可复算、自动跑 | 见 §6.1 |
| **三 · 人/Agent 评审** | 主观 | 只判「对不对、够不够好」 |

### 6.1 交付物回执五要素中四项机器可验

| 要素 | 自动验 |
|---|---|
| 件（路径或 commit 40hex） | ✅ 存在性可查 |
| sha256（最终态当场算，报后不改） | ✅ 可复算比对 |
| 行数 + 字节（`wc -c` 口径） | ✅ 可复算 |
| 自测结果（命令 + 摘要） | ✅ 命令可重跑 |
| 门结果（PASS/FAIL + 失败最小复现） | ❌ 需要人 |

⇒ **交付物合格约八成可自动判，门方只判剩下两成**，同时解决门方瓶颈。

### 6.2 状态机变更是重活，不是改点

引入 `passed` / `awaiting_gate` 等门禁状态属**状态机设计变更**，必须一并重定义：
状态迁移图与不变量 / worker 何时 `Release` / `GateResult` 原语（CAS、幂等键、代际 guard、gate-3 授权、**证据持久化**）/
FAIL → `append_revision` 回流建图 / reconciler stray 谓词 / 读模型全套 / CHECK 约束迁移 /
**门方映射迁入台账**（当前仅内存）/ `awaiting_gate` 期间资源与恢复语义 / **gate FAIL 与执行 failed 的语义分野** /
**迁移机制本身**（须先造：版本探测 + 原子 rebuild + 回滚备份 + 旧库兼容测试）/ 回归面含 ingress、driver、一切读 node 状态的消费者。

**唯一可独立先落的一项**：`Terminal(done=true)` 前置 `result_ref != ''`。

**治理成本**：属 C1 原语面语义变更 → 须重两签（按 §24 攒批）。

## §7 门禁纪律

### 7.1 上线前置（硬）

| # | 前置 | 判据 |
|---|---|---|
| **P1** | **per-session principal 可信** | **端到端**：连接层 → 信封 → Receiver 的认证主体传播 + trusted 开关原子切换 + 非合规会话清零 + **负向测试（伪造 principal 必须被拒）**。未就绪时一切 mutating op 与状态观测 **fail-closed**，仅放行只读查询 |
| **P2** | **控制授权闸在每个可接收控制指令的实体上同构生效**（无缝隙） | 执行组边界亦须有 |
| **P3** | **逐闸命中计数入台账** | LLM 兜底占比 = 调度者健康指标 |

**P1 是地基**；但不阻塞 board 状态机的离线设计与实现，二者可并行。

### 7.2 五条纪律

- 门方是 **per-段指定的 principal**，不是角色
- **implementer 不能自签门 PASS**
- **执行席不得自行收口**（收口 = 调度者唯一关闭权）
- **LLM 判读不授权**（gate-5 结论须回 gate-3）
- **身份用 per-session principal，不信信封自述 `from`**

### 7.3 未达成时的处理

| 情形 | 机制 |
|---|---|
| 重试耗尽 | `retry_exhausted` → blocked |
| 超时 | `sla_deadline` + reconciler `TimeoutAnnotated` |
| 依赖失败 | `dep_failed` → 下游 blocked |
| 无人可派 | `starved` |
| 投递悬空 | `delivery_unresolved` → redeliver 收敛 |
| 等人输入 | `awaiting_input` |
| 需决策 | 升级链 → 调度者 → 判属产品决策则升业主 |
| 卡死无解 | `owner_override`（**指令须唯一映射到白名单 op，禁自由文本直写**）/ `owner_takeover` |

**关键决策请求格式**：`决策项 / 选项(a,b,c…) / 各选项影响一行 / 调度者建议+理由 / 不拍时的默认行为与时限`。
**一次一批，禁流式追问。**

### 7.4 门 FAIL 的回流

**门 FAIL → 建修订 node（`append_revision`）→ 优先派回原 worker。**
修订 node 不依赖 worker 记忆，靠**不可变派发快照**重灌（§11.6）。

## §8 发版

### 8.1 发版不做成新 op

发版是**一类 task 的 node 模板**，不是新 `stateOps`——扩 op 会触发 C1 重两签，落成模板则不会。

### 8.2 收口格（第 ⑧ 格）的交付物

收口由**调度者唯一关闭权**执行，同一事务内产出四项：

| # | 交付物 |
|---|---|
| 1 | **版本摘要 → 晋升归属域**（§11.3） |
| 2 | **spec 预授权失效登记**（§23.3） |
| 3 | **部署锚登记**：组件 × 环境 × commit × 制品 sha256（§13.2） |
| 4 | **阶段复盘**（§9） |

> **收口是平台的「事实登记点」**——它是唯一一个既知道「改了什么」又知道「上到哪里」的时刻。
> **无复盘、无部署锚登记，不得收口。**

## §9 阶段复盘

**复盘是交付物，不是自觉行为。无复盘不得收口。**

### 9.1 输入（现成，无须回忆）

该阶段的**帖子流** + **交付物清单** + **门记录**（含 FAIL 与整改）+ **blocker 记录**。
⇒ 草稿由廉价模型生成（同 §20），执行者 / 评审者定稿。

### 9.2 输出必须四段，任一段为空须写明理由

| 段 | 内容 | 去向 |
|---|---|---|
| 1 | **本阶段沉淀的事实** | 知识库（§12） |
| 2 | **可复用操作** | skill（§16） |
| 3 | **应固化能力** | MCP（§14.2 判型 · §14.6 准入） |
| 4 | 🔴 **本阶段的判断失误** | 知识库「坑清单」类目（§12.4 第 7 类），**参与逐级晋升**（D3→D2→D1→D0，须去标识化） |

**第 4 段的价值全在能被下一轮读到**：前三段是「产出了什么」，只有它是「哪里想错了」。
**晋升到平台级前必须去标识化**（判断失误常牵涉具体人与具体事故）。

> 强制四段的理由：不强制，复盘会退化成「顺利完成」四个字。

# 第四部 · 上下文、记忆与知识库

## §10 知识与记忆的总体模型：四个正交维度

> 🔴 **v3.3 统一（甲#1）**：v3.0 说「二维」、§11 说「两轴」，v3.1 又加了 visibility ——
> **实际已是四个维度，文中却仍按二维描述**。此处统一为唯一定义处，
> §11 只展开其中的归属域与生命周期两维，**不再自称「两轴」**。

**四个维度彼此正交，任一维不得替代另一维**：

| # | 维度 | 决定 | 取值 | 定义处 |
|---|---|---|---|---|
| 1 | **归属域** `domain_level` | **谁拥有、谁维护、辖域多大** | `D0` / `D1` / `D2` / `D3` | §11.2 |
| 2 | 🔴 **可见性** `visibility` | **该域内谁能看** | `public` / `internal` / `restricted` | §11.4a |
| 3 | **生命周期** | **暂存与晋升**（不是「层」） | 任务上下文 → 版本上下文 → 汇入归属域 | §11.3 |
| 4 | **记忆类型** | **怎么存、怎么取、何时清** | 工作记忆 / **过程性记忆（skill）** / 事实记忆 | 本节 |

⚠️ **1 与 2 最易混**：**归属域回答「归谁」，可见性回答「谁能看」**。
D0 的条目**不等于**全员可见 —— 装载前须同时求 **归属域 ∩ 可见性**（§11.4a）。
🔴 **§12.6 第 3 条已改为「`domain_level` 与 `visibility` 分别判定」**——**归属域本身不是密级**，
且 **visibility 变更不得改变 domain**（§11.4b #2a）。

> **skill 是过程性记忆，必须有归属域**（平台级 = D0，业务级 = D1，租户级 = D2，项目级 = D3），
> 与知识条目**共用同一套晋升、同一套装载、同一套 RLS**。
> 否则「导入上下文」与「skill 晋升」会成为两套并行机制，出现「知识灌到了、skill 没同步」。

## §11 归属分层与生命周期

### 11.1 🔴 归属域与生命周期不得排成一列（v3.0 重构）

> **v2.x 的 K0–K3 把两件事排成了一列**：K0/K1 分的是**组织归属**，K2/K3 分的是**生命周期粒度**。
> 二者正交，须分开。

> **总体模型见 §10（四个维度）**。本节只展开其中两维；**可见性见 §11.4a，记忆类型见 §10**。

| 维度 | 决定 | 取值 |
|---|---|---|
| **归属域** | 谁拥有、谁维护、辖域多大（**不含「谁能看」，那是可见性**） | **D0 / D1 / D2 / D3** |
| **生命周期** | 暂存与晋升 | 任务上下文 → 版本上下文 → **汇入归属域某一级** |

**生命周期不是「层」，是晋升管道。** 其终点是归属域的某一级，由收口原语触发。

### 11.2 归属域四级

> 🔴 **符号约定（v3.2 扩为三套）**：文中曾出现三种互不相干的分级，须各用各的符号，**不得混用**：
>
> | 用途 | 符号 | 定义处 |
> |---|---|---|
> | **风险级别** | `L1–L3` | §5.3 · §23.5 |
> | **归属域** | `D0–D3` | §11.2（本节） |
> | **出站闸层级** | `G1–G3` | §19.2 |
>
> v3.0 曾用 `L0–L3` 表归属域、§19.2 又用 `L1–L3` 表出站闸层级 ——
> **同一符号三义**，「L3」无法判断是高风险 node、项目域，还是最强出站闸层。
> v3.0 曾用 `L0–L3` 表示归属域，与 §5.3 的风险级全局同名，
> 「L3 node」无法判断是**高风险 node** 还是**项目域 node** —— schema / DMN / API / UI 会各自选择不同解释。

| 级 | 范围 | 谁维护 | 分发 |
|---|---|---|---|
| **D0 平台级** | 企业级 / 团队 —— 不受具体业务影响，可独立于各项目存在 | 平台级 ops | **push 全体，强制** |
| **D1 业务级** | 业务线 / 部门-团队 —— 该业务线共通 | 业务线 ops | **push 其辖下租户**；线外不可见 |
| **D2 租户级** | 该租户共通 | 租户级 ops | 辖域＝其辖下项目；**具体分发动作见 §15.1b/§15.1c** |
| **D3 租户项目级** | 单个项目 | 项目管理方 | 不 push |

**三类资产共用本轴**：知识库条目 · skill · MCP。

### 11.3 生命周期与晋升（三条入口）

| 阶段 | 内容 | 载体 | 晋升时机 |
|---|---|---|---|
| **任务上下文** | 派发信封 + `acceptance`/`deps`/`result_ref`/门结果 | board 台账 | 实时 |
| **版本上下文** | 目标/范围/决策记录/变更摘要/已知问题 | 版本库（git + task 聚合） | **任务收口时汇入** |
| **汇入归属域** | 版本摘要 → 归属域某一级 | 见 §12 | **版本收口时晋升** |

🔴 **知识库有三条写入管道，不止收口一条**（v3.1 更正 —— v3.0 只写了第一条，与 §12.6 企业公共库导入、§13.5 人工 curation 冲突）：

| # | 管道 | 触发 | 写入方 |
|---|---|---|---|
| 1 | **项目生产管道** | 任务收口 → 版本收口 | 引擎（自动） |
| 2 | **策展 / 外部导入管道** | 提案 → 权限与评审 → **锚定** → 落入归属域 | 该级 ops（§12.6） |
| 3 | **人工订正管道** | 发现错漏 → 新 revision | 该级 ops |

⚠️ **管道 3 走新 revision，不得原地改历史**（同 §21.4b 解绑不得重写历史审计）。

### 11.4 ⛔ K0-sec 已撤销（v3.0）

> v2.5–v2.8 曾把 K0 拆为 `K0-pub` / `K0-sec`，把「服务架构 / 网络架构 / 数据库设计」整体划入受限域。
> **v3.0 撤销该拆分**，因为它把两件性质不同的东西排进了同一格：

| 原 K0-sec 内含 | 实际性质 | v3.0 归处 |
|---|---|---|
| **架构的设计层 / 逻辑视图** | 低频、可公开全员、旧值仍是有效历史 | **D0 知识库**（§12） |
| **实际运行态**（真实 IP · 代理链 · 隔离网段 · pod · 日志 · 数据量） | 高频、旧值立刻误导、且部分高敏 | 🔴 **不入知识库** —— 走**受限 MCP 查询面**（§14.5） |

> **原动因（防「每个 Agent 上下文里都有全平台拓扑」）仍被满足**，且用了更轻的机制：
> **不是「放进知识库再加一层墙」，而是「它压根不属于知识库」。**

### 11.4a 🔴 第三个维度：visibility（v3.1 新增）

> 撤销 K0-sec 只解决了**易变性**，没有解决**稳定但敏感**的那一类。
> **易变性与保密性正交**：版本化的信任边界、网络分区原则、数据流向、灾备设计、威胁模型
> 都是**低频、有版本、旧值仍是有效历史**（故应固化），**但不应自动全量灌给每个 Agent**。
> 而 §11.2 的归属域只表达「谁维护、辖域多大」，D0 又是 push 全体 —— **模型里没有「平台域内受限可见」的表达能力**。

**⇒ 归属域之外，增加一个正交的 `visibility` 属性**：

| 取值 | 含义 | 装载 |
|---|---|---|
| `public` | 该归属域内全员可见 | 随该域装载规则 |
| `internal` | 该归属域内按角色可见 | **按需切片 + 角色判定** |
| `restricted` | 逐条授权 | **按需切片 + RLS + 逐次落账** |

#### 11.4b visibility 的四条硬性（v3.2 补，甲#2）

| # | 规定 |
|---|---|
| 1 | 🔴 **默认值 = `restricted`**（fail-closed）—— 未显式定级者按最严处理，**不得默认 public** |
| 2 | 🔴 **降级须审批并落账**（`restricted`→`internal`→`public` 每一跳皆是），升级无需。<br>**门方＝该条目所属归属域的 owner / ops**（D1 由业务线 ops、D2 由租户级 ops、D3 由项目管理方）。<br>🔴 **仅 D0 条目降 `public`**、**或该降级本身构成平台域基线变更时**，才走 §24。 |
| 2a | 🔴 **visibility 变更不得改变 domain**（v3.4 更正，甲域最终确认）：<br>v3.3 曾写「D1/D2/D3 降 public 即脱离该域边界，一律走 §24」——**那是让 visibility 去改变 domain**，<br>违反 §10「四维正交，任一维不得替代另一维」。<br>**`public` 的含义始终是「该归属域内全员可见」，不是「全平台可见」。**<br>⇒ **跨 domain 是 §15 的【晋升】（须过该级准入判据），不是 visibility 的【降级】。二者不可互相代替。** |
| 3 | 🔴 **继承取严（v3.3 扩为逐级）**：引用了某条目者，**其自身不得低于被引用者的可见性** ——<br>引用 `restricted` ⇒ 不得低于 `restricted`；**引用 `internal` ⇒ 不得为 `public`**。<br>⚠️ v3.2 只写了 `restricted` 一档，**`internal` 可派生出 `public`，是缺口** |
| 4 | **每次按 visibility 放行须落账**（谁 · 何条目 · 何时 · 依据哪条授权） |

⚠️ **与 §11.4 的表述冲突已消**：§11.4 说「架构设计层可公开」指的是**其默认候选值**，
仍须逐条按本节定级；**「可公开」不等于「自动 public」**。

🔴 **装载前须同时求 `归属域 scope ∩ visibility 授权`，两者缺一不可。**
**D0 只能全量装载其 `public` 子集**；`internal` / `restricted` 一律检索式。

⚠️ **与凭据分级（§22.4 S0/S1/S2）不是同一套**：那套管的是**凭据**，本属性管的是**知识条目的可见性**。
**两者不得互相替代，也不得混用符号。**

**归入 `restricted` 的典型**：信任边界与分区原则 · 数据流向 · 灾备设计 · 威胁模型 · 网络架构逻辑视图。

### 11.5 装载规则

| 来源 | 灌法 |
|---|---|
| D0 知识库 | **仅其 `public` 子集全量**（稳定前缀，可吃 prompt caching）；`internal`/`restricted` **按需切片**（§11.4a） |
| D1 / D2 / D3 知识库 | **按需切片**（`Query(q, topK)`，§13.4） |
| 版本上下文 | 当前版本摘要全量（量小） |
| 任务上下文 | 本任务全量（即派发信封本体） |
| 已批准 skill | 按 §15 辖域 push + 已 pull 者 |
| **运行态** | 🔴 **不灌** —— 需要时经 MCP 查（§14.5） |

**D1/D2/D3 必须是检索式的，不得全量灌。**

### 11.6 任务上下文的装载与隔离

- **每任务清空上下文**：新 Spawn = 新上下文
- **灌入什么由派发信封定义**，信封自带完整性判据：**缺任一字段 = 无效派发，执行小组拒接**
- **亲和（`OriginHint`）仅 pick 权重，不承担正确性**
- 🔴 **前置：不可变派发快照**。修订 node 摆脱 worker 记忆依赖，派发时必须持久化<br>（**下表即字段全集，不写死数量**，增删以本表为准；引用侧一律不得复述条数——E.3 #36a）：

| 字段 | 用途 |
|---|---|
| `envelope_ref` | 该次派发的完整信封引用 |
| 原交付物锚 | 上一轮 `result_ref` + sha256（**锚，不是路径**） |
| **完整 FAIL evidence + 失败最小复现** | 当前未持久化，须补 |
| `acceptance` 锚 | 判据的 commit/blob sha256（判据一改锚即变，防悄改判据） |
| 规则版本 | 分级规则表 version |
| 上下文版本 | 各归属域装载时的版本 |

## §12 知识库

### 12.1 🔴 第一判据：不知道这件事，会不会导致做错

> **会 ⇒ 必须在知识库里，且停在够用的抽象层。**
> **不会 ⇒ 不必写；写了也不必维护。**

知识库的维护成本大半来自**写了但没人需要、又必须跟着变**的条目。本判据先把它们挡在外面。

### 12.2 🔴 第二判据：固化 还是 运行时取

> **变了之后旧值【会误导】的 ⇒ 不固化，运行时取（MCP）。**
> **变了之后旧值【仍是有效历史】的 ⇒ 固化，入知识库。**

**这条判据规范里早已存在，只是长在别处**——§14.2「skill 不得内嵌 API schema，须在运行时经 MCP 查」
正是同一条原则用在 skill 上。**v3.0 起统一为一条通则，见 §14.4。**

### 12.3 🔴 第三判据：架构描述停在能支撑理解与决策的抽象层

**不下沉到实现细节。**

| 例 | 抽象层（写） | 实现层（不写） |
|---|---|---|
| 数据库 | **一套数据库系统** | 由哪些独立代理组成隔离网络 |
| 跨城集群 | **同一套机制** | 数据实际落在 A 城还是 B 城、怎么存 |

**理由同 §12.2**：抽象层的旧值不误导（还是那一套 DB），实现层的旧值会误导（那个代理已经下线了）。

#### 12.3a ⚠️ 抽象在什么时候会漏

**抽象层是默认视图；当实现细节会影响开发的【正确性】时，它必须上浮到抽象层。**

跨城集群的四处泄漏点：**一致性模型**（多为最终一致，按强一致写就会错）· **延迟量级**（决定超时与重试）·
**分区行为** · **数据驻留约束**（某些数据不得出城/出境）。

> 🔴 **但上浮的不是「实现是什么」，是「你据此该怎么做」**：
> 写「**按最终一致编写，勿假设读己之写**」，**不写**「A 城 3 副本、B 城 2 副本」。

### 12.4 条目类型（按 §12.2 分两栏）

> 🔴 **v3.1 更正（甲#7）**：v3.0 把业务流程 / 接口语义 / 对象介绍**整类**判为运行时取，是**误判**。
> 判据须对**定义/契约版本**与**当前生效实例**分开求值 —— 否则新 Agent 为理解「这个接口是干什么的」
> 必须实时探查代码，**反而违背 §12.1「不知道会做错就应入知识库」**。
> 故此四类各拆为 **a（定义/契约，固化）** 与 **b（当前实例，运行时取）**。

| # | 类型 | 权威源 | 固化 / 运行时 | 默认归属域 |
|---|---|---|---|---|
| 1 | 产品定义 | spec | **固化**（有版本） | D3（可升 D2/D1） |
| 2 | **业务架构** 🆕 | 设计文档 | **固化** | **D1**（业务线共通） |
| 3 | **服务架构** | 设计文档 + 代码 | **固化**（设计层） | D0 / D1 |
| 4a | **数据架构 · 逻辑**（数据模型 · 约束 · 分片**策略** · 数据流向**原则**） | 设计文档 | **固化** | D0 / D1 |
| 4b | 数据架构 · **当前物理拓扑**（实际分片位置 · 复制状态） | 运行系统 | ⚠️ 运行时取 | —— |
| 5 | **网络架构 · 逻辑视图** | 设计文档 | **固化**（有哪些系统 · 怎么连 · 边界在哪） | D0 |
| 6 | 前代系统与迁移 | 人 | **固化**（历史事实） | D2 / D3 |
| 7 | 🔴 **坑清单 / 判断失误** | **复盘**（§9.2 第 4 段） | **固化**（历史事实，最该固化的一类） | 起于 D3，**可逐级晋升至 D0**（须去标识化） |
| 8 | 运维预案 / 生产访问规范 | 人 | **固化**（有版本有评审；**上线后的授权依据**，§23.4） | D2 / D3 |
| 9 | 版本志 | 版本收口 | **固化**（历史事实） | D3 |
| 10a | 业务流程 · **定义**（流程、角色、状态转换） | spec + 设计文档 | **固化**（版本化产品事实） | D1 / D3 |
| 10b | 业务流程 · **当前实例状态** | 运行系统 | ⚠️ 运行时取 | —— |
| 11 | 代码位置 | 代码 | ⚠️ **运行时取** | —— |
| 12a | 接口 · **契约与语义**（版本化） | 设计文档 + spec | **固化**（绑交付物锚） | D1 / D3 |
| 12b | 接口 · **当前部署版本 / 动态 schema / 端点状态** | 运行系统 | ⚠️ 运行时取 | —— |
| 13a | 领域对象 · **概念、关系、不变量** | 设计文档 | **固化** | D1 / D3 |
| 13b | 对象 · **实例 / 数量 / 当前状态** | 运行系统 | ⚠️ 运行时取 | —— |
| 14 | **物理表结构** | `migrations/` DDL | ⚠️ **运行时生成** | —— |

**另有运行态一类，不属知识库任何一级** —— 见 §14.5。

### 12.5 知识**来源**有四类权威源，不是一个

**设计文档 / 代码抽取 / 复盘 / 收口**——权威源不同，不得指望一个 code-scanner 全包。

> ⚠️ **与 §11.3 的「三条写入管道」不是同一件事**（v3.2 消歧 —— v3.1 两处都叫「管道」，字面像矛盾）：
> **本节说的是「知识从哪来」（权威源，4 类）**；**§11.3 说的是「怎么写进去」（写入入口，3 条）**。
> 一个权威源可经不同入口写入（如设计文档既可经收口晋升、也可经策展导入）。
> ⇒ 本节起改称**「权威源」**，「管道」一词**只用于 §11.3 的写入入口**。

### 12.6 企业公共库的导入与链接

企业既有的公共知识库可**导入**（拷贝）或**链接**（引用）。**四点须先定**：

| # | 问题 | 规定 |
|---|---|---|
| 1 | 导入 or 链接 | **导入**＝可锚可控，但会漂移且要同步；**链接**＝永远最新，但**可用性与权限受制于人**。按条目性质择一，须在条目上标明 |
| 2 | 锚 | 外部源无我方 commit ⇒ **须指定替代锚**（其版本号 / 内容 sha256 / 快照时刻）。**无锚则 §13.3 的 stale 状态机失效** |
| 3 | 归属与可见性 | 🔴 **`domain_level` 与 `visibility` 分别判定，均不继承外部标注**（v3.4 更正）：<br>`domain_level` 按该条目服务于哪一级确定（§11.2 准入判据）；`visibility` 按其内容敏感度独立定级（§11.4a，默认 `restricted`）。<br>**两者是 §10 的两个正交维度，不得用一个推出另一个。** |
| 4 | 可信度 | 🔴 外部内容**不受本平台的评审与门约束** ⇒ **不得直接作为施工依据**，须显式标注来源 |

### 12.7 多租户下「现网」有两个

平台自身的现网（D0，平台级 ops 域）与各租户业务的现网（D2/D3，租户级 ops 域），
**部署锚来源、权限域、脱敏要求均不同**。⇒ **抽取管道参数化于租户，不得各租户各建一套。**

## §13 新鲜度与腐坏

### 13.1 每条目必带锚

`KBDoc.Meta` 必含：

| 字段 | 说明 |
|---|---|
| `domain_level` | `D0` / `D1` / `D2` / `D3`（§11.2） |
| `owner_key` | 该级的归属主体（业务线 / 租户 / 项目的稳定标识） |
| `visibility` | `public` / `internal` / `restricted`（§11.4a） |
| `type` | §12.4 条目类型 |
| 🔴 `anchors[]` | **数组，可多条** —— 一条目常有多个权威源（如设计文档 ＋ 代码），每条为 `{anchor_type, value}`；<br>`anchor_type ∈ {code, deploy, artifact, external}`（§13.2）。<br>⚠️ **单 anchor 无法覆盖「设计 ＋ 代码」双源**，v3.1 的单值字段已改 |
| `version` · `updated_at` | —— |

> ⚠️ v3.0 的 `{project, ...}` **无法表达 D0/D1/D2 的归属**（只有项目一维），已改。
⚠️ **`baseline_anchor` 一词已废**（v3.2）—— 它只是 `anchors[]` 中 `anchor_type=code` 的那一条，不再单列。

**失败模式**：写进去的内容过期了没人知道——**比没有知识库更危险，因为它会误导。**

### 13.2 四类锚，按条目权威源选（v3.2 更正：v3.0/v3.1 称「三种」，实为四类）

| 锚 | 检测什么 | 用于 |
|---|---|---|
| **代码锚** `code` = commit 40hex / blob sha256 | 「条目所述的代码位置变了」 | 权威源含代码的条目 |
| 🔴 **部署锚** = 组件 × 环境 × commit × 制品 sha256 | 「文档描述的是 A 分支，而线上跑的是 B 分支」 | 「基于现网」类断言 |
| 🔴 **交付物锚**（v3.0 新增）= 所锚交付物的 **sha256 ＋ 版本** | 「该条目所依据的 spec / 设计方案 / 测试报告出了新版」 | **权威源是设计文档的条目** —— §12.4 中标「固化」且权威源含设计文档者：**1 · 2 · 3 · 4a · 5 · 8 · 10a · 12a · 13a**<br>⚠️ v3.3 更正：v3.2 写「第 1–5、8 类」，**误含 4b（运行时取）**，且**漏了 10a/12a/13a**（v3.1 新拆的固化项） |
| 🔴 **外部锚** `external` = 外部源的版本号 / 内容 sha256 / 快照标识 | 「外部源变了」 | §12.6 导入或链接的条目 |

**为什么必须有交付物锚**：一条源于设计方案的知识，其新鲜度应随**那份设计方案**变，**而不是随代码变**
——**两者会各自独立漂移**。v2.x 只有代码锚，这类条目无法判 stale。

**部署锚由 §8.2 第 3 项收口登记提供**；**交付物锚由 §25.3 的交付物链路提供**，均不另造机制。

**外部源条目**（§12.6）无我方锚 ⇒ 须按 §12.6 第 2 条指定替代锚，**否则不得入库**。

🔴 **多锚条目的 `suspect` 判定取「或」**：**任一锚触发即 suspect** —— 设计变了或代码变了，
该条目都可能已失真，**不得要求全部锚同时变化才标记**。

### 13.3 生命周期状态机（按锚型分判据，v3.1 更正）

> v3.0 新增三种锚后，stale 判据仍只写「锚落后且两锚间 diff 覆盖该条目所述路径」——
> **那只适用于代码锚**。部署锚、交付物锚、外部锚**未必存在代码路径 diff**，因而永远进不了 `suspect`。
> **新增的锚只是存了字段，没有可执行的生命周期。**

| `anchor_type` | `suspect` 判据 |
|---|---|
| `code` | 锚落后 **且** 两锚间 diff 覆盖该条目所述路径 |
| `deploy` | **条目所锚的组件 × 环境的部署锚发生变化** |
| `artifact` | **所锚交付物的 digest 或版本发生变化**（§25.3 链路视图提供） |
| `external` | **外部源的 version / hash / snapshot 标识发生变化**（§12.6 第 2 条指定的替代锚） |

**`archived` 判据统一**：连续两个版本仍 `suspect`。



| 状态 | 判据 |
|---|---|
| `active` | 锚匹配 |
| `suspect` | **按 `anchor_type` 分判，见上表** |
| `archived` | 连续两个版本仍 `suspect` |

**判据用锚，不用时间。**（按时间会误伤——一份三年未改的稳定接口文档不因无人查阅而过期。）

### 13.4 检索

**必须先 RLS 过滤后检索，禁止先检索后过滤**——后者会经摘要片段泄露正文。

**排序计分**（初值见附录 A）：

```
score = w_use · log₁₊(使用量)归一  +  w_rel · relevance  +  w_imp · importance
importance 由归属域给定（**D0 > D1 > D2 > D3**）
suspect 条目乘以降权系数
```

> **锚失配必须参与排序降权，不能只打标记。标了不参与排序，等于没标。**

### 13.5 写权

- **`ingest` = 管理域**（知识策展）；`query` = 按 RLS 与条目分级
- **管道 1（项目生产）的 ingest 仅由「版本收口」原语触发**；管道 2 / 3 各有其入口，见 §11.3
- 人工订正走独立 curation 流程，**落审计**

# 第五部 · skill 与 MCP 体系

## §14 判据

### 14.1 skill vs 机制（第一判据）

> **凡是「丢了上下文就该失效」的，做 skill；**
> **凡是「丢了上下文仍须成立」的，做机制。**

| 事项 | 归属 |
|---|---|
| 「先写 spec 再写代码」的流程指引 | skill |
| 「门方 ≠ 执行者」 | **机制**（board） |
| 「node DAG 走不通就是走不通」 | 机制 |

### 14.2 skill vs MCP（第二判据，两维）

| 维 | skill | MCP |
|---|---|---|
| **状态与认证** | 无状态的流程、判断、参考材料 | **有状态 + 有认证的连接** |
| **变不变** | 稳定的 | **易变的**（运行时查） |

**⇒ skill 不得内嵌 API schema，须在运行时经 MCP 查**，使 skill 轻量且不因后端变更而过期。

**一件事既是系统又是用法时**（多数真实工程属此）：**建一个小 server 管访问 + 一个 skill 管用法。**

### 14.3 MCP 工具面：动词 × 资源类型

**MCP 工具数量收敛到动词集，不随资源数量线性增长**（如 `list/get/create/update/delete/execute/search/describe/schema/diagnose/status`）。
这与平台已确立的「工具语义在 MCP 层，线上只有一个 type，枚举零膨胀」是同一做法。

### 14.3a MCP 的归属分级（v3.0 新增）

**MCP 与知识库、skill 共用 §11.2 的四级归属轴**：

| 级 | 例 | 谁维护 |
|---|---|---|
| **D0 企业 / 团队级 MCP** | 平台运行态查询 · 企业公共数据源 | 平台级 ops |
| **D1 业务级 MCP** | 业务线共用的数据源与工具 | 业务线 ops |
| **D2 租户级 MCP** | 该租户的业务系统接入 | 租户级 ops |
| **D3 项目级** | 少见，多数应升 D2 | 项目管理方 |

> 🔴 **MCP 分级不只是「工具归谁」，也是「能查到谁的运行态」**（§14.5）：
> 租户只能查自己的 pod 与日志，平台级 ops 才能查全平台。

### 14.4 🔴 通则：易变的不固化，运行时取（三处合一）

同一条原则此前分散在三处，v3.0 合并为一条通则：

| 应用面 | 表述 |
|---|---|
| **skill** | skill **不得内嵌 API schema**，须运行时经 MCP 查 —— 使其轻量且不因后端变更而过期 |
| **知识条目** | §12.2 固化 vs 运行时取 |
| **抽象层次** | §12.3 架构描述停在抽象层，不下沉实现细节 |

**三者的判据是同一个**：**变了之后旧值会不会误导。**

### 14.5 运行态查询（v3.0 新增，原不属规范任何一节）

**运行态不属知识库任何一级**，走 MCP 查询面，动词用既有的 `status` / `diagnose` / `list` / `get`，**不新造**。

| 类别 | 数据源 | 密级 |
|---|---|---|
| 运行 pod / 实例 · 在哪台机 · 跑哪版 · 健康 | 编排系统 API | 中 |
| 日志 | 日志系统 | ⚠️ **按内容定级**——可能含 token / IP |
| 数据量 · 慢查询 · 连接数 · 复制延迟 | DB 指标 | 中 |
| 🔴 真实 IP · 代理链 · 隔离网段 · 连通性 | 网络与部署系统 | **S0 / S1，受限** |
| 业务量 · 转化指标 | 业务系统 | 按租户 |

#### 14.5a 🔴 运行态须有统一 PDP / PEP（v3.1，SA-04）

编排 API · 日志系统 · 指标系统 · 网络与部署系统**不在同一 PG 表 / RLS 执行面上**。
只写「受 §22 RLS 约束」，**在这些后端上没有可执行的强制点**。

| # | 要求 |
|---|---|
| 1 | **每次后端调用前**求值：服务端派生的 `principal` × `tenant` × `domain_level` × `resource selector` × 数据密级 |
| 2 | 🔴 **后端无法表达该 selector 或脱敏策略 ⇒ 拒绝调用**（fail-closed），不得降级为「尽力过滤」 |
| 3 | **聚合 / 缓存 / 分页 / 错误信息**同样须过滤与脱敏 —— **缓存键与游标必须带作用域** |
| 4 | 🔴 明确 **D0 平台 ops 与 D2/D3 租户数据之间的 scope 交集规则**，不得默认「平台可见一切」 |
| 5 | 每个数据源补四类负测：**越权 · 跨租户 · 错误信息泄漏 · 缓存泄漏** |

**三条硬性**：
1. **运行态不得灌入上下文**（§11.5），只在需要时查
2. **查询作用域按 §14.3a 分级**，且受 §22 与 §14.5a 的 PDP/PEP 约束
3. 🔴 **无可执行强制点的数据源不得接入** —— 接了就是给了一条无闸的路

### 14.6 MCP 化的准入（三层）

> 🔴 **v2.5 更正（复审两轮均指出，本席核实成立）**：v2.1–v2.4 把「≥3 提出方且跨项目」
> 放在**判型之前**，等于**让复用度门槛决定安全实现形态**——
> 一个单项目、单提出方但**有状态且需认证**的连接，会因未达复用阈值而被挡在 MCP 之外。
> **这是把安全边界交给了流行度。**

**改为三层，安全判据优先且不受采用人数影响**：

| 层 | 问题 | 判据 | 不受什么影响 |
|---|---|---|---|
| **① 技术形态（安全判据，最先判）** | 必须是 MCP 吗 | 🔴 **凡需要状态、认证或动态 schema 的连接，一律经 MCP / 受控 server 承载** | **不受采用人数、复用度影响** |
| **② 其余情形的判型** | skill 还是 MCP | 按 §14.2：无状态的流程判断 → skill | —— |
| **③ 平台产品化 / 晋升** | 要不要推广、升到哪层 | **≥3 个不同提出方 且 跨项目** + §15.1 三判据 | 这才是复用度该管的地方 |

**显式例外**：**安全强制**或**业主指定**可跳过 ③ 的复用门槛直接产品化，**但须落账**。

## §15 分发：按辖域 push，向上 pull

### 15.1 🔴 分界在辖域，不在层级高低（v3.0 重定）

> v2.x 定的是**两级两通道**（平台级 push / 租户级 pull）。四级归属轴之后须重定，否则业务级无处安放。

| 规则 | 内容 |
|---|---|
| **push 的作用域 ＝ 该层级的辖域** | D0 全体 · D1 其辖下租户 · D2 其辖下项目 · D3 不 push。<br>⚠️ **本行定的是辖域上界，不是「一定 push」**；分资产的实际动作见 §15.1b/§15.1c |
| **pull 只能向上取** | D3 可 pull D2/D1/D0；D2 可 pull D1/D0；以此类推 |
| 🔴 **禁止横向取** | 租户 A 不得 pull 租户 B；业务线甲不得 pull 业务线乙 |

**禁止横向取的理由**（§15.3 的推广）：**横向取用会绕过归属边界**，无论那个边界是租户之间还是业务线之间。
跨边界复用的唯一路径是**抽象化 → 脱敏 → 晋升到共同上级 → 由上级 push**。

### 15.1a 各级的准入判据（v3.0 新增）

> v2.x 的三判据是**为 D0 写的**；**D1 业务级按定义就受业务限制**，它过不了那三条。各级须有各自的判据。

| 升入 | 判据（同时满足） |
|---|---|
| **D0 平台级** | ① 不引用任何具体业务概念 ② 移出任一项目后仍完整可用 ③ 描述「怎么做」而非「做什么」 |
| **D1 业务级** | ① **不引用任何具体项目概念**（可引用业务域概念）② 移出该业务线任一租户后仍可用 |
| **D2 租户级** | ① 不引用任何具体项目概念 ② 该租户内跨项目已出现 |
| D3 项目级 | 无（创建即在此级） |

### 15.1b 三类资产的分发形态

> 🔴 **本表是分资产形态的唯一定义处**（v3.1 明确）。§11.2 归属域表的「分发」列只表达**辖域与可见范围**，
> **不表达具体分发动作**；动作一律以本表为准。二者若不一致，以本表为准。

| | 知识库 | skill | MCP |
|---|---|---|---|
| D0 | push 全体 | push 全体，强制 | 全体可调用（按 RLS 限作用域） |
| D1 | push 辖下租户 | push 辖下租户 | 辖下租户可调用 |
| D2 | push 辖下项目 | **见 §15.1c** | 租户内可调用 |
| D3 | 项目内 | 项目内 | 项目内 |

### 15.1c D2 租户级 skill：push 还是 pull

> v3.0 在四处给了两种答案（§11.2 与 §15.1 说 push，§15.1b 与 §26.2 说 pull），
> 且 E.1 #83「越级 push 数」的判定基准会随取哪节而**相反**。v3.1 统一如下：

| 情形 | 分发 | 理由 |
|---|---|---|
| **租户强制统一的** skill（如该租户的发布检查、合规操作） | **push 辖下项目** | 与 D0/D1 同理：强制的东西不用挑 |
| **租户内可选复用的** skill | **pull 自取** | 项目按需取，走 §13.4 排序 |

**判据**：**该 skill 是否被租户级 ops 标记为 `mandatory`**（§15.2）。
**`mandatory` ⇒ push；否则 ⇒ pull。**

⇒ E.1 #83 的判定基准随之明确：**仅当非 `mandatory` 的 D2 skill 被强制下发时，才计为越级 push。**

⚠️ **排序只对 pull 层有意义**（§13.4）——**push 是强制的，强制的东西不用挑**。

### 15.2 两个属性必须分开

| 属性 | 含义 | 约束谁 |
|---|---|---|
| **mandatory** | 租户不可停用 | 租户 |
| **immutable** | 内容不可被修改（Agent 连提案都不能提） | Agent 与一切下游 |

四种组合均有意义；平台级纪律类（产品定义规范、发版流程、门方所有权）为 **mandatory + immutable**。

### 15.3 🔴 跨租户扩散只有一条合法路径

```
租户 A 的 skill
   ① 抽象化：剥离业务概念（§15.1 三判据）
   ② 脱敏：去项目名 / 内部地址 / 表名 / 业务术语
   ③ 晋升审批（平台级 = 平台域基线变更，走 §24）
        ↓
平台级 skill（push 给全体）
        ↓
租户 B 拿到的是【抽象后的版本】，不是 A 的原件
```

**禁止租户 B 直接 pull 租户 A 的 skill。**

**受限对象的边界（v2.3 明确）**：

> 🔴 **v2.5 补 MCP 边界（复审两轮均指出）**：v2.3–v2.4 只解释了 skill 制品，
> **未给 MCP 的跨租户边界**。而 S4 标的是 skill **与 MCP** 体系。

**本节的「唯一晋升路径」只约束【可复用制品】。** 四层必须分开治理：

| 层 | skill | MCP | 可否随制品晋升 |
|---|---|---|---|
| **code / 制品** | `SKILL.md` 正文、随附脚本、引用模板 | **server 代码、工具 schema** | ✅ **可抽象晋升**，走本节唯一路径 |
| **config** | 参数默认值 | **连接配置、端点** | 🔴 **不可**——租户专属，随租户走 |
| **credential** | —— | 🔴 **secret / token / 连接凭据** | 🔴 **绝不可**，任何情形 |
| **runtime data / 业务数据** | 执行记录 | **连接状态、缓存、业务数据** | 🔴 **绝不可** |

**目录可见性**：skill 与 MCP 的**存在性与名称**同样受限——**目录按 RLS 过滤**，否则名称即泄漏项目信息。
**同一租户内**跨项目流转 ✅ 不受限，由租户级 ops 自管。已晋升的**平台级**版本 ✅ push 给全体。

> 🔴 **一处必须防的误读**：本节是**制品复用**的规则，**不是所有跨租户动作的总规则**。
> **已授权的跨租户业务数据访问由 §22.1c 的 capability 与 §23 治理**，
> **不得被解释为「制品晋升」而套用本节路径**。二者是不同的事。
理由：skill 正文可能含项目名、内部地址、表结构、业务术语——
**RLS 管的是数据表，管不到一份 Markdown 正文里写了什么。**

> ⇒ **「进一步抽象，进入平台级」不只是提升复用度，「抽象」这一步同时承担跨租户扩散的脱敏关口职能。**

## §16 生命周期

### 16.1 三件事必须分开判，不得混为一谈

> ⚠️ **v2.3 更正**：v2.1–v2.2 把「频次触发」与「业务无关性」并列为「两条判据串联」，**是错的**——
> 业务无关性是**平台晋升**的判据，与「要不要固化成 skill」无关。
> 一个刚生成的 skill 天然是项目级，**不需要业务无关**。三件事被混在了一起。

| # | 问题 | 判据 | 输出 |
|---|---|---|---|
| **① 候选触发** | **要不要固化** | 见 §16.1a | 一个**候选**（默认落在**项目级**） |
| **② 判型** | **固化成 skill 还是 MCP** | §14.2 两维 + §14.6 三层 | skill 或 MCP |
| **③ 晋升** | **要不要升层、升到哪层** | §15.1 三判据 | 项目级 / 租户级 / 平台级 |

**三者顺序执行，各自独立。① 不引用 ③ 的判据；③ 不因 ① 的频次自动成立。**

#### 16.1a 候选触发（仅决定「要不要固化」）

**触发情形（任一即触发一次总结）**：

1. 完成一个 **≥N 次工具调用的复杂任务且成功**（N 为可调参数，见附录 A）
2. **从错误中恢复 / 死胡同脱困**
3. 🔴 **用户或评审方纠正揭示了正确做法**

> 第 3 条价值最高：顺利路径只证明「这样可行」；**被纠正的路径额外编码了「默认做法是错的」**，
> 它拦住的是**会重复发生的错误**。与 §9.2 第 4 段是同一洞见的两个尺度（单次操作级 / 阶段级），**两者都要**。

**触发后须判「是否可复用」**（同样的步骤序列是否会对不同输入再次发生），**可复用才入库**。
**次数是启发式，不是判据**——不设此闸，一次性排障会淹没 skill 库。

#### 16.1b 晋升（独立发生，与创建解耦）

**晋升不由使用频次自动触发。** 频次可作为**「该评估了」的提示信号**，
但**升不升、升到哪层，只看 §15.1 三判据**；平台级晋升另须经 §24 审批。

### 16.2 自我进化：准入，但必须以暂存审批模式

**允许 Agent 提案，不允许 Agent 批准。**

| # | 前提（硬性） |
|---|---|
| 1 | **写入审批（`write_approval`）在平台级与租户级默认开启** |
| 2 | 暂存件**跨重启存活** |
| 3 | 可 **diff 审阅**后批准/拒绝 |
| 4 | 🔴 **前台回合与后台自我改进一视同仁**——不给后台特权路径 |
| 5 | 叠加 §16.5 immutable 名单 |

### 16.3 回写纪律：何时改 + 怎么改

| 问题 | 规定 |
|---|---|
| **何时改** | **只在该 skill 把本次执行带偏时**（命令失败、缺步骤）才回写；执行顺利则**只计使用量，不改内容** |
| **怎么改** | **`patch`（定向替换）优先，禁止用整篇 `edit` 做常规修订** |

**`patch` 优先的首要理由不是省 token，是可审**：`patch` 的 diff 小、可审；整篇 `edit` 的 diff 审不动。
在 200+ Agent 并发 + 写入审批的场景下，**审批会先成为瓶颈，然后被绕过**。

**不设负反馈闸的自动回写会制造持续冲突**：每次运行都产生 diff，skill 库变成噪声源。

### 16.4 变更须附 SYNC IMPACT REPORT

**凡平台级 skill 变更，必须附**：版本变更 / bump 理由 / 新增章节 / **逐个复核了哪些下游件并打 ✅** / 遗留 TODO。

> **diff 小 ≠ 影响小。** patch 保证可审，SYNC IMPACT REPORT 保证影响面被显式声明。

### 16.5 🔴 immutable 名单

**安全类 / 合规类 / 平台域基线类 skill 标为 immutable——Agent 连提案都不能提。**

理由：写入审批只保证「有人看」，**不保证「看的人看得出来」**——一个被巧妙 patch 的安全类 skill，
在 diff 里可能只有一行。

**首批名单（优先级最高）：Spec Kit 及其模板。** 它同时满足三条件：

| 条件 | 事实 |
|---|---|
| 平台级 | 全网 spec 产出都依赖它 |
| **承载纪律** | `checklist-template.md` 的「checklist 是 reviewer-owned」= §7.2「implementer 不能自签门 PASS」。**一次 patch、一行 diff 即可废掉它** |
| **影响授权判据** | spec 是授权凭据（§4.3）；**能改 Spec Kit 的人，能改「预授权该长什么样、门方该检查什么」** |

⚠️ **immutable 名单本身的变更须重两签**，否则「把某件移出名单」成为新的绕过点。

### 16.6 装与卸必须对称

分发通道**必须同时提供安装与卸载**（`install_skill` / `uninstall_skill`、`install_mcp` / `uninstall_mcp`）。

**理由**：晋升机制必然包含降级与下架——坏 skill、被平台级版本取代、安全召回。
**没有卸载 = 晋升是单向的 = 坏 skill 推出去就收不回来。**
且防降级的版本单调闸会让「推一个空版本覆盖」这条替代做法也走不通。

> 🔴 **v2.5 推翻 v2.3 的分类依据（复审指出，本席核实成立）**：
> v2.3–v2.4 称 A 类安全召回「只减不增，最坏后果是可用性下降」。**该判断不成立。**
> **卸载鉴权、审计、DLP、安全门类的 skill / MCP，会直接扩大权限或可达范围**——
> 这与 §24.3a 的总判据「任何情形下都不可能扩大任何主体的权限或可达范围」**正相冲突**。
>
> 且「携带有害证据」只能证明**该制品有问题**，**证明不了删除后的权限效果是单调的**。
> **本席原来的分类是按【动作名】判的，应当按【capability effect】判。**

**改为按 capability effect 判，不按动作名判**：

| 判据（唯一） | 说明 |
|---|---|
| 🔴 **该动作执行后，是否存在任一主体的权限或可达范围被扩大** | 存在 ⇒ **不得走紧急路径**，无论它叫「卸载」还是别的 |

**紧急路径可用的原语（注意：不含 `uninstall`）**：

| 原语 | 语义 | 前提 |
|---|---|---|
| `disable` | 停用，制品仍在 | —— |
| `quarantine` | 隔离，不可被调用 | —— |
| `revoke` | 吊销凭据 / 撤销授权 | —— |

> **前提（对上述三者均适用）**：**必须存在 fail-closed fallback 或替代控制**。
> 停用一个安全门而无兜底 = 门消失 = 权限扩大 ⇒ **该操作不合法，无论多紧急**。

**会移除安全控制的卸载**：**必须先切换到安全版本或兜底机制，再卸载**，且走**事前**审批。
**删除动作本身不可被枚举为「天然安全」。**

**常规 install / uninstall 保持对称审批**（事前、同级）。

| 其余要求 | 说明 |
|---|---|
| 🔴 **tombstone / fencing**（v2.5 新增） | 卸载须留 **tombstone**；**重装同版本必须形成新的 `installation_generation`**。<br>**迟到的 ACK、旧任务、旧 delivery 不得复活已卸载的实例**——按 generation 栅栏丢弃 |
| 幂等语义 | 卸载后再装同版本，不得被误判为「已装」（由 generation 保证，非由版本号保证） |
| 审计 | 卸载与安装同等落账；紧急路径的 `disable`/`quarantine`/`revoke` 另须记录事后补审结果与所用兜底机制 |

### 16.7 上下文预算

**skill 目录的常驻上下文成本必须设硬预算**（初值见附录 A），采**渐进披露**：

- 常驻只放 `name` + 简要描述，**正文按需加载**
- 描述文本设字符上限

> **排序解决「列表太长怎么办」；渐进披露解决「列表为什么会太长」。**
> **渐进披露是主解，排序是次解。** 这是唯一能防止 skill 库随规模膨胀吃掉上下文的机制。

# 第六部 · 协同：帖子流与通知面

## §17 要解决的问题

现有协同全靠平台通信转发，产生两个后果：**作业无痕**（看不到交付物是怎么产出的）与**消息风暴**
（多方产出无效或过期消息）。

**根因：三件事被混在同一条消息流里**——工作过程讨论 / 状态通知 / 控制指令。**必须分开。**

## §18 帖子流

### 18.1 载体与列定义（v3.0 补列）

**帖子正文须独立表**，不得塞进事件表——读写模式不同（看板高频全扫 vs 按 node 低频增量读；封存后可归档）。

| 列 | 用途 | 入 digest 规范序列 |
|---|---|---|
| `post_id` | 消费侧幂等去重（§18.3） | ❌ |
| `tenant` | 租户边界 | ✅ |
| `node` | 归属 node | ✅ |
| `seq` | 单调序号 | ✅ |
| `actor` | 发帖 principal | ✅ |
| `ts` | 时刻 | ✅ |
| `content` | 正文 | ✅ |
| `kind` | 正常帖 / 门结果 / 引擎事件 | ✅ |
| `in_reply_to` | 回指（可空） | ✅ |
| `attachments[]` | 🔴 **附件引用 ＋ sha256 ＋ 密级**（§25.7）；**引用不内联 blob** | ✅ |
| `delivery_id` | 投递去重（§18.3） | ❌ |
| `cursor` | 读游标基准 | ❌ |

> **规则**：**凡影响「这条帖子说了什么」的列，必须入 digest 规范序列**；
> 纯投递/去重元数据不入。**附件必须入** —— 否则换掉一张图而 digest 不变。

### 18.2 传播范围

**每个任务的消息仅在该任务的执行者 / 门方 / 其他 `task_role` 成员之间传播。**

### 18.3 读取：游标增量，引擎推送，Agent 不轮询

1. **Agent 完全不轮询、不主动读**
2. 派发 node 时，把该 node 帖子流的**增量**（`cursor > 该 principal 上次读到的位置`）打包进**派发信封**
3. 成本上界 = O(成功覆盖的 post-recipient 对 + 重投开销)

**保证 at-least-once + dedupe，不宣称 exactly-once**：

| 机制 | 要求 |
|---|---|
| delivery / outbox | 冻结 `[from, to]` 区间 + `delivery_id` |
| 游标推进 | **ACK 后**以 **CAS 单调推进** |
| 并发控制 | 同 principal **并发租约** |
| 消费侧 | 按 `post_id` / `delivery_id` **幂等去重** |
| 未 ACK | 可重投 |

### 18.4 阶梯硬门

**帖子数是分歧探测器，不是话痨指标。** 用**原始计数**而非「有效帖数」——有效性是主观判断，
两人数不出同一结果，违反 §5.1 可重复判定。**原始计数的价值恰在客观、不可辩。**

| 阈值（每 node 每轮） | 动作 | 解封权 |
|---|---|---|
| ≤ 阈值 A | 正常 | —— |
| **> A** | 三段式封锁 | **调度者可解封（首次），并须同时向业主预警** |
| **> B** | 三段式封锁 | **仅该租户业主可解封** |

**三段式封锁**：

| 段 | 动作 |
|---|---|
| ① **停注入** | 停止自动推送 / 上下文注入，冻结 reader cursor。**这才是真正止血的一刀** |
| ② **禁新帖** | 拒绝新增 post |
| ③ **保留受限只读** | 固定 digest / snapshot；按需单次读取或 break-glass；**带预算与审计** |

> **禁的是「注入」，不是「读取」。** token 在注入时就花掉了，事后禁读追不回来，
> 却会伤及可追溯、崩溃恢复、新成员接手、参与者核对摘要四项。

**读权豁免**：调度者（解封权人）、该租户业主、摘要 agent（只读）——**摘要正在产出解封决策所依赖的依据**。

**解封必须产出裁定物，不得只是放行**：

| 层级 | 必须产出 |
|---|---|
| 调度者 | ① **分歧点陈述**（争的是什么、双方各自的裁剪、裁定或判属产品决策升业主）② **同时向业主发预警** |
| 业主 | 决策记录（§7.3 格式）；且**裁定结果须回写定义层**（spec / constitution / 分级规则） |

> **不回写定义层的解封，等于给同一个 bug 反复续命**——下一批帖子会重复上一批的争论。

**首次解封必须预警业主**：若只在第二档通知，业主第一次知情时分歧已烧掉两倍配额。

**开放讨论豁免**：建 node 时可标记为开放讨论型（阈值放宽或不设）；
**豁免必须落账** `{node, 标记人, 理由, 时间}`——**可审计，不可匿名突破**；**不得由执行方自行标记**。

### 18.5 三层封存

| 层级 | 封存时机 | 晋升产物 |
|---|---|---|
| **node 帖子流** | `execution done ∧ verdict ∈ {not_required, pass, fail}`；**`pending` 不封** | → 环节小结 |
| **task 帖子流** | 任务收口（调度者唯一关闭权） | → 任务摘要 → **版本上下文**（§11.3） |
| **version 帖子流** | 版本收口 | → 版本摘要 → **归属域**（§11.3） |

**封存条件必须含 `fail`**，否则门 FAIL 的 node 永不封存，其帖子流长期可写、digest 永不生成。

**顺序**：先落 FAIL evidence / gate result，**再**算 digest。

**返工天然不污染**：门 FAIL 走 `append_revision` 建**新 node**，新 node 有新帖子流。

> 「环节结束后还想讨论怎么办」有答案：**属于上一层**。node 封了 task 层还开着，task 封了 version 层还开着。

### 18.6 封存的威胁模型（承诺须准确）

**表述为「篡改可检测（限定威胁模型）」，不得表述为「防篡改」**——
digest 与数据同在一个可写库，能改帖的人通常也能改 digest。

| # | 最低配套 | 作用 |
|---|---|---|
| 1 | 封存后 DB 权限 / trigger 拒 `UPDATE`/`DELETE` | 阻断常规写路径 |
| 2 | digest 覆盖 **§18.1 表中标记「入 digest」的全部列**的**规范序列** | 防止只改内容不改元数据。<br>🔴 **附件必须入** —— 否则换掉一张图而 digest 不变，正是本节要防的篡改面。<br>⚠️ **本行不重复枚举，以 §18.1 为唯一定义处** |
| 3 | **外部或更高权限锚定 + 定期核验** | **唯一能对抗「改帖者亦可改 digest」的一层** |

**未做到第 3 项前，对恶意篡改的防护为零**，只覆盖非协同损坏与误操作。

**digest 选型**：**整流 sha256**，算前用 RFC 8785 (JCS) 规范序列化（平台已有实现，直接复用不自造）。
将来若需局部验证，可在保留 sha256 基础上追加 Merkle root。

## §19 通知面收敛

### 19.1 通知 taxonomy

| 类 | 例 |
|---|---|
| 任务状态（六类） | `new` / `status` / `result` / `reject` / `gate_result` / `close` |
| delivery ACK | 投递确认 |
| security / platform health | 安全事件、平台健康 |
| break-glass | 应急通道启用 |
| 决策请求 | 升业主 |
| 跨 task 协调 | 双方无共同 node 时 |

### 19.2 出站闸（三层）

**纪律在此处必然失效**——善意且准确的转述仍会产生版本错位。**故须机制约束。**

| 层 | 约束 |
|---|---|
| **G1** | 出站消息若 recipient 是某 task 参与者、且**可信结构化头**（`meta.op`/`event_type` + `task`/`node`/`tenant`/`version`）不属允许集 → **拒发，回指帖子流**。🔴 **判定只读结构化头，绝不读正文** |
| **G2** | agent↔agent 直接消息通道**仅承载已批准的通知 taxonomy**；一切自由文本必须落 node 帖子流 |
| **G3** | 调度者收件面**不提供任何「转述/转发」op**；堵住自由文本旁路 |
| **跨租户** | **默认拒发**，白名单放行 |

**必须保留的例外通道**：应急（break-glass）、决策升级、平台运维通告。
例外**不得停在开放清单后直接上高强度层**，须先在 G1 试点计量。

### 19.3 交接纪律

**每一次评审、转述、交接，必须带 `commit + sha256 + 行数/字节`。**
（本条源于实际发生的三次版本错位事故，已由团队采纳。）

## §20 摘要 agent

| 维度 | 规定 |
|---|---|
| **触发** | **事件驱动，不定时轮询**：node 进终态 / 触门 / 距上次摘要已积累 N 条新帖 |
| **模型** | **廉价模型**——任务是抽取，不是推理 |
| **输入** | **仅增量帖**（游标区间）+ node 结构化头 |
| **输出** | **结构化**：`{tenant, node_id, cursor_range, 进度一句话, 阻塞项[], 需支援[], 分歧点[], 建议升级?}` |
| **租户** | 🔴 **必须租户内**——它用廉价模型、跑得频繁、读很多帖，是**易被忽略的泄漏面** |
| **是否入帖子流** | **不入**，单独存 `node_digest`——**入了会推高帖子计数、触发硬门，而摘要恰是解封决策的依据。工具不该污染它测量的东西** |
| **权威性** | **非权威 observation ledger**；不写权威状态机、不授权（LLM 判读不授权） |
| **输入信任级** | 🔴 **按不可信数据隔离**——帖子是 agent 写的文本，**可能嵌入针对摘要器的提示注入**。摘要 principal 须 tenant + node 最小只读 |

**质量校验**：

| 存证项 | 校验项 |
|---|---|
| `input digest` | **覆盖率**（增量区间是否全被处理） |
| `prompt` + `schema` + `model` + `version` | **引用存在性**（citations 指向的帖子是否真实存在） |
| `output digest` | **结构化事实一致性**（摘要断言与台账事实是否冲突） |
| `post cursor citations` | —— |

**三条硬性**：

1. **不得用「摘要说无阻塞、随后触门」这类跨时点比较作为误报指标**——状态可能在摘要之后合法变化。改为**按 `cursor_range` 截止时刻的结构化事实对账**。
2. **关键决策不得只依赖摘要**：解封决策时调度者**必须能看原帖**。**摘要是加速器，不是唯一依据。**
3. **不得声称「可复算：重跑核对」**——LLM 非确定性，重跑得到的是另一个输出。改为**存证 + 引用校验**。

### 20.1 租户级周工作进展汇报（v3.0 新增）

**每周以租户为单位输出。**

| 维度 | 规定 |

# 第七部 · 身份、租户、权限与授权

## §21 身份模型

### 21.1 三级映射

```
  人（企业 IM 身份验证）
   └─→ 租户（业主级隔离域，RLS 主体）
        └─→ 会话 / Agent（执行主体，持 token）
```

**审计与授权挂在人身上，执行挂在会话身上。**
这不是「加个登录页」——它是 per-session principal（§7.1 P1）的完整形态。

### 21.2 因子分级

| 角色 | 平台 | 身份锚 |
|---|---|---|
| **主因子**（回答「你是谁」） | **飞书 / 企微 / Slack / Google Chat** | **企业目录账号**，可接 SSO，**可被企业吊销** |
| **次因子**（回答「是不是本人」） | SMS / 邮件 | 电话 / 邮箱 |

**WhatsApp 不参与身份识别**，仅作通信渠道（§27）——其身份锚是电话号码，与 SMS 次因子同链路。

### 21.3 双因子不等于双人

| 机制 | 回答 | 挡得住 | 挡不住 |
|---|---|---|---|
| **双因子** | 是不是**你本人** | 冒名、消息伪造、账号单点失陷 | **本人被骗 / 判断失误 / 被胁迫 / 内部越权** |
| **重两签** | 这件事**该不该做** | 单人误判、单人越权、单人被胁迫 | —— |

> **二次验证做到极致，仍然只有一个人在决定。**
> 高危操作须重两签，依据不是「因子弱」，而是**单人不足以承担其后果**。

### 21.4 渠道账号与人的绑定（v3.0 新增）

> §21.1 的三级映射把「人」当成已解析的单一实体，但未说这个实体**怎么从多个渠道账号里认出来**。
> **P1 解决的是「这个会话是谁」，不解决「这个『谁』和那个『谁』是不是同一个人」。**

`platform_subject` **平台内唯一、不可变、不复用**。

**三条合并路径**：

| 路径 | 条件 | 可自动 |
|---|---|---|
| **A · IdP 断言** | 两渠道均由**同一企业 IdP** 断言**同一 subject**（`sub`/`employeeId`） | ✅ 可自动——企业目录本身是权威源 |
| **B · 显式绑定** | 三要件缺一不可：① 由**已认证的主身份在强身份面发起**（不是从新渠道发起）② 新渠道出示**一次性 challenge 所有权证明** ③ **双向确认** | 须人工 + 落账 |
| **C · 禁止** | 🔴 按**邮箱 / 手机号 / 显示名相同**自动合并 | ❌ 永不允许 |

**C 的理由**：§21.2 已定邮箱与 SMS 是**次因子**。用次因子做合并键 = **让弱因子决定强身份** ——
谁控制那个邮箱就能把渠道挂到已有身份上。**那是账号接管，不是账号合并。**

#### 21.4-1 路径 A / B 的可验证绑定要求（v3.1，SA-03）

| 路径 | 必须校验 |
|---|---|
| **A · IdP 断言** | 精确 **issuer + tenant** · 已验证断言的 **audience** · subject **稳定且不可复用**的语义 · 🔴 **IdP 账号重分配的 revoke / rebind 流程**（同一 `sub` 被分配给新人时必须解绑） |
| **B · 显式绑定** | challenge 须绑 **`platform_subject` + 目标渠道账户 + 请求目的 + 短有效期 + 单次 + 代际**；🔴 **确认双方不得复用同一会话或同一受损因子** |

> 仅有「一次性」与「双向确认」**不足以**防 challenge 换绑、重放到另一账户、或弱因子闭环确认。
> 上述字段与流程须落成 schema 与负测，否则「三条路径穷尽且安全」不成立。

**B 第 ① 要件的理由**：**新渠道不能批准自己的绑定**，否则攻击者拿下任一弱渠道即可自助挂入已有身份 ——
**拿下一个弱渠道 = 获得该人全部权限**。同 §24.2a：**提案方不能是批准方。**

#### 21.4a 🔴 合并身份 ≠ 合并渠道强度

**直觉做法（错的）**：这人已通过飞书强验证，故其任一已绑渠道都算强身份。
**后果**：**最弱渠道继承最强渠道的信任** —— 外部 workspace 一被攻破，等于拿到企业级权限。

> **正确做法：身份是同一个，但每次授权按【本次实际使用的渠道】的因子强度判。**

| 本次经由 | 可终结的授权档 |
|---|---|
| 飞书 / 企微 / Slack / Google Chat（企业目录） | 低危可终结 · 中危 + 次因子可终结 · **高危仍只能发起** |
| 已绑但外部 workspace | 低危可终结 · **中危须回主渠道** · 高危只能发起 |
| SMS / 邮件 / WhatsApp | **不可发起任何授权** |

🔴 **渠道必须是每次授权决策的【输入】，不只是审计字段**（v3.1，SA-02）：

| 位置 | 要求 |
|---|---|
| 授权凭据 / 待决项 / challenge / gate-verdict 的 **schema** | `channel_id` · 可信 issuer · 因子/assurance · **绑定代际** 列为**必填且被签名覆盖** |
| 授权策略求值 | **必须拒绝缺失 / 未知 / 已吊销的渠道**；显式以 §21.4a 矩阵为约束 |
| 恒零计数器 | 「授权决策**输入中缺 channel**」数、「按 `platform_subject` 求值而未判渠道」数 |

> ⚠️ **只把渠道写进审计是事后可见性，不是事前授权闸。**
> 若授权服务只按 `platform_subject` ＋ 角色 ＋ 风险档求值，
> **已绑的外部 workspace 会被当作同一人的强渠道**，从而终结本应回主渠道的中危授权。

🔴 **审计必录「经哪个渠道」** —— 否则事后分不清「从企业飞书批的」与「从外部渠道批的」，
而这两件事的可信度完全不同。**审计挂在人身上（§21.1），但渠道来源是必录字段。**

#### 21.4b 解绑与吊销

| 项 | 规定 |
|---|---|
| 解绑严格度 | **与绑定同级**，由主身份在强身份面发起；若解绑的是主渠道，**须先指定新主锚，不允许身份无主锚** |
| 企业吊销 | 企业目录账号被吊销 ⇒ **该渠道绑定立即失效**（这正是选企业目录作主锚的原因） |
| 🔴 历史审计 | **解绑不得重写历史审计** —— 已发生的授权是事实，解绑只影响此后。**否则解绑会变成一条抹除痕迹的路径** |
| 紧急处置 | 渠道疑似失陷 ⇒ 走 §24.3a **单调收紧**：`revoke` 该绑定。**不允许经紧急通道新增绑定** |

## §22 租户与隔离

### 22.1 租户是外层硬边界，fail-closed

#### 22.1a 🔴 tenant 必须由服务端从可信 principal 派生

> **禁止从客户端输入、信封自述字段、请求参数或任何调用方可控来源取得 tenant。**
> tenant **只能**由服务端依据**已通过 §7.1 P1 校验的 per-session principal**派生。

**理由**：若 tenant 可由调用方自述，RLS 的全部策略都建在一个调用方可控的值上——
**整套隔离形同虚设，且失效时无任何报错**（策略照常执行，只是执行在错误的租户上）。

| 要求 | 说明 |
|---|---|
| 派生源 | 已验证 principal → 服务端映射表 |
| 缺 principal | **fail-closed**，不得回退到默认租户或匿名租户 |
| principal 到 tenant 多对一 | 允许；**一对多须显式选择且落账**，不得静默取第一个 |
| 计数器 | 「tenant 取自非派生来源的请求数」应恒为 0 |

#### 22.1b 其余边界

- 缺租户上下文 → **默认拒**
- 跨租户 → **默认拒**，白名单放行（须满足 §22.1c）
- 解封阶梯收敛到租户内

#### 22.1c 🔴 跨租户白名单不得成为旁路

> ⚠️ **v2.3 新增（评审方指出）**：仅写「白名单放行」而不约束白名单本身，
> **白名单会退化为一条合法旁路**——它绕过的正是 §22.1a 想守的那条边界。

> 🔴 **v2.5 再次收窄（复审指出，本席核实成立）**：v2.3–v2.4 的四元组
> `(源租户, 目标租户, 操作, 有效期)` **仍然过宽**——缺 principal / 资源范围 / 用途 / capability 身份。
> **一个抽象的 `read` 或 `export` 操作仍可覆盖整个目标租户。**
> 且它与已 PASS 增补件中「跨租户广播须独立 `platform_notice` capability、不得以白名单旁路」
> **不完全对齐**。

**改为：白名单只作 capability policy 的【索引】，不作直接放行依据。**

| # | 硬性约束 |
|---|---|
| 1 | 🔴 **放行由 guarded capability 执行，不由白名单执行**。白名单只用于查找「有没有这条 policy」 |
| 2 | 每条 policy **必须绑定六项**：**源 principal / service role** · **目标资源范围**（不得是整租户）· **typed capability / op**（不得是抽象动词）· **用途** · **有效期** · **capability identity** |
| 3 | **禁止通配**任一项；**禁止按「租户对」整体放行** |
| 4 | **必须有有效期**，到期自动失效，不得无限期 |
| 5 | 🔴 **capability 自身须做幂等、审计与数据最小化**——不得只在入口判一次就放行整条链路 |
| 6 | 🔴 **跨租户通知继续只走 `platform_notice` 独立 capability**，**不得回退为通用白名单** |
| 7 | policy 的新增与延期属平台域基线变更，走 §24，且按 §24.2a **属高危项，整批升重两签** |
| 8 | 每次实际使用**逐次落账**（源 principal、目标资源、capability、用途、时刻） |
| 9 | 计数器：「经通配、缺有效期、或缺六项绑定中任一项的 policy 放行的跨租户请求数」应恒为 0 |

### 22.2 存储隔离的最低配套

> ⚠️ **本节以 C.3 的存储选型裁定落地为前提**（v3.1 补）。C.3 三方案并列**未单裁**，
> 下表是**「若裁 PG + RLS」的配套**；若最终裁「每租户独立库」或「受控仓储 API」，本节须整体改写。
> **不得据本节反推存储选型已定。**

#### 22.2a 与形态无关的三条（任何方案都须满足）

| # | 要求 |
|---|---|
| 1 | **缺租户上下文默认拒**（fail-closed） |
| 2 | **跨租户默认拒**，须经 §22.1c 的 guarded capability |
| 3 | **必须有越权负测**：伪造 tenant、跨租户读、缺 context 三类各一 |

#### 22.2b 若裁 PG + RLS 的配套

**RLS 不是「自动的机制」，它自己也需要一套纪律。配错即失效。**

| 必做 | 说明 |
|---|---|
| `ALTER TABLE ... FORCE ROW LEVEL SECURITY` | **表 owner 默认可绕**，不 FORCE 即无效 |
| **每事务 `SET LOCAL`** | 用会话级 `SET` 会把租户上下文泄漏给下一个借用连接者，**且恰在高并发下才暴露** |
| 最小权限 runtime role，**不得带 `BYPASSRLS`** | —— |
| **缺 context 默认拒** | 漏设即泄漏 |
| 所有关联表与间接查询策略 | 含 view / `SECURITY DEFINER` 审查 |
| 跨租户 admin 独立角色 | —— |
| **负测** | 必须有「越权查询被拒」的测试 |

### 22.3 ops 两类

| 类 | 职责 |
|---|---|
| **平台级 ops** | 生产系统、平台运维、**公共资源**（含平台级 skill / MCP / spec 模板） |
| **租户级 ops** | 本租户的业务模块开发、测试环境等 |

### 22.4 凭据分级

| 级 | 范围 | 纪律 |
|---|---|---|
| **S0** | VPN 凭据、签名私钥、根证书 | **不落任何文档、帖子、流、日志** |
| **S1** | 生产（不可重置） | 严控，按需授权 |
| **S2** | 沙盒 / 研发测试（可重置） | 常规 |

**判据是「爆炸半径可否重置」，不是「看起来敏感不敏感」。**

**默认按不放松执行**；对**有安全基座、不影响生产的研发测试系统**可适当放宽，
放宽须**以环境属性为条件显式声明**，不得默认放宽后再逐个收紧。

### 22.5 敏感内容识别（v3.1 新增 —— 本席交界对撞产物）

> 规范有**三处**「敏感内容不得进入」的硬约束：§22.4（S0 不落任何文档/帖子/流/日志）·
> §25.7（附件须内容扫描定级，S0 一律拒收）· §26.4.1（工单不含 `credentials`）。
> **但从未定义「什么算敏感内容」的判定机制** —— 三处都写成「不许进」，
> **没有一处回答「怎么认出它是它」**。
> ⇒ 这类约束在实现时只能退化为人工自觉，**正是 §29 反对的那种「假装被管住了」**。

| # | 规定 |
|---|---|
| 1 | **判定对象**：文本 · 结构化字段 · 附件（含视频抽帧）· 工单/表单任意字段 · 日志与错误信息 |
| 2 | **判定形态**：模式匹配（IP / 私钥头 / token 形态 / 主机名）＋ 词表 ＋ 结构启发（高熵串） |
| 3 | 🔴 **fail-closed**：**判不准时按更高密级处理**，不得放行 |
| 4 | **判定点分【入站】与【出站】两类**（v3.2，SA-08）：<br>**入站**＝入帖子流前 · 入知识库前 · 入工单前 · 上传前<br>**出站 A · 应用层**＝应用日志 · 错误与异常 · 审计流 · trace/span · scanner 自身遥测 · **§25.4.5 紧急面本地审计**；另 **scanner 自身失败 · 异常 handler / stack trace · audit sink 自身的错误**，一律先过同一 pre-sink |
| 4a | 🔴 **出站 fail-closed 须分层**：<br>**紧急面审计**判定失败 ⇒ **拒绝该条指令或中止后续动作** —— fail-closed 作用在**被审计的动作**上，不只作用在记录上，否则「执行成功但无审计」即旁路<br>**普通应用日志** ⇒ 可丢该条原记录，**但须产安全健康告警**（告警不含输入与匹配内容）<br>**审计流 / trace / 遥测** ⇒ 同紧急面：**宁可不做，不可无痕**<br>**判定器不可用不得静默降级为放行** |
| 4b | 🔴 **出站 B · 基础设施层（v3.3，SA-09）—— pre-sink 管不到，须另一套机制**：<br>**edge / 反代** access log · error log（记 **URL 含 query · header · cookie**）· **宿主** systemd/syslog · **容器与编排日志** · **外部日志 collector**。<br>⚠️ **它们在应用之前或之外记录**，判定器拦不住 ⇒ **不得靠把它们加进 #4 的清单来解决**。<br>**三条硬性**：① **日志字段白名单，默认遮蔽 `Authorization` · `Cookie` · 全部 query string** ② **敏感值不得置于会被 B 层记录的位置**（见 §25.4.2） ③ **每层各出配置级负测**：构造含敏感值的请求，验证不入任何一层日志 |

## §23 授权

### 23.1 审批的两个轴，并存取严

> ⚠️ **v2.3 更正（评审方指出，本席原表述过度极端）**：
> v2.1–v2.2 写「审批层级**不由**数据敏感度决定，**而由**是否事先声明决定」。
> **该表述会让一句预声明把 S0/S1 级访问降成低危**——预声明是**流程事实**，
> 它改变不了**爆炸半径**这一客观事实。

**正确表述：两个轴并存，各管一件事，取更严者。**

| 轴 | 决定 | 取值来源 |
|---|---|---|
| **预声明** | **审批【路径】**——走谁、几步、是否需临时申请 | spec / 运维预案中是否事先声明（§23.2、§23.4） |
| **敏感度与爆炸半径** | **审批【层级】**——单签 / 双因子 / 重两签 | §22.4 凭据分级 + 数据分级（S0/S1/S2） |

**判定规则**：

1. **有预声明** ⇒ 路径为「项目管理方逐次判断」，**无须每次找业主**
2. **无预声明** ⇒ 路径升为「业主授权」
3. 🔴 **无论有无预声明，层级仍由敏感度与爆炸半径独立决定**——
   **触及 S0/S1、跨租户、平台域基线者，即使已预声明，仍须按 §23.5 的对应层级审批**
4. 二者冲突时**取更严**

> **一句话**：**预声明能省掉「找谁批」的往返，省不掉「批到什么份上」。**

### 23.2 spec 预授权

| # | 规则 |
|---|---|
| 1 | spec 预授权**须经评审** |
| 2 | **仅在产品定义后 ~ 上线前（研发测试阶段）有效** |
| 3 | 🔴 **产品上线后，spec 作用域失效，须另行授权** |
| 4 | 有效期内**仍须项目管理方逐次判断**（预授权是必要不充分条件） |
| 5 | **无预授权则须业主授权** |
| 6 | 预授权**必须具体**：范围 / 用途 / 时限。**禁用「可能」「视情况」「相关」等不可判定表述，笼统兜底视同无预授权** |

### 23.3 失效由机制触发，不靠人记得

**发版收口（§8.2 第 2 项）同一事务内将关联的 spec 预授权标记 `expired`。**

⚠️ **粒度**：失效须按**「spec 预授权条目 × 其声明的作用域」**判定，**不得按 task_id 一刀切**——
子 spec 收口不应连带失效父 spec 下其他仍在研发期的子 spec。

### 23.4 上线后由运维预案承接

**授权文档随阶段交接**：

| 阶段 | 授权文档 |
|---|---|
| 产品定义前 | 无 → **业主授权** |
| 定义后 ~ 上线前 | **spec 预授权** |
| **上线后** | **运维预案 / 生产访问规范**（知识库第 8 类，§12.4） |

两者形式对称：**都须经评审、都不自动放行、都须具体到范围·用途·时限。交接点就是上线。**

### 23.5 渠道授权分级

| 级别 | 范围 | 渠道可做到哪一步 |
|---|---|---|
| **查询** | 项目进展（只读，**须走 RLS 过滤后返回**） | 可信渠道即可 |
| **低危** | spec 预授权范围内的一次读取、复盘定稿、**L1 级 node 的门 PASS** | **渠道可终结**（+ 一次性挑战码） |
| **中危** | 单会话 provision、租户级 skill 晋升、跨项目读 | 渠道**可发起**，须**次因子确认** |
| 🔴 **高危** | 全网批量下发、平台级 skill/MCP 晋升、跨租户、S0/S1 凭据、平台域基线变更、**L3 级 node 的门 PASS** | **渠道只能发起，不能终结**；须回强身份面 + **重两签** |

> ⚠️ **门 PASS 不可统一归为低危**（v2.3 更正，评审方指出）：
> **门 PASS 的危险度继承其所属 node 的分级**——
> 一个 L3 node 的架构评审门 PASS，其后果与该 L3 变更等价，**不因「只是打个勾」而变低**。
> ⇒ **规则：门 PASS 的授权层级 = 该 node 的分级层级（L1→低危 / L2→中危 / L3→高危）。**

**授权动作必须绑定一次性凭据**：平台生成 challenge（含**待批事项摘要 + 有效期 + 单次使用**），
业主回复该 challenge 而非自由文本。

> 🔴 **「同意」两个字不构成授权**——它可被重放、可被群内他人冒名、
> 也可能是 Agent 把引用的历史文本当成了新指令。

## §25 界面与入口

### 25.1 审批入口 = 单一 typed 待决队列

**不做成多个页面。** 授权、阻塞、无效讨论的共同点是「**都在等一个人做决断**」；
做成 N 个入口，就要巡 N 个地方才知道有没有事。

| 类型 | 数据来源 | 决断者 |
|---|---|---|
| 授权待批 | spec 预授权、平台域资产下发、上线后运维预案授权 | 按 §23 分级 |
| 当前阻塞 | `blocker_reason` 枚举 + `sla_deadline` | 项目管理方 |
| 无效讨论 | §18.4 解封请求 | 调度者 / 业主 |
| 门 FAIL 待整改 | 门记录 | 执行者 + 门方 |
| 复盘待定稿 | §9 | 执行者 |
| 平台域批次待签 | §24.2 | 平台管理者 |

**每项必带**：类型 / 发起方 / **等待时长** / **逾期标记** / 一键决断入口。

> **「等待时长」是关键字段**——按它排序，直接把「任务丢失、环节丢失、交付物丢失」变成显眼的逾期项。

**所有高危执行面必须从该队列取授权凭据**，不得自带审批。

### 25.2 知识查询入口

- 覆盖 §12.1 全部条目类型
- **必须走 RLS + 条目级分级**，禁止做成「登录即可全文检索」
- **检索在 RLS 过滤后的集合上做**（§13.4）
- 显示条目的 **全部 `anchors[]`**、`updated_at`、生命周期状态（`active`/`suspect`/`archived`）

### 25.3 交付物与规范查阅入口（v3.0 扩）

**与知识库分开**——知识库是**事实**（现状是什么），本入口是**规范与交付物**（约定应当是什么、实际交了什么）。

**覆盖七类**：spec · 设计方案 · 测试用例设计 · 实现（代码变更）· 测试报告 · 交付验证记录 · 复盘。

> 🔴 **必须按任务 / 版本组织成【链路视图】，不得分成七个列表。**
> 理由与 §25.1 同源：**分成七个入口，就要巡七个地方才知道哪一环缺了。**

**每行须显示**：交付物 · **锚与规模**（件 / sha256 / 行数＋字节，即 §6.1 回执五要素的机器可验部分）· 门 · 门方。
**第五要素「门结果 ＋ 失败最小复现」需要人**，故门与门方单列。

- **spec 须另显示**：版本 / 评审状态 / 预授权条目及作用域 / 生命周期状态（§4.3）
- **架构设计文档须另显示**：所处评审等级与已过的门
- **链路视图同时是交付物锚的来源**（§13.2）

### 25.4 直连 Agent 的交互通道（v3.0 重写）

> **v2.x 原文两行**：「不砍 view 页，sidecar 常开做旁路。理由：平台故障时……」
> **该句把两个断言捆在一起，却只给了 sidecar 的理由** —— view 页本身是平台的一部分，平台挂了它一样挂。
> **业主 2026-08-24 裁定：砍 view，仅保留 sidecar。** 本节据此重写。

#### 25.4.1 两个入口

| | 常规交互面 | ops 紧急对话面 |
|---|---|---|
| 经过 | 平台 | **不经平台** · 跑在 sidecar 上 |
| 身份 | 三级映射（§21.1） | 三级映射**不可用**（平台可能已挂） |
| 凭据 | 不需要额外的码 | **临时 web 密码**（带外） |
| 平台故障时 | 不可用 | **仍可用** —— 这是它存在的全部理由 |
| 能力 | 全量（按角色与授权） | **收窄**（§25.4.4） |

> **为什么紧急面用密码不算倒退**：**常规面**身份基础设施在线，**有身份却不用、改用一个码**，那是缺陷（原 view 页的 unlock 即此）；
> **紧急面**平台已挂，三级映射**本来就不可用** ⇒ 必须有带外凭据。
> **同一个机制，前提不同：一个是漏洞，一个是必需。**

#### 25.4.2 访问路径与鉴权

| | 路径 | 鉴权 |
|---|---|---|
| **云端** | 浏览器 → **Nginx（统一鉴权）** → 会话宿主 `127.0.0.1:port` sidecar | **在 Nginx 层做** |
| **本地** | 浏览器 → `127.0.0.1:port` 直连 | **无需 Nginx 转发授权**（已在本机物理边界内） |

**前提（代码已成立）**：sidecar **只绑 `127.0.0.1`**，裸端口从公网不可达。

🔴 **鉴权须认得出「是谁」**：共享静态凭据（如 HTTP Basic）**与 §21 三级映射不接**——
它认的是「知道这个密码的人」，不是「哪个人」，§21.1「审计与授权挂在人身上」落不了地；
且**共享凭据下任一持有者可访问任一会话的 sidecar**。

**⇒ 规定**：Nginx 校验**平台签发的会话级受限令牌**，**不复用平台会话 cookie**：

| claim | 说明 |
|---|---|
| `platform_subject` | 谁 |
| 🔴 `target_session` | **限定到单个会话** —— 一处泄露只影响那一个 |
| `scope` | 如 `sidecar.interact` |
| `channel` | 本次经由（§21.4a） |
| `exp` | **分钟级** |

**同 §22.1c 的思路：不给通用凭据，给限定作用域的能力。**

🔴 **但 `target_session` 单独不构成保证（v3.1，SA-05）。令牌验证须同时满足**：

| # | 要求 |
|---|---|
| 1 | **issuer / audience 校验** ＋ **签名验证** ＋ **密钥轮换**方案 |
| 2 | `target_session` **规范化后精确匹配**，不得前缀或模糊匹配 |
| 3 | `scope` **映射到具体 HTTP method 与 sidecar capability**，不得是抽象动词 |
| 4 | **令牌换发本身须做授权检查**（不得凭旧令牌无条件续期） |
| 5 | **replay 防护 ＋ session-generation 绑定**（会话换代后旧令牌立即失效） |
| 6 | 🔴 **令牌不得置于 URL / query string**（v3.3，SA-09）—— 仅允许 `Authorization` header 或 `HttpOnly` cookie。<br>理由：**URL 会被 edge access log · 浏览器历史 · Referer 头 · 代理链逐层留存**，而这些位置**全部在应用 pre-sink 之外**（§22.5 #4b） |

#### 25.4.2a 🔴 两条路由必须在配置上分开，且不可互相降级

> v3.0 先写「Nginx 校验平台签发令牌」，再抽象地说「紧急路由不依赖平台应用层」，
> **没有明确紧急路由【不使用】该令牌**。与原型合读会得出「平台挂了就无法新登录」的相反解释。

| 路由 | 契约 |
|---|---|
| **常规** | 消费平台签发令牌，须满足上表五条；**平台不可用时该路由不可用**——这是可接受的 |
| 🔴 **紧急** | **不消费平台令牌、不访问平台应用层**；Nginx **只做固定会话的转发**，认证**全部在 sidecar 本地**完成 |

**验收判据**（E.3 须覆盖）：**平台完全不可用、且事先无任何有效令牌时，紧急路由仍能完成认证**；
并**负测两条路由不能互相降级或越权**（常规路由不得回落到本地密码；紧急路由不得获得常规路由的 scope）。

**连带四条**：① cookie 用**同域路径前缀**，**不放宽 `Domain`**（放宽则该域下所有服务都能拿到）
② `SameSite=Strict` ＋ `HttpOnly` ＋ CSRF token（sidecar 端点**有副作用**）
③ 无状态令牌**签出去撤不回** ⇒ 分钟级有效期；**高危操作不靠此令牌**，仍走待决队列与重两签
④ 🔴 **Nginx 的紧急路由不得依赖平台应用层** —— 否则平台一挂全拒，云端紧急通道等于不存在。
**两条路径在 Nginx 配置上就要分开。**

#### 25.4.3 临时密码的生成与取用

**核心约束：密码不能只存在平台侧**——平台挂了还要靠平台校验，这条通道就是假的。

| 环节 | 做法 | 平台挂了 |
|---|---|---|
| 生成 · 轮转 | **本机 sidecar 本地**，写入仅 ops 可读的本地文件 | ✅ |
| 取用 · 本体 | **宿主本地读取** | ✅ |
| 取用 · 便利 | 平台在线时镜像一份到 ops 的强身份渠道 | ❌ 仅在线可用 |
| 校验 | **sidecar 本地校验，不回平台** | ✅ |
| 吊销 | 在线可远程吊销；离线以本地轮转为准 | ✅ 降级但可用 |

⚠️ **便利路径不得成为唯一路径**，否则退化为「平台好的时候才能用的应急通道」。
**须限速 + 失败锁定 + 每次尝试本地落账。**

#### 25.4.4 🔴 紧急面能力必须收窄

该面绕开平台**全部**管控（无三级映射、无 RLS、无出站闸、无待决队列、无重两签）。
**若它是全权的，它就是一个带密码的后门。** 按 §24.3a 同一逻辑：**只允许单调收紧**。

| 允许 | 禁止 |
|---|---|
| 查看状态 / 日志 / 水位 · 只读诊断 · `disable`/`quarantine`/`revoke`（须有 fail-closed fallback）· 重启本会话 · 与 ops-Agent 对话让它去恢复平台 | 安装或升级制品 · 签发凭据 · 新增或放宽 policy · 跨租户 · 收口 / 签门 / 批批次 · 读 S0/S1 · 改 immutable 件 |

**判据仍是 capability effect，不是动作名。存疑即拒。**

#### 25.4.4a 🔴 输出面与间接执行同样须收窄（v3.1，SA-06）

> **本席在本节自我违反了自己刚立的判据**：写着「判 capability effect 不判动作名」，
> 却把「查看日志」与「与 ops-Agent 对话」作为**宽泛能力**放行 ——
> 而这两个动作的 **effect 是无界的**。§14.5 自己已写明日志可能含 token / IP。

| 面 | 收窄要求 |
|---|---|
| **只读输出** | 声明**固定字段集 ＋ 脱敏器**；日志有**条数与时间窗上限**；🔴 **禁止原始文件 / 环境变量 / secret / 下载** |
| **诊断命令** | 只允许**显式 allowlist** 的只读命令；输出同样过脱敏器 |
| 🔴 **与 ops-Agent 对话** | **只能调用显式 allowlist 的恢复 capability**；由 **sidecar 侧做 effect gate ＋ target 绑定**；自由文本**不得直接转成工具调用** |
| 代理网络访问 | **禁止**——否则可经 Agent 间接达成跨租户读取或对外请求 |

> 「让 ops-Agent 去恢复平台」仍**允许**，但它给的是**「够到它」**的能力，不是**「替它做决定」**的能力，
> **更不是「借它的手做紧急面自己不许做的事」**。
> ⇒ 上述路径须加入 E.1 / E.3 负测。

#### 25.4.5 🔴 离线期间的审计

**不能因为平台挂了就没有审计**，否则「**先把平台弄挂，再走紧急通道**」就成了一条**清空审计的路径**
（同 §21.4b「解绑不得重写历史审计」）。

| 项 | 规定 |
|---|---|
| 离线期间 | **本地 append-only 落账**：登录尝试 · 每条指令 · 每个结果。<br>🔴 **写入前须过 §22.5 判定器**，命中即以元数据替代原值入账；<br>**判定失败 ⇒ 拒绝该条指令或中止后续动作**（§22.5 #4a），不得「执行了但没痕迹」 |
| 判定器位置 | 🔴 **须为 sidecar 本地实现，与紧急面同生共死，无任何远程依赖** —— 不得因「平台已挂，判定器可能不可用」而跳过 |
| 平台恢复后 | **强制回传补账**；**回传前该 ops-Agent 不得领新件** |
| 计数器 | 「紧急通道使用后**未完成回传补账**的次数」应恒为 0 —— **这是「先弄挂再操作」的探测点** |
| 事后 | 每次启用**必须进入下一批次补审**（§24.3 事后 flag 制，不新造通道） |

#### 25.4.6 原生交互的适用范围（业主定）

**Agent 原生交互只用于两类场景，其余走帖子流**：

| 场景 | 为什么帖子流不够用 |
|---|---|
| **ops 场景** | **平台可能已挂，帖子流不可达**——它本身就在平台上 |
| **开放性讨论**（产品定义 · 架构探索 · 技术探索） | 需要**快速来回**、**多模态**、**不受条数闸约束**——帖子流的**形态**不适合探索式对话 |

⚠️ **待裁**：本席建议**开放性讨论仍应落帖子流** —— 帖子流对讨论不适合的是**形态**，不是**记录**；
若讨论完全不落账，**「作业无痕」就从这个口子回来了**（§17）。
**原生交互是【输入形态】，帖子流是【记录形态】，不是二选一。**
落法现成：§18.4 的**「开放讨论型」node**（阈值放宽或不设，豁免须落账，不得由执行方自行标记）。

### 25.5 Agent 名册（v3.0 新增）

§26 只定义了**管理动作**，未定义「**看它们在干什么**」。本节补：

**须显示**：会话 · 形态 · 角色 · 凭据级 · **项目** · 当前 node · 水位 · 状态（`active`/`idle`/`silent_notice`/`restarting`/`dead`）。
**受项目维度筛选**（§25.9）。

🔴 **`starved`（执行席 ≤2 占满）与「无人愿接」必须在界面上分得开** —— 否则会被读成团队不配合。
**`dead` 后由引擎换代重派**，不靠人发现。

### 25.6 Agent 工作面（v3.0 新增）

一个 Agent 自己看到的面。**须含**：

| 区 | 要点 |
|---|---|
| 我的任务清单 | 🔴 **「每次一项闸」须提前显示**——名下有 `in_progress` 时新件的拉取应先灰掉，**而不是点了才回 409** |
| 派发信封 | **§11.6 全部快照字段逐项显示齐否**——缺任一即无效派发、执行小组拒接，**该判据必须可见**。<br>⚠️ **不写死数量**（v3.5 删去原写「现为 6 项」，属 E.3 #36a 的远端计数引用）：字段集随 §11.6 变，界面按该节枚举渲染 |
| 我的阻塞点 | 六值枚举，🔴 **每行必须给出「谁能解」**——阻塞不是「我干不动」，是「引擎判定此处需要外部动作」 |
| 我该读什么 | 引擎推增量、不轮询；封锁时**停注入但仍可读固定 snapshot** |

### 25.7 多模态交互与上传（v3.0 新增）

支持图 / 文 / 视频 / 文档上传。**六项治理**：

| 项 | 规定 |
|---|---|
| 存哪 | 对象存储（§26.4 资源池）；**对话与帖子流内只留引用 ＋ sha256**，不内联 blob |
| 🔴 密级 | **上传前须内容扫描定级**。一张运维截图可能含**主机 IP / token / 拓扑** ⇒ 属 S0，而 §22.4 定 S0 **不落任何文档、帖子、流、日志**，对话入帖子流 ⇒ **直接违反**。**S0 一律拒收**。⚠️ 改指处**不是知识库** —— §22.4 定 S0 不落任何文档、§11.4 定运行态不入知识库；含 IP/token/拓扑的截图类内容**正确归处是 §14.5 受限 MCP 查询面** |
| 跨租户 | 附件继承所在 node 的租户，**禁止跨租户流动**（同 §15.3：**RLS 管数据表，管不到一张图里画了什么**） |
| 入 digest | **附件必须入封存 digest**（§18.1 列表已定），否则换掉一张图而 digest 不变 |
| 视频处理 | 自动抽帧供模型读；**抽帧结果是派生物**，同样受密级与租户约束，**不得因「只是缩略图」而降级** |
| 体积闸 | 单文件上限 + 单 node 累计上限；**超限不静默截断，明确拒收并说明** |

**view 页已砍**（§25.4）。其常规交互职能由主界面内的 Agent 对话面承担，**unlock 面随之消失**。

> 顺带关闭一条历史悬项：`VS_AUTO_UNLOCK` 曾默认为 `"1"`、自动 POST `{"code":"0000"}` 到 mock-unlock 端点；
> 其当时不可用是**组件不匹配的意外，不是配置**。**砍掉 view 后不需要设 0 了，因为没有那个开关了。**

**项目是界面层的一等分组筛选维度**，作用于：Agent 名册 · 看板 · 待决队列 · 交付物链路 · 知识检索 · 帖子流。

数据面本已具备（`KBDoc.Meta.project`、`TaskDims{Project, Stage, Version}`），**界面层此前未用上**。

## §26 Agent 管理

### 26.1 三种接入形态，信任等级不同

| 形态 | 宿主受控度 | 凭据等级 |
|---|---|---|
| **云上 Agent**（平台新建/关闭/重启） | 平台完全受控 | 可持 S1，按角色授予 |
| **IDE 插件 Agent** | 企业设备，部分受控 | S2 为主；S1 须显式授权 + 时限 |
| 🔴 **本地笔记本 / 台式机 CLI** | **不受控终端** | **默认仅 S2**；S1/S0 须逐次授权 |

**本地接入的 token 必须**：短时效 + 可远程吊销 + 绑定设备指纹；**默认不授予**跨租户与平台域读权。

> 本地终端接入意味着平台凭据离开可控边界，落到平台无法审计、无法擦除的机器上。
> **不设此限，凭据分级会在最薄弱的一环失效。**

### 26.2 导入上下文 = 分层注入

```
新建 Agent(tenant=T, project=P, role=R)
  → D0 平台级知识库 全量
  + D1 业务级（T 所属业务线，检索式）
  + D2 租户级（T，检索式）
  + D3 项目级（项目 P，检索式）
  + 版本 / 任务上下文（角色 R 的作用域）
  ⚠️ 运行态不注入 —— 需要时经 MCP 查（§14.5）
  + 已批准 skill：按 §15.1b / §15.1c 的分发形态（D0/D1 push · D2 依 mandatory 判 push 或 pull）
```

**沉淀与注入必须同源**（§10），否则会出现「复盘写进了知识库，新 Agent 却读不到」。

### 26.3 管理面新建，下发面复用

**管理面**（新建 / 关闭 / 重启 / 上下文注入决策）属项目/任务侧内核，**新建**；
**下发面**（把 skill / MCP / 代码推到远端）**复用现有 provision 通道**。二者分层，不重复造。

### 26.4 运行环境供给与资源池（v3.0 新增）

> §26 此前只有三形态的信任与凭据等级、K 层与 skill 的注入、管理面/下发面分工。
> **缺的是「Agent 靠什么真的跑起来」**——注入了知识与 skill，但连不上模型端点、clone 不了仓库、
> 没有可写沙盒，**Agent 仍然干不了活**。

#### 26.4.1 工单：只有引用与范围，没有凭据

**新建 Agent 经工单提交，从资源池引用环境。**

🔴 **工单结构上不含 `credentials` 键，且不允许存在。**
理由：§22.4 定 VPN 凭据 / 签名私钥 / 根证书为 **S0——不落任何文档、帖子、流、日志**；
而工单是一份**会流经审批并落账**的记录。
**照常识画的表单会有「VPN 账号/密码」输入框——那就直接违反 §22.4。**

> 按 §29 的说法：**小心处理是纪律，结构上不给它位置才是机制。**

🔴 **但仅禁 `credentials` 键不够（v3.1，SA-07）** —— 凭据可经
`description` · `reason` · 环境变量 · 仓库 URL 的 userinfo/query · 资源备注 · 附件 · 评论 · 失败日志 ·
**任意新增 JSON 字段**进入落账记录。**改个键名即可绕过。**

| # | 要求 |
|---|---|
| 1 | 工单采用**版本化 closed schema**（`additionalProperties=false`）＋ 字段白名单 ＋ 类型约束 |
| 2 | 资源**只能引用受控 ID**；🔴 **禁止任意 URL / 环境变量 / 附件 / 自由文本承载敏感材料** |
| 3 | 确需理由的文本字段，**须过 §22.5 的敏感内容识别并拒收命中项** |
| 4 | 🔴 **实例化 · 审批 · 审计 · 错误记录 · 事件流复用同一 redaction / secret-detection 闸**，不各写各的 |
| 5 | 端到端负测：把凭据分别塞进上列每一个字段，验证均被拒 |

#### 26.4.2 环境类目

| 类目 | 形态 | 说明 |
|---|---|---|
| 大模型出口 VPN · 企业环境 VPN | **企业统一资源**，**平台级 ops 统一维护** | 工单侧只决定**用不用、用哪条**，不涉及配置与凭据 |
| 对象存储 | 租户资源 | **读/写/删逐项声明**，不给整桶 |
| git 环境 | 仓库 + 提交身份 | 写权默认关；**push 到 protected branch 须另行授权**；**签名私钥须业主授权一次** |
| 开发测试环境 | 沙盒 / 准生产 | 判据是**爆炸半径可否重置**（§22.4） |
| 工作区 · sidecar 端口 · 时区语言 | 本机 | 时间统一 UTC，`date -u` 实取 |

#### 26.4.3 资源池

**资源池是引用的唯一来源，工单不得填池外资源**——否则等于绕过分级与授权。
**新增池条目本身是平台域基线变更**（§24）。

**条目模型**：`编号 · 资源 · 类型 · 授权含义 · 归属 · 谁可引用`。

> ⚠️ **「授权含义」列 ≠ 资源自身密级**：
> **企业统一资源**（VPN 等）标 `ops 域` —— **密级与配置由平台级 ops 承担，工单侧只是选用哪条**；
> **对象存储 / 环境**标 S1 / S2 —— **授权范围由工单声明**，故需按形态与权限判。

#### 26.4.4 形态 × 密级的可授予矩阵

| 形态 | 凭据上限 | 说明 |
|---|---|---|
| 云上 | **S1** | 平台完全受控 |
| IDE 插件 | S2 为主 | S1 须显式授权 + 时限 |
| 🔴 本地终端 CLI | **仅 S2** | 不受控终端；S1/S0 须逐次授权 |

**工单校验（机器判，四条）**：
① 本地 / IDE 形态请求 S1 资源 ⇒ **拒**
② 对生产对象存储请求**写权** ⇒ **高危**，须回强身份面 + 重两签（§23.5）
③ 勾选提交签名 ⇒ 须业主授权一次（私钥永不进工单）
④ 申请门方角色而席位已满 ⇒ **排队，非拒**（§4.5 执行席 ≤2）。
🔴 **界面须把「席满排队」与「无人愿接」分开显示。**

**工单提交后落入 §25.1 待决队列**，按派生凭据上限分档。

## §27 渠道接入

### 27.1 约束：不增加 Agent 多余负担

**渠道差异必须在平台侧吸收干净，Agent 只见一种统一信封。**

平台侧须消化：消息格式规范化 / 长度上限与分片重组 / 富文本与附件能力差异 /
回执语义归一 / 乱序与重投 / **幂等键贯穿**（重投不重执行）。

### 27.2 本项落在现有通信层的延长线上

## §28 工作纪律（五条）

| # | 纪律 |
|---|---|
| 1 | **行为证据优先**——断言系统行为须有可复现的行为证据，不以代码阅读或文档描述替代 |
| 2 | 🔴 **声明搜索范围，且搜索范围必须 ≥ 断言的作用域**——对包级现象的断言不得只搜单文件；对全集的断言不得只搜子集 |
| 3 | **反向克制**——撤回一个未经测量的断言时，不得代之以相反的未经测量的断言 |
| 4 | **全文复述同步**——修改一处结论时，须查找并同步全部依赖该结论的表述；**依赖点未必与复述点用同一词汇** |
| 5 | **证据不外推**——子集上的证据不得外推为全集结论 |

**一条动机层纪律**：**不得以「能落在数据上就不落在契约上」为由绕过契约成本。**
凡改变权限或产生副作用的数据变更，须承担相应的契约与审批成本。

## §29 自检通则

> **每加一条流程约束，同时加一个可观测的失效探测手段。**
> 否则约束失效了没人知道——这正是「环节丢失造成项目损失」最隐蔽的一种。

### 29.1 ⚠️ 「恒零计数器」不是唯一形态（v2.2 细化）

逐条配齐（附录 E）后发现：**并非每条约束都能配恒零计数器。** 强行都配会得到一堆永远为 0
且从未被检查的假指标。**按可探测形态分四类，各配各的手段**：

| 类 | 约束性质 | 探测手段 | 失效表现 |
|---|---|---|---|
| **I 恒零计数器** | 运行时可判定的违规 | 计数器，**本应恒为 0**，>0 即告警 | 计数上涨 |
| **II 趋势指标** | 可测但**不应为零** | 阈值 + 趋势告警 | 偏离基线 |
| **III 建成核验项** | 结构性事实，建成即成立 | **一次性核验 + 回归测试钉死** | 回归被改掉 |
| **IV 评审检查项** | 人的判断，机器不可判 | 🔴 **落入 checklist 作为门** | 门方漏检 |

### 🔴 29.1b 一条必问的检查视角：这个机制自己会不会承载它要防的东西（v3.2 新增）

> **本阶段同一模式出现五次，五处全是本席写的，写的时候都以为是在加固**：

| # | 机制 | 自身携带了它要防的东西 |
|---|---|---|
| 1 | §22.5「拒收须说明命中了什么」 | **回显 secret** |
| 2 | §25.4.5「每条指令每个结果落审计」 | **审计成了 S0 的落点** |
| 3 | §25.4.4「与 ops-Agent 对话去恢复平台」 | **恢复通道成了绕过通道** |
| 4 | §22.5 判定规则表 | **保护内网的规则本身是内网地图** |
| 5 | §22.5「判定器不可用则不写该记录」 | **动作照做、无痕** |

> **⇒ 凡新增一条防护机制，须问：这个机制自己会不会承载它要防的那个东西？**
> **且 fail-closed 要作用在【被保护的动作】上，不能只作用在【记录】上。**
>
> ⚠️ **这一问机器判不了** —— 它需要理解「这个机制在防什么」。故登记为 **E.4 人工判断项**（#54），
> 不配恒零计数器（按 §29.1 第 IV 类）。

### 🔴 29.1a 四类**不互斥**——一条约束可同时需要多种手段（v2.4 更正）

> ⚠️ **v2.2–v2.3 把四类做成了互斥分类，每条约束只归一处。这是错的。**
> 复审指出：**多数有价值的约束是复合的**——它有一个机器可判的骨架，和一个机器判不了的实质。
> 只配机器项，会放过实质；只配人工项，会放过本可自动拦截的低级违规。

**复合约束的典型形态**：

| 约束 | 机器可判的部分（I/III） | 人机器判不了的部分（IV） |
|---|---|---|
| 预授权**必须具体**（§23.2） | 三字段非空；不含「可能/视情况/相关」等禁用词 | **范围划得够不够窄**、用途陈述是否成立 |
| 跨租户晋升前**须脱敏**（§15.3） | 词表扫描：项目名/表名/内部地址/会话名 | **是否仍能由上下文反推出业务信息** |
| 解封须**回写定义层**（§18.4） | 是否存在指向 spec/constitution/规则表的引用，且该文件在解封后确有变更 | **回写的内容是否真的解决了该分歧** |
| 平台级**准入三判据**（§15.1） | 正文模式匹配是否含具体业务概念 | **移出项目后是否真的仍完整可用** |
| 复盘四段**须实质**（§9.2） | 四段是否齐、是否非空 | **是否敷衍**（「顺利完成」四个字也占满四段） |

> **规则：一条约束若同时具备机器骨架与人工实质，必须在两处都登记，不得二选一。**
> **机器项负责「拦住明显错的」，checklist 项负责「判断剩下的对不对」。**

**第 IV 类仍是关键**：把机器判不了的东西硬配成计数器，等于假装它被管住了。
其正确归宿是 checklist（reviewer-owned，§4.1）——这也是 §0.4 第 2 项必须由评审方产出的原因之一。
