# 第一部 · 总则

## §1 总纲

**整个系统是产品定义驱动、流程保障的。**（业主原话，本件第一原则）

由此派生三条：

| # | 原则 |
|---|---|
| 1 | **一旦进入项目开发，驱动的是流程引擎，而不是 Agent。** |
| 2 | **约束必须存在于上下文之外。** 存在于上下文里的约束，上下文一丢就跟着丢。 |
| 3 | **靠机制，不靠记忆。** 每加一条流程约束，同时加一个「本应恒为 0」的计数器（§29）。 |

## §2 实现路径

### 2.1 不受现有代码约束

本规范的实现**不必基于现有 DingWei 平台代码**；现有实现不满足需要时**可新开发**。（业主裁定）

### 2.2 根因：现有平台的建模中心是通信，不是项目/任务管理

| | |
|---|---|
| **现有平台** | 消息是一等公民，任务/项目是消息的附属账 |
| **本规范要求** | **项目 / 任务 / 交付物是一等公民，消息是它们的投影** |

这不是加字段能改的，是把主外键关系倒过来。可指认的事实：

- `store/migrations/0008_projects.sql` 的 `project` 表全部字段为通知路由 + 取证配置，无 spec / 里程碑 / 阶段 / 交付物 / 验收 / 任务关联
- `datad` 的 `task` 表归属维度是 `owner_session`（会话），且**无 `project_id`**
- `board/schema.sql:11` 的 `task` 表含 `origin_envelope_id`——任务的身份锚是消息的身份
- project / task 台账 / task DAG 分处三个库，零外键

### 2.3 保留 / 重建分界

> **凡建模的是「消息如何可靠传到」的，保留；凡建模的是「工作如何被定义、被验收、被追责」的，重建。**

| 组件 | 处置 | 依据 |
|---|---|---|
| provision 分发通道 | **保留** | 安全模型扎实：hub 只下发数据不下发指令；5 道闸；版本号只在 `ack(ok=true)` 后推进 |
| sessionhelper sidecar | **保留** | 实测补 2 处腐点后 5/5 端点可用 |
| `internal/store/` 迁移框架 | **保留复用** | 已到 migration 0031，可作迁移基座 |
| `datad` | **schema 级重构** | 全包无租户维度、无 RLS；表结构是单租户模型 |
| admin 后台 | **重建管理面** | 无角色模型；且「租户」一词已被占用为 API-key 归属空间（`registered_service` 表） |
| **`mcsd` 调度语义** | 🔴 **保留**（与 §4.5 一致） | 其承担的是通用引擎做不了的部分：agent 择人、worker 判死换代重派、记账先行→外呼的崩溃切点、per-段门方授权矩阵、执行席≤2 |
| **`board` 存储层** | **重写** | SQLite 单写者串行化是其线性化点，换存储即换该不变量的实现方式；无 migration runner；CHECK 约束无法就地改 |
| **`board` 状态模型** | 🔴 **按新契约重构，不作整体重写** | 见下方 v2.5 更正 |
| **身份与幂等层** | **重建** | C0.1 未实现；幂等键仅部分原语闭合 |
| `mcsd` 对 board 的调用面 | **随 board 重写而调整**，语义不变 | —— |

# 第二部 · 定义层与分级层

## §3 四层架构

```
  定义层（Spec Kit：spec / constitution / checklist）
      ↓ 产品定义
  分级层（属性表 → DMN 决策表 → 必过环节并集）
      ↓ 该走哪些门
  执行层（board DAG + mcsd 派发 + 门禁）
      ↓ 交付物 + 门结果
  保障层（台账、封存、晋升、自检计数器）
```

## §4 定义层：产品定义规范

### 4.1 选型：Spec Kit

采用 Spec Kit 作为产品定义规范的载体。三项直接使用：

| 件 | 用途 |
|---|---|
| `constitution.md` | 项目治理原则的唯一载体 |
| `/speckit.checklist` | 生成质量检查清单 → 落成 `node.acceptance` |
| `/speckit.analyze` | 跨制品一致性检查 = 环节丢失的输入端检测器 |

沿用其两项设计，不重新发明：

1. **`Constitution Check` 前后各检一次**（`plan-template.md`）；违规须书面论证（`Violation | Why Needed | Simpler Alternative Rejected Because`）
2. **checklist 是 reviewer-owned**，只有 reviewer 能打 `[x]`，IMPLEMENT 命令读 checkbox 当 gate 且不得修改标记——**与 §7.2「implementer 不能自签门 PASS」是同一条纪律**

### 4.2 Spec Kit 及三个外部件的性质：它们是平台级 skill

Spec Kit / OpenSpec / Superpowers 的约束住在 agent 上下文里、由斜杠命令承载、无外部系统拦截
——**按 §14.1 判据，它们是 skill，不是机制**。

**由此的硬性要求**：

| # | 要求 |
|---|---|
| 1 | 三者按平台级 skill 治理（§15、§16），不另设「外部件引入」流程 |
| 2 | 🔴 **Spec Kit 及其模板列入 immutable 名单第一批**（§16.5）——它同时满足**平台级 + 承载纪律 + 影响授权判据** |
| 3 | **硬门仍须落在 board。** 自律型工具不承担门禁 |

### 4.3 spec 是授权凭据

spec 中可写**预授权**（§23.2）。因此：

- spec 的**评审带安全权重**：凡含跨边界数据访问声明的 spec，其评审门方**必须包含有权批准该访问的角色**
- spec 查阅入口**必须显示**：版本 / 评审状态 / 所含预授权条目及作用域 / 生命周期状态（研发测试期有效 / 已因上线 `expired`）

### 4.4 spec 拆分

一份 spec 可拆多个子 spec。数据模型**必须预留** `parent / child` 维度与跨租户引用位置。

### 4.5 流程引擎：不引入新的

**保留 `mcsd`**——不引入任何外部流程引擎替代它。
唯一引入的外部件是 **DMN 决策表**（用其决策表，不用其执行引擎），供 PM 自维护分级规则。

> ⚠️ **与 §2.3 的关系（v2.3 澄清，原两处冲突）**：
> **「保留 mcsd」指保留其调度语义与契约；「重写 board」指重写其存储层与状态机实现。**
> 二者不矛盾。v2.2 及以前把 §2.3 写成「board / mcsd 整体重建」，与本节直接冲突，**已改正**。
>
> **且「整体重建」的证据本不充分**：所列依据（SQLite 单写者、无 migration runner、
> C0.1 未实现、幂等键未闭合）支持的是**存储层与身份层重建**，**不支持调度逻辑重建**。
>
> 🔴 **v2.5 再次收窄（复审指出）**：v2.3–v2.4 仍写「board 存储层**与状态机**重写」。
> **上述证据只证明存储实现须换，不能单独证明状态机算法应整体重写。**
> 门 verdict 独立化等确会改变状态模型，但那是**契约驱动的重构**，不是「因为旧的不行」。
>
> **修订表述**：**board 存储层重写；状态模型按新契约重构；
> 既有并发与代际语义（CAS、`generation`、迟到结果处置、fan-out、reconciler 谓词）
> 须由 conformance suite 先固化，再逐项判保留或替换。**
> **无 conformance suite 之前，不得以「重写」为由丢弃任一既有并发语义。**

## §5 分级层

### 5.1 属性表判据

| # | 判据 |
|---|---|
| 1 | **可重复判定**——同一份 spec、同一角色的两个人，依同一份判定说明应得同一结果 |
| 2 | **可由产物反证**——声明与最终产物不符时机器能查出来 |

**宁可粗（三档枚举），不可细（十档打分）。打分制一定退化成主观。**

### 5.2 属性（起点 7 项）与填写归属

| 类 | 属性 | 取值 | 填写方 |
|---|---|---|---|
| A 影响面 | `外部契约变更` | 无 / 兼容新增 / **破坏性** | 业务语义层=PM，接口层=tech |
| | `数据模型变更` | 无 / 加列加表 / **改列删列改语义** | tech |
| | `影响范围` | 单模块 / 跨模块 / **跨服务** | tech |
| B 风险 | `在产影响` | 不影响 / 灰度可回滚 / **直接影响在产** | ops / owner |
| | `回滚成本` | 重启即回滚 / 需回滚数据 / **不可回滚** | ops / owner |
| | `安全面` | 否 / **是** | ops / owner |
| C 规模 | `预估节点数` | 数字 | tech |

**两条硬性纪律**：

1. **`安全面` 必须是独立维度，不得被「改动小」稀释。** 五行改动若动了鉴权，它就是高风险。
2. **每个属性须有事后可机器验证的对应物。** 声明「数据模型变更=无」而交付物 diff 中出现 migration → **自动告警并强制升级**。

### 5.3 门按属性算，级别只是标签

**每个属性独立映射到「必须加哪些门」→ 取并集。** 禁止先算总级别再查门。

L1/L2/L3 **按触发的最高风险档命名**，不按门数量命名；**级别只供人沟通，不参与计算**。

### 5.4 并集法的五项必备规则

| # | 规则 |
|---|---|
| 1 | DMN hit policy = **COLLECT / UNION**，须在决策表上显式声明 |
| 2 | **基础必过模板**：恒必过的最小环节集（实现 → 代码评审 → 测试执行），并集在此之上追加 |
| 3 | **冲突消解按 §5.5 四步**（禁止「取更严者」） |
| 4 | **可解释输出**：每次判定输出 `{命中 rule id, 规则表 version, reason}` |
| 5 | 允许**跨属性组合规则** |

### 5.5 冲突消解四步

**输出取要求集合的合取，不取「更严的那一条」**——责任域不同的评审互补而非可替代。

| 步 | 规则 |
|---|---|
| 1 | 同 gate、同责任域 → 按**稳定 gate key** 去重 |
| 2 | 同 gate、不同责任域 → **要求并存**，或升级为 **multi-sign** |
| 3 | 仅当存在预定义 **subsumption / precedence 表**时，才允许高覆盖低 |
| 4 | 无法比较 → **fail-closed，升调度者裁定**（不猜、不默认取严、不默认取宽） |

单调膨胀由**稳定 gate key** + **subsumption 表**控制；gate catalog 是有限集。

### 5.6 映射表（起点）

| 属性取值 | 强制追加的环节 |
|---|---|
| 外部契约 = 破坏性 | 架构评审 + 用例评审 + 交付验证 |
| 外部契约 = 兼容新增 | 文档评审 |
| 数据模型 = 改列/删列/改语义 | 架构评审 + 交付验证（含回滚演练） |
| 数据模型 = 加列/加表 | 文档评审 |
| **安全面 = 是** | 架构评审 + 代码评审（**门方必须是安全角色**） |
| 在产影响 = 直接影响在产 | 交付验证 + 执行结果评审 |
| 回滚成本 = 不可回滚 | 架构评审 + **业主签署** |
| 影响范围 = 跨服务 | 架构评审 |
| 皆否 | 只留基础环节 |

### 5.7 环节数不固定

低级别更少，高级别追加架构评审。**若列固定，分级即无意义。**
看板必须处理**变长列**——低级别任务的某些格子是 **N/A**，不是「未完成」。

### 5.8 门方是矩阵的输出列

| 环节 | 门方 |
|---|---|
| 代码评审 | 不得是该 node 的 implementer；`安全面=是` 时**必须**为安全角色 |
| 交付验证 | `qa_owner` |
| 架构评审 | 调度者或指定架构角色 |
| 业主签署 | 业主 principal（C0.1 校验，非自述） |

### 5.9 防绕过

1. 属性**三方分填**，填在 `spec.md` 的 `**Key**: value` 头块
2. **执行者不得单方定级**：可补技术属性，**不得下调**任何已声明的风险档；下调须走门方或调度者
3. 叠加 §5.2 第 2 条机器交叉验证

# 第三部 · 执行层与保障层

## §6 判定模型三层：能机器判的绝不交给人

| 层 | 性质 | 内容 |
|---|---|---|
| **一 · 结构闸** | 违规不可能发生，不存在「谁来判断」 | schema / 状态机约束 |
| **二 · 机器校验** | 客观、可复算、自动跑 | 见 §6.1 |
| **三 · 人/Agent 评审** | 主观 | 只判「对不对、够不够好」 |

### 6.1 交付物回执五要素中四项机器可验

| 要素 | 自动验 |
|---|---|
| 件（路径或 commit 40hex） | ✅ 存在性可查 |
| sha256（最终态当场算，报后不改） | ✅ 可复算比对 |
| 行数 + 字节（`wc -c` 口径） | ✅ 可复算 |
| 自测结果（命令 + 摘要） | ✅ 命令可重跑 |
| 门结果（PASS/FAIL + 失败最小复现） | ❌ 需要人 |

⇒ **交付物合格约八成可自动判，门方只判剩下两成**，同时解决门方瓶颈。

### 6.2 状态机变更是重活，不是改点

引入 `passed` / `awaiting_gate` 等门禁状态属**状态机设计变更**，必须一并重定义：
状态迁移图与不变量 / worker 何时 `Release` / `GateResult` 原语（CAS、幂等键、代际 guard、gate-3 授权、**证据持久化**）/
FAIL → `append_revision` 回流建图 / reconciler stray 谓词 / 读模型全套 / CHECK 约束迁移 /
**门方映射迁入台账**（当前仅内存）/ `awaiting_gate` 期间资源与恢复语义 / **gate FAIL 与执行 failed 的语义分野** /
**迁移机制本身**（须先造：版本探测 + 原子 rebuild + 回滚备份 + 旧库兼容测试）/ 回归面含 ingress、driver、一切读 node 状态的消费者。

**唯一可独立先落的一项**：`Terminal(done=true)` 前置 `result_ref != ''`。

**治理成本**：属 C1 原语面语义变更 → 须重两签（按 §24 攒批）。

## §7 门禁纪律

### 7.1 上线前置（硬）

| # | 前置 | 判据 |
|---|---|---|
| **P1** | **per-session principal 可信** | **端到端**：连接层 → 信封 → Receiver 的认证主体传播 + trusted 开关原子切换 + 非合规会话清零 + **负向测试（伪造 principal 必须被拒）**。未就绪时一切 mutating op 与状态观测 **fail-closed**，仅放行只读查询 |
| **P2** | **控制授权闸在每个可接收控制指令的实体上同构生效**（无缝隙） | 执行组边界亦须有 |
| **P3** | **逐闸命中计数入台账** | LLM 兜底占比 = 调度者健康指标 |

**P1 是地基**；但不阻塞 board 状态机的离线设计与实现，二者可并行。

### 7.2 五条纪律

- 门方是 **per-段指定的 principal**，不是角色
- **implementer 不能自签门 PASS**
- **执行席不得自行收口**（收口 = 调度者唯一关闭权）
- **LLM 判读不授权**（gate-5 结论须回 gate-3）
- **身份用 per-session principal，不信信封自述 `from`**

### 7.3 未达成时的处理

| 情形 | 机制 |
|---|---|
| 重试耗尽 | `retry_exhausted` → blocked |
| 超时 | `sla_deadline` + reconciler `TimeoutAnnotated` |
| 依赖失败 | `dep_failed` → 下游 blocked |
| 无人可派 | `starved` |
| 投递悬空 | `delivery_unresolved` → redeliver 收敛 |
| 等人输入 | `awaiting_input` |
| 需决策 | 升级链 → 调度者 → 判属产品决策则升业主 |
| 卡死无解 | `owner_override`（**指令须唯一映射到白名单 op，禁自由文本直写**）/ `owner_takeover` |

**关键决策请求格式**：`决策项 / 选项(a,b,c…) / 各选项影响一行 / 调度者建议+理由 / 不拍时的默认行为与时限`。
**一次一批，禁流式追问。**

### 7.4 门 FAIL 的回流

**门 FAIL → 建修订 node（`append_revision`）→ 优先派回原 worker。**
修订 node 不依赖 worker 记忆，靠**不可变派发快照**重灌（§11.4）。

## §8 发版

### 8.1 发版不做成新 op

发版是**一类 task 的 node 模板**，不是新 `stateOps`——扩 op 会触发 C1 重两签，落成模板则不会。

### 8.2 收口格（第 ⑧ 格）的交付物

收口由**调度者唯一关闭权**执行，同一事务内产出四项：

| # | 交付物 |
|---|---|
| 1 | **版本摘要 → 晋升 K1** |
| 2 | **spec 预授权失效登记**（§23.3） |
| 3 | **部署锚登记**：组件 × 环境 × commit × 制品 sha256（§13.2） |
| 4 | **阶段复盘**（§9） |

> **收口是平台的「事实登记点」**——它是唯一一个既知道「改了什么」又知道「上到哪里」的时刻。
> **无复盘、无部署锚登记，不得收口。**

## §9 阶段复盘

**复盘是交付物，不是自觉行为。无复盘不得收口。**

### 9.1 输入（现成，无须回忆）

该阶段的**帖子流** + **交付物清单** + **门记录**（含 FAIL 与整改）+ **blocker 记录**。
⇒ 草稿由廉价模型生成（同 §20），执行者 / 评审者定稿。

### 9.2 输出必须四段，任一段为空须写明理由

| 段 | 内容 | 去向 |
|---|---|---|
| 1 | **本阶段沉淀的事实** | 知识库（§12） |
| 2 | **可复用操作** | skill（§16） |
| 3 | **应固化能力** | MCP（§17） |
| 4 | 🔴 **本阶段的判断失误** | 知识库「坑清单」类目，**参与三级晋升** |

**第 4 段的价值全在能被下一轮读到**：前三段是「产出了什么」，只有它是「哪里想错了」。
**晋升到平台级前必须去标识化**（判断失误常牵涉具体人与具体事故）。

> 强制四段的理由：不强制，复盘会退化成「顺利完成」四个字。

# 第四部 · 上下文、记忆与知识库

## §10 记忆模型是二维的

**权限域与记忆类型正交，必须做成二维，不得二选一。**

| 维度 | 决定 | 取值 |
|---|---|---|
| **权限域** | **谁能看**（RLS 作用域） | K0 平台域 / K1 项目·租户 / K2 版本 / K3 任务 |
| **记忆类型** | **怎么存、怎么取、何时清** | 工作记忆 / **过程性记忆（skill）** / 事实记忆 |

> **skill 是过程性记忆，必须有 K 层归属**（平台级 = K0，租户级 = K1，项目级 = K1/K2），
> 与知识条目**共用同一套晋升、同一套装载、同一套 RLS**。
> 否则「导入上下文」与「skill 晋升」会成为两套并行机制，出现「K 层灌到了、skill 没同步」。

## §11 K 分层

### 11.1 五层（K0 拆分后）

| 层 | 内容 | 易变 | 载体 | 晋升时机 |
|---|---|---|---|---|
| **K0-pub** | Agent 身份/寻址/通信纪律/Git 身份/凭据纪律/工作区约定 | 极低 | 平台上下文目录 | 平台变更时 |
| 🔴 **K0-sec** | **服务架构 / 网络架构 / 数据库设计**（含主机 IP、拓扑、表结构） | 中 | 同上，**分级存放** | 平台变更时 |
| **K1** | 项目知识库（§12.1 八类） | 低 | `KBProvider`，每项目一 namespace | **版本收口时晋升** |
| **K2** | 版本上下文：目标/范围/决策记录/变更摘要/已知问题 | 中 | 版本库（git + task 聚合） | **任务收口时晋升** |
| **K3** | 任务上下文：派发信封 + `acceptance`/`deps`/`result_ref`/门结果 | 高 | board 台账 | 实时 |

### 11.2 K0 必须拆 pub / sec

**理由**：K0 全量装载 + `query = 全员` ⇒ **每个 Agent 的上下文里都有全平台拓扑**。
而网络架构、数据库设计、服务架构正是横向移动最想要的东西。

| | K0-pub | K0-sec |
|---|---|---|
| 装载 | **全量**（稳定前缀，可吃 prompt caching） | **按需切片** |
| 读权 | 全员 | **RLS + 条目级分级（S0/S1/S2）** |

**K0-sec 在完成分级脱敏前，不得开放全租户只读。**

### 11.3 装载规则

| 层 | 灌法 |
|---|---|
| K0-pub | 全量 |
| **K0-sec** | **按需切片 + RLS** |
| K1 | **按需切片**（`Query(q, topK)`） |
| K2 | 当前版本摘要全量（量小） |
| K3 | 本任务全量（即派发信封本体） |
| **已批准 skill** | 平台级 push 全量 + 租户级已拉取者（§15） |

**K1 与 K0-sec 必须是检索式的，不得全量灌。**

### 11.4 任务上下文的装载与隔离

- **每任务清空上下文**：新 Spawn = 新上下文
- **灌入什么由派发信封定义**，信封自带完整性判据：**缺任一字段 = 无效派发，执行小组拒接**
- **亲和（`OriginHint`）仅 pick 权重，不承担正确性**
- 🔴 **前置：不可变派发快照**。修订 node 摆脱 worker 记忆依赖，派发时必须持久化：

| 字段 | 用途 |
|---|---|
| `envelope_ref` | 该次派发的完整信封引用 |
| 原交付物锚 | 上一轮 `result_ref` + sha256（**锚，不是路径**） |
| **完整 FAIL evidence + 失败最小复现** | 当前未持久化，须补 |
| `acceptance` 锚 | 判据的 commit/blob sha256（判据一改锚即变，防悄改判据） |
| 规则版本 | 分级规则表 version |
| 上下文版本 | 各 K 层装载时的版本 |

## §12 知识库

### 12.1 八类条目

| # | 类型 | 权威源 | 归属层 |
|---|---|---|---|
| 1 | 产品定义 | **spec**（不在代码里） | K1 |
| 2 | 业务流程 | 代码 + spec | K1 |
| 3 | 代码位置 | 代码 | K1 |
| 4 | 各接口业务逻辑 | 代码（结构可抽，语义须摘要） | K1 |
| 5 | 各主要对象介绍 | 代码 | K1 |
| 6 | **服务架构** | 代码 + 部署配置 | **K0-sec** |
| 7 | **网络架构** | **部署环境**（不在代码里） | **K0-sec** |
| 8 | **数据库设计** | `migrations/` DDL（近乎全自动） | **K0-sec** |
| 9 | 前代系统与迁移 | 人 | K1 |

### 12.2 知识库是四根管道，不是一根

**代码抽取 / 部署环境 / spec / 复盘**——权威源不同，不得指望一个 code-scanner 全包。

### 12.3 多租户下「现网」有两个

平台自身的现网（K0，平台级 ops 域）与各租户业务的现网（K1，租户级 ops 域），
**部署锚来源、权限域、脱敏要求均不同**。⇒ **抽取管道参数化于租户，不得各租户各建一套。**

## §13 新鲜度与腐坏

### 13.1 每条目必带锚

`KBDoc.Meta` 必含 `{project, type, version, baseline_anchor, updated_at}`。
`baseline_anchor` = commit 40hex 或 blob sha256。

**失败模式**：写进去的内容过期了没人知道——**比没有知识库更危险，因为它会误导。**

### 13.2 代码锚 ≠ 部署锚，两者都要

| 锚 | 检测什么 |
|---|---|
| **代码锚**（`baseline_anchor`） | 「条目所述的代码位置变了」 |
| 🔴 **部署锚** | 「文档描述的是 A 分支，而线上跑的是 B 分支」 |

**部署锚由 §8.2 第 3 项收口登记提供**，不另造机制。
**无部署锚，「基于现网代码」的知识库无法成立**——它会精确描述一份不是线上那份的代码。

### 13.3 生命周期状态机

| 状态 | 判据 |
|---|---|
| `active` | 锚匹配 |
| `suspect` | **锚落后 且 两锚间 diff 覆盖该条目所述路径** |
| `archived` | 连续两个版本仍 `suspect` |

**判据用锚，不用时间。**（按时间会误伤——一份三年未改的稳定接口文档不因无人查阅而过期。）

### 13.4 检索

**必须先 RLS 过滤后检索，禁止先检索后过滤**——后者会经摘要片段泄露正文。

**排序计分**（初值见附录 A）：

```
score = w_use · log₁₊(使用量)归一  +  w_rel · relevance  +  w_imp · importance
importance 由层级给定（平台级 > 租户级 > 项目级）
suspect 条目乘以降权系数
```

> **锚失配必须参与排序降权，不能只打标记。标了不参与排序，等于没标。**

### 13.5 写权

- **`ingest` = 管理域**（知识策展）；`query` = 按 RLS 与条目分级
- **K1 的 ingest 仅由「版本收口」原语触发**
- 人工订正走独立 curation 流程，**落审计**

# 第五部 · skill 与 MCP 体系

## §14 判据

### 14.1 skill vs 机制（第一判据）

> **凡是「丢了上下文就该失效」的，做 skill；**
> **凡是「丢了上下文仍须成立」的，做机制。**

| 事项 | 归属 |
|---|---|
| 「先写 spec 再写代码」的流程指引 | skill |
| 「门方 ≠ 执行者」 | **机制**（board） |
| 「node DAG 走不通就是走不通」 | 机制 |

### 14.2 skill vs MCP（第二判据，两维）

| 维 | skill | MCP |
|---|---|---|
| **状态与认证** | 无状态的流程、判断、参考材料 | **有状态 + 有认证的连接** |
| **变不变** | 稳定的 | **易变的**（运行时查） |

**⇒ skill 不得内嵌 API schema，须在运行时经 MCP 查**，使 skill 轻量且不因后端变更而过期。

**一件事既是系统又是用法时**（多数真实工程属此）：**建一个小 server 管访问 + 一个 skill 管用法。**

### 14.3 MCP 工具面：动词 × 资源类型

**MCP 工具数量收敛到动词集，不随资源数量线性增长**（如 `list/get/create/update/delete/execute/search/describe/schema/diagnose/status`）。
这与平台已确立的「工具语义在 MCP 层，线上只有一个 type，枚举零膨胀」是同一做法。

### 14.4 MCP 化的准入（两步）

> 🔴 **v2.5 更正（复审两轮均指出，本席核实成立）**：v2.1–v2.4 把「≥3 提出方且跨项目」
> 放在**判型之前**，等于**让复用度门槛决定安全实现形态**——
> 一个单项目、单提出方但**有状态且需认证**的连接，会因未达复用阈值而被挡在 MCP 之外。
> **这是把安全边界交给了流行度。**

**改为三层，安全判据优先且不受采用人数影响**：

| 层 | 问题 | 判据 | 不受什么影响 |
|---|---|---|---|
| **① 技术形态（安全判据，最先判）** | 必须是 MCP 吗 | 🔴 **凡需要状态、认证或动态 schema 的连接，一律经 MCP / 受控 server 承载** | **不受采用人数、复用度影响** |
| **② 其余情形的判型** | skill 还是 MCP | 按 §14.2：无状态的流程判断 → skill | —— |
| **③ 平台产品化 / 晋升** | 要不要推广、升到哪层 | **≥3 个不同提出方 且 跨项目** + §15.1 三判据 | 这才是复用度该管的地方 |

**显式例外**：**安全强制**或**业主指定**可跳过 ③ 的复用门槛直接产品化，**但须落账**。

## §15 分发：两条通道

**平台级与租户级不是同一通道的优先级差异，是两条不同的分发通道。**

| | **平台级** | **租户级** |
|---|---|---|
| 分发 | 🔴 **push，强制** | 🔴 **pull，租户主动拉取** |
| 判据 | **不受具体业务影响、可独立存在于各项目之外** | 与租户所从事项目、工作类型有关 |
| 例 | 产品定义规范、流程执行、消息投递、帖子投递、标准、发版流程与规范 | 业务专用操作 |
| 排序 | ❌ **不需要**——强制的东西不用挑 | ✅ **需要**（§13.4 计分） |
| 属性 | **mandatory**；**immutable 按 §16.5 名单逐件判定，非一律** | 默认 optional + mutable |

### 15.1 平台级准入三判据（须同时成立）

1. **不引用任何具体业务概念**（不含具体项目名、表名、内部地址、业务术语）
2. **移出任一项目后仍完整可用**
3. **描述的是「怎么做」而非「做什么」**

### 15.2 两个属性必须分开

| 属性 | 含义 | 约束谁 |
|---|---|---|
| **mandatory** | 租户不可停用 | 租户 |
| **immutable** | 内容不可被修改（Agent 连提案都不能提） | Agent 与一切下游 |

四种组合均有意义；平台级纪律类（产品定义规范、发版流程、门方所有权）为 **mandatory + immutable**。

### 15.3 🔴 跨租户扩散只有一条合法路径

```
租户 A 的 skill
   ① 抽象化：剥离业务概念（§15.1 三判据）
   ② 脱敏：去项目名 / 内部地址 / 表名 / 业务术语
   ③ 晋升审批（平台级 = 平台域基线变更，走 §24）
        ↓
平台级 skill（push 给全体）
        ↓
租户 B 拿到的是【抽象后的版本】，不是 A 的原件
```

**禁止租户 B 直接 pull 租户 A 的 skill。**

**受限对象的边界（v2.3 明确）**：

> 🔴 **v2.5 补 MCP 边界（复审两轮均指出）**：v2.3–v2.4 只解释了 skill 制品，
> **未给 MCP 的跨租户边界**。而 S4 标的是 skill **与 MCP** 体系。

**本节的「唯一晋升路径」只约束【可复用制品】。** 四层必须分开治理：

| 层 | skill | MCP | 可否随制品晋升 |
|---|---|---|---|
| **code / 制品** | `SKILL.md` 正文、随附脚本、引用模板 | **server 代码、工具 schema** | ✅ **可抽象晋升**，走本节唯一路径 |
| **config** | 参数默认值 | **连接配置、端点** | 🔴 **不可**——租户专属，随租户走 |
| **credential** | —— | 🔴 **secret / token / 连接凭据** | 🔴 **绝不可**，任何情形 |
| **runtime data / 业务数据** | 执行记录 | **连接状态、缓存、业务数据** | 🔴 **绝不可** |

**目录可见性**：skill 与 MCP 的**存在性与名称**同样受限——**目录按 RLS 过滤**，否则名称即泄漏项目信息。
**同一租户内**跨项目流转 ✅ 不受限，由租户级 ops 自管。已晋升的**平台级**版本 ✅ push 给全体。

> 🔴 **一处必须防的误读**：本节是**制品复用**的规则，**不是所有跨租户动作的总规则**。
> **已授权的跨租户业务数据访问由 §22.1c 的 capability 与 §23 治理**，
> **不得被解释为「制品晋升」而套用本节路径**。二者是不同的事。
理由：skill 正文可能含项目名、内部地址、表结构、业务术语——
**RLS 管的是数据表，管不到一份 Markdown 正文里写了什么。**

> ⇒ **「进一步抽象，进入平台级」不只是提升复用度，「抽象」这一步同时承担跨租户扩散的脱敏关口职能。**

## §16 生命周期

### 16.1 三件事必须分开判，不得混为一谈

> ⚠️ **v2.3 更正**：v2.1–v2.2 把「频次触发」与「业务无关性」并列为「两条判据串联」，**是错的**——
> 业务无关性是**平台晋升**的判据，与「要不要固化成 skill」无关。
> 一个刚生成的 skill 天然是项目级，**不需要业务无关**。三件事被混在了一起。

| # | 问题 | 判据 | 输出 |
|---|---|---|---|
| **① 候选触发** | **要不要固化** | 见 §16.1a | 一个**候选**（默认落在**项目级**） |
| **② 判型** | **固化成 skill 还是 MCP** | §14.2 两维 + §14.4 两步 | skill 或 MCP |
| **③ 晋升** | **要不要升层、升到哪层** | §15.1 三判据 | 项目级 / 租户级 / 平台级 |

**三者顺序执行，各自独立。① 不引用 ③ 的判据；③ 不因 ① 的频次自动成立。**

#### 16.1a 候选触发（仅决定「要不要固化」）

**触发情形（任一即触发一次总结）**：

1. 完成一个 **≥N 次工具调用的复杂任务且成功**（N 为可调参数，见附录 A）
2. **从错误中恢复 / 死胡同脱困**
3. 🔴 **用户或评审方纠正揭示了正确做法**

> 第 3 条价值最高：顺利路径只证明「这样可行」；**被纠正的路径额外编码了「默认做法是错的」**，
> 它拦住的是**会重复发生的错误**。与 §9.2 第 4 段是同一洞见的两个尺度（单次操作级 / 阶段级），**两者都要**。

**触发后须判「是否可复用」**（同样的步骤序列是否会对不同输入再次发生），**可复用才入库**。
**次数是启发式，不是判据**——不设此闸，一次性排障会淹没 skill 库。

#### 16.1b 晋升（独立发生，与创建解耦）

**晋升不由使用频次自动触发。** 频次可作为**「该评估了」的提示信号**，
但**升不升、升到哪层，只看 §15.1 三判据**；平台级晋升另须经 §24 审批。

### 16.2 自我进化：准入，但必须以暂存审批模式

**允许 Agent 提案，不允许 Agent 批准。**

| # | 前提（硬性） |
|---|---|
| 1 | **写入审批（`write_approval`）在平台级与租户级默认开启** |
| 2 | 暂存件**跨重启存活** |
| 3 | 可 **diff 审阅**后批准/拒绝 |
| 4 | 🔴 **前台回合与后台自我改进一视同仁**——不给后台特权路径 |
| 5 | 叠加 §16.5 immutable 名单 |

### 16.3 回写纪律：何时改 + 怎么改

| 问题 | 规定 |
|---|---|
| **何时改** | **只在该 skill 把本次执行带偏时**（命令失败、缺步骤）才回写；执行顺利则**只计使用量，不改内容** |
| **怎么改** | **`patch`（定向替换）优先，禁止用整篇 `edit` 做常规修订** |

**`patch` 优先的首要理由不是省 token，是可审**：`patch` 的 diff 小、可审；整篇 `edit` 的 diff 审不动。
在 200+ Agent 并发 + 写入审批的场景下，**审批会先成为瓶颈，然后被绕过**。

**不设负反馈闸的自动回写会制造持续冲突**：每次运行都产生 diff，skill 库变成噪声源。

### 16.4 变更须附 SYNC IMPACT REPORT

**凡平台级 skill 变更，必须附**：版本变更 / bump 理由 / 新增章节 / **逐个复核了哪些下游件并打 ✅** / 遗留 TODO。

> **diff 小 ≠ 影响小。** patch 保证可审，SYNC IMPACT REPORT 保证影响面被显式声明。

### 16.5 🔴 immutable 名单

**安全类 / 合规类 / 平台域基线类 skill 标为 immutable——Agent 连提案都不能提。**

理由：写入审批只保证「有人看」，**不保证「看的人看得出来」**——一个被巧妙 patch 的安全类 skill，
在 diff 里可能只有一行。

**首批名单（优先级最高）：Spec Kit 及其模板。** 它同时满足三条件：

| 条件 | 事实 |
|---|---|
| 平台级 | 全网 spec 产出都依赖它 |
| **承载纪律** | `checklist-template.md` 的「checklist 是 reviewer-owned」= §7.2「implementer 不能自签门 PASS」。**一次 patch、一行 diff 即可废掉它** |
| **影响授权判据** | spec 是授权凭据（§4.3）；**能改 Spec Kit 的人，能改「预授权该长什么样、门方该检查什么」** |

⚠️ **immutable 名单本身的变更须重两签**，否则「把某件移出名单」成为新的绕过点。

### 16.6 装与卸必须对称

分发通道**必须同时提供安装与卸载**（`install_skill` / `uninstall_skill`、`install_mcp` / `uninstall_mcp`）。

**理由**：晋升机制必然包含降级与下架——坏 skill、被平台级版本取代、安全召回。
**没有卸载 = 晋升是单向的 = 坏 skill 推出去就收不回来。**
且防降级的版本单调闸会让「推一个空版本覆盖」这条替代做法也走不通。

> 🔴 **v2.5 推翻 v2.3 的分类依据（复审指出，本席核实成立）**：
> v2.3–v2.4 称 A 类安全召回「只减不增，最坏后果是可用性下降」。**该判断不成立。**
> **卸载鉴权、审计、DLP、安全门类的 skill / MCP，会直接扩大权限或可达范围**——
> 这与 §24.3a 的总判据「任何情形下都不可能扩大任何主体的权限或可达范围」**正相冲突**。
>
> 且「携带有害证据」只能证明**该制品有问题**，**证明不了删除后的权限效果是单调的**。
> **本席原来的分类是按【动作名】判的，应当按【capability effect】判。**

**改为按 capability effect 判，不按动作名判**：

| 判据（唯一） | 说明 |
|---|---|
| 🔴 **该动作执行后，是否存在任一主体的权限或可达范围被扩大** | 存在 ⇒ **不得走紧急路径**，无论它叫「卸载」还是别的 |

**紧急路径可用的原语（注意：不含 `uninstall`）**：

| 原语 | 语义 | 前提 |
|---|---|---|
| `disable` | 停用，制品仍在 | —— |
| `quarantine` | 隔离，不可被调用 | —— |
| `revoke` | 吊销凭据 / 撤销授权 | —— |

> **前提（对上述三者均适用）**：**必须存在 fail-closed fallback 或替代控制**。
> 停用一个安全门而无兜底 = 门消失 = 权限扩大 ⇒ **该操作不合法，无论多紧急**。

**会移除安全控制的卸载**：**必须先切换到安全版本或兜底机制，再卸载**，且走**事前**审批。
**删除动作本身不可被枚举为「天然安全」。**

**常规 install / uninstall 保持对称审批**（事前、同级）。

| 其余要求 | 说明 |
|---|---|
| 🔴 **tombstone / fencing**（v2.5 新增） | 卸载须留 **tombstone**；**重装同版本必须形成新的 `installation_generation`**。<br>**迟到的 ACK、旧任务、旧 delivery 不得复活已卸载的实例**——按 generation 栅栏丢弃 |
| 幂等语义 | 卸载后再装同版本，不得被误判为「已装」（由 generation 保证，非由版本号保证） |
| 审计 | 卸载与安装同等落账；紧急路径的 `disable`/`quarantine`/`revoke` 另须记录事后补审结果与所用兜底机制 |

### 16.7 上下文预算

**skill 目录的常驻上下文成本必须设硬预算**（初值见附录 A），采**渐进披露**：

- 常驻只放 `name` + 简要描述，**正文按需加载**
- 描述文本设字符上限

> **排序解决「列表太长怎么办」；渐进披露解决「列表为什么会太长」。**
> **渐进披露是主解，排序是次解。** 这是唯一能防止 skill 库随规模膨胀吃掉上下文的机制。

# 第六部 · 协同：帖子流与通知面

## §17 要解决的问题

现有协同全靠平台通信转发，产生两个后果：**作业无痕**（看不到交付物是怎么产出的）与**消息风暴**
（多方产出无效或过期消息）。

**根因：三件事被混在同一条消息流里**——工作过程讨论 / 状态通知 / 控制指令。**必须分开。**

## §18 帖子流

### 18.1 载体

**帖子正文须独立表**，不得塞进事件表——读写模式不同（看板高频全扫 vs 按 node 低频增量读；封存后可归档）。

### 18.2 传播范围

**每个任务的消息仅在该任务的执行者 / 门方 / 其他 `task_role` 成员之间传播。**

### 18.3 读取：游标增量，引擎推送，Agent 不轮询

1. **Agent 完全不轮询、不主动读**
2. 派发 node 时，把该 node 帖子流的**增量**（`cursor > 该 principal 上次读到的位置`）打包进**派发信封**
3. 成本上界 = O(成功覆盖的 post-recipient 对 + 重投开销)

**保证 at-least-once + dedupe，不宣称 exactly-once**：

| 机制 | 要求 |
|---|---|
| delivery / outbox | 冻结 `[from, to]` 区间 + `delivery_id` |
| 游标推进 | **ACK 后**以 **CAS 单调推进** |
| 并发控制 | 同 principal **并发租约** |
| 消费侧 | 按 `post_id` / `delivery_id` **幂等去重** |
| 未 ACK | 可重投 |

### 18.4 阶梯硬门

**帖子数是分歧探测器，不是话痨指标。** 用**原始计数**而非「有效帖数」——有效性是主观判断，
两人数不出同一结果，违反 §5.1 可重复判定。**原始计数的价值恰在客观、不可辩。**

| 阈值（每 node 每轮） | 动作 | 解封权 |
|---|---|---|
| ≤ 阈值 A | 正常 | —— |
| **> A** | 三段式封锁 | **调度者可解封（首次），并须同时向业主预警** |
| **> B** | 三段式封锁 | **仅该租户业主可解封** |

**三段式封锁**：

| 段 | 动作 |
|---|---|
| ① **停注入** | 停止自动推送 / 上下文注入，冻结 reader cursor。**这才是真正止血的一刀** |
| ② **禁新帖** | 拒绝新增 post |
| ③ **保留受限只读** | 固定 digest / snapshot；按需单次读取或 break-glass；**带预算与审计** |

> **禁的是「注入」，不是「读取」。** token 在注入时就花掉了，事后禁读追不回来，
> 却会伤及可追溯、崩溃恢复、新成员接手、参与者核对摘要四项。

**读权豁免**：调度者（解封权人）、该租户业主、摘要 agent（只读）——**摘要正在产出解封决策所依赖的依据**。

**解封必须产出裁定物，不得只是放行**：

| 层级 | 必须产出 |
|---|---|
| 调度者 | ① **分歧点陈述**（争的是什么、双方各自的裁剪、裁定或判属产品决策升业主）② **同时向业主发预警** |
| 业主 | 决策记录（§7.3 格式）；且**裁定结果须回写定义层**（spec / constitution / 分级规则） |

> **不回写定义层的解封，等于给同一个 bug 反复续命**——下一批帖子会重复上一批的争论。

**首次解封必须预警业主**：若只在第二档通知，业主第一次知情时分歧已烧掉两倍配额。

**开放讨论豁免**：建 node 时可标记为开放讨论型（阈值放宽或不设）；
**豁免必须落账** `{node, 标记人, 理由, 时间}`——**可审计，不可匿名突破**；**不得由执行方自行标记**。

### 18.5 三层封存

| 层级 | 封存时机 | 晋升产物 |
|---|---|---|
| **node 帖子流** | `execution done ∧ verdict ∈ {not_required, pass, fail}`；**`pending` 不封** | → 环节小结 |
| **task 帖子流** | 任务收口（调度者唯一关闭权） | → 任务摘要 → **K2** |
| **version 帖子流** | 版本收口 | → 版本摘要 → **K1** |

**封存条件必须含 `fail`**，否则门 FAIL 的 node 永不封存，其帖子流长期可写、digest 永不生成。

**顺序**：先落 FAIL evidence / gate result，**再**算 digest。

**返工天然不污染**：门 FAIL 走 `append_revision` 建**新 node**，新 node 有新帖子流。

> 「环节结束后还想讨论怎么办」有答案：**属于上一层**。node 封了 task 层还开着，task 封了 version 层还开着。

### 18.6 封存的威胁模型（承诺须准确）

**表述为「篡改可检测（限定威胁模型）」，不得表述为「防篡改」**——
digest 与数据同在一个可写库，能改帖的人通常也能改 digest。

| # | 最低配套 | 作用 |
|---|---|---|
| 1 | 封存后 DB 权限 / trigger 拒 `UPDATE`/`DELETE` | 阻断常规写路径 |
| 2 | digest 覆盖 `tenant`/`node`/`seq`/`actor`/`ts`/`content` 的**规范序列** | 防止只改内容不改元数据 |
| 3 | **外部或更高权限锚定 + 定期核验** | **唯一能对抗「改帖者亦可改 digest」的一层** |

**未做到第 3 项前，对恶意篡改的防护为零**，只覆盖非协同损坏与误操作。

**digest 选型**：**整流 sha256**，算前用 RFC 8785 (JCS) 规范序列化（平台已有实现，直接复用不自造）。
将来若需局部验证，可在保留 sha256 基础上追加 Merkle root。

## §19 通知面收敛

### 19.1 通知 taxonomy

| 类 | 例 |
|---|---|
| 任务状态（六类） | `new` / `status` / `result` / `reject` / `gate_result` / `close` |
| delivery ACK | 投递确认 |
| security / platform health | 安全事件、平台健康 |
| break-glass | 应急通道启用 |
| 决策请求 | 升业主 |
| 跨 task 协调 | 双方无共同 node 时 |

### 19.2 出站闸（三层）

**纪律在此处必然失效**——善意且准确的转述仍会产生版本错位。**故须机制约束。**

| 层 | 约束 |
|---|---|
| **L1** | 出站消息若 recipient 是某 task 参与者、且**可信结构化头**（`meta.op`/`event_type` + `task`/`node`/`tenant`/`version`）不属允许集 → **拒发，回指帖子流**。🔴 **判定只读结构化头，绝不读正文** |
| **L2** | agent↔agent 直接消息通道**仅承载已批准的通知 taxonomy**；一切自由文本必须落 node 帖子流 |
| **L3** | 调度者收件面**不提供任何「转述/转发」op**；堵住自由文本旁路 |
| **跨租户** | **默认拒发**，白名单放行 |

**必须保留的例外通道**：应急（break-glass）、决策升级、平台运维通告。
例外**不得停在开放清单后直接上高强度层**，须先在 L1 试点计量。

### 19.3 交接纪律

**每一次评审、转述、交接，必须带 `commit + sha256 + 行数/字节`。**
（本条源于实际发生的三次版本错位事故，已由团队采纳。）

## §20 摘要 agent

| 维度 | 规定 |
|---|---|
| **触发** | **事件驱动，不定时轮询**：node 进终态 / 触门 / 距上次摘要已积累 N 条新帖 |
| **模型** | **廉价模型**——任务是抽取，不是推理 |
| **输入** | **仅增量帖**（游标区间）+ node 结构化头 |
| **输出** | **结构化**：`{tenant, node_id, cursor_range, 进度一句话, 阻塞项[], 需支援[], 分歧点[], 建议升级?}` |
| **租户** | 🔴 **必须租户内**——它用廉价模型、跑得频繁、读很多帖，是**易被忽略的泄漏面** |
| **是否入帖子流** | **不入**，单独存 `node_digest`——**入了会推高帖子计数、触发硬门，而摘要恰是解封决策的依据。工具不该污染它测量的东西** |
| **权威性** | **非权威 observation ledger**；不写权威状态机、不授权（LLM 判读不授权） |
| **输入信任级** | 🔴 **按不可信数据隔离**——帖子是 agent 写的文本，**可能嵌入针对摘要器的提示注入**。摘要 principal 须 tenant + node 最小只读 |

**质量校验**：

| 存证项 | 校验项 |
|---|---|
| `input digest` | **覆盖率**（增量区间是否全被处理） |
| `prompt` + `schema` + `model` + `version` | **引用存在性**（citations 指向的帖子是否真实存在） |
| `output digest` | **结构化事实一致性**（摘要断言与台账事实是否冲突） |
| `post cursor citations` | —— |

**两条硬性**：

1. **不得用「摘要说无阻塞、随后触门」这类跨时点比较作为误报指标**——状态可能在摘要之后合法变化。改为**按 `cursor_range` 截止时刻的结构化事实对账**。
2. **关键决策不得只依赖摘要**：解封决策时调度者**必须能看原帖**。**摘要是加速器，不是唯一依据。**
3. **不得声称「可复算：重跑核对」**——LLM 非确定性，重跑得到的是另一个输出。改为**存证 + 引用校验**。

# 第七部 · 身份、租户、权限与授权

## §21 身份模型

### 21.1 三级映射

```
  人（企业 IM 身份验证）
   └─→ 租户（业主级隔离域，RLS 主体）
        └─→ 会话 / Agent（执行主体，持 token）
```

**审计与授权挂在人身上，执行挂在会话身上。**
这不是「加个登录页」——它是 per-session principal（§7.1 P1）的完整形态。

### 21.2 因子分级

| 角色 | 平台 | 身份锚 |
|---|---|---|
| **主因子**（回答「你是谁」） | **飞书 / 企微 / Slack / Google Chat** | **企业目录账号**，可接 SSO，**可被企业吊销** |
| **次因子**（回答「是不是本人」） | SMS / 邮件 | 电话 / 邮箱 |

**WhatsApp 不参与身份识别**，仅作通信渠道（§27）——其身份锚是电话号码，与 SMS 次因子同链路。

### 21.3 双因子不等于双人

| 机制 | 回答 | 挡得住 | 挡不住 |
|---|---|---|---|
| **双因子** | 是不是**你本人** | 冒名、消息伪造、账号单点失陷 | **本人被骗 / 判断失误 / 被胁迫 / 内部越权** |
| **重两签** | 这件事**该不该做** | 单人误判、单人越权、单人被胁迫 | —— |

> **二次验证做到极致，仍然只有一个人在决定。**
> 高危操作须重两签，依据不是「因子弱」，而是**单人不足以承担其后果**。

## §22 租户与隔离

### 22.1 租户是外层硬边界，fail-closed

#### 22.1a 🔴 tenant 必须由服务端从可信 principal 派生

> **禁止从客户端输入、信封自述字段、请求参数或任何调用方可控来源取得 tenant。**
> tenant **只能**由服务端依据**已通过 §7.1 P1 校验的 per-session principal**派生。

**理由**：若 tenant 可由调用方自述，RLS 的全部策略都建在一个调用方可控的值上——
**整套隔离形同虚设，且失效时无任何报错**（策略照常执行，只是执行在错误的租户上）。

| 要求 | 说明 |
|---|---|
| 派生源 | 已验证 principal → 服务端映射表 |
| 缺 principal | **fail-closed**，不得回退到默认租户或匿名租户 |
| principal 到 tenant 多对一 | 允许；**一对多须显式选择且落账**，不得静默取第一个 |
| 计数器 | 「tenant 取自非派生来源的请求数」应恒为 0 |

#### 22.1b 其余边界

- 缺租户上下文 → **默认拒**
- 跨租户 → **默认拒**，白名单放行（须满足 §22.1c）
- 解封阶梯收敛到租户内

#### 22.1c 🔴 跨租户白名单不得成为旁路

> ⚠️ **v2.3 新增（评审方指出）**：仅写「白名单放行」而不约束白名单本身，
> **白名单会退化为一条合法旁路**——它绕过的正是 §22.1a 想守的那条边界。

> 🔴 **v2.5 再次收窄（复审指出，本席核实成立）**：v2.3–v2.4 的四元组
> `(源租户, 目标租户, 操作, 有效期)` **仍然过宽**——缺 principal / 资源范围 / 用途 / capability 身份。
> **一个抽象的 `read` 或 `export` 操作仍可覆盖整个目标租户。**
> 且它与已 PASS 增补件中「跨租户广播须独立 `platform_notice` capability、不得以白名单旁路」
> **不完全对齐**。

**改为：白名单只作 capability policy 的【索引】，不作直接放行依据。**

| # | 硬性约束 |
|---|---|
| 1 | 🔴 **放行由 guarded capability 执行，不由白名单执行**。白名单只用于查找「有没有这条 policy」 |
| 2 | 每条 policy **必须绑定六项**：**源 principal / service role** · **目标资源范围**（不得是整租户）· **typed capability / op**（不得是抽象动词）· **用途** · **有效期** · **capability identity** |
| 3 | **禁止通配**任一项；**禁止按「租户对」整体放行** |
| 4 | **必须有有效期**，到期自动失效，不得无限期 |
| 5 | 🔴 **capability 自身须做幂等、审计与数据最小化**——不得只在入口判一次就放行整条链路 |
| 6 | 🔴 **跨租户通知继续只走 `platform_notice` 独立 capability**，**不得回退为通用白名单** |
| 7 | policy 的新增与延期属平台域基线变更，走 §24，且按 §24.2a **属高危项，整批升重两签** |
| 8 | 每次实际使用**逐次落账**（源 principal、目标资源、capability、用途、时刻） |
| 9 | 计数器：「经通配、缺有效期、或缺六项绑定中任一项的 policy 放行的跨租户请求数」应恒为 0 |

### 22.2 存储与 RLS 的最低配套

**RLS 不是「自动的机制」，它自己也需要一套纪律。配错即失效。**

| 必做 | 说明 |
|---|---|
| `ALTER TABLE ... FORCE ROW LEVEL SECURITY` | **表 owner 默认可绕**，不 FORCE 即无效 |
| **每事务 `SET LOCAL`** | 用会话级 `SET` 会把租户上下文泄漏给下一个借用连接者，**且恰在高并发下才暴露** |
| 最小权限 runtime role，**不得带 `BYPASSRLS`** | —— |
| **缺 context 默认拒** | 漏设即泄漏 |
| 所有关联表与间接查询策略 | 含 view / `SECURITY DEFINER` 审查 |
| 跨租户 admin 独立角色 | —— |
| **负测** | 必须有「越权查询被拒」的测试 |

### 22.3 ops 两类

| 类 | 职责 |
|---|---|
| **平台级 ops** | 生产系统、平台运维、**公共资源**（含平台级 skill / MCP / spec 模板） |
| **租户级 ops** | 本租户的业务模块开发、测试环境等 |

### 22.4 凭据分级

| 级 | 范围 | 纪律 |
|---|---|---|
| **S0** | VPN 凭据、签名私钥、根证书 | **不落任何文档、帖子、流、日志** |
| **S1** | 生产（不可重置） | 严控，按需授权 |
| **S2** | 沙盒 / 研发测试（可重置） | 常规 |

**判据是「爆炸半径可否重置」，不是「看起来敏感不敏感」。**

**默认按不放松执行**；对**有安全基座、不影响生产的研发测试系统**可适当放宽，
放宽须**以环境属性为条件显式声明**，不得默认放宽后再逐个收紧。

## §23 授权

### 23.1 审批的两个轴，并存取严

> ⚠️ **v2.3 更正（评审方指出，本席原表述过度极端）**：
> v2.1–v2.2 写「审批层级**不由**数据敏感度决定，**而由**是否事先声明决定」。
> **该表述会让一句预声明把 S0/S1 级访问降成低危**——预声明是**流程事实**，
> 它改变不了**爆炸半径**这一客观事实。

**正确表述：两个轴并存，各管一件事，取更严者。**

| 轴 | 决定 | 取值来源 |
|---|---|---|
| **预声明** | **审批【路径】**——走谁、几步、是否需临时申请 | spec / 运维预案中是否事先声明（§23.2、§23.4） |
| **敏感度与爆炸半径** | **审批【层级】**——单签 / 双因子 / 重两签 | §22.4 凭据分级 + 数据分级（S0/S1/S2） |

**判定规则**：

1. **有预声明** ⇒ 路径为「项目管理方逐次判断」，**无须每次找业主**
2. **无预声明** ⇒ 路径升为「业主授权」
3. 🔴 **无论有无预声明，层级仍由敏感度与爆炸半径独立决定**——
   **触及 S0/S1、跨租户、平台域基线者，即使已预声明，仍须按 §23.5 的对应层级审批**
4. 二者冲突时**取更严**

> **一句话**：**预声明能省掉「找谁批」的往返，省不掉「批到什么份上」。**

### 23.2 spec 预授权

| # | 规则 |
|---|---|
| 1 | spec 预授权**须经评审** |
| 2 | **仅在产品定义后 ~ 上线前（研发测试阶段）有效** |
| 3 | 🔴 **产品上线后，spec 作用域失效，须另行授权** |
| 4 | 有效期内**仍须项目管理方逐次判断**（预授权是必要不充分条件） |
| 5 | **无预授权则须业主授权** |
| 6 | 预授权**必须具体**：范围 / 用途 / 时限。**禁用「可能」「视情况」「相关」等不可判定表述，笼统兜底视同无预授权** |

### 23.3 失效由机制触发，不靠人记得

**发版收口（§8.2 第 2 项）同一事务内将关联的 spec 预授权标记 `expired`。**

⚠️ **粒度**：失效须按**「spec 预授权条目 × 其声明的作用域」**判定，**不得按 task_id 一刀切**——
子 spec 收口不应连带失效父 spec 下其他仍在研发期的子 spec。

### 23.4 上线后由运维预案承接

**授权文档随阶段交接**：

| 阶段 | 授权文档 |
|---|---|
| 产品定义前 | 无 → **业主授权** |
| 定义后 ~ 上线前 | **spec 预授权** |
| **上线后** | **运维预案 / 生产访问规范**（K1 知识库第 11 类） |

两者形式对称：**都须经评审、都不自动放行、都须具体到范围·用途·时限。交接点就是上线。**

### 23.5 渠道授权分级

| 级别 | 范围 | 渠道可做到哪一步 |
|---|---|---|
| **查询** | 项目进展（只读，**须走 RLS 过滤后返回**） | 可信渠道即可 |
| **低危** | spec 预授权范围内的一次读取、复盘定稿、**L1 级 node 的门 PASS** | **渠道可终结**（+ 一次性挑战码） |
| **中危** | 单会话 provision、租户级 skill 晋升、跨项目读 | 渠道**可发起**，须**次因子确认** |
| 🔴 **高危** | 全网批量下发、平台级 skill/MCP 晋升、跨租户、S0/S1 凭据、平台域基线变更、**L3 级 node 的门 PASS** | **渠道只能发起，不能终结**；须回强身份面 + **重两签** |

> ⚠️ **门 PASS 不可统一归为低危**（v2.3 更正，评审方指出）：
> **门 PASS 的危险度继承其所属 node 的分级**——
> 一个 L3 node 的架构评审门 PASS，其后果与该 L3 变更等价，**不因「只是打个勾」而变低**。
> ⇒ **规则：门 PASS 的授权层级 = 该 node 的分级层级（L1→低危 / L2→中危 / L3→高危）。**

**授权动作必须绑定一次性凭据**：平台生成 challenge（含**待批事项摘要 + 有效期 + 单次使用**），
业主回复该 challenge 而非自由文本。

> 🔴 **「同意」两个字不构成授权**——它可被重放、可被群内他人冒名、
> 也可能是 Agent 把引用的历史文本当成了新指令。

## §24 平台域基线变更

### 24.1 范围

平台级 skill / MCP / spec 模板的晋升与变更、immutable 名单变更、K0 条目变更、C1 原语面语义变更。

### 24.2 审批形态

| 环节 | 谁 | 产物 |
|---|---|---|
| **整理汇总** | **ops**（平台级） | 批次清单：每项含**谁提的 / 为什么 / 影响面** |
| **集中审批** | **平台管理者** | 对整批签一次（签数按 §24.2a 定） |

- **「平台管理者」是一个角色**，区别于 ops 的整理汇总职能；本部署下由业主担任
- **粒度：批为审批单位，项为追溯单位**——一次签，但批内每项事后可查
- 「影响面」一栏用 §16.4 的 SYNC IMPACT REPORT 格式，不另立

#### 24.2a 🔴 批次的签数由批内最高危项决定

> ⚠️ **v2.3 更正（评审方指出）**：v2.2 写「平台管理者对整批签一次」= **单人单签**，
> 与 §16.5「immutable 名单变更须重两签」、§23.5「高危须重两签」**直接冲突**。

> 🔴 **v2.5 更正（复审指出，本席核实成立）**：v2.3–v2.4 把「平台级 skill/MCP **常规晋升**」
> 列为普通项允许单签，**与 §23.5 明列「平台级 skill/MCP 晋升」为高危须重两签直接冲突**——
> **同一动作在两节得到相反签数**。这是本席在 §24 暗中给它降了级。
>
> **统一为：保留 §23.5，所有平台级 skill/MCP 晋升一律高危、须重两签。**
> （若日后要按内容风险分层，**必须同步重写 §23.5 并定义机器可判的分层属性**，不得在 §24 单方降级。）

| 批次内容 | 签数 |
|---|---|
| 全部为普通项——**未列入 immutable 名单**（§16.5）**且不改变语义**的文案修订 | **平台管理者单签** |

> ⚠️ **v2.6 收窄（复审建议，本席采纳）**：v2.5 举例为「spec 模板小改」，**与 §16.5 已把 Spec Kit 及其模板列入 immutable 首批直接冲突**——immutable 件的任何变更本就须重两签。
> **判据改为「是否在 immutable 名单内」，不举具体件为例**，避免例子与名单打架。

| 🔴 **含任一高危项**——**平台级 skill / MCP 晋升**（任何形式）/ immutable 名单变更 / S0·S1 凭据 / 跨租户 capability / 全网批量下发 / C1 原语面语义变更 | **整批升重两签**（两个**独立** principal） |

**批次 manifest 必须不可变、逐项可追溯**；签名覆盖 manifest 摘要，不覆盖「一堆事」。

**规则：批次的签数取批内最高危项的要求，不取多数，不取平均。**

> **消解方式的选择理由**：另一种做法是把高危项拆出单独走——但那会让「拆批」本身成为一个
> 可被用来降低审批强度的操作。**整批升签更简单，且没有可乘之机。**
> 代价是可能因一个高危项拖慢整批；**这是应当承担的代价**，不接受为效率而降签。

### 24.3 紧急件

安全召回、凭据撤销、下架出问题的平台级件等不了批次周期
⇒ 走**事后 flag 制**，单独放行、事后补入批次。**不新造紧急通道**——新造一条紧急通道，就是新造一条绕过点。

#### 24.3a 🔴 紧急通道只允许单调收紧

> ⚠️ **v2.3 新增（评审方指出）**：不加此限，紧急通道就是一条完整的绕过点。

| 允许（须逐项通过 capability effect 判据） | 🔴 **禁止（增加或放宽）** |
|---|---|
| `disable` / `quarantine` / `revoke`（**须有 fail-closed fallback**，见 §16.6） | **安装或升级任何制品** |
| ⚠️ **`uninstall` 不在允许列**——它可能移除安全控制（§16.6） | —— |
| 吊销凭据、缩短有效期 | **签发凭据、延长有效期** |
| 收紧或删除白名单条目 | **新增或放宽白名单条目** |
| 把件加入 immutable 名单 | **把件移出 immutable 名单** |
| 提高门的强度 | **降低门的强度、跳过门** |

**判据**：该动作**在任何情形下都不可能扩大任何主体的权限或可达范围**，才允许走紧急通道。
**存疑即按非紧急处理（fail-closed）。**

| 其余要求 | 说明 |
|---|---|
| 落账 | 紧急放行**逐次落账**，含发起人、事实依据、时刻 |
| 补审 | **必须进入下一批次补审**；补审否决时须给出回退动作 |
| 计数器 | 「紧急通道中出现放宽类动作的次数」应恒为 0 |

### 24.4 分发面必须校验批准

**分发前须校验台账**：`target` + `version` 必须在对应表中且状态为「已批准」，否则拒发。

> **批准与执行分处两个服务、两套写权**——符合「生产系统中 git 管理员与 DB 管理员不应是同一人」的分离原则。

### 24.5 分发面的其余硬性要求

| # | 要求 |
|---|---|
| 1 | 保留现有五道闸：来源鉴权 / sha256 完整性 / host 白名单 / 动作白名单 / **不执行制品内脚本** |
| 2 | **只下发数据，不下发指令**——更新逻辑固化在接收端，下发方无法改变它 |
| 3 | 版本号**只在收到接收端 ack(ok=true) 后推进**（下发成功 ≠ apply 成功） |
| 4 | 🔴 **管理面必须有角色模型**；provision / api-keys / config 三类高危端点与只读端点分权 |
| 5 | 🔴 **范围闸**：单会话下发 = 平台 ops 单签；**全网批量 = 重两签 + 业主知会** |
| 6 | 装卸对称（§16.6） |

# 第八部 · 平台能力

## §25 界面与入口

### 25.1 审批入口 = 单一 typed 待决队列

**不做成多个页面。** 授权、阻塞、无效讨论的共同点是「**都在等一个人做决断**」；
做成 N 个入口，就要巡 N 个地方才知道有没有事。

| 类型 | 数据来源 | 决断者 |
|---|---|---|
| 授权待批 | spec 预授权、平台域资产下发、上线后运维预案授权 | 按 §23 分级 |
| 当前阻塞 | `blocker_reason` 枚举 + `sla_deadline` | 项目管理方 |
| 无效讨论 | §18.4 解封请求 | 调度者 / 业主 |
| 门 FAIL 待整改 | 门记录 | 执行者 + 门方 |
| 复盘待定稿 | §9 | 执行者 |
| 平台域批次待签 | §24.2 | 平台管理者 |

**每项必带**：类型 / 发起方 / **等待时长** / **逾期标记** / 一键决断入口。

> **「等待时长」是关键字段**——按它排序，直接把「任务丢失、环节丢失、交付物丢失」变成显眼的逾期项。

**所有高危执行面必须从该队列取授权凭据**，不得自带审批。

### 25.2 知识查询入口

- 覆盖 §12.1 全部条目类型
- **必须走 RLS + 条目级分级**，禁止做成「登录即可全文检索」
- **检索在 RLS 过滤后的集合上做**（§13.4）
- 显示条目的 `baseline_anchor`、`updated_at`、生命周期状态（`active`/`suspect`/`archived`）

### 25.3 spec 与架构设计文档查阅入口

**与知识库分开**——知识库是**事实**（现状是什么），本入口是**规范**（约定应当是什么）。

| | 知识库 | 文档入口 |
|---|---|---|
| 时态 | 描述现在 | **约束未来** |
| 生命周期 | 随代码漂移，需锚 | **有版本、有评审状态、有生效期** |

- **spec 须显示**：版本 / 评审状态 / 预授权条目及作用域 / 生命周期状态（§4.3）
- **架构设计文档须显示**：所处评审等级与已过的门——否则无法判断「这份设计能不能作为施工依据」

### 25.4 直连 Agent 的交互通道

**不砍 view 页，sidecar 常开做旁路。**
理由：平台故障时，若唯一通道是平台自身，ops-Agent 无法恢复平台。

## §26 Agent 管理

### 26.1 三种接入形态，信任等级不同

| 形态 | 宿主受控度 | 凭据等级 |
|---|---|---|
| **云上 Agent**（平台新建/关闭/重启） | 平台完全受控 | 可持 S1，按角色授予 |
| **IDE 插件 Agent** | 企业设备，部分受控 | S2 为主；S1 须显式授权 + 时限 |
| 🔴 **本地笔记本 / 台式机 CLI** | **不受控终端** | **默认仅 S2**；S1/S0 须逐次授权 |

**本地接入的 token 必须**：短时效 + 可远程吊销 + 绑定设备指纹；**默认不授予**跨租户与平台域读权。

> 本地终端接入意味着平台凭据离开可控边界，落到平台无法审计、无法擦除的机器上。
> **不设此限，凭据分级会在最薄弱的一环失效。**

### 26.2 导入上下文 = 分层注入

```
新建 Agent(tenant=T, project=P, role=R)
  → K0-pub 全量
  + K0-sec 按需（按 R 的授权）
  + K1（T 的项目 P 知识库，检索式）
  + K2/K3（角色 R 的作用域）
  + 已批准 skill：平台级全量 push + T 已拉取的租户级
```

**沉淀与注入必须同源**（§10），否则会出现「复盘写进了知识库，新 Agent 却读不到」。

### 26.3 管理面新建，下发面复用

**管理面**（新建 / 关闭 / 重启 / 上下文注入决策）属项目/任务侧内核，**新建**；
**下发面**（把 skill / MCP / 代码推到远端）**复用现有 provision 通道**。二者分层，不重复造。

## §27 渠道接入

### 27.1 约束：不增加 Agent 多余负担

**渠道差异必须在平台侧吸收干净，Agent 只见一种统一信封。**

平台侧须消化：消息格式规范化 / 长度上限与分片重组 / 富文本与附件能力差异 /
回执语义归一 / 乱序与重投 / **幂等键贯穿**（重投不重执行）。

### 27.2 本项落在现有通信层的延长线上

按 §2.3 分界原则（「消息如何可靠传到」的保留），渠道接入属通信面，
**是现有能力的扩展，不是新建**。

### 27.3 可信渠道能做什么

| 能力 | 规定 |
|---|---|
| **查询业主项目进展** | ✅ 允许，只读，**必须 RLS 过滤后返回** |
| **执行授权** | 按 §23.5 分级；**高危只能发起不能终结** |

# 第九部 · 纪律与自检

## §28 工作纪律（五条）

| # | 纪律 |
|---|---|
| 1 | **行为证据优先**——断言系统行为须有可复现的行为证据，不以代码阅读或文档描述替代 |
| 2 | 🔴 **声明搜索范围，且搜索范围必须 ≥ 断言的作用域**——对包级现象的断言不得只搜单文件；对全集的断言不得只搜子集 |
| 3 | **反向克制**——撤回一个未经测量的断言时，不得代之以相反的未经测量的断言 |
| 4 | **全文复述同步**——修改一处结论时，须查找并同步全部依赖该结论的表述；**依赖点未必与复述点用同一词汇** |
| 5 | **证据不外推**——子集上的证据不得外推为全集结论 |

**一条动机层纪律**：**不得以「能落在数据上就不落在契约上」为由绕过契约成本。**
凡改变权限或产生副作用的数据变更，须承担相应的契约与审批成本。

## §29 自检通则

> **每加一条流程约束，同时加一个可观测的失效探测手段。**
> 否则约束失效了没人知道——这正是「环节丢失造成项目损失」最隐蔽的一种。

### 29.1 ⚠️ 「恒零计数器」不是唯一形态（v2.2 细化）

逐条配齐（附录 E）后发现：**并非每条约束都能配恒零计数器。** 强行都配会得到一堆永远为 0
且从未被检查的假指标。**按可探测形态分四类，各配各的手段**：

| 类 | 约束性质 | 探测手段 | 失效表现 |
|---|---|---|---|
| **I 恒零计数器** | 运行时可判定的违规 | 计数器，**本应恒为 0**，>0 即告警 | 计数上涨 |
| **II 趋势指标** | 可测但**不应为零** | 阈值 + 趋势告警 | 偏离基线 |
| **III 建成核验项** | 结构性事实，建成即成立 | **一次性核验 + 回归测试钉死** | 回归被改掉 |
| **IV 评审检查项** | 人的判断，机器不可判 | 🔴 **落入 checklist 作为门** | 门方漏检 |

### 🔴 29.1a 四类**不互斥**——一条约束可同时需要多种手段（v2.4 更正）

> ⚠️ **v2.2–v2.3 把四类做成了互斥分类，每条约束只归一处。这是错的。**
> 复审指出：**多数有价值的约束是复合的**——它有一个机器可判的骨架，和一个机器判不了的实质。
> 只配机器项，会放过实质；只配人工项，会放过本可自动拦截的低级违规。

**复合约束的典型形态**：

| 约束 | 机器可判的部分（I/III） | 人机器判不了的部分（IV） |
|---|---|---|
| 预授权**必须具体**（§23.2） | 三字段非空；不含「可能/视情况/相关」等禁用词 | **范围划得够不够窄**、用途陈述是否成立 |
| 跨租户晋升前**须脱敏**（§15.3） | 词表扫描：项目名/表名/内部地址/会话名 | **是否仍能由上下文反推出业务信息** |
| 解封须**回写定义层**（§18.4） | 是否存在指向 spec/constitution/规则表的引用，且该文件在解封后确有变更 | **回写的内容是否真的解决了该分歧** |
| 平台级**准入三判据**（§15.1） | 正文模式匹配是否含具体业务概念 | **移出项目后是否真的仍完整可用** |
| 复盘四段**须实质**（§9.2） | 四段是否齐、是否非空 | **是否敷衍**（「顺利完成」四个字也占满四段） |

> **规则：一条约束若同时具备机器骨架与人工实质，必须在两处都登记，不得二选一。**
> **机器项负责「拦住明显错的」，checklist 项负责「判断剩下的对不对」。**

**第 IV 类仍是关键**：把机器判不了的东西硬配成计数器，等于假装它被管住了。
其正确归宿是 checklist（reviewer-owned，§4.1）——这也是 §0.4 第 2 项必须由评审方产出的原因之一。

**完整逐条映射见附录 E。** 核心恒零计数器（第 I 类）：
