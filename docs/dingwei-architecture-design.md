| 件 | 回答的问题 | 变了要做什么 |

#### A§0.1a 「只锚不述」的准确口径（v0.2 补，甲域 sol 实测本件做不到）

> ⚠️ **原文写成了绝对自律，而本件做不到** —— 甲域实测出 A§3 / A§4 / A§9 / A§13 四处规范性复述。
> 一份架构文档若一句规则都不许摘，读者每读一段都要跳去 SpecDoc，反而没人读。
> ⇒ **把口径改准，而不是假装遵守**：

| | 允许 | 禁止 |
|---|---|---|
| **架构不变量** | 一句话摘要 ＋ `§X` 锚（如「门方 ≠ 执行者，见 §5.8」） | —— |

| **判据与阈值** | —— | **抄写具体值**，一律指锚 |

🔴 **冲突时以 SpecDoc 为权威**：本件任一摘要若与 SpecDoc 不一致，**以 SpecDoc 为准，本件即为缺陷**。

🔴 **A§ / § 切分把「双命中」变成了「可解析但可能指错」——消除的是歧义，不是错误。**

⚠️ **本件不自报 § 引用数**（同 E.3 #36「计数型表述不写死数量」）——
早前正文写过「53 个 § 引用」，那是手写值，内容改过之后就不对了，被甲域实算打脸。

### A§0.2 抽象层原则（业主定）

> **架构描述停在能支撑理解与决策的抽象层。**
> 抽象层记录的不是「实现是什么」，是「**你据此该怎么做**」。

⇒ 本件**不画**真实 IP、主机名、端口全集、代理链细节。

🔴 **口径收窄（v0.2，甲乙两域口径统一）**：甲域指出 A§8 写了 `127.0.0.1` 与反代路径，与本节自禁冲突；
乙域清查后判定 `127.0.0.1` 属**架构关系（回环）**，不是真实部署标识，PASS。**两说都对，是本节口径写宽了。**

| 允许 | 禁止 |
|---|---|
| **架构关系性标识**：`127.0.0.1` / `localhost` / 「经反代」/ 组件间调用方向 | **可定位到具体机器的**：真实 IP · 主机名 · 内网段 · 代理链拓扑 |
| **对外语义路径前缀**（如 `/dingwei/`），因其属**接口契约**，非部署标识 | **端口全集**与其绑定关系 |

**判据：这个值换一台机器部署还成立吗？** 成立 ⇒ 是架构关系，可写；不成立 ⇒ 是部署标识，不写。
业主原话：「实现了从 A 城到 B 城的集群，但对研发来说理解为同一套机制，
至于实际数据在哪里如何存储，不影响开发测试就可以了。」
⚠️ 那些内容属 **D0 · `restricted`**（§11.4a），不落本件（§22.4 S0 亦不落任何文档）。

### A§0.3 🔴 现状 / 目标 / 差距 三分，不得混写

架构文档最常见的失败是**把「想要的」写成「有的」**。本件每个要素强制标注：

| 标记 | 含义 |
|---|---|
| ✅ **现状** | 代码里已有，本件写作时实测过 |
| 🎯 **目标** | SpecDoc 已定但代码未实现 |
| ⚠️ **差距** | 现状与目标的距离，**须有承接的子 spec** |

⇒ **凡标 🎯 者，不得作为「系统已具备」对外陈述**（同 §28「声明搜索范围，且搜索范围须 ≥ 断言作用域」；E.4 #58 是其在「所有 X」类表述上的实例）。

### A§0.4 本件自身的门

**本件尚未过架构评审 ⇒ 不得作为施工依据**（§25.3）。
与 SP7a「形态已定为受控仓储 API」是两回事：**形态定了，设计未过审**。

# 第一部 · 业务架构

## A§1 业务实体与关系

```
  人（企业 IM 身份）
   └─→ 租户（业主级隔离域，隔离主体）        ← §21.1 三级映射
        ├─→ 项目（D3 归属域）
        │    └─→ 任务 / node（执行单元）
        └─→ 会话 / Agent（执行主体，持 token）

  横切三类资产（共用归属域轴 D0–D3 与晋升链）： ← §11.2
    知识条目 · skill（过程性记忆） · MCP
```

**一个人可在多个租户有身份**（§21.1）—— 这条决定了很多东西：
周报「人视图」须按 `(人 × 租户)` 出（§20.1）、跨租户读须 §22.1c capability（SA-10）。

## A§2 业务主链：从需求到知识沉淀

```
  ① 需求提出
      └─→ ② spec 起草（五个必备面，§4.7.1）
            └─→ ③ 准入硬门（§4.6.2，机器判）
                  ├─不过─→ 【待完善池】（带结构化缺项原因）──回炉──┐
                  │                                                  │
                  └─过──→ ④ 人审（§4.6.4）──不过─→ 【待完善池】──────┘
                              └─过─→ 【待认领开发任务池】
                                        └─⑤ 认领（此后正文不得再改，§4.7.3 #3）
                                              └─⑥ node 派发（不可变快照，§11.6）
                                                    └─⑦ 门（§7 门禁纪律）
                                                          └─⑧ 收口（§8.2 四交付物）
                                                                └─⑨ 知识沉淀（§12/§13）
                                                                      └─⑩ 复盘（§9.2）
```

**三处是这条链的承重点，其余都可调**：

| # | 承重点 | 为什么 |
|---|---|---|
| 1 | **③④ 之间机器与人的分工** | §4.6.4：机器决定「是否值得占用人审」，**不决定「是否需要人审」** |
| 2 | **⑤ 认领后 spec 冻结** | 否则「认领的是 A、做的是 B」，而 `acceptance` 是按 A 生成的 |
| 3 | **⑥ 派发快照不可变** | 修订 node 不依赖 worker 记忆（§11.6）；快照可变则复现不可能 |

## A§3 角色对架构的两条要求

> ⚠️ **v0.2 删去原角色 × 权限矩阵**（甲域 sol：那是 §5.8 / §21 / §23 的**规则正文**，属 A§0.1a 禁止的成条复述）。
> 角色权限一律见 **§5.8 门方矩阵 · §21 身份模型 · §23 授权**。本节只留**规则对系统构成提出的要求**：

| # | 架构要求 | 锚 |
|---|---|---|
| 1 | **执行者与门方须能被系统区分**——不是靠流程约定，而是数据模型里两者是不同字段、且可比对 | §5.8 · E.1 #3 |
| 2 | **一人多角是常态**，故权限须挂在**「人 × 域」**上，不是挂在「人」上——否则 D2 的 ops 会顺带拿到 D0 权限 | §11.2 · §21.1 |

🔴 **第 2 条是本件对数据模型的硬要求**：`principal` 单独存不够，**必须与 `domain_level` 一起构成授权判定的输入**。

#### A§8.3a 🔴 紧急面的可达性边界（v0.3 更正，乙域 terra AD-SA-03）

> ⚠️ **本席上一版写「ops 紧急面必须有独立于边缘层的可达路径」—— 那是自造，且有害。**
> §25.4.2 的云端紧急路径原文就是「浏览器 → **Nginx** → `127.0.0.1` sidecar」；
> §25.4.2a 要求的是**不消费平台令牌、不访问平台应用层**，Nginx **只做固定会话的转发**。
> ⇒ **「不依赖平台应用层」被本席读成了「不经过 edge」。**

🔴 **依赖 ≠ 路径。** 这是本席这轮的新错法，与之前三次同族但形状不同：
前三次是**拿一个安全属性冒充另一个**（限制输出冒充授权 · 不泄漏存在性冒充拒绝 · 入口收口冒充隔离）；
这次是**把「不依赖 X」推成「不经过 X」** —— 一个是**故障传播关系**，一个是**网络路径**，两回事。

⚠️ **而且推错的方向恰好是扩攻击面**：真去建第二入口，它就绕过了 edge 的
**剥头（A§8.1 #2）· 日志遮蔽 · TLS · 限流 · 路由隔离**，
且第二入口自身的认证 / 固定 `target_session` / 能力收窄 / 审计 / 网络暴露**一条都还没定义**。

**⇒ 采纳 terra 方案 A（＝现行 SpecDoc 设计）**：

| # | 架构约束 | 锚 |
|---|---|---|
| 1 | 紧急面**独立于平台应用层与常规认证路径**，**但仍经 Nginx edge 固定转发** | §25.4.2 · §25.4.2a |
| 2 | **常规 / 紧急两条路由在 Nginx 配置上分开，且不可互相降级** | §25.4.2a |
| 3 | 紧急路由**不消费平台令牌**；认证**全部在 sidecar 本地**完成 | §25.4.2a |
| 4 | **edge 是可用性依赖**：平台应用挂、而 edge ＋ sidecar 存活时，紧急面**仍可用** | §25.4.2a |
| 5 | 验收沿用 §25.4.2a 既有负测（平台完全不可用且无有效令牌时仍能认证；两条路由不得互相降级或越权） | §25.4.2a |

⚠️ **「抗 edge 故障」是另一个目标，业主未提出。** 若日后确要，须另立 L3 设计并定义第二入口的
认证 · 仅到 sidecar · 同等或更严的最小能力 · 审计闸 · 限流 · TLS · 网络暴露面 · 不可降级负测 ——
**不得由本件顺手推出**。

> 而后者才是隔离本身 —— 一个规规矩矩传了 A 租户 `TenantCtx` 却去读 B 租户资源的调用，
> 甲组三条**一条都拦不住**。本席原表把「入口收口」当成了「隔离达成」，
> 与 SA-10「限制输出冒充授权」、PB-01「不泄漏存在性冒充拒绝」是同一个滑坡的第三次。

**跨租户读须【四项同时】验（§22.2a #3）**：

| # | 断言 | 为什么不能省 |
|---|---|---|
| 1 | **PEP 在 selector / 资源解析【之前】拒绝**；仓储查询 spy 计数 **＝ 0** | 与 #2 **独立验**，否则漏掉「**先查了再拒**」——对外拒了，但查询已落到库上，跨租户读实际发生过 |
| 2 | 调用语义为 **deny**；**禁 200 / 禁成功空集合** | 「成功的空集合」把 fail-closed 降格成一次看似成功的查询（§22.2a #2a） |
| 3 | 目标**存在与不存在**的响应不可区分——**状态码 · 响应体 · 时延**三者皆同 | 任一维可区分，存在性即已泄漏（时延维机器不易判 ⇒ E.4 #64 人审） |
| 4 | **最小化拒绝审计存在**（源 principal · 派生 tenant · 请求 op · capability/policy 判定 · 时刻） | §22.2a #2b；且内容须最小化，**不得回显判定器输入**（§22.5 #5） |

⚠️ **#1 与 #2 必须分开验**，这是本组的骨：只验 #2 会让「先查再拒」通过验收。

⚠️ **不可回滚风险**：SP7b（领域 schema 迁移与 cutover）按 §0.3 **由各领域 spec 自己交付**，
不作统一前置——因为 SP2/SP3/SP5 都会定义各自的领域模型，统一前置会造成循环阻塞。
