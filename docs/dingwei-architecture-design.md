#### A§0.1a 「只锚不述」的准确口径

| | 允许 | 禁止 |
|---|---|---|
| **架构不变量** | 一句话摘要 ＋ `§X` 锚（如「门方 ≠ 执行者，见 §5.8」） | —— |
| **规则正文** | —— | **成条复述**（判据列表 · 门方矩阵 · 禁用词表 · 审批层级等） |
| **判据与阈值** | —— | **抄写具体值**，一律指锚 |

🔴 **冲突时以 SpecDoc 为权威**：本件任一摘要若与 SpecDoc 不一致，**以 SpecDoc 为准，本件即为缺陷**。

⚠️ **`arch-refcheck.sh` 判不了「引对号引错义」**：

### A§0.2 抽象层原则（业主定）

> **架构描述停在能支撑理解与决策的抽象层。**
> 抽象层记录的不是「实现是什么」，是「**你据此该怎么做**」。

⇒ 本件**不画**真实 IP、主机名、端口全集、代理链细节。

🔴 **口径按下表两列判**（收窄过程见沿革记录 A§0.2 条）：

| 允许 | 禁止 |
|---|---|
| **架构关系性标识**：`127.0.0.1` / `localhost` / 「经反代」/ 组件间调用方向 | **可定位到具体机器的**：真实 IP · 主机名 · 内网段 · 代理链拓扑 |
| **对外语义路径前缀**（如 `/dingwei/`），因其属**接口契约**，非部署标识 | **端口全集**与其绑定关系 |

**判据：这个值换一台机器部署还成立吗？** 成立 ⇒ 是架构关系，可写；不成立 ⇒ 是部署标识，不写。
业主原话：「实现了从 A 城到 B 城的集群，但对研发来说理解为同一套机制，
至于实际数据在哪里如何存储，不影响开发测试就可以了。」
⚠️ 那些内容属 **D0 · `restricted`**（§11.4a），不落本件（§22.4 S0 亦不落任何文档）。

### A§0.3 🔴 现状 / 目标 / 差距 三分，不得混写

架构文档最常见的失败是**把「想要的」写成「有的」**。本件每个要素强制标注：

| 标记 | 含义 |
|---|---|
| ✅ **现状** | 代码里已有，本件写作时实测过 |
| 🎯 **目标** | SpecDoc 已定但代码未实现 |
| ⚠️ **差距** | 现状与目标的距离，**须有承接的子 spec** |

⇒ **凡标 🎯 者，不得作为「系统已具备」对外陈述**（同 §28「声明搜索范围，且搜索范围须 ≥ 断言作用域」；E.4 #58 是其在「所有 X」类表述上的实例）。

# 第一部 · 业务架构

## A§1 业务实体与关系

```
  企业 / 团队（强隔离域，人的集合体）        ← §21.1 租户第一层
   └─→ 人（企业行为的执行责任方）            ← §21.1 租户第二层
        ├─→ 项目（该人即项目负责人）
        │    └─→ 任务 / node（执行单元）
        └─→ 会话 / Agent（行为主体，持 token）

  横切三类资产（共用归属域轴 D0–D3 与晋升链）： ← §11.2
    知识条目 · skill（过程性记忆） · MCP
```

🔴 **租户是【双层】隔离结构，不是单层**（§21.1）：第一层企业、第二层人。
这条决定了很多东西，逐条列在 A§1.1 隔离矩阵。

**一人属且仅属一个企业。** 同一自然人在两个企业各有身份时，
是**两个互不关联的人主体**，其间一切访问按企业间强隔离办理。

### A§1.1 🔴 隔离矩阵（本件对数据模型与部署的总约束）

⚠️ **执行面与沉淀面不是两类【内容】，是同一份内容的两个【阶段】**（§11.3）：
收口前为执行面，经 §8.2「版本摘要 → 晋升归属域」后为沉淀面。
⇒ 「文档」不构成独立一类：规范类文档已是沉淀面；业务文档与项目各环节输出，**收口前属执行面**。

| 边界 | 执行面<br>项目 · Agent · 任务 · **未收口的产出** | 沉淀面<br>**已晋升的** skill · 周报 · 知识库 · 复盘 · MCP |
|---|---|---|
| **企业内 · 人之间** | 🔴 **强隔离**（§22.2a #3 四项全适用） | ✅ 可流通：人主动发起 ＋ ops 核准 ＋ §22.5 敏感内容过滤 |
| **企业之间** | 🔴 **不允许任何交流** | 🔴 **不允许任何交流** |

**架构后果，逐条**：

| # | 后果 |
|---|---|
| 1 | **企业间隔离靠库边界**（一企业一库，A§12）——查询在结构上跨不过去 |
| 2 | **人间隔离靠应用层谓词**（`owner_principal`）——沉淀面流通须能被**选择性打开**，物理隔离做不了这件事 |
| 3 | 🔴 **执行面跨企业不设例外**：一旦跨企业可达，库边界即失去意义 |
| 4 | 🔴 **协作不依赖执行面可见**：人无须看见他人的项目或 Agent，经流通的沉淀面产物即为协作载体 |
| 5 | 🔴 **「不允许」是策略，不是隔离**：策略拦不住配置失误 ⇒ `owner_principal` 谓词与 §22.2a #3 四项负测**照做不误** |

### A§1.2 Agent 的归属与 principal

**Agent 由其所属的人派生**，不得自行构成 principal，亦不得冒充调度者身份。

| 面 | 归属 |
|---|---|
| **资源归属** | 该人 ＋ 其项目 ＋ 角色 |
| **行为归属** | 🔴 **该人的 per-session principal**（§7.1 P1），全程同一个，不得中途重建或降级 |

⚠️ **两套归属必须由同一条链连起来**：建 Agent 时即绑定其所属人的 principal。
🔴 **本件写作时该链尚未实现**（🎯 SP1）：现状是资源归属与行为归属之间**无任何条款连接** ——
建 Agent 只给（人、项目、角色），principal 从哪来没有定义。

🔴 **连带：`门方 ≠ 执行者` 的比对主体是 `principal`**，不是会话、不是 Agent id。
同一人派生的两个 Agent，一个执行一个评审，**判定为门方 ＝ 执行者，拒**（§5.8）。
⇒ 单人场景不默认放行、亦不默认拒死：**L3 级门按 §23.5 走重两签**
（业主 ＋ 一名 principal 不同的外部门方）。依据 §21.3：
「二次验证做到极致，仍然只有一个人在决定……**单人不足以承担其后果**」。

### A§1.3 项目的责任与资产分离

| 面 | 挂哪 | 可否转移 |
|---|---|---|
| **责任** | 该项目负责人（一个具体的人） | ✅ 随人事变动转移 |
| **资产与数据** | **企业** | 🔴 **不随负责人转移或消失** |

⇒ 项目实体须同时具备**企业归属**（不可变更为他企业）与**责任人**（可转移）两维。
⚠️ 二者混为一谈，则人一离职，项目数据跟着走或跟着消失。

## A§2 业务主链：从需求到知识沉淀

```
  ① 需求提出
      └─→ ② spec 起草（五个必备面，§4.7.1）
            └─→ ③ 准入硬门（§4.6.2，机器判）

                                              └─⑥ node 派发（不可变快照，§11.6）
                                                    └─⑦ 门（§7 门禁纪律）
                                                          └─⑧ 收口（§8.2 四交付物）
                                                                └─⑨ 知识沉淀（§12/§13）
                                                                      └─⑩ 复盘（§9.2）
```

**三处是这条链的承重点，其余都可调**：

| # | 承重点 | 为什么 |
|---|---|---|
| 1 | **③④ 之间机器与人的分工** | §4.6.4：机器决定「是否值得占用人审」，**不决定「是否需要人审」** |
| 2 | **⑤ 认领后 spec 冻结** | 否则「认领的是 A、做的是 B」，而 `acceptance` 是按 A 生成的 |
| 3 | **⑥ 派发快照不可变** | 修订 node 不依赖 worker 记忆（§11.6）；快照可变则复现不可能 |

## A§3 角色对架构的两条要求

> **角色权限一律见 §5.8 门方矩阵 · §21 身份模型 · §23 授权** —— 那是规则正文，
> 按 A§0.1a 不在本件复述。本节只留**规则对系统构成提出的要求**：

| # | 架构要求 | 锚 |
|---|---|---|
| 1 | **执行者与门方须能被系统区分**——不是靠流程约定，而是数据模型里两者是不同字段、且可比对 | §5.8 · E.1 #3 |
| 2 | **一人多角是常态**，故权限须挂在**「人 × 域」**上，不是挂在「人」上——否则 D2 的 ops 会顺带拿到 D0 权限 | §11.2 · §21.1 |

🔴 **第 2 条是本件对数据模型的硬要求**：`principal` 单独存不够，**必须与 `domain_level` 一起构成授权判定的输入**。

#### A§8.1 🔴 trusted principal 端到端链（SP1 承接）

现状：nginx 是 HTTP 基础认证，给不出 per-session principal，与 §21.1「审计与授权挂在**人**身上」冲突。

#### A§8.3a 🔴 紧急面的可达性边界

> **§25.4.2 的云端紧急路径原文即为**「浏览器 → **Nginx** → `127.0.0.1` sidecar」；
> §25.4.2a 要求的是**不消费平台令牌、不访问平台应用层**，Nginx **只做固定会话的转发**。

🔴 **依赖 ≠ 路径。** 「不依赖 X」不得推成「不经过 X」——
一个是**故障传播关系**，一个是**网络路径**，两回事。
⚠️ **推错的方向恰好扩攻击面**：若据此另建第二入口，它就绕过了 edge 的
**剥头（A§8.1 #2）· 日志遮蔽 · TLS · 限流 · 路由隔离**，
而第二入口自身的认证 / 固定 `target_session` / 能力收窄 / 审计 / 网络暴露面**一条都还没定义**。
误读经过见沿革记录 A§8.3a 条。

⚠️ **而且推错的方向恰好是扩攻击面**：真去建第二入口，它就绕过了 edge 的
**剥头（A§8.1 #2）· 日志遮蔽 · TLS · 限流 · 路由隔离**，
且第二入口自身的认证 / 固定 `target_session` / 能力收窄 / 审计 / 网络暴露**一条都还没定义**。

**⇒ 采纳 terra 方案 A（＝现行 SpecDoc 设计）**：

| # | 架构约束 | 锚 |
|---|---|---|
| 1 | 紧急面**独立于平台应用层与常规认证路径**，**但仍经 Nginx edge 固定转发** | §25.4.2 · §25.4.2a |
| 2 | **常规 / 紧急两条路由在 Nginx 配置上分开，且不可互相降级** | §25.4.2a |
| 3 | 紧急路由**不消费平台令牌**；认证**全部在 sidecar 本地**完成 | §25.4.2a |

**C.3 已裁：受控仓储 API 单点，强制租户上下文；一企业一 PG 库（A§10.1）。**

🔴 **收编在此不再只是「代码整洁」**：一企业一库之后，**选库＝选 DSN**，

**验收判据**（§22.2c · §22.2a，机器可判）：

**甲组 · 收口是否完成**
- **建库调用集 + 句柄逃逸恒为 0**（唯一判定处 `scripts/repo-boundary-gate.sh`，与 SpecDoc §22.2c 同源）
- 未被仓储包引用的表数 **恒为 0**
- 漏传 `TenantCtx` **编译失败**（负测须存在）
- 🔴 **选库（DSN 解析）只在仓储包内发生**，包外零处 —— 一企业一库的前提（A§10.1）

**乙组 · 隔离是否成立**

> 🔴 **甲组只证明了「收口」与「缺 context 被拒」，证不了「持【有效】`TenantCtx` 的跨租户请求被拒」。**
> 而后者才是隔离本身 —— 一个规规矩矩传了 A 租户 `TenantCtx` 却去读 B 租户资源的调用，
> 甲组三条**一条都拦不住**。
> 🔴 **「入口收口」不得当成「隔离达成」** —— 与 SA-10「限制输出冒充授权」、
> PB-01「不泄漏存在性冒充拒绝」同属**安全属性互相冒充**这一族。

🔴 **四项按【边界 × 资产类】分别适用**（A§1.1），不得一律适用、亦不得一律豁免：

| 四项 | 企业之间 | 企业内·人之间<br>执行面 | 企业内·人之间<br>沉淀面 |
|---|---|---|---|
| ① PEP 前置拒 ＋ spy=0 | 必须 | **必须** | 不适用 |
| ② deny 非空集 | 必须 | **必须** | 不适用 |
| ③ 存在性不可区分 | 必须 | **必须** | 不适用 |
| ④ 最小化拒绝审计 | 必须 | **必须** | 不适用 |

⚠️ 沉淀面「不适用」指**不适用越权负测**，不是不受管 —— 它受流通关口管辖（人发起 ＋ ops 核准 ＋ §22.5 过滤）。
🔴 **企业内人与人之间今天就能验**：两个人即可造测例，不必等第二家企业上线。

**跨越读须【四项同时】验（§22.2a #3）**：

| # | 断言 | 为什么不能省 |
|---|---|---|
| 1 | **PEP 在 selector / 资源解析【之前】拒绝**；仓储查询 spy 计数 **＝ 0** | 与 #2 **独立验**，否则漏掉「**先查了再拒**」——对外拒了，但查询已落到库上，跨租户读实际发生过 |
| 2 | 调用语义为 **deny**；**禁 200 / 禁成功空集合** | 「成功的空集合」把 fail-closed 降格成一次看似成功的查询（§22.2a #2a） |
| 3 | 目标**存在与不存在**的响应不可区分——**状态码 · 响应体 · 时延**三者皆同 | 任一维可区分，存在性即已泄漏（时延维机器不易判 ⇒ E.4 #64 人审） |
| 4 | **最小化拒绝审计存在**（源 principal · 派生 tenant · 请求 op · capability/policy 判定 · 时刻） | §22.2a #2b；且内容须最小化，**不得回显判定器输入**（§22.5 #5） |

## A§15 分级 worked example（组 5：验「定义能否可重复判定、规则是否可复算」）

> 🔴 **本节不依赖系统实现**：它验的是**定义本身**能否让两个人得出同一结果。
> 引擎一致性回归另挂 SP0/SP2（见 A§21）。

**输入**（同一份变更，两名填写者各自独立填）：

> 「给 `session_endpoint` 加一列 `assurance_level`，并在鉴权路径读取它。」

| 属性（§5.2） | 填写者甲 | 填写者乙 | 一致？ |
|---|---|---|---|
| `外部契约变更` | 无 | 无 | ✓ |
| `数据模型变更` | 加列加表 | 加列加表 | ✓ |
| `影响范围` | 跨模块 | 跨模块 | ✓ |
| `在产影响` | 灰度可回滚 | 灰度可回滚 | ✓ |
| `回滚成本` | 需回滚数据 | 需回滚数据 | ✓ |
| **`安全面`** | **是** | **是** | ✓ ← 读取路径进鉴权即为是 |
| `预估节点数` | 3 | 4 | ✗ **数字不参与定级，不影响结论** |

**复算链**（任何人可独立重跑）：

```
规则表 version = RULES-2026.08          ← 权威定义见 SpecDoc §5.4a
安全面 = 是             → R-SEC-01 → L3 · 追加 架构评审(门方须安全角色) ＋ 代码评审
数据模型 = 加列加表      → R-DM-02  → L2 · 追加 文档评审
外部契约变更 = 无        → 无命中
影响范围 = 跨模块        → 无命中   ← §5.6 未为「跨模块」定义追加环节
在产影响 = 灰度可回滚    → 无命中   ← 同上
回滚成本 = 需回滚数据    → 无命中   ← 同上
                        ────────────────────────────────
级别 = max(L3, L2) = **L3**
环节集 = 追加并集 ∪ 基础必过模板（§5.4 规则 2：实现 → 代码评审 → 测试执行）
       = {实现, 代码评审(门方须安全角色), 测试执行, 架构评审, 文档评审}
rule_ids = [R-SEC-01, R-DM-02]
```

🔴 **本链现在可独立重跑**：每个 `rule_id` 与 `version` 在 **SpecDoc §5.4a** 有权威定义，
任何人拿 §5.4a 的表 ＋ 上方七项属性，应得出**逐项相同**的结果。

🔴 **规则表没有的行，样例里不能有** —— 补了就是在样例里悄悄扩规则。
「跨模块 / 灰度可回滚 / 需回滚数据」三项 §5.6 未定义强制追加环节，故一律判「无命中」。
🔴 **一个不能被独立重跑的样例，不构成可重复判定的证据。** 重算经过见沿革记录 A§15 条。

🔴 **可重复判定的判据在这里**：两人对**七项属性中的六项**一致；
唯一不一致的 `预估节点数` 是**规模属性、不参与定级**，故**结论仍一致**。
⚠️ 若不一致的是 `安全面`，级别会从 L3 掉到 L2、门集少两道 ——
**这正是 §5.2「安全面必须是独立维度、不得被『改动小』稀释」要防的**。

## A§17 复盘回写验收场景（组 6 · 设计半）

**场景**：node 触门 → 解封裁定 → 定义层 diff → 四段复盘，**四者须可串成一条链**。

| 环节 | 须留下什么 | 验收判据 |
|---|---|---|
| 1 分歧原帖 | `post_id` + digest | 可定位到具体帖，非「某次讨论」 |
| 2 解封裁定 | 裁定人 principal · 时刻 · 理由 | **理由须指向原帖的具体分歧点**，不得只写「已澄清」 |
| 3 定义层 diff | SpecDoc/架构设计的 commit diff | 🔴 **diff 须真的改了那条有分歧的规则** —— 改了别处即回写未生效 |
| 4 四段复盘 | §9.2 四段齐 | **第 4 段「本阶段的判断失误」不得为空** |

🔴 **链断即未回写**：四环缺任一，或第 3 环的 diff 与第 1 环的分歧点对不上，**判 FAIL**。
⚠️ 这条防的是「开会讨论完了、规则没改」——最常见的假回写。

## A§18 摘要/周报的同源与提示注入威胁模型（组 6 · 设计半）

**同源要求**：摘要输出、原帖引用、台账事实、三视图聚合**须来自同一份 cursor-range**。

| # | 规定 | 判据 |
|---|---|---|
| 1 | 摘要须**逐条带原帖引用**（`post_id`） | 无引用的结论＝不可核，判 FAIL |
| 2 | 台账事实与摘要冲突时**以台账为准**，且须显式标注冲突 | 静默取一边＝掩盖 |
| 3 | 三视图（租户/项目/人）**由同一事实层聚合** | 三视图各自取数即三个事实源 |

**提示注入威胁模型**

| 威胁 | 载体 | 缓解 |
|---|---|---|
| 帖子正文含「忽略以上指令」类内容 | 用户可写的帖子 | 🔴 **摘要 agent 的输入须结构化包裹**，正文只作 data 不作 instruction |
| 附件文件名/元数据携带指令 | 上传面 | 文件名不进模型上下文（同 §22.5 #5 不回显判定器输入） |
| 跨租户内容混入 | 聚合读 | **先经受控仓储 API 按租户过滤、后检索**（§13.4 · §22.2c）；聚合读本身是 §22.1c 的受限面 |
| 摘要结论被当成事实回写知识库 | 回写链 | 摘要入库须标 `derived`，**不得与实测事实同权**（§12.5 权威源） |

## A§19 外部锚设计合同（组 6 · 设计半）

| 项 | 规定 |
|---|---|
| **manifest** | 每批次含：起止 `seq` · 每帖 digest · 批次 root · 前序 root |
| **high-water** | 已锚定的最大 `seq`；**单调不减** |
| 🔴 **前序 root** | 每批 manifest 须含**上一批的 root** ⇒ 形成 hash-chain，**断链可检出** |
| 🔴 **权限分离** | 写外部锚的主体**不得**是可写帖子库的主体 —— 否则同一主体可改帖再改锚，链条无意义（E.4 #24/#34）|
| **RPO** | 锚定周期 ≤ 1 小时；**未锚定窗口内的帖子，篡改防护为零**（须在界面明示，不得默认用户知道）|

⚠️ **本合同不改变现状判断**：外部锚**未建**，故当前对恶意篡改**防护为零**（A§7 已明写）。
本节定的是「建的时候按什么建、验收看什么」，**不是「已经有了」**。
