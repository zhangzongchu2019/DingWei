### A0.4 根因 —— 业主 2026-08-23 补充（**本席核出三层字面证据**）

> **业主原话**：「因为现有平台的实现是基于**通讯能力**的基础上实现的，而不是基于**项目/任务管理**的角度实现的。」

**本席核实：这不是概括，是可以逐表指认的事实。** 搜索范围：`internal/store/migrations/` 全部 31 个迁移、
`internal/datad/pgstore.go` 建表段、`internal/mcs/board/schema.sql` 全文。

#### 证据一：`project` 表里没有一个字段是项目管理的

`internal/store/migrations/0008_projects.sql` 原文：

```sql
CREATE TABLE IF NOT EXISTS project (
  id TEXT PRIMARY KEY, name TEXT NOT NULL,
  notify_chat_id  TEXT NOT NULL DEFAULT '',            -- 通知去哪个群
  notify_bot_id   TEXT NOT NULL DEFAULT 'unifiedrobot',-- 用哪个机器人
  transcript_dirs TEXT NOT NULL DEFAULT '',            -- 从哪读会话记录
  evidence_cron   TEXT NOT NULL DEFAULT '',            -- 什么时候取证
  evidence_tz     TEXT NOT NULL DEFAULT '',
  active INTEGER NOT NULL DEFAULT 1, created_at TEXT, updated_at TEXT);
```

**无 spec、无里程碑、无阶段、无交付物、无验收、无任务关联。**
全部字段是「通知路由 + 取证配置」。周边表同源：`project_weekly_report`（汇报产物）、
`project_aggregate_source`（把几个项目的通知汇到一起）、`project_member(project_id, owner_key)`（`owner_key`=通信 key）。

> ⇒ **「project」在现有平台里的实义是「一个通知分组 + 一份取证配置」。**

#### 证据二：`task` 的归属维度是**会话**，且 task 与 project **不相连**

`internal/datad/pgstore.go` 原文：

```sql
CREATE TABLE IF NOT EXISTS task (
  id TEXT PRIMARY KEY, title TEXT NOT NULL, owner_session TEXT NOT NULL, ...);
```

**归属维度 = `owner_session`（会话），不是人、不是角色、不是项目。**
且该表**无 `project_id` 字段**——**平台里的 task 与 project 之间没有任何外键**。

#### 证据三：任务的起源锚是**一个信封**

`internal/mcs/board/schema.sql:11` 原文：

```sql
CREATE TABLE IF NOT EXISTS task (
  task_id TEXT PRIMARY KEY, board_id TEXT NOT NULL REFERENCES orchestrator(board_id),
  title TEXT NOT NULL, root_body TEXT NOT NULL,
  origin_addr TEXT NOT NULL, origin_envelope_id TEXT NOT NULL, ...);
```

**`origin_envelope_id` 是铁证：任务由消息产生，任务的身份锚就是消息的身份。**
`task_role.who` 的注释也写着「会话/人 标识(如 `zzc-devo48-2642`)」——**先是会话，才是人**。

#### 证据四（结构层）：三个模型分处三个库，互不引用

| 概念 | 落在 | 存储 |
|---|---|---|
| project | `internal/store/` | hub SQLite |
| task（台账） | `internal/datad/` | PG |
| task（DAG 执行） | `internal/mcs/board/` | 另一个 SQLite |

**三库三模型、零外键。** 若当初是从项目/任务管理出发建的，这三者会是**同一棵树**；
现在它们是**三条通信链各自长出来的附属账**。

#### A0.4a 由此得到的结论 —— 以及一处必须讲公道的地方

**⚠️ 先讲公道**：以上不说明现有实现质量差。**恰恰相反——它对自己所建模的东西建得很好**：
provision 作为**消息通道**安全模型扎实；board 的单写者串行化作为**投递线性化点**是正确设计；
`origin_envelope_id` 作为**消息溯源锚**恰如其分。**问题不在质量，在建模中心。**

**⇒ 差距的准确表述**：

> **现有平台：消息是一等公民，任务/项目是消息的附属账。**
> **纲领要求：项目 / 任务 / 交付物是一等公民，消息是它们的投影。**
>
> **这不是加字段能改的，是把主外键关系倒过来。**

这也解释了 §C.4e 五处缺口**为什么会同时出现**——它们不是五个独立疏漏，
而是**同一个建模中心的一致后果**：消息没有「审批」这个概念（消息只有投递保证），
所以 provision 有完整性、有审计、有防降级，**唯独没有「谁准的」**。

#### A0.4b 与 §A0.1 的收敛（本席的分界与业主的根因指向同一条线）

本席在 §A0.1 是**逐组件按证据**划的保留/重建线，事后对照业主根因，**两条线重合**：

| §A0.1 判断 | 该组件建模的是 | 与根因的关系 |
|---|---|---|
| ✅ 保留 provision / sidecar / `store` 迁移框架 | **通信面** | 建模中心与其职责**相符** ⇒ 留 |
| ⚠️ 重构 datad | 台账（骑在通信身份上：`owner_session`） | **半相符** ⇒ 改 schema |
| ❌ 重建 board / mcsd | **任务面**（却以信封为锚） | 建模中心与其职责**错位** ⇒ 换 |

> **⇒ 本席据此把 §A0.1 的分界原则明确化，供实施期直接使用：**
> **凡建模的是「消息如何可靠传到」的，保留；凡建模的是「工作如何被定义、被验收、被追责」的，重建。**
> 新内核以项目/任务/交付物为主体，**现有通信层作为其投影与传输面保留**——两者不是取舍关系，是分层关系。

### B.1 F10 —— 「C1 的概念是什么？」

**C1** 是 `docs/dispatcher-system-P2-contracts.md` 的章节号：**「C1 调度者↔引擎（引用契约，零新语义）」**，
定义调度者与 board 引擎之间的**原语集**（18 个：`CreateTask` / `AddNode` / `SetTaskRoles` / `Send` /
`Processing` / `Terminal` / `Reassign` / `SteerReserve` / `SteerFinalize` / `InterruptIntent` /
`InterruptFinalize` / `Redeliver` / `DeliverFail` / `EnqueueResult` / `AckResult` / `Sweep` /
`Takeover` / `Renew`）。

**关键条款 C1.3**：「C1 引用面的任何语义变更 = 引擎设计变更，**须另开窗重两签**」。

→ **「零 C1」= 不新增也不修改这 18 个原语的语义 = 不必重两签。**

**F10 的实质**：发版的**实际执行**（deploy / rollback）由谁承载？

| 情形 | C1 影响 |
|---|---|
| 由 board **之外**的部署服务执行，board 只记录其回传的 `result_ref` | **零 C1，零重两签** |
| 让 board 自己去执行部署 | **新原语，须重两签** |

→ **按业主 F4' 描述的现状（ops 执行发版），执行层本就在 board 外 ⇒ 大概率零 C1。**
**建议 F10 直接裁为「执行层在 C1 外部，零 C1」**，只需确认 board 不承担执行动作。

### B.2 F11 —— 「capability 与扩 `task_role` 的区别？哪个更有利？」

| | 扩 `task_role` 枚举 | tenant-scoped capability |
|---|---|---|
| 做法 | CHECK 里加 `'ops'`，**per-task** 绑一行 | 独立授权维度：「某 principal 在某 tenant 持有 ops 权限」，**不绑 task** |

| 副作用 | ⚠️ **C2.6「执行席 ≤ 2」**（执行席 = implementer + tester）。加 ops 须决定占不占席，**占了就挤掉真正的执行者** | 无 |

> 是两个不同的问题。

### B.3 F14 —— 「单活消费者的意义？一个帖子被多个 Agent 查询算单活还是多活？」

**「多个 Agent 读同一帖子流」不是多活。**

关键不在「几个 Agent 读」，而在「**同一个 principal 会不会并发读**」：

| 情形 | 判定 |
|---|---|
| 多个**不同** Agent 读同一帖子流 | **各有各的 cursor，互不干扰 ⇒ 单活** ✅ |
| **同一个 principal** 在多 worker / 多容器同时读 | **共享同一 cursor ⇒ 互相推进对方进度 ⇒ 漏读** ❌ |

当前 mcs 模型下一个 node 同时只派给一个 worker（`assigned_agent`），正常是单活。**两种情况会破**：
① 重试 / reassign 时短暂并存；② **200+ Agent 规模下，同一 agent 身份可能在多容器跑**。

> ~~本席建议：默认按多活设计，直接加 `consumer_id`。~~
> ⚠️ **v0.2 精化（评审方 2026-08-24 判断，本席接受）：本席原案太薄。**

**修订建议：数据模型按【多活】预留，运行默认【单活】。**

| 项 | 内容 |
|---|---|
| key | `tenant + node + principal + consumer_id` |
| **consumer 生命周期** | **注册 / 租约 / fencing / 回收**——**一个字段不是完整保险**；无生命周期管理会出现**无限 consumer 放大重复投递** |
| **两种多活语义须分辨** | ① **竞争消费**（同 principal 多 worker 分担）→ **消费组共享进度**<br>② **每个 worker 都必须获得上下文** → **各自 consumer cursor** |
| 与投递账的关系 | `delivery_id` / outbox / ACK **仍独立**，不由 cursor 承担 |
| 上线策略 | **预留字段不必等业主确认；但运行默认单活，待多活测试后再开启** |

> **本席原错**：把「加个字段」当成了完整方案。
> `consumer_id` 本身是**一整套生命周期**（注册/租约/fencing/回收），不是一列。
> 且本席**未分辨「竞争消费」与「各自需上下文」两种语义**——它们的正确解法不同（消费组 vs 各自 cursor）。
> **仍需业主确认实际语义**，但预留可先做。

### B.5 F7'' —— 「平台域是什么？」业主点破了本席造的一处歧义

## C. 待团队形成建议（业主上线前收敛）

### C.1 F1'' 信号的具体落法 —— 本席建议：**不动 CHECK 枚举**

业主裁定「须有信号告知所有参与方停止读写、进入等待态」。落法有三选：

| 方案 | 代价 | 评价 |
|---|---|---|
| 复用 `blocker_reason='awaiting_input'` | 零 schema 变更 | 语义贴合（确实在等人裁），但**与其他等待原因混淆，无法区分是"等输入"还是"触门"** |
| 新增枚举值 `thread_gate` | **CHECK 变更**（撞迁移机制；PG 下成本低但非零） | 语义最清晰 |
| **独立闸态字段 / 表**（如 `node_thread_gate(node, state, quota, unlock_count)`） | 新表，**无 CHECK 变更** | ✅ **本席倾向**——闸态本就是独立于 blocker 的一个维度，且要记配额与解封次数（F1' 需要） |

> **本席建议：第三方案（独立表）。** 理由：F1' 的递减配额**必须持久化**，无论如何要建表。
>
> ✅ **评审方判定：独立 `node_thread_gate` 是【正确建模】，不是旁路。**
> 理由：**闸态 / quota / unlock_count 与 node 执行生命周期【正交】**；
> 塞进 `awaiting_input` 或新 status **都会制造状态笛卡尔积**。既然配额必须持久化，独立表最自然。
>
> ⚠️ **但评审方同时纠正了本席一处错误论证**：
> **【避开 CHECK 迁移 ≠ 避开契约成本】。**
>
> gate / unlock **会改变可读写权、配额并发与通知**，因此**仍须新增一个 guarded primitive / capability**，
> 且必须具备：**受授权 · 幂等 · CAS/代际 · 审计 · 与 outbox 原子**，并**过相应设计门**。
>
> `thread_gated` 作为**已批准 taxonomy 的 event** 合理，**不必成为 `stateOp`**——
> 前提是**正文不驱动状态**（同 C5 5.0a）。
>
> → **结论：这不是绕契约，而是【把状态放对表，同时诚实承担新语义成本】。**
> **本席原表述「不动 CHECK ⇒ 无 C1 变更」是错的**——真正的成本不在 schema，在新增的 guarded primitive。
> 本席问「是不是又在找旁路」，答案是：**建模对了，成本算错了。**

### C.2 F9 威胁模型的具体落法 —— 本席建议复用 git 作外部锚

业主裁定「有限范围内尽可能做高 + 有健全追踪机制即可」。三档：

| 档 | 措施 | 成本 |
|---|---|---|
| 最低 | 封存后 DB 层拒 `UPDATE`/`DELETE`（权限或 trigger） | 低 |
| 中 | digest 写入**仅平台域高权限角色可写**的表；日常 ops 无写权 | 低 |
| **高** | **定期外部锚定** | —— |

> **本席建议「中 + 高」，高档复用 git 作外部锚。**
>
> ✅ **评审方判定：git 锚【可满足】当前目标（内部半可信、检测 DB 侧篡改），但有七项前提条件。**
> **不满足这些条件，它就只是「另存一份 hash」，不构成锚定。**

| # | 条件 | 防的是什么 |
|---|---|---|
| 1 | **独立 anchor 仓 + 独立 bot 凭据** | 与业务仓、与 DB 权限分离 |
| 2 | **protected branch：禁 force-push、禁删历史** | 事后改写 |
| 3 | **签名提交**（建议） | 冒名提交 |
| 4 | **多地只读镜像** | 单点失效 |
| 5 | **root manifest 须含：日期 / tenant 范围 / digest 数量 / DB cursor high-water / 前一日 root** —— 形成 **hash chain** | ⚠️ **omission attack**：只 push 一个裸 root，攻击者可在计算 root 前**删掉记录**，缩小后的集合仍能算出合法 root。**须靠数量 + cursor high-water + 链式前值才能检出漏项与重排** |
| 6 | **DB 回写 anchor commit** + **独立定时任务反向核验** | 单向锚定无人核验 = 无效 |
| 7 | **写明 RPO** | 每日窗口 ⇒ **当天内的攻击不可即时发现** |

> ⚠️ **独立性前提（评审方特别指出）**：
> **git 管理员与 DB 管理员若是同一人 / 同一凭据，独立性即失效**，整个锚定退化为「另存一份 hash」。
>
> ✅ **业主 2026-08-24 确认，该前提【成立】**：
> 「生产系统中不会出现 git 管理员和 DB 管理员是同一个，**git 管理员、CI、DB、日志等都会有专门的 ops 维护**」。
> → **git 锚方案的独立性前提已满足，F9 可按 §C.2 七项条件落地。**
>
> **本席原案漏了 omission attack 与独立性前提**——只想到「改不掉已 push 的历史」，
> 没想到**攻击者不必改历史，只需在生成 root 前少放几条**。

### C.3 F4' 发版环节 —— 业主给了现状，本席补缺口

**业主描述的现状**：开发者提交 → coordinator 决定时机 → 业主授权 → ops 执行（不同项目不同 ops）；
发版前准备一键回滚、监测标准。

**建议的 node 模板**（发版 task）—— **v0.3 按评审方口径修订**：

> ✅ **评审方确认本席指出的三处缺口成立**：
> 「**回滚包 ≠ 回滚判据；灰度观察 ≠ 有人出门结果；失败也必须区分瞬态重试与实质修订**」。

**最小主链（8 格）**：

| # | 环节 | 类型 | 关键交付物 / 判据 |
|---|---|---|---|
| ① | 发布请求 | 执行 | **immutable release manifest + 基线锚**（commit 40hex / 制品 sha256）+ 影响面属性（复用 Q1） |
| ② | **readiness 门** | **门** | 备份 · 回滚命令 · **回滚阈值与负责人** · 监测窗口（v0.3：原「预案就绪」并入此格） |
| ③ | 业主审批 | 门 | C3.1 格式决策记录 |
| ④ | 灰度执行 | 执行 | 执行记录（谁/何时/何命令）+ 可中止点 |
| ⑤ | **灰度观察门** | **门** | 观察窗实测 + **门方裁决**（v0.3：原「观察期 + 观察期门」两格合一） |
| ⑥ | 全量执行 | 执行 | 执行记录 |
| ⑦ | **全量观察 / 交付验证门** | **门** | **v0.3 新增——本席原稿漏了这一格**。全量后仍需观察与出门 |
| ⑧ | 收口 | 门 | 调度者唯一关闭权；版本摘要 → 晋升 K1；**+ spec 预授权失效登记**（v0.6 新增，见 §C.4d-2d——上线动作本身触发授权失效，不靠人记得） |

**回滚的正确位置（v0.3 更正）**：

> ⚠️ 本席原稿把 rollback 画成**末尾一条独立分支**。**错。**
> **rollback 是挂在 ④–⑦ 每个阶段上的【事件分支】**，任一阶段都可触发。

**触发矩阵必须写全五项**：**指标 · 阈值 · 持续时间 · 裁决者 · 自动或人工**。

**失败后处置必须三分（本席原稿笼统当一件事）**：

| 失败类型 | 处置 |
|---|---|
| **执行瞬态故障** | **同 delivery 幂等重试**（不新建 node） |
| **产物 / 方案缺陷** | 走 **`append_revision`** 建修订 node |
| **回滚后是否重发** | **必须新 revision + 新审批**；**不得在原节点直接 `resume`** |

> 最后一条是安全规则：**回滚意味着上一次审批的前提已被推翻**，
> 原审批不能自动继承到重发。

### C.4d F7' 授权流程 —— 业主裁定：**由「是否事先在文档中声明」决定审批层级**（v0.5 新增）

**业主 2026-08-24 裁定**：

> 若在项目开工时可确定、且**项目文档中有记录** → 由**项目管理者（如 coordinator）授权业务侧 ops 执行**；
> 若**文档中没有记录、属临时起意** → **须业主本人授权**。
>
> **可推广**：系统内的数据读取，若由相关文档**预先授权**，仍需要相关管理方（Agent）**判断 + 授权**；
> 若**没有预设的设计文档授权**，则需**业主授权**。

#### C.4d-1 本席对该原则的理解（请业主校正）

**核心是一次判据的转移**：

> **审批层级不由【数据有多敏感】决定，而由【是否事先在设计文档中声明】决定。**

| 路径 | 前提 | 批准方 |
|---|---|---|
| **预授权** | 设计文档中**已具体记录**该访问需求 | **调度者**（但**仍须逐次判断**，非自动放行） |
| **临时起意** | 文档无记录 | **业主本人** |

**两点必须写清**：

1. **预授权是【必要不充分】条件。** 有文档记录 ≠ 自动放行；
   业主原话「**仍需要相关管理方（Agent）判断 + 授权**」——**逐次判断这一环不能省**。
2. **「有无文档记录」是可重复判定的**（是/否），满足增补提案 §6.1.1 的判据要求——
   这比「数据敏不敏感」这种程度判断稳得多。

#### C.4d-2 这条原则的分量：**设计文档成为授权凭证**

本席认为这条**超出 F7' 本身**，是一条平台级原则：

- **spec / 设计文档不再只是「说明做什么」，而同时是「预先批准了什么」。**
- 这与纲领总纲「**产品定义驱动**」同源：访问需求若属产品定义的一部分，就在**设计阶段**被审批；
  未在定义中出现的访问 = **未经规划的偏离** ⇒ 必然升业主。
- **它天然制造正向激励**：提前声明可降低后续审批负担，临时起意则代价最高。

**由此产生一个必须同步的要求**：

> ⚠️ **spec 评审从此带有安全权重。** 若某份 spec 预授权了跨边界读取，
> **评审该 spec 的门方，就是在批准未来的数据访问**。
> → **门方人选须能判断该访问是否正当**，不能只看技术可行性。
> → 建议在 §6.2.5「门方也是矩阵的输出列」中补一条：
> **凡 spec 含跨边界数据访问声明，其文档评审门方须含有权批准该访问的角色。**

#### C.4d-2b 预授权的生命周期（业主 2026-08-24 补充四条，v0.6 新增）

**业主补充**：

> ① spec 预授权**需要经过评审**
> ② spec 预授权**仅在该产品定义后 + 研发测试阶段有效**
> ③ **产品上线后，spec 的作用域失效，需要另外的授权**
> ④ spec 预授权**有效期内，仍需要项目管理方判断**
> ⑤ **spec 是基础，没有这个预授权就需要业主授权**

**②③ 是本席没想到的一个洞。** 原模型里，spec 里写下的预授权会**永久有效**，
包括延续进生产——而**同一个访问动作在测试期与上线后的爆炸半径完全不同**
（与业主 §C.4c 的凭据分级判据同源：沙盒可重置 ⇒ S2；生产不可 ⇒ S1）。
**授权不该跨越这个分界继承。**

**修订后的完整模型**：

| 阶段 | 授权来源 | 是否自动放行 |
|---|---|---|
| 产品定义**之前** | 无 spec ⇒ **业主授权** | 否 |
| 产品定义后 ~ **上线前**（研发测试阶段） | **spec 预授权（须经评审）** | **否——仍须项目管理方逐次判断** |
| **上线后** | ⚠️ **spec 作用域失效 ⇒ 须另行授权** | 否 |

#### C.4d-2c 上线后由谁授权 —— 由「运维预案」承接（✅ 业主已批 2026-08-23）

业主指出上线后「需要另外的授权」，但未指定来源。**按业主自己确立的原则

#### C.4d-2d 失效由机制触发，不靠人记得（✅ 业主已批 2026-08-23）

**②③ 制造了一个明确的转换点：上线。** 但**谁来让 spec 预授权失效？**

若靠人记得「我们上线了，spec 授权作废了」——**这就是纲领反复反对的「靠记忆不靠机制」**。

> ✅ **业主已批**：把「使相关 spec 预授权失效」写成**发版收口的一个副作用**。
> 即 **F4' 第 ⑧ 格「收口」**（调度者唯一关闭权）执行时，
> **同一事务内**将该 task 关联的 spec 预授权标记为 `expired`。
>
> 这样：**上线动作本身即触发授权失效，无需任何人记得。**
> 且它天然落账（收口本就要写 `board_event`）。

✅ **业主已批**，F4' 第 ⑧ 格交付物除「版本摘要 → 晋升 K1」外，**增加「spec 预授权失效登记」**（已同步改 F4' 表）。

> **一处实施注意（本席标注，不另立待裁）**：收口时该 task 关联的预授权可能**不止一条**，
> 且可能有**跨 task 共享的预授权**（同一 spec 拆多子 spec 的场景——业主已明确会出现）。
> 故失效动作的粒度须按 **spec 预授权条目 × 其声明的作用域**判定，**不能简单按 task_id 一刀切**：
> 子 spec 收口不应连带失效父 spec 下其他仍在研发期的子 spec。**实现期必须处理，否则会误伤。**

#### C.4d-3 ⚠️ 必须现在堵的一个漏洞：预授权被写宽

**可预见的规避方式**：在 spec 里写一句笼统的兜底
（如「本项目**可能需要**读取相关租户数据」），即可永久绕开业主审批。

**这与增补提案 §6.2.6「分级不能由执行者自己填」是同一类风险**——
只是这次被规避的不是分级，而是审批层级。

**建议约束（本席提出，待裁）**：

> **预授权必须是【具体的】，否则不成立，视同无预授权。**

| 必填 | 说明 |
|---|---|
| **范围** | 哪些租户 / 项目 / 数据类别 |
| **用途** | 为完成哪个环节所必需 |
| **时限** | 有效期；**不得无限期** |
| **不得使用** | 「可能」「视情况」「相关」等**不可判定**的表述 |

**判据同 §6.1.1**：**若两个人读同一份预授权得出不同的「这次访问算不算被覆盖」，则该预授权无效。**

#### C.4d-4 落账字段（回答 F7' 原问题）

| 路径 | 落账内容 |
|---|---|
| 预授权 | **spec 文档引用（commit 40hex + 锚点 + sha256）** · 调度者**逐次判断记录** · 实际范围 · 时限 · 用途 |
| 业主授权 | **C3.1 格式决策记录** · 范围 · 时限 · 用途 · 业主 principal |
| 两者共同 | 落 `board_event`；**强制记 actor**（禁匿名事件，同既有 `insertEvent` 约束） |

> 仿 C2.6 `role_exemption` 的既有口径：**可审计，不可匿名突破。**

### C.4c 凭据分级判据（v0.4 新增，据业主补充形式化）

#### C.4e-3 本席建议方案（待裁）

**建议一：资产台账统一到「一类资产 = 一张表 + 一个批准端点」，三类齐备。**

| 资产类 | 台账 | 批准 | 现状 |

| **spec 模板** | 需新增 `spec_template` 表 | 需新增 approve 端点 | ❌ 缺（新资产类） |

**建议二：provision 下发改为「只能下发台账里 `approved` 的制品」。**

即 `manageProvision` 在 `SendProvision` 前增加一次台账校验：`target` + `version` 必须在对应表中且 `status='approved'`，否则 409。
**这一条同时闭合缺口 1 和缺口 4**——审批不必在后台页面上新做一套 UI，**复用 datad 已有的批准流即可**；后台只是执行面，批准发生在台账面。

> 本席认为这比「在后台加一个审批按钮」更好：**批准与执行天然分处两个服务、两套写权**，
> 符合业主 §C.4c 关于「生产系统中 git 管理员与 DB 管理员不应同一人」的分离原则。

**建议三：批准主体按业主的两类 ops 划分改判。**

T18 设计定的是「批准=coordinator」（2026-08-04），**早于**业主 2026-08-24 的两类 ops 划分。
按业主「生产系统、平台运维、公共资源都是平台级 ops 工作」，spec 模板 / skill / MCP 的全网注入属**公共资源**，
故批准主体应为**平台级 ops**，coordinator 不再是唯一批准者。

⚠️ **但业主 F15 又说「ops 仅听命于 coordinator/业主」。** 二者需要对齐：
本席理解为 **平台级 ops 执行并对制品负技术责任，coordinator 或业主授权**——即**双方各出一签，正好构成重两签**。
**此点请业主确认**，它同时是 F15 的落地形态。

**建议四：`requireAuth` 增加角色。** 当前后台无角色概念，建议二落地前，
至少把 provision / api-keys / config 三类高危端点与只读端点分权。**这是机制约束，不是纪律约束**（业主 F6 原则）。

**建议五：范围闸。** 全网批量下发（`target_mode`=全体）应当与单会话下发**分级**：
单会话 = 平台 ops 单签；**全网批量 = 重两签 + 业主知会**（与增补提案 §F1 阶梯硬门同构）。

### C.4f 平台域基线变更的审批形态 —— 业主裁定（2026-08-23）

> **业主原话**：「平台域基线变更，**一般不会很多变更**，由 **ops 整理汇总**，**平台管理者集中审批**即可。」

**这一条同时关闭了三处悬项**：

| 悬项 | 如何被关闭 |
|---|---|
| **§C.4e 建议三**（批准主体按两类 ops 改判） | ✅ **ops = 整理汇总方（提案），平台管理者 = 批准方**——**分离已成立**，本席所虑的「同一人既维护又批准」不发生 |
| **R2-33**（平台级 skill「专人管理」中管理者是否兼批准者） | ✅ 同上 |
| **F12**（三个 C1 新语义是否攒批一次重两签） | ⚠️ **本席判其落在同一原则下，建议按「攒批 + 集中审批」关闭**。C1 新语义改的是平台自身契约、影响全体，属平台域基线变更。**若业主认为 C1 契约变更须单独处理，请指出。** |

#### C.4f-1 ⚠️ 「一般不会很多变更」是一个**前提**，而 R2 正在让它变松

**攒批成立的条件是量小。** 但 R2 新增的需求会把以下事项都变成平台域基线变更：

平台级 skill 晋升（要求 9）· MCP 晋升（要求 10）· spec 模板变更 · immutable 名单变更（R2-18）· K0 条目变更

> 若再叠加 **skill 自我进化**（R2-17，已改判可进本期）与 **200+ Agent 并行**，
> **候选量可能远超「不会很多」。**
>
> 🔴 **攒批在量大时的失效形态很具体：一次批一大堆没细看的东西。**
> 这不是假设——它是审批制度最常见的退化路径。
>
> **⇒ 本席建议设量的阈值，超过即说明前提失效**（要么准入判据太松，要么确实需要更细的流程）。
> **形式建议复用业主已批的 §F1 阶梯硬门语言**（>20 coordinator 解封并预警业主，>40 业主解封）
> ——**同一个设计语言，不新造。**

#### C.4f-2 ⚠️ 攒批与「紧急」冲突 —— 但纲领已有现成解法，不必新造

有些平台域变更**等不了批次周期**：安全召回一个坏 skill、撤销一个泄露的凭据、下架一个出问题的平台级件。

> **⇒ 建议：紧急平台域变更走【事后 flag 制】（P2 契约 C3.3 已有），单独放行、事后补入批次记录。**
> **不新造紧急通道**——新造一条紧急通道，就是新造一条绕过点。

#### C.4f-3 攒批下「重两签」的粒度：**批为审批单位，项为追溯单位**

| 方案 | 效率 | 可追责 |
|---|---|---|
| 整批一签，批内不留项级记录 | 高 | ❌ 单项责任模糊 |
| 逐项两签 | ❌ 低（违背业主减负意图） | 高 |
| 🔴 **批为审批单位 + 项为追溯单位**（本席建议） | **高** | **高** |

> 即：**平台管理者对整批签一次**；但**批内每一项须独立可追溯**——
> 谁提的、为什么、影响面（此处正可用 R2-29 的 SYNC IMPACT REPORT 格式）。
> **一次签，但事后能查到每一项是怎么进来的。**

#### C.4f-4 ⚠️ 「平台管理者」是谁 —— 须业主明确

业主此处用了一个新词。已有角色为：**业主 / coordinator / 平台级 ops / 租户级 ops**。

> 本席理解**「平台管理者」≠ 平台级 ops**（后者是整理汇总方），故应为 **coordinator 或业主**。
>
> **本席建议：批次的审批人随【批内最高危等级】上浮**（复用阶梯语言）：
>
> | 批次内容 | 审批人 |
> |---|---|
> | 普通平台级 skill / MCP 晋升 | **coordinator** |
> | 🔴 含 **immutable 名单变更**、**影响授权判据的件**（如 Spec Kit 模板，见 R2-27）、**K0-sec 条目** | **业主** |
>
> **请业主确认「平台管理者」的具体所指，以及是否采上浮规则。**
