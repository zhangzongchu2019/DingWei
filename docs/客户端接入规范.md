## 0. 一句话原则

**平台只支持「经实测验证并进入下载区」的 CLI。未验证的 CLI 不接入、不保证。** `CLI_PROFILES` 表 = 白名单，进表 = 验证通过。

---

## 1. 为什么要这条规范（动因）

2026-07-13 发现 **`is_idle` 死锁**：reviewer（opencode）整天没回任何消息 —— 不是失联，是它的 helper 因 `is_idle` 永假、消息永不注入。根因是**平台过去没有「接入前实测忙闲判定」这道门槛**，opencode 带病上岗。

**⇒ 未知客户端 = 未知的忙闲行为 = 潜在死锁。取消「未知客户端」这个类别，问题从根上消失。**

## 2. Driver 模式优先级（选错模式 = 自找死锁）

**同一个 CLI，用不同模式接，风险天差地别**（实例见 §5 Qoder）。按此顺序选：

| 优先级 | 驱动模式 | 忙闲信号 | 输出 | 死锁风险 | 适配 |
|---|---|---|---|---|---|
| **①a 最优** | **headless stream-json**：`cli -p --output-format stream-json`，stdin/参数送消息 | **逐行 JSON 的 `type` 字段**（`thinking`/`tool_call`/`assistant` = 忙；`done`/`result` = 闲）—— CLI **自己声明**的状态，最精细 | 流式结构化 JSON | **无** | CodeBuddy / Qoder / 一代 `-p` CLI |
| **①b 次优** | **headless JSON**：`cli -p --output-format json` | **进程存活**（`poll() is None`=忙，退出=闲，OS 级确定信号；比 ①a 粗但足够） | 完成时一个 JSON | **无** | 同上（不需要流式时） |
| **② 次选** | 交互 + 权威落盘源 | transcript「最后一轮是否 assistant 且完成」/ db「有无进行中 turn」 | 从落盘源读 | 低（用权威源判，非 PTY 代理） | 现存 claude/codex（transcript）、opencode（opencode_db） |
| **③ 禁止** | 纯 TUI 交互，无落盘源 | 只能靠 PTY `last_output_at`（TUI 重绘被 `clean_output` 清空 → 永假） | 猜 PTY | **高（必死锁）** | aider/cline/gemini（无 `output_source`）—— **禁止裸接** |

**忙闲源优劣序（写死）**：**stream-json 事件类型 > 进程存活 > 权威落盘源（transcript/db）> PTY 猜测（`last_output_at`）**。越靠前越确定、越不可能死锁。

**核心结论**：危险的不是「TUI 类 CLI」，是「**用 TUI 模式去驱动一个本可以用 headless 模式的 CLI**」。**优先 headless，能规避绝大多数风险。**

## 3. 接入验证清单（进下载区的门槛，不接受从文档推断，必须实测）

> **今天的教训写死：文档说的 ≠ 实际行为。每一条都要真机跑过。**

**A. 忙闲判定（头号，直接决定会不会 `is_idle` 死锁）**
- [ ] 该 CLI 的权威忙闲信号是什么？（进程存活 / transcript 轮次 / db turn）
- [ ] 启动后**从不产生输出**时，helper 是否会误判为「永远忙」？（就是 reviewer 那个死锁，必测）
- [ ] CLI **正在忙但暂时无输出**（思考 / 跑长工具）时，是否被误判为「闲」而遭注入打断？

**B. 上下文续接（headless 模式的头号问题）**
- [ ] headless 每条消息是独立进程 → **多轮之间怎么保持记忆？**（`--resume` / `--continue` / `--session-id`？）
- [ ] session id 存哪、怎么管、会不会失效？
- [ ] **若无会话续接机制 → 每条消息「失忆」→ 比 `is_idle` 更根本，接入前必须解决。**

**C. 输出与错误**
- [ ] 成功输出格式（JSON schema：回复在哪个字段？有无 status/error 字段？）
- [ ] 退出码：成功 / 失败 / 被打断分别返回什么？
- [ ] 长消息、含特殊字符的消息：走 stdin 还是参数更稳？

**D. 登录态（无头服务器）**
- [ ] token / 环境变量登录怎么配？会不会中途失效？失效了 helper 能不能感知？

**E. 注入与捕获**
- [ ] 消息能被 CLI 正确接收并执行？
- [ ] 回复能被 helper 完整捕获（不截断、不混入控制码）？

**任一项失败 → 不进下载区，不接入。**

## 5. 范例：Qoder CN CLI 接入分析

Qoder 有 TUI 模式（`qoderclicn`）和 Print 模式（`qoderclicn -p --output-format text/json/stream-json`，支持 stdin 管道）。

| 接法 | 结果 |
|---|---|
| **TUI 模式** | 🔴 又一个 opencode —— ANSI 重绘被清空、`is_idle` 死锁；且文档未提它有可查询会话库 → 纯 TUI 高危 |
| **Print 模式 `-p --output-format json`** | ✅ 输出结构化 JSON、忙闲靠进程存活、stdin 送消息 → `is_idle`/`clean_output`/TUI 死锁全部不存在 |

**决定：Qoder 走 headless JSON 模式（优先级 ①）。** 头号验证项 = 上下文续接（`-p` 怎么保持多轮记忆）。

**更大的意义**：`-p --output-format json` 是 claude code 开创、这一代 CLI 通用的约定。**一个通用 headless JSON driver 可能一次适配一大批 CLI**（Qoder / CodeBuddy / 乃至 claude/codex 迁移）—— 见 backlog「headless JSON driver」。

## 5.5 范例：CodeBuddy CLI —— 证明"一代 CLI 同约定"

CodeBuddy 与 Qoder **共用同一套 headless 约定**（几乎逐字一致，都源自 claude code）：
```
codebuddy -p "<消息>" --output-format stream-json --dangerously-skip-permissions
cat error.log | codebuddy -p "分析" --dangerously-skip-permissions        # 支持 Unix 管道输入
```
- **`--output-format stream-json`**：逐行 JSON 事件（`type: thinking/tool_call/assistant/done/result`）→ **最优忙闲源（①a）**。
- **`@tencent-ai/agent-sdk`**：官方 Agent SDK，比子进程更稳（自定义权限回调/Hook）—— **另一条集成路径**（见 §5.6）。
- **环境**：Node ≥ 18.20；认证读 `CODEBUDDY_API_KEY` 环境变量或已登录凭据。

**⇒ Qoder 与 CodeBuddy 用同一个 headless driver 就能接。** 这就是"一次适配一代"。

## 5.6 headless driver 的实现要点与坑（写进开发说明）

**接管子进程的标准做法（全双工管道）**：
- 三管道：`stdin=PIPE`（送消息）+ `stdout=PIPE` + **`stderr=STDOUT`（合并，防死锁）**。
- **后台线程 `readline()` 循环**读 stdout，绝不用 `process.communicate()`（它阻塞到进程结束，破坏实时性）。
- **行缓冲**：`bufsize=1`, `text=True`；注意块缓冲——底层 python 加 `-u`，其它加 `stdbuf -oL`。
- **忙闲**：解析 stream-json 的 `type` 维护 `IDLE/BUSY/ERROR` 状态机；辅以 `psutil` 查进程健康（防僵尸/静默崩溃 → 父进程永远等待）。

**🔴 安全边界（必须写清，不是隐患是设计约束）**：
- headless 模式工具调用无法弹确认框 → **必须 `--dangerously-skip-permissions`（claude/codebuddy 同名参数）**。
- **含义**：该 CLI 能**无人确认地**改文件、发网络请求、跑命令。
- **信任假设**：这在"受控 agent 运维"场景可接受（claude code 自己也这么跑），但 **provision/接入验证必须确认该 CLI 跑在预期的沙箱/工作目录内**，不能让它无边界地动系统。接入验证 §3 增补此项。

## 6. 分发与准入的执行链（与已有机制咬合）

```
实测验证通过 → 进平台下载区(dingwei.wegoab.com/downloads) → 版本门控放行 → provision 分发
   ↑本规范           ↑唯一可信源(provision 白名单已指向它)   ↑跑验证版本   ↑update_self 远程推
```

- **下载区** = 唯一客户端来源（不从别处装）。
- **版本门控**（`WP_VERSION_ENFORCE`）= 确保跑的是验证过的版本。
- **provision `update_self`** = 验证过的新版远程推送（见《设计-provision自动升级通道》）。
