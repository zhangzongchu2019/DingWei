为什么必须有部署锚 §13.2

代码锚检测「条目所述的代码位置变了」；部署锚检测「文档描述的是 A 分支，而线上跑的是 B 分支」。前者查不出后者。

③ 满足条件后，是否一定需要人审？ 业主问 · 拟 §4.6

🔴 本席答：不能因「机器项全过」而免人审。
理由一 · 规范已有明文：§5.4 规则 2「基础必过模板」＝无论属性如何恒必过的最小环节集 （实现 → 代码评审 → 测试执行）。代码评审在任何级别都不可省，spec 同理不应比代码宽松。

理由二 · 免人审会把检查项变成攻击面：一旦「过检查项即免审」，就会出现为过检查项而写的 spec —— 字段填齐、禁用词避开、锚格式合法，而实质仍是空的。
这与本席在评审中被抓出的「按名字判而非按效果判」是同一族错误：检查项判的是形状，人审判的是是不是那么回事。

⇒ 正确关系：机器决定「是否值得占用人审」，不决定「是否需要人审」。

⚠️ 搜索范围声明：以上关于「HTTP 基础认证」的判断来自代码注释；实际 nginx 配置本席无主机权限，未核。 若线上已用更强方式，请 prodops 指正。
⚠️ 一条不能漏的约束：Nginx 的紧急路由不得依赖平台应用层。

⇒ Nginx 须支持两种模式：常规（校验平台签发凭据）· 紧急（直接放行到 sidecar 的紧急端点， 由 sidecar 本地校验临时密码，全程不问平台）。

跨城集群确实有影响开发的时候：一致性模型（跨城多为最终一致，若按强一致写就会错）· 延迟量级（决定超时与重试策略）· 分区行为（网络分区时怎么办）· 数据驻留约束（某些数据不得出城/出境）。

⇒ 抽象层是默认视图；当实现细节会影响开发的【正确性】时，它必须上浮到抽象层。
但上浮的不是「有几个机房」，而是「你据此该怎么做」 —— 例如写「按最终一致编写，勿假设读己之写」， 而不是写「A 城 3 副本、B 城 2 副本」。
抽象层记录的不是「实现是什么」，是「你据此该怎么做」。
📌 由此两条判据其实是同一个问题的两问：
「旧值会不会误导」→ 决定固化还是运行时取 · 「不知道会不会做错」→ 决定该不该写进抽象层。
合起来一句：不知道这件事会不会导致做错？会 ⇒ 必须在知识库里，且停在够用的抽象层；不会 ⇒ 不必写，写了也不必维护。
📌 MCP 动词已经在了，缺的是「查什么」。 §14.3 定的动词集含 list · get · describe · status · diagnose —— status 与 diagnose 正是为运行态查询准备的，只是规范从未说它们查什么。 本次把「运行 pod / 日志 / 数据量」接上去，不必新造动词。
