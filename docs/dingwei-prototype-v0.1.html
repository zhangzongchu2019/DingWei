为什么必须有部署锚 §13.2

代码锚检测「条目所述的代码位置变了」；部署锚检测「文档描述的是 A 分支，而线上跑的是 B 分支」。前者查不出后者。
上表第 3 条即实例：文档写灰度 df40ae38，线上 view_service 实跑 416a1231。 无部署锚，「基于现网代码」的知识库无法成立 —— 它会精确描述一份不是线上那份的代码，比没有更危险。
部署锚由发版收口第 ⑧ 格登记（组件 × 环境 × commit × 制品 sha256），不另造机制。

装卸对称 §16.6

紧急路径可用
disable 停用 · quarantine 隔离 · revoke 吊销
前提：必须存在 fail-closed fallback 或替代控制。停用一个安全门而无兜底 = 门消失 = 权限扩大 ⇒ 该操作不合法，无论多紧急。
紧急路径不可用
uninstall 已移出允许列
判据改为 capability effect，不按动作名：该动作执行后是否存在任一主体权限或可达范围被扩大。
卸载鉴权 / 审计 / DLP / 安全门类制品会直接扩权 —— 「携带有害证据」只证明制品有问题，证明不了删除后的权限效果单调。
会移除安全控制的卸载：必须先切到安全版本或兜底，再卸，走事前审批。
其余：tombstone / fencing —— 卸载留 tombstone，重装同版本必须形成新 installation_generation； 迟到 ACK、旧任务、旧 delivery 不得复活已卸载的实例，按 generation 栅栏丢弃。

三层封存 §18.5 · §18.6

层级封存时机晋升产物状态
node 帖子流execution done ∧ verdict ∈ {not_required, pass, fail}；pending 不封 → 环节小结已封 N-1140
task 帖子流任务收口（调度者唯一关闭权）→ 任务摘要 → K2开着
version 帖子流版本收口→ 版本摘要 → K1开着
「环节结束后还想讨论怎么办」有答案：属于上一层。node 封了 task 层还开着，task 封了 version 层还开着。
返工天然不污染：门 FAIL 走 append_revision 建新 node，新 node 有新帖子流。
封存条件必须含 fail，否则门 FAIL 的 node 永不封存，帖子流长期可写、digest 永不生成。
⚠️ 承诺表述为「篡改可检测（限定威胁模型）」，不是「防篡改」 —— digest 与数据同在一个可写库，能改帖的人通常也能改 digest。
最低配套三项：① 封存后 DB 权限/trigger 拒 UPDATE·DELETE ② digest 覆盖 tenant·node·seq·actor·ts·content 规范序列 ③ 外部或更高权限锚定 ＋ 定期核验（唯一能对抗「改帖者亦可改 digest」的一层）。
未做到第 3 项前，对恶意篡改的防护为零。

摘要 agent §20

触发
事件驱动，不定时轮询：node 进终态 / 触门 / 距上次已积累 N 条新帖
模型
廉价模型 —— 任务是抽取，不是推理
输入
仅增量帖（游标区间）＋ node 结构化头
租户
🔴 必须租户内 —— 它用廉价模型、跑得频繁、读很多帖，是易被忽略的泄漏面
是否入帖子流
不入，单独存 node_digest —— 入了会推高帖子计数、触发硬门， 而摘要恰是解封决策的依据。工具不该污染它测量的东西。
输入信任级
按不可信数据隔离 —— 帖子是 agent 写的文本，可能嵌入针对摘要器的提示注入
🔴 关键决策不得只依赖摘要：解封决策时调度者必须能看原帖。摘要是加速器，不是唯一依据。
且不得声称「可复算：重跑核对」 —— LLM 非确定性，重跑得到的是另一个输出。改为存证 ＋ 引用校验。
