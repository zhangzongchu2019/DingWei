## 0. 本席对十条的结构化理解

业主给的是十条并列需求，但本席核下来它们**不是十件独立的事**，而是三组：

| 组 | 条目 | 本质 |
|---|---|---|
| **甲组 · 经验沉淀回路** | 1 复盘、2 知识库、9 skill 化、10 MCP 化 | **一个发现环节 + 三个固化出口**，共用一套三级晋升 |
| **乙组 · 管理与查阅入口** | 3 审批入口、4 文档入口 | 业主/管理者的**决断面**与**依据面** |
| **丙组 · 身份与接入** | 5 Agent 管理、6 登录验证、7 渠道直连、8 渠道授权 | **谁是谁**，以及**从哪进来** |

> 按组设计比按条设计省一半工作量——甲组四条共用晋升机制与审批闸，乙组两条共用一个待办队列，
> 丙组四条共用一套身份模型。**若按十条各做一套，会做出四套晋升、三个待办页、两套身份。**

## 甲组 · 经验沉淀回路（要求 1 / 2 / 9 / 10）

### 甲.0 回路总图

```
         ┌──────────────── 阶段复盘（要求1，发现环节）────────────────┐
         │  输入：该阶段帖子流 + 交付物 + 门记录 + blocker 记录         │
         └───────┬───────────────┬───────────────┬───────────────────┘
                 │               │               │
         事实类  ▼        操作类  ▼        能力类  ▼
        ┌────────────┐  ┌────────────┐  ┌────────────┐
        │ 知识库(2)  │  │ skill(9)   │  │ MCP(10)    │
        └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
              └───────────────┴───────────────┘
                              │
                  三级晋升（项目级 → 租户级 → 平台级）
                  平台级晋升 = 平台域基线变更 = 走 §C.4e 审批闸
```

**三个出口的判据差异**（不可混用）：

| 出口 | 固化的是 | 判据 | 载体 |
|---|---|---|---|
| **知识库** | **事实**（现状是什么） | 会被反复查询 | 条目 + commit 锚 |
| **skill** | **操作**（我怎么做） | 同一操作序列会再发生 | 步骤包 |
| **MCP** | **能力**（给我一个功能） | 多方反复提出**同类分析需求** | 服务 + API 契约 |

> MCP 有服务端、有 API 契约、有运维成本，**比 skill 重一个量级**。
> 判据必须严于 skill，否则会长出一堆无人维护的 MCP。

### 甲.1 要求 1 —— 阶段性复盘纳入项目管理

**业主原话**：「项目阶段性复盘总结，纳入项目管理的一部分。」

**「纳入项目管理的一部分」= 复盘是交付物，不是自觉行为。** 本席据此提三条落法：

1. **复盘是阶段收口的必备交付物**，与 F4' 第 ⑧ 格「版本摘要 → 晋升 K1」「spec 预授权失效登记」并列。
   **无复盘不得收口**——这是机制约束，符合业主 F6「尽可能机制约束而非纪律约束」。
2. **复盘的输入是现成的**，不需要人回忆：该阶段的**帖子流**（增补提案已解「作业无痕」）+ **交付物清单** + **门记录**（含 FAIL 与整改）+ **blocker 记录**（board 已有 `blocker_reason` 六值枚举 + `sla_deadline`）。
   ⇒ **草稿可由廉价模型生成**（同增补提案 §F 的摘要 Agent），执行者/评审者定稿。
3. **复盘的输出必须分流到三个出口**（甲.0），而不是写一篇存档了事。
   **复盘报告的结构应当强制三段**：本阶段沉淀的**事实** / **可复用操作** / **应固化能力**。
   任一段为空须写明理由——**否则复盘会退化成「顺利完成」四个字**。

4. ✅ **业主已批（2026-08-23）：复盘增设第四段「本阶段的判断失误」。**
   前三段都是「产出了什么」，只有这一段是「哪里想错了」。
   **本席自己十四轮评审中 11 次同类方法缺陷、9 次由他审抓出**，若当时有这一段，第 2 次就该被拦住。

   > **落法要点**：此段的价值全在**能被下一轮读到**。故它不能只存进复盘报告，
   > **须与「坑总结」同一条通路进知识库**（甲.2 第八类），并**参与三级晋升**——
   > 一个项目里犯过的判断失误，租户内其他项目应当读得到。
   > ⚠️ 但**须先脱敏**：判断失误常牵涉具体人与具体事故，晋升到 K0 前须去标识化。

### 甲.2 要求 2 —— 知识库八类 + 界面查询入口

**业主指定的八类**：产品 / 业务（基于现网代码）/ 服务架构 / 网络架构 / 数据库设计 / 各接口业务逻辑 / 各主要对象介绍 / 遇到的各种坑总结。

#### 甲.2a ⚠️ 「基于现网代码」是本条的技术难点，也是最容易做废的地方

业主特意在「业务」后面加了「（基于现网代码）」。**这是要求知识与代码同源，不是手写文档。**

| 类别 | 是否会漂移 | 必须 |
|---|---|---|
| 产品 | 慢 | — |
| **业务（基于现网代码）** | **快** | **绑 commit 锚 + 漂移检测** |
| **服务架构** | **快** | **绑 commit 锚** |
| 网络架构 | 中 | 绑部署版本 |
| **数据库设计** | **快** | **绑 migration 号** |
| **各接口业务逻辑** | **快** | **绑 commit 锚** |
| 各主要对象介绍 | 中 | 绑 commit 锚 |
| 坑总结 | 不漂移（历史事实） | 绑发生时的 commit |

> 🔴 **本席须明确警告**：**不绑锚的知识库，三个月后就是下一个「作业无痕」——看起来有，实际全过期，
> 且比没有更危险**，因为人会信它。
>
> **本席自己踩过这个坑**：三血脉调查中，文档描述与线上实际运行的代码不是一回事，
> 最终只能靠**行为指纹**（信封 meta 键 / 404 来源区分 / renderer blob 字节比对）反推。
> 那次调查之所以要做，正是因为**当时没有一个绑锚的架构知识**。

**落法建议**：每个条目强制字段 `anchor`（commit / migration 号 / 部署版本）+ `verified_at`；
**锚落后于当前 HEAD 超过阈值即自动标 `stale`** 并在界面上显示，不是删除，是**降级为「历史快照」**。

#### 甲.2b 🔴 安全约束：这八类里有三类是 S0/S1 内容，入口不能是全员 wiki

**网络架构**（主机 IP、拓扑）、**数据库设计**（表结构、连接方式）、**服务架构**（部署形态）
——这三类正是攻击者做横向移动最想要的东西。

> 这与裁定记录已确认的一条直接相关：**K0（`/opt/agent-context/`）含主机 IP、会话全名、部署拓扑，
> 未完成分级脱敏前不得开放全租户只读。**
>
> ⇒ **知识库入口必须走 PG-RLS + 条目级分级**（S0/S1/S2），
> **不能做成一个「登录即可全文检索」的界面**。否则一次账号失陷 = 整个平台拓扑外泄。
>
> ⚠️ 尤须注意：**全文检索本身会绕过条目级权限**——检索结果的摘要片段可能泄露正文。
> **检索必须在 RLS 过滤后的集合上做，不能先检索后过滤。**

#### 甲.2d 业主问：「是实现不了，还是不方便接入？还是难在哪里？」

**本席答：都不是。抽取不难，是工程量；🔴 难点在「现网」二字，不在「代码」二字。**

##### ① 先把「抽取」这一半说清楚——它基本不构成难点

| 八类 | 权威源 | 可机械抽取程度 | 说明 |
|---|---|---|---|
| **数据库设计** | `migrations/*.sql` DDL | **高（近乎全自动）** | 本仓 `internal/store/migrations/` 已有 31 个有序迁移，是现成的权威源 |
| **各接口业务逻辑** | 路由注册 + handler | **中** | 端点清单可机械抽（如 `admin.Mount` 里 ~40 条 `HandleFunc` 一次 grep 即得）；**「业务逻辑」是语义，须 LLM 摘要** |
| **各主要对象介绍** | 类型定义 | **中** | 结构可抽，语义须摘要 |
| **服务架构** | 进程 / 端口 / 依赖 + 部署配置 | **中** | 代码给出**应然**，部署配置给出**实然** |
| **网络架构** | 🔴 **不在代码里** | **低** | 在部署环境与网络设备里，须由平台级 ops 维护 |
| **产品 / 业务** | 🔴 **不在代码里** | **低** | 代码只有 implementation，没有 intent。**这是 spec 的职责，不是抽取的职责**（正好接要求 4） |
| **坑总结** | 🔴 **不在代码里** | — | 来自复盘（甲.1），本就不是抽取问题 |

> ⇒ **八类里只有 4 类真正「基于现网代码」**，另 4 类的权威源根本不是代码。
> **这本身就是一条设计结论：知识库不是一根管道，是四根**
> （代码抽取 / 部署环境 / spec / 复盘），**不能指望一个 code-scanner 全包**。

##### ② 真正的难点：**你得先知道「现网」跑的是哪份代码**

**本席对这一点有直接的、代价不小的证据。** 三血脉调查中已核实：

| 组件 | 线上实际跑的血脉 |
|---|---|
| hub | trunk 血脉（`main`） |
| view_service | `feat/dev55-t403-vs-preprod`（`416a1231`，583 行） |
| renderer | **第四条血脉** `review/view-canary-port-r1` |

三份 VS 互不为祖先（主站 583 行 / 灰度 1053 行 / trunk 824 行）。
**当时本席只能靠行为指纹反推**——信封 meta 键、Go 404 与 nginx 404 的来源区分、
renderer blob 跨 268 refs 的字节比对——**因为没有任何一处权威记录说「现在线上是哪个 commit」。**

> 🔴 **⇒ 若在今天这个状态上建「基于现网代码」的知识库，
> 它会精确地描述某一份代码，而那份代码可能根本不是线上跑的那份。**
> **这比没有知识库更糟**——它会让人停止怀疑。

##### ③ 但这个前提条件，**F4' 已经有位置了**

「现网跑的是哪个 commit」不需要新造机制去猜——**它是发版的自然副产品**。

> **⇒ 本席建议（R2-12）：F4' 发版 8 格第 ⑧ 格「收口」的交付物再增一项：
> 「部署锚登记」——组件 × 环境 × commit × 制品 sha256。**
>
> 该格已经在同一事务里做两件事了：**版本摘要 → 晋升 K1**（原有）、
> **spec 预授权失效登记**（§C.4d-2d，业主已批）。**再加一项部署锚登记，成本近于零。**
>
> **收口这一格正在成为平台的「事实登记点」**——三项都是「此刻起，什么变成了既成事实」。
> 这不是巧合：**它是唯一一个既知道『改了什么』又知道『上到哪里』的时刻。**

##### ④ 有了部署锚，「新鲜度」问题随即变成机械问题

| 无部署锚 | 有部署锚 |
|---|---|
| 「这条知识还准吗」= **无法判定** | `entry.anchor` vs `deploy.anchor` **一次比对即得** |
| 重新生成 = 全量重扫（贵） | 只对**两锚之间 diff 覆盖到的条目**重生成（增量，便宜） |
| stale 靠人发现 | **自动标 `stale` 并在界面降级为「历史快照」** |

##### ⑤ 一个多租户下的附加问题（提请注意，非阻塞）

「现网代码」在多租户下有**两个**：平台自身的现网（K0，平台级 ops 域），与各租户业务的现网（K1，租户级 ops 域）。
**两者的部署锚来源不同、权限域不同、脱敏要求不同**（§甲.2b：平台侧的服务/网络/DB 架构属 S0/S1）。
⇒ **抽取管道应参数化于租户，而不是各租户各建一套。**

### 甲.3 要求 10 —— 重度分析任务的 MCP 化

**业主原话**：「对于需要中都分析的任务，可考虑在多人需求提出后，形成一套 MCP。」

✅ **业主已确认（2026-08-23）：「重度」。** 本条语义确定为：
**当同类的重度分析需求被多方反复提出时，把该分析能力固化成 MCP 服务。**

**与要求 9 的关系**：二者是同一模式的两个出口，**触发信号不同**：

| | skill 化（9） | MCP 化（10） |
|---|---|---|
| 触发信号 | **单方**的操作序列重复 | **多方**提出同类需求 |
| 固化的是 | 步骤 | 能力 |
| 谁受益 | 做同样操作的人 | 提同样问题的人 |
| 成本 | 低（步骤包） | **高（服务 + 契约 + 运维）** |

**本席建议的 MCP 化判据**（三条同时满足）：
① **≥3 个不同提出方**（防单人偏好）② 需求**跨项目**出现（防项目专用）
③ 该分析**有稳定输入输出契约**（否则做不成 API，只能做 skill）。

### 甲.4 要求 9 —— skill 化、三级晋升与排序

**业主原话**：「每个 Agent 操作，在执行结束后，总结一下，如果操作步骤依赖外部工具超过 8 次，
进入 skill 化整理，需要有一个 skill 管理，当这个 skill 被多次使用时，升级成租户级推广的 skill（标签），
同时进一步抽象，进入平台级 skill。（所有 skill 管理是一个排序过程，使用越多，排序越靠前。
可参考一下其他人是如何实现的，比如 GitHub 上开源项目各类 harness）」

#### 甲.4a 三级晋升与 K 分层同构 —— 一个值得利用的对称

| skill 级别 | 对应 K 层 | 晋升闸 |
|---|---|---|
| 会话/项目级 | K3 / K1 | 自动（≥8 次触发器） |
| **租户级** | **K1** | 租户级 ops 批准 |
| **平台级** | **K0** | 🔴 **平台域基线变更 ⇒ 走 §C.4e 审批闸** |

> **这一条正好补上 §C.4e 的缺口。** 裁定记录已核出：`internal/datad/` 有 `skill` 表与
> `POST /v1/skills/{name}/{ver}/approve` 端点（写权 coordinator），
> 但 `/admin/provision` 的 `install_skill` **下发时不查这张台账**（§C.4e 缺口 4）。
>
> ⇒ **要求 9 的「平台级 skill」与 §C.4e 建议二是同一件事的两端**：
> 有了平台级晋升，就必须有平台级批准；有了批准，下发就必须校验批准。**两条应合并实施。**

#### 甲.4b ⚠️ 「≥8 次外部工具依赖」是触发器，不是判据

**8 次只说明「步骤多」，不说明「可复用」。** 一次性的复杂排障也会超过 8 次
（本席的三血脉调查远超 8 次工具调用，但**它不该被 skill 化**——那是一次性取证）。

> **建议：8 次触发**总结**，总结中判**是否可复用**，可复用才进 skill 库。
> 判据：**同样的步骤序列是否会对不同输入再次发生**。
> 否则 skill 库会迅速被一次性操作淹没，**而排序机制会让它们沉底但不消失**。

#### 甲.4c ⚠️ 纯频次排序有三个已知失效模式

业主定的是「使用越多，排序越靠前」。**本席建议加三个修正项**：

| 失效模式 | 后果 | 修正 |
|---|---|---|
| **冷启动 / 马太效应** | 新 skill 永远排后面，永远得不到使用，永远排后面 | **新 skill 给曝光窗口**（如前 N 次调用中保证可见） |
| **频次 ≠ 质量** | 一个坏 skill 因排前面被反复用，**失败也计入频次**，自我强化 | **计分 = 使用次数 × 成功率**，失败应**扣分**而非计数 |
| **陈旧 skill 不下沉** | 半年前高频、现已过时的 skill 长期占据首位 | **时间衰减**（近期使用权重更高） |

> 🔴 **第二条尤其要紧**：若失败也算「使用」，则**越是让人反复重试的坏 skill，排名越高**。
> 这是排序机制会主动放大的错误，**不是随机噪声**。

#### 甲.4d 业主指定的调研 —— GitHub / 开源 harness 如何实现（✅ 已执行 2026-08-23）

**来源**（均为公开资料，无内部信息）：
Voyager（NVIDIA，arXiv 2305.16291）/ Generative Agents（Park et al., Stanford UIST 2023）/
Claude Code Skills 官方文档 / MCP Scorecard 与各 MCP registry / 业界 Skills-vs-MCP 实践讨论。

##### 发现一：触发判据 —— **没有一家用「步骤数」**

| 系统 | 何时把一段操作提升为可复用单元 |
|---|---|
| **Voyager** | 🔴 **自我验证通过之后**。技能是「已验证成功的代码片段」，失败的不入库 |
| **Claude Code** | 「你反复粘贴同一段指令/清单/多步流程」，或「CLAUDE.md 里某段**从事实长成了流程**」 |
| **Claude Code（自动记录）** | `/run-skill-generator`、`/verify` 在**跑通之后**把有效配方写成 per-project skill |
| **业主方案** | 外部工具依赖 **≥8 次** |

> **⇒ 共同点：判据是「成功」与「重复」，不是「复杂」。**
> **本席 §甲.4b 提的「8 次是触发器不是判据」由此得到外部印证**，并可进一步收紧：
> **触发条件建议改为「≥8 次 **且** 本次执行成功」**——失败的长流程不该进 skill 库，
> 它属于复盘第四段「判断失误」（甲.1），是另一条通路。

---

##### 发现二：排序 —— **业界有两条路线，且都不用纯频次**

**路线甲「算分排序派」** —— 用加权多因子，**使用量从不单独决定名次**：

| 系统 | 公式 |
|---|---|
| **Generative Agents**（业界事实标准，MemGPT/Mem0/LangGraph 均沿用或有意偏离） | `score = α·recency + β·relevance + γ·importance`，**recency 用指数衰减**（原文 γ=0.995/小时，按**最后一次访问**计），relevance = 描述向量余弦相似度，importance = LLM 打分 |
| **MCP Scorecard**（MCP 生态的信任评分） | **Adoption 35%（stars+下载量，🔴 取对数压缩）** + **Growth 15%（30 天趋势）** + **Maintenance 25%（更新新近度与发布节奏）** + Trust 15%（一方命名空间/开源许可/公开仓） + Security 10%（有无未修复告警） |

> 🔴 **这两套都是对本席 §甲.4c 三点担忧的外部印证，而且给出了比本席更具体的解法**：
>
> | 甲.4c 担忧 | 业界解法（比本席建议更具体） |
> |---|---|
> | 马太效应 | **对使用量取对数**（MCP Scorecard）——1000 次与 100 次的差距被压到远小于 10 倍 |
> | 新条目冷启动 | **增长率单独占 15%**——新条目靠**趋势**得分，不靠存量 |
> | 陈旧不下沉 | **指数衰减按「最后访问」计**（Generative Agents）+ **Maintenance 占 25%**（MCP Scorecard） |
> | 频次≠质量 | Generative Agents 的 **importance（LLM 打分）**、Scorecard 的 **Security 10%** ——本席原只提了成功率，**漏了「安全性」这一维** |
>
> **⇒ 本席修订 §甲.4c 的建议**：计分不应是「次数 × 成功率 × 衰减」这样的乘式，
> 而应是**加权和**，且**使用量取对数并限制其权重上限（建议 ≤40%）**。

**路线乙「不排序派」** —— Claude Code 的做法**根本不排序**：

- 常驻上下文里**只有 `name` + `description`（+`when_to_use`）**，二者合并后**硬截断在 1,536 字符**；
- **正文按需加载**（用到才进上下文，官方措辞：长参考材料在用到前「几乎不花钱」）；
- 选哪一个，靠模型读 description 判断相关性。

> 🔴 **这是一个比排序更根本的解法：与其把长列表排好，不如让列表本身便宜。**
> **排序解决的是「列表太长怎么办」；渐进披露解决的是「列表为什么会太长」。**
>
> **⇒ 本席建议业主采两条路线之和，且有主次**：
> **主解 = 渐进披露**（skill 列表只放名称+描述，正文延迟加载，并设硬性字符预算）；
> **次解 = 加权排序**（当同类 skill 仍多到描述都装不下时，才用排序决定谁进列表）。
> 业主原方案「使用越多排序越靠前」是次解的一个变体，**单独使用会遇到上面四个已知失效模式**。

---

##### 发现三：作用域分层 —— Claude Code 的四级与**冲突解析方向**

| 级别 | 位置 | 生效范围 |
|---|---|---|
| Enterprise | 受管设置 | **组织内全体** |
| Personal | `~/.claude/skills/` | 该用户全部项目 |
| Project | `.claude/skills/` | 仅本项目 |
| Plugin | `<plugin>/skills/` | 插件启用处 |

**冲突解析规则（🔴 这条对业主方案是一个必须现在做的选择）**：

> **「enterprise 覆盖 personal，personal 覆盖 project」——越上层，优先级越高。**
> 且 **plugin 用 `plugin-name:skill-name` 命名空间，因此永不冲突**。

**这不是唯一可能的选择，而是一个有取向的选择**：

| 取向 | 规则 | 得到 | 失去 |
|---|---|---|---|
| **治理优先**（Claude Code 选此） | 上层覆盖下层 | 平台/企业**能强制统一** | 下层无法就地特化 |
| 特化优先（另一种常见直觉） | 下层覆盖上层 | 租户/项目可特化 | 平台推不动统一 |

> **⇒ 业主的三级晋升（项目级 → 租户级 → 平台级）必须回答：平台级与租户级同名时谁赢？**
> **本席建议采「治理优先 + 命名空间逃生舱」的组合**（即 Claude Code 的完整形态）：
> **平台级覆盖租户级**（保证平台能统一推行安全/合规类 skill），
> **同时提供命名空间机制**让租户特化版可以并存而不冲突（`tenant-x:deploy` 与 `deploy` 共存）。
> **只取覆盖不给逃生舱，会逼租户去改平台 skill——那正是平台域基线变更闸要防的事（§C.4e）。**

---

##### 发现四：Skill 与 MCP 的边界 —— 业界的线比本席 v0.1 画得更准

**业界表述**：
> Skill 给的是**判断**（流程、模板、质量检查）；MCP 给的是**访问**（连数据库/API/SaaS 的标准协议）。
> **「若你的能力是一个带状态与认证的连接，就建 server；若是流程、判断与参考材料，就建 Skill。」**

**对照本席 v0.1 的判据**：

| | 本席 v0.1 | 业界 | 评 |
|---|---|---|---|
| skill | 「我怎么做」 | 流程/判断/参考材料，**无状态** | 一致 |
| MCP | 「给我一个功能」 | **有状态 + 有认证的连接** | 🔴 **业界更准**。本席第 ③ 条判据「有稳定输入输出契约」是摸到了边，但**真正的分界是「有没有状态与认证」**，不是「契约稳不稳」 |

**与业主判据的关系 —— 二者不冲突，是两个问题**：

| 判据 | 回答的问题 |
|---|---|
| **业主：多方反复提出同类需求** | **值不值得做**（需求聚合） |
| **业界：是否带状态与认证的连接** | **该做成哪个**（技术性质） |

> **⇒ 合并为两步判定**：① 业主判据过关（≥3 个不同提出方 + 跨项目）⇒ 值得固化；
> ② 业界判据分流（**有状态/认证连接 → MCP；无状态流程判断 → skill**）。
> **业界还有一条组合建议**：当一件事**既是系统又是用法**（多数真实工程属此），
> **建一个小 server 管访问 + 一个 skill 管用法**。

---

##### 发现五：一条别人踩过的坑 —— **自动 skill 化会制造噪声**

Claude Code 文档中一条实战记录（关于自动记录的 `/verify` skill）：

> 早期版本让 Claude **把每次运行学到的都折回 skill 文件**，结果造成**频繁的 merge 冲突**；
> 现改为：**只有当该 skill 把这次运行带偏了**（命令失败、缺步骤）**才改它**，
> 于是这个文件可以放心提交，不会每次会话都产生 diff。

> 🔴 **这条直接命中业主要求 9 的「每个 Agent 操作执行结束后总结 → skill 化整理」。**
> 若每次操作都回写 skill 库，**skill 库会变成噪声源，且在多 Agent 并发下产生持续冲突**
> ——而 DingWei 的目标规模是 **200+ Agent 并行**，这个问题会比单人使用严重得多。
>
> **⇒ 本席建议（新增 R2-13）：skill 自动更新须设「负反馈闸」——
> 只在该 skill 把执行带偏时才回写，执行顺利则只计一次使用量，不改内容。**
> 这与发现一的「成功才入库」是一对：**成功决定「进不进」，失败决定「改不改」。**

## 乙组 · 管理与查阅入口（要求 3 / 4）

### 乙.1 要求 3 —— 项目管理审批入口

**业主原话**：「项目管理的审批入口，如：授权、查看当前阻塞、无效讨论等。」

#### 乙.1a 本席的核心建议：这不是三个页面，是**一个待决队列**

业主举的三例——授权、当前阻塞、无效讨论——**共同点是「都在等一个人做决断」**。
若做成三个入口，业主要巡三个地方才知道有没有事；**做成一个 typed 队列，一次登录看完**。

| 类型 | 数据来源（已存在或已裁定） | 决断者 |
|---|---|---|
| **授权待批** | spec 预授权（§C.4d）、平台域资产下发（§C.4e）、上线后运维预案授权 | 按 §C.4d/§C.4e 分级 |
| **当前阻塞** | board `blocker_reason` 六值枚举 + `sla_deadline`（**数据面现成，缺的只是入口**） | 项目管理方 |
| **无效讨论** | 增补提案 §F1 阶梯硬门的解封请求（>20 coordinator 解封并**预警业主**，>40 业主解封） | coordinator / 业主 |
| 门 FAIL 待整改 | 门记录 | 执行者 + 门方 |
| 复盘待定稿 | 甲.1 | 执行者 |

> **每项须带**：类型、发起方、等待时长、**逾期标记**、一键决断入口。
> **「等待时长」是关键字段**——业主早期指出的核心痛点正是「靠 coordinator 管理，
> 容易丢失上下文后任务丢失、环节丢失、交付物丢失」。**一个按等待时长排序的队列，
> 直接把「丢失」变成「显眼的逾期项」。**

#### 乙.1b 授权入口与 §C.4e 的对接

§C.4e 核出：`/admin/provision` 有审计、有完整性校验、有防降级，**唯独没有「谁准的」**。
**要求 3 的「授权入口」正是那个缺失的「谁准的」的落点。**

⇒ 建议：**授权入口不是新增一个审批 UI，而是让所有高危执行面强制从这个队列取授权凭据**。
批准发生在队列侧，执行发生在执行面——**天然满足职责分离**（§C.4e 建议二，与业主「git 管理员 ≠ DB 管理员」同源）。

### 乙.2 要求 4 —— spec 与架构设计文档查阅入口

**业主原话**：「项目中 spec 文档和架构设计的文档查阅入口。」

#### 乙.2a 与要求 2 的区别（**必须分开，否则会做成一个东西**）

| | 要求 2 知识库 | 要求 4 文档入口 |

§C.4d 已裁定：**spec 是授权凭据**。⇒ 查阅 spec 时若看不到授权状态，等于看不到最要紧的部分。

**生命周期状态**（研发测试期有效 / **已因上线而 `expired`**，§C.4d ②③）。

## 丙组 · 身份与接入（要求 5 / 6 / 7 / 8）

### 丙.1 要求 6 —— 用户登录授权与多渠道身份验证

**业主原话**：「用户登录授权，接入飞书、企微、what's、邮件、SMS 等，用于验证身份。」

#### 丙.1a 这一条补上了 C0.1 缺失的那一半

已核实事实：契约 **C0.1「身份真实性锚（per-session principal）」在 `internal/m8/*.go` 零命中——未实现**，
而契约要求所有 mutating 操作在缺此锚时 fail-closed。这正是 mcsd 卡在 E1 的原因。

**且按 §A0.4 的根因，现有平台的 principal 是「会话」**（`owner_session`、`task_role.who`「会话/人 标识」）。
**要求 6 引入人类身份后，正确形态是三级映射**：

```
    人（飞书/企微/邮件/SMS 验证）
     └─→ 租户（业主级隔离域，RLS 主体）
          └─→ 会话 / Agent（执行主体，持 token）
```

> ⇒ **要求 6 不是「加个登录页」，它是 C0.1 的正确实现形态**：
> principal 从「会话」升为「人 → 租户 → 会话」的链，**审计与授权挂在人身上，执行挂在会话身上**。

#### 丙.1b 身份模型 —— 业主 2026-08-23 更正本席的读法

> **业主原话**：「SMS/邮件 这类身份通道**不是用于鉴别你是谁**，而是为了**二次验证你的身份对不对**。
> **主要身份识别标识依旧是飞书、企微、what's、Slack、Google Chat 这类强企业身份的平台**。」

**本席 v0.1 把 SMS/邮件读成了主身份通道，据此推出的风险偏高。按业主的正确读法**：

```
  主因子：企业 IM 身份（飞书 / 企微 / Slack / Google Chat / WhatsApp）——回答「你是谁」
     +
  次因子：SMS / 邮件 一次性验证 ——————————————————————回答「是不是本人」
     = 双因子
```

⇒ **丙.4b「中危须强因子确认」中的『强因子』，业主已经给出了具体形态：就是这个二次验证。**
本席 v0.1 悬着的那一格，业主这句话把它填上了。

#### 丙.1b-1 双因子解决的是冒名，**不解决**误判、内部越权与胁迫

**这一点必须与双因子分开记，否则会误以为上了双因子就够了**：

| 机制 | 回答的问题 | 挡得住 | 挡不住 |
|---|---|---|---|
| **双因子**（主 IM + 次验证） | **是不是你本人** | 冒名、消息伪造、账号单点失陷 | **本人被骗 / 本人判断失误 / 本人被胁迫 / 内部越权** |
| **重两签**（C1.3） | **这件事该不该做** | 单人误判、单人越权、单人被胁迫 | — |

> ⇒ **双因子 ≠ 双人。** 二次验证做到极致，仍然只有**一个人**在决定。
> **故丙.4b 表中「高危须重两签」的结论不因本次更正而改变**——
> 它依据的从来不是「因子弱」，而是「**单人不足以承担平台域基线变更的后果**」。
> ⚠️ 本席 v0.1 把这条建议的论据错误地挂在了「SMS 弱」上，**论据换掉，结论保留**。

#### 丙.1b-2 一处仍须业主定的事实差异：WhatsApp 的身份锚是电话号

业主把 WhatsApp 与飞书/企微/Slack/Google Chat 并列为「强企业身份平台」。**本席须指出一处技术差异**：

| 平台 | 身份锚 | 企业管理后台 | 设备绑定 | 可被企业吊销 |
|---|---|---|---|---|
| 飞书 / 企微 | 企业目录账号 | ✅ | ✅ | ✅ |
| Slack / Google Chat | 企业目录账号（可接 SSO） | ✅ | ✅ | ✅ |
| **WhatsApp**（含 Business API） | 🔴 **电话号码** | ❌（无企业目录） | 弱 | ❌ |

> ⇒ **WhatsApp 的身份锚与 SMS 是同一个东西——电话号**，因此**同一次 SIM swap 可同时攻破主因子与次因子**。
> 其余四家不存在这个问题（主因子在企业目录，次因子在电话/邮箱，**两条独立链路**）。
>
> **本席建议（待裁 R2-11）**：WhatsApp 归入**通信渠道**（要求 7）可以；
> 归入**身份识别**（要求 6）时降一档，或**要求其次因子改用邮件**而非 SMS，以恢复双链路独立。
> **若业主的实际使用场景中 WhatsApp 仅用于外部联络而非内部身份，此条自动不适用**——请业主一句话说明。

---

### 丙.2 要求 7 —— 渠道直连 Agent，且不增加 Agent 负担

**业主原话**：「允许飞书/企微/what's 等直接与 Agent 通讯，尽可能在不增加 Agent 多余负担的情况下实现顺畅通讯。」

#### 丙.2a 「不增加 Agent 多余负担」是明确的架构约束

**⇒ 渠道差异必须在平台侧吸收干净，Agent 只见一种统一信封。**

负担的具体来源（**须由平台侧消化，不得透出给 Agent**）：
① 各渠道**消息格式**不同 ② **长度上限**不同（现有 `send.py` 的 **3KB 分片**坑，T18 已列为待修三坑之一）
③ **富文本 / 附件**能力不同 ④ **回执语义**不同 ⑤ **乱序与重投**特性不同。

**平台侧须做**：格式规范化 → 统一信封；分片与重组；回执归一；**幂等键**贯穿（重投不重执行）。

#### 丙.2b 本条**基本落在现有能力的延长线上**（罕见的「不必重建」项）

按 §A0.4b 分界原则——**「消息如何可靠传到」保留**——本条属通信面：
现有平台已有 `bot_channel`、fanout 代理（T17）、`unifiedrobot` 默认投递机器人、多渠道投递账。
⇒ **要求 7 是现有通信层的扩展，不是新建。** 这是十条里唯一可以明确说「用现有的」的一条。

### 丙.3 要求 5 —— Agent 管理（三种接入形态）

**业主原话**：「Agent 管理，云上 Agent 新建、关闭、重启 + 导入上下文，本地笔记本/台式电脑上运行独立 Agent CLI 接入，开发环境 IDE 的插件 Agent 接入。」

#### 丙.3a 三种形态的信任等级不同，不能同一套凭据策略

| 形态 | 宿主受控度 | 建议凭据等级（按 §C.4c 分级） |
|---|---|---|
| **云上 Agent**（平台新建/关闭/重启） | **平台完全受控** | 可持 S1（生产级），按角色授予 |
| **IDE 插件 Agent** | 企业设备，部分受控 | S2 为主；S1 须显式授权 + 时限 |
| **本地笔记本 / 台式机 CLI** | 🔴 **不受控终端** | **默认仅 S2（沙盒级）**；S1/S0 须逐次授权 |

> 🔴 **本席须明确指出**：本地终端接入意味着**平台凭据离开可控边界**，落到一台平台无法审计、
> 无法擦除、可能同时装着别的软件的机器上。这与业主已定的分级原则（S0 不落任何文档/帖子/流/日志；
> 沙盒可重置 ⇒ S2，生产不可 ⇒ S1）**必须挂钩**，否则分级在最薄弱的一环失效。
>
> **建议**：本地接入的 token **短时效 + 可远程吊销 + 绑定设备指纹**，且**默认不授予**跨租户与平台域读权。

#### 丙.3b 「导入上下文」= K0–K3 分层注入，这是本条的技术核心

「新建 Agent + 导入上下文」不是拷贝一堆文件，是**按该 Agent 的租户/项目/角色，注入对应 K 层**：

```
新建 Agent(tenant=T, project=P, role=R)
  → 注入 K0（平台域·已脱敏部分）
  + K1（T 的项目 P 知识库）
  + K2/K3（角色 R 的作用域）
  + 已批准的 skill（平台级 + T 租户级，按甲.4 排序）
```

> ⇒ **要求 5 与甲组是同一套数据的两个用途**：甲组管**沉淀**，要求 5 管**注入**。
> **沉淀与注入必须同源**，否则会出现「复盘写进了知识库，新 Agent 却读不到」。

#### 丙.3c 管理面新建，下发面可复用 provision（§A0.4b 分界原则的应用实例）

§A0.1 已判 provision 通道**保留**（安全模型扎实：hub 只下发数据不下发指令；5 道闸；
版本号只在 `ack(ok=true)` 后推进）。
⇒ **Agent 管理的「管理面」（新建/关闭/重启/上下文注入决策）是新建的项目/任务侧内核；
「下发面」（把 skill/MCP/代码推到远端）复用 provision。** 二者分层，不重复造。

### 丙.4 要求 8 —— 🔴 可信渠道执行授权（**本批十条中风险最高的一条，建议优先裁定**）

**业主原话**：「飞书/企微/what's 等可信渠道可直接查询业主项目进展情况，可以执行授权操作。」

#### 丙.4a 风险陈述（v0.2 已按业主更正重估，风险等级下调）

⚠️ **本席 v0.1 的陈述有误，已作废**：v0.1 写的是「若 SMS/邮件也算可信渠道，则一次短信劫持 = 获得授权能力」。
**业主已更正（丙.1b）：SMS/邮件从来不是主身份，是次因子。** 该风险按此不成立。

**按正确的身份模型重估**：

| | v0.1 误判 | v0.2 实际 |
|---|---|---|
| 攻破授权所需 | 一次短信劫持 | **企业 IM 账号失陷 + 次因子失陷（两条独立链路）** |
| 风险等级 | 🔴 高 | **中**——已是双因子，属常规企业级强度 |

**⇒ 本席撤回「本批十条中风险最高」的定性。** 要求 8 在正确读法下是**常规双因子授权**，
建议照批其主体。**但丙.4b 的分级建议保留，论据换为丙.1b-1**：

> 双因子把关的是**「是不是你」**；
> 而**全网批量下发 / 平台级晋升 / 跨租户 / S0-S1 凭据 / 平台域基线变更**，
> 风险不在「是不是你」，在**「一个人够不够」**。
> **这类操作即使身份百分之百确证，仍应重两签。**

**唯一仍属高风险的具体项**（与身份强度无关，见丙.4c）：**渠道消息的重放与上下文混淆**。

#### 丙.4b 本席建议：查询与授权分离，授权按危险度分级

**① 查询进展 —— 可信渠道即可。** 只读，且**必须走 RLS 过滤后返回**（业主看自己租户的，不是全平台的）。
**这部分本席无保留意见，建议照批。**

**② 执行授权 —— 按危险度三级**：

| 级别 | 范围 | 渠道可做到哪一步 |
|---|---|---|
| **低危** | spec 预授权**范围内**的一次读取、门 PASS、复盘定稿 | **渠道可终结**（+ 一次性挑战码） |
| **中危** | 单会话 provision、租户级 skill 晋升、跨项目读 | 渠道**可发起**，须**强因子确认** |
| 🔴 **高危** | **全网批量下发**、**平台级 skill/MCP 晋升**、**跨租户**、**S0/S1 凭据**、**平台域基线变更** | **渠道只能发起，不能终结**；须回到强身份面 + **重两签**（C1.3） |

> **这与业主已批准的两条机制同构，不是本席另起炉灶**：
> 增补提案 **§F1 阶梯硬门**（>20 coordinator 解封并预警业主，>40 业主解封）
> 与 **C1.3 重两签**——**便利性随危险度递减**，是同一个设计语言。

#### 丙.4c 一处必须防的具体攻击

**渠道消息可被伪造或重放。** 若「回复『同意』即授权」，则：
① 消息可被截获重放 ② 群内他人可冒名 ③ Agent 可能误把**引用的历史文本**当成新指令。

**⇒ 授权动作必须绑定一次性凭据**：平台侧生成 challenge（含**待批事项摘要 + 有效期 + 单次使用**），
业主回复该 challenge 而非自由文本。**「同意」两个字不构成授权。**

#### 丙.4d 本席同时记下业主已表明的放宽立场

业主此前已明确：「对于有安全基座的环境，不影响生产的研发测试系统，可适当放宽管制」，
且「我们仍然可以先按照不放松原则执行」。

⇒ **本席建议：丙.4b 的分级按「不放松」写入纲领；放宽以「环境属性」为条件显式声明**
（如：研发测试环境 + 有安全基座 ⇒ 中危可降为渠道终结），**而不是默认放宽后再逐个收紧**。
**这符合业主自己定的顺序。**
