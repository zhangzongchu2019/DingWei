## 0. 本席对十条的结构化理解

业主给的是十条并列需求，但本席核下来它们**不是十件独立的事**，而是三组：

| 组 | 条目 | 本质 |
|---|---|---|
| **甲组 · 经验沉淀回路** | 1 复盘、2 知识库、9 skill 化、10 MCP 化 | **一个发现环节 + 三个固化出口**，共用一套三级晋升 |
| **乙组 · 管理与查阅入口** | 3 审批入口、4 文档入口 | 业主/管理者的**决断面**与**依据面** |
| **丙组 · 身份与接入** | 5 Agent 管理、6 登录验证、7 渠道直连、8 渠道授权 | **谁是谁**，以及**从哪进来** |

> 按组设计比按条设计省一半工作量——甲组四条共用晋升机制与审批闸，乙组两条共用一个待办队列，
> 丙组四条共用一套身份模型。**若按十条各做一套，会做出四套晋升、三个待办页、两套身份。**

## 甲组 · 经验沉淀回路（要求 1 / 2 / 9 / 10）

### 甲.0 回路总图

```
         ┌──────────────── 阶段复盘（要求1，发现环节）────────────────┐
         │  输入：该阶段帖子流 + 交付物 + 门记录 + blocker 记录         │
         └───────┬───────────────┬───────────────┬───────────────────┘
                 │               │               │
         事实类  ▼        操作类  ▼        能力类  ▼
        ┌────────────┐  ┌────────────┐  ┌────────────┐
        │ 知识库(2)  │  │ skill(9)   │  │ MCP(10)    │
        └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
              └───────────────┴───────────────┘
                              │
                  三级晋升（项目级 → 租户级 → 平台级）
                  平台级晋升 = 平台域基线变更 = 走 §C.4e 审批闸
```

**三个出口的判据差异**（不可混用）：

| 出口 | 固化的是 | 判据 | 载体 |
|---|---|---|---|
| **知识库** | **事实**（现状是什么） | 会被反复查询 | 条目 + commit 锚 |
| **skill** | **操作**（我怎么做） | 同一操作序列会再发生 | 步骤包 |
| **MCP** | **能力**（给我一个功能） | 多方反复提出**同类分析需求** | 服务 + API 契约 |

> MCP 有服务端、有 API 契约、有运维成本，**比 skill 重一个量级**。
> 判据必须严于 skill，否则会长出一堆无人维护的 MCP。

### 甲.1 要求 1 —— 阶段性复盘纳入项目管理

**业主原话**：「项目阶段性复盘总结，纳入项目管理的一部分。」

**「纳入项目管理的一部分」= 复盘是交付物，不是自觉行为。** 本席据此提三条落法：

1. **复盘是阶段收口的必备交付物**，与 F4' 第 ⑧ 格「版本摘要 → 晋升 K1」「spec 预授权失效登记」并列。
   **无复盘不得收口**——这是机制约束，符合业主 F6「尽可能机制约束而非纪律约束」。
2. **复盘的输入是现成的**，不需要人回忆：该阶段的**帖子流**（增补提案已解「作业无痕」）+ **交付物清单** + **门记录**（含 FAIL 与整改）+ **blocker 记录**（board 已有 `blocker_reason` 六值枚举 + `sla_deadline`）。
   ⇒ **草稿可由廉价模型生成**（同增补提案 §F 的摘要 Agent），执行者/评审者定稿。
3. **复盘的输出必须分流到三个出口**（甲.0），而不是写一篇存档了事。
   **复盘报告的结构应当强制三段**：本阶段沉淀的**事实** / **可复用操作** / **应固化能力**。
   任一段为空须写明理由——**否则复盘会退化成「顺利完成」四个字**。

⚠️ **本席建议增设一段：本阶段的判断失误**。理由：前三段都是「产出了什么」，
只有这一段是「哪里想错了」。**本席自己十四轮评审中 11 次同类方法缺陷、9 次由他审抓出**，
若当时有这一段，第 2 次就该被拦住，不必到第 11 次。**此条待业主裁。**

### 甲.2 要求 2 —— 知识库八类 + 界面查询入口

**业主指定的八类**：产品 / 业务（基于现网代码）/ 服务架构 / 网络架构 / 数据库设计 / 各接口业务逻辑 / 各主要对象介绍 / 遇到的各种坑总结。

#### 甲.2a ⚠️ 「基于现网代码」是本条的技术难点，也是最容易做废的地方

业主特意在「业务」后面加了「（基于现网代码）」。**这是要求知识与代码同源，不是手写文档。**

| 类别 | 是否会漂移 | 必须 |
|---|---|---|
| 产品 | 慢 | — |
| **业务（基于现网代码）** | **快** | **绑 commit 锚 + 漂移检测** |
| **服务架构** | **快** | **绑 commit 锚** |
| 网络架构 | 中 | 绑部署版本 |
| **数据库设计** | **快** | **绑 migration 号** |
| **各接口业务逻辑** | **快** | **绑 commit 锚** |
| 各主要对象介绍 | 中 | 绑 commit 锚 |
| 坑总结 | 不漂移（历史事实） | 绑发生时的 commit |

> 🔴 **本席须明确警告**：**不绑锚的知识库，三个月后就是下一个「作业无痕」——看起来有，实际全过期，
> 且比没有更危险**，因为人会信它。
>
> **本席自己踩过这个坑**：三血脉调查中，文档描述与线上实际运行的代码不是一回事，
> 最终只能靠**行为指纹**（信封 meta 键 / 404 来源区分 / renderer blob 字节比对）反推。
> 那次调查之所以要做，正是因为**当时没有一个绑锚的架构知识**。

**落法建议**：每个条目强制字段 `anchor`（commit / migration 号 / 部署版本）+ `verified_at`；
**锚落后于当前 HEAD 超过阈值即自动标 `stale`** 并在界面上显示，不是删除，是**降级为「历史快照」**。

#### 甲.2b 🔴 安全约束：这八类里有三类是 S0/S1 内容，入口不能是全员 wiki

**网络架构**（主机 IP、拓扑）、**数据库设计**（表结构、连接方式）、**服务架构**（部署形态）
——这三类正是攻击者做横向移动最想要的东西。

> 这与裁定记录已确认的一条直接相关：**K0（`/opt/agent-context/`）含主机 IP、会话全名、部署拓扑，
> 未完成分级脱敏前不得开放全租户只读。**
>
> ⇒ **知识库入口必须走 PG-RLS + 条目级分级**（S0/S1/S2），
> **不能做成一个「登录即可全文检索」的界面**。否则一次账号失陷 = 整个平台拓扑外泄。
>
> ⚠️ 尤须注意：**全文检索本身会绕过条目级权限**——检索结果的摘要片段可能泄露正文。
> **检索必须在 RLS 过滤后的集合上做，不能先检索后过滤。**

#### 甲.2c 与 K0–K3 分层的映射

| 八类 | 归属层 | 说明 |
|---|---|---|
| 产品、业务、接口逻辑、对象介绍 | **K1（项目/租户域）** | 随项目走 |
| 服务架构、网络架构、数据库设计 | **K0（平台域）**，且分级 | 平台级 ops 维护 |
| **坑总结** | **起于 K3/K1，可晋升 K0** | 与 skill 三级晋升同构（甲.4） |

### 甲.3 要求 10 —— 重度分析任务的 MCP 化

**业主原话**：「对于需要中都分析的任务，可考虑在多人需求提出后，形成一套 MCP。」

⚠️ **一处需业主确认的字**：「中都」本席理解为**「重度」**（重度分析任务）。
按此理解，本条语义为：**当同类的重度分析需求被多方反复提出时，把该分析能力固化成 MCP 服务。**
**若业主本意为「中台」或其他，本条判据需重写——请业主一句话确认。**

**与要求 9 的关系**：二者是同一模式的两个出口，**触发信号不同**：

| | skill 化（9） | MCP 化（10） |
|---|---|---|
| 触发信号 | **单方**的操作序列重复 | **多方**提出同类需求 |
| 固化的是 | 步骤 | 能力 |
| 谁受益 | 做同样操作的人 | 提同样问题的人 |
| 成本 | 低（步骤包） | **高（服务 + 契约 + 运维）** |

**本席建议的 MCP 化判据**（三条同时满足）：
① **≥3 个不同提出方**（防单人偏好）② 需求**跨项目**出现（防项目专用）
③ 该分析**有稳定输入输出契约**（否则做不成 API，只能做 skill）。

### 甲.4 要求 9 —— skill 化、三级晋升与排序

**业主原话**：「每个 Agent 操作，在执行结束后，总结一下，如果操作步骤依赖外部工具超过 8 次，
进入 skill 化整理，需要有一个 skill 管理，当这个 skill 被多次使用时，升级成租户级推广的 skill（标签），
同时进一步抽象，进入平台级 skill。（所有 skill 管理是一个排序过程，使用越多，排序越靠前。
可参考一下其他人是如何实现的，比如 GitHub 上开源项目各类 harness）」

#### 甲.4a 三级晋升与 K 分层同构 —— 一个值得利用的对称

| skill 级别 | 对应 K 层 | 晋升闸 |
|---|---|---|
| 会话/项目级 | K3 / K1 | 自动（≥8 次触发器） |
| **租户级** | **K1** | 租户级 ops 批准 |
| **平台级** | **K0** | 🔴 **平台域基线变更 ⇒ 走 §C.4e 审批闸** |

> **这一条正好补上 §C.4e 的缺口。** 裁定记录已核出：`internal/datad/` 有 `skill` 表与
> `POST /v1/skills/{name}/{ver}/approve` 端点（写权 coordinator），
> 但 `/admin/provision` 的 `install_skill` **下发时不查这张台账**（§C.4e 缺口 4）。
>
> ⇒ **要求 9 的「平台级 skill」与 §C.4e 建议二是同一件事的两端**：
> 有了平台级晋升，就必须有平台级批准；有了批准，下发就必须校验批准。**两条应合并实施。**

#### 甲.4b ⚠️ 「≥8 次外部工具依赖」是触发器，不是判据

**8 次只说明「步骤多」，不说明「可复用」。** 一次性的复杂排障也会超过 8 次
（本席的三血脉调查远超 8 次工具调用，但**它不该被 skill 化**——那是一次性取证）。

> **建议：8 次触发**总结**，总结中判**是否可复用**，可复用才进 skill 库。
> 判据：**同样的步骤序列是否会对不同输入再次发生**。
> 否则 skill 库会迅速被一次性操作淹没，**而排序机制会让它们沉底但不消失**。

#### 甲.4c ⚠️ 纯频次排序有三个已知失效模式

业主定的是「使用越多，排序越靠前」。**本席建议加三个修正项**：

| 失效模式 | 后果 | 修正 |
|---|---|---|
| **冷启动 / 马太效应** | 新 skill 永远排后面，永远得不到使用，永远排后面 | **新 skill 给曝光窗口**（如前 N 次调用中保证可见） |
| **频次 ≠ 质量** | 一个坏 skill 因排前面被反复用，**失败也计入频次**，自我强化 | **计分 = 使用次数 × 成功率**，失败应**扣分**而非计数 |
| **陈旧 skill 不下沉** | 半年前高频、现已过时的 skill 长期占据首位 | **时间衰减**（近期使用权重更高） |

> 🔴 **第二条尤其要紧**：若失败也算「使用」，则**越是让人反复重试的坏 skill，排名越高**。
> 这是排序机制会主动放大的错误，**不是随机噪声**。

#### 甲.4d 业主指定的调研任务（本席承接，待启动）

业主明确要求「参考一下其他人是如何实现的，比如 GitHub 上开源项目各类 harness」。

**本席建议的调研范围**：开源 Agent harness 的 skill/tool 复用机制——
主要关注 ① 何时把一段操作提升为可复用单元的**触发判据** ② **排序/检索**机制（是否也用频次，如何避免马太效应）
③ **作用域分层**（个人 / 团队 / 全局）与晋升方式 ④ skill 与 MCP-tool 的**边界如何划**。

⚠️ **此项需要联网检索，本席尚未执行。** 本件其余部分不依赖它，故先交付。
**请业主示下是否现在启动**——本席估计需要一轮专门的检索与比对。

## 乙组 · 管理与查阅入口（要求 3 / 4）

### 乙.1 要求 3 —— 项目管理审批入口

**业主原话**：「项目管理的审批入口，如：授权、查看当前阻塞、无效讨论等。」

#### 乙.1a 本席的核心建议：这不是三个页面，是**一个待决队列**

业主举的三例——授权、当前阻塞、无效讨论——**共同点是「都在等一个人做决断」**。
若做成三个入口，业主要巡三个地方才知道有没有事；**做成一个 typed 队列，一次登录看完**。

| 类型 | 数据来源（已存在或已裁定） | 决断者 |
|---|---|---|
| **授权待批** | spec 预授权（§C.4d）、平台域资产下发（§C.4e）、上线后运维预案授权 | 按 §C.4d/§C.4e 分级 |
| **当前阻塞** | board `blocker_reason` 六值枚举 + `sla_deadline`（**数据面现成，缺的只是入口**） | 项目管理方 |
| **无效讨论** | 增补提案 §F1 阶梯硬门的解封请求（>20 coordinator 解封并**预警业主**，>40 业主解封） | coordinator / 业主 |
| 门 FAIL 待整改 | 门记录 | 执行者 + 门方 |
| 复盘待定稿 | 甲.1 | 执行者 |

> **每项须带**：类型、发起方、等待时长、**逾期标记**、一键决断入口。
> **「等待时长」是关键字段**——业主早期指出的核心痛点正是「靠 coordinator 管理，
> 容易丢失上下文后任务丢失、环节丢失、交付物丢失」。**一个按等待时长排序的队列，
> 直接把「丢失」变成「显眼的逾期项」。**

#### 乙.1b 授权入口与 §C.4e 的对接

§C.4e 核出：`/admin/provision` 有审计、有完整性校验、有防降级，**唯独没有「谁准的」**。
**要求 3 的「授权入口」正是那个缺失的「谁准的」的落点。**

⇒ 建议：**授权入口不是新增一个审批 UI，而是让所有高危执行面强制从这个队列取授权凭据**。
批准发生在队列侧，执行发生在执行面——**天然满足职责分离**（§C.4e 建议二，与业主「git 管理员 ≠ DB 管理员」同源）。

## 丙组 · 身份与接入（要求 5 / 6 / 7 / 8）

### 丙.1 要求 6 —— 用户登录授权与多渠道身份验证

**业主原话**：「用户登录授权，接入飞书、企微、what's、邮件、SMS 等，用于验证身份。」

#### 丙.1a 这一条补上了 C0.1 缺失的那一半

已核实事实：契约 **C0.1「身份真实性锚（per-session principal）」在 `internal/m8/*.go` 零命中——未实现**，
而契约要求所有 mutating 操作在缺此锚时 fail-closed。这正是 mcsd 卡在 E1 的原因。

**且按 §A0.4 的根因，现有平台的 principal 是「会话」**（`owner_session`、`task_role.who`「会话/人 标识」）。
**要求 6 引入人类身份后，正确形态是三级映射**：

```
    人（飞书/企微/邮件/SMS 验证）
     └─→ 租户（业主级隔离域，RLS 主体）
          └─→ 会话 / Agent（执行主体，持 token）
```

> ⇒ **要求 6 不是「加个登录页」，它是 C0.1 的正确实现形态**：
> principal 从「会话」升为「人 → 租户 → 会话」的链，**审计与授权挂在人身上，执行挂在会话身上**。

#### 丙.1b 🔴 因子强度必须分级（这是要求 8 的前提）

| 渠道 | 因子强度 | 已知失效方式 |
|---|---|---|
| **SMS** | **弱** | SIM swap、短信劫持、运营商侧泄露 |
| **邮件** | **弱** | 邮箱账号失陷即身份失陷 |
| 飞书 / 企微 | 中（企业受控、有设备绑定） | 企业账号失陷 |
| 强因子（硬件密钥 / 平台侧独立凭据） | 强 | — |

**验证身份**用弱因子可以；**用它授权高危操作不可以**。见丙.4。

### 丙.2 要求 7 —— 渠道直连 Agent，且不增加 Agent 负担

**业主原话**：「允许飞书/企微/what's 等直接与 Agent 通讯，尽可能在不增加 Agent 多余负担的情况下实现顺畅通讯。」

#### 丙.2a 「不增加 Agent 多余负担」是明确的架构约束

**⇒ 渠道差异必须在平台侧吸收干净，Agent 只见一种统一信封。**

负担的具体来源（**须由平台侧消化，不得透出给 Agent**）：
① 各渠道**消息格式**不同 ② **长度上限**不同（现有 `send.py` 的 **3KB 分片**坑，T18 已列为待修三坑之一）
③ **富文本 / 附件**能力不同 ④ **回执语义**不同 ⑤ **乱序与重投**特性不同。

**平台侧须做**：格式规范化 → 统一信封；分片与重组；回执归一；**幂等键**贯穿（重投不重执行）。

#### 丙.2b 本条**基本落在现有能力的延长线上**（罕见的「不必重建」项）

按 §A0.4b 分界原则——**「消息如何可靠传到」保留**——本条属通信面：
现有平台已有 `bot_channel`、fanout 代理（T17）、`unifiedrobot` 默认投递机器人、多渠道投递账。
⇒ **要求 7 是现有通信层的扩展，不是新建。** 这是十条里唯一可以明确说「用现有的」的一条。

### 丙.3 要求 5 —— Agent 管理（三种接入形态）

**业主原话**：「Agent 管理，云上 Agent 新建、关闭、重启 + 导入上下文，本地笔记本/台式电脑上运行独立 Agent CLI 接入，开发环境 IDE 的插件 Agent 接入。」

#### 丙.3a 三种形态的信任等级不同，不能同一套凭据策略

| 形态 | 宿主受控度 | 建议凭据等级（按 §C.4c 分级） |
|---|---|---|
| **云上 Agent**（平台新建/关闭/重启） | **平台完全受控** | 可持 S1（生产级），按角色授予 |
| **IDE 插件 Agent** | 企业设备，部分受控 | S2 为主；S1 须显式授权 + 时限 |
| **本地笔记本 / 台式机 CLI** | 🔴 **不受控终端** | **默认仅 S2（沙盒级）**；S1/S0 须逐次授权 |

> 🔴 **本席须明确指出**：本地终端接入意味着**平台凭据离开可控边界**，落到一台平台无法审计、
> 无法擦除、可能同时装着别的软件的机器上。这与业主已定的分级原则（S0 不落任何文档/帖子/流/日志；
> 沙盒可重置 ⇒ S2，生产不可 ⇒ S1）**必须挂钩**，否则分级在最薄弱的一环失效。
>
> **建议**：本地接入的 token **短时效 + 可远程吊销 + 绑定设备指纹**，且**默认不授予**跨租户与平台域读权。

#### 丙.3b 「导入上下文」= K0–K3 分层注入，这是本条的技术核心

「新建 Agent + 导入上下文」不是拷贝一堆文件，是**按该 Agent 的租户/项目/角色，注入对应 K 层**：

```
新建 Agent(tenant=T, project=P, role=R)
  → 注入 K0（平台域·已脱敏部分）
  + K1（T 的项目 P 知识库）
  + K2/K3（角色 R 的作用域）
  + 已批准的 skill（平台级 + T 租户级，按甲.4 排序）
```

> ⇒ **要求 5 与甲组是同一套数据的两个用途**：甲组管**沉淀**，要求 5 管**注入**。
> **沉淀与注入必须同源**，否则会出现「复盘写进了知识库，新 Agent 却读不到」。

#### 丙.3c 管理面新建，下发面可复用 provision（§A0.4b 分界原则的应用实例）

§A0.1 已判 provision 通道**保留**（安全模型扎实：hub 只下发数据不下发指令；5 道闸；
版本号只在 `ack(ok=true)` 后推进）。
⇒ **Agent 管理的「管理面」（新建/关闭/重启/上下文注入决策）是新建的项目/任务侧内核；
「下发面」（把 skill/MCP/代码推到远端）复用 provision。** 二者分层，不重复造。

### 丙.4 要求 8 —— 🔴 可信渠道执行授权（**本批十条中风险最高的一条，建议优先裁定**）

**业主原话**：「飞书/企微/what's 等可信渠道可直接查询业主项目进展情况，可以执行授权操作。」

#### 丙.4a 风险陈述

本条把**授权**（平台上最高危的动作）放到了**丙.1b 中最弱的身份因子**上。
**与要求 6 合起来看**：若 SMS/邮件也算「可信渠道」，则**一次短信劫持或邮箱失陷 = 获得授权能力**。

而按 §C.4e 已核出的事实，授权能力在本平台意味着什么：
**一次下发即可替换全网 200+ Agent 的执行代码，或注入任意 MCP。**

> ⚠️ 需说明：§C.4e 的结论是**代码事实**（`main` = hub 所跑血脉），
> 该端点生产可达性仍待 prodops 核，本席无主机权限，不外推。
> **但要求 8 是在设计未来能力，风险评估应按「授权能力完整可用」来做。**

#### 丙.4b 本席建议：查询与授权分离，授权按危险度分级

**① 查询进展 —— 可信渠道即可。** 只读，且**必须走 RLS 过滤后返回**（业主看自己租户的，不是全平台的）。
**这部分本席无保留意见，建议照批。**

**② 执行授权 —— 按危险度三级**：

| 级别 | 范围 | 渠道可做到哪一步 |
|---|---|---|
| **低危** | spec 预授权**范围内**的一次读取、门 PASS、复盘定稿 | **渠道可终结**（+ 一次性挑战码） |
| **中危** | 单会话 provision、租户级 skill 晋升、跨项目读 | 渠道**可发起**，须**强因子确认** |
| 🔴 **高危** | **全网批量下发**、**平台级 skill/MCP 晋升**、**跨租户**、**S0/S1 凭据**、**平台域基线变更** | **渠道只能发起，不能终结**；须回到强身份面 + **重两签**（C1.3） |

> **这与业主已批准的两条机制同构，不是本席另起炉灶**：
> 增补提案 **§F1 阶梯硬门**（>20 coordinator 解封并预警业主，>40 业主解封）
> 与 **C1.3 重两签**——**便利性随危险度递减**，是同一个设计语言。

#### 丙.4c 一处必须防的具体攻击

**渠道消息可被伪造或重放。** 若「回复『同意』即授权」，则：
① 消息可被截获重放 ② 群内他人可冒名 ③ Agent 可能误把**引用的历史文本**当成新指令。

**⇒ 授权动作必须绑定一次性凭据**：平台侧生成 challenge（含**待批事项摘要 + 有效期 + 单次使用**），
业主回复该 challenge 而非自由文本。**「同意」两个字不构成授权。**

#### 丙.4d 本席同时记下业主已表明的放宽立场

业主此前已明确：「对于有安全基座的环境，不影响生产的研发测试系统，可适当放宽管制」，
且「我们仍然可以先按照不放松原则执行」。

⇒ **本席建议：丙.4b 的分级按「不放松」写入纲领；放宽以「环境属性」为条件显式声明**
（如：研发测试环境 + 有安全基座 ⇒ 中危可降为渠道终结），**而不是默认放宽后再逐个收紧**。
**这符合业主自己定的顺序。**
