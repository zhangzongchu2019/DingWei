# Design

## Context

现有旧Spec/任务门不是Git七阶段状态机；R7已有不可变事实存储但真实适配器未装配，R9尚未实现。能力最小基线和context记录已核路径；本轮只规定行为，不建新API/表/错误码。

## Goals / Non-Goals

- 覆盖R8-001～009：固定版本前向推进、确认/PM/交接/场景/发布证据、并发与可核查界面。
- 不部署、不实现R9渠道、R10锁、仓库写回、自动测试命名关联或新回退状态；不重开旧Spec。

## Decisions

1. **阶段与证据分开（R8-001/008/009）。** 状态对象有受控提供方/实例、仓库、变更、显式目标完整SHA及历史事件。目标版本不随HEAD静默改绑；SPEC_APPROVED及其批准前提重核时必须与提供方当前MR head完整SHA相等，前移须同步再核，不能只挑旧目标绕过当前审阅；七阶段之外的“旧版本/待核对/缺证据”是界面说明而非新增状态。工具归档是来源事件，不能直接写平台阶段。阶段只由获权显式操作和守卫结果推进，非执行部署。
2. **守卫表（R8-001～005）。** 所有边先核主体/仓库授权、目标及预期前态；各守卫都要求输入集合完整，查询失败不当零项。

| 合法边 | 业务前提 | 反向检查 |
| --- | --- | --- |
| DRAFT→SPEC_REVIEW | 明确提交审阅，受控目标版本/变更存在 | 短SHA、缺变更、无权不能提交；不是R1签核门 |
| SPEC_REVIEW→SPEC_APPROVED | 普通：当前MR head完整SHA的所需审阅批准＋全部PM同SHA明确回应；显式委员会范围额外核R7同SHA确认 | 旧SHA批准、漏所需审阅人、PM缺项/未知不放行；普通无Console确认可过，委员会缺R7不能过 |
| SPEC_APPROVED→IMPLEMENTING | 显式开始实现，重新核当前head、显式类别及对应MR/PM/按需R7前提仍有效 | head/标记变化、批准撤销或回应失效不能借旧状态开工；不新增R10锁前提 |
| IMPLEMENTING→ACCEPTANCE | 全部任务完成且有交接记录/适用关联 | 勾选单一证据、漏任务/缺交接/未知映射不放行 |
| ACCEPTANCE→ARCHIVED | 场景状态/证据完整，FAIL=0，未执行/不适用有理由 | FAIL或缺项拒绝；允许归档的未执行不能标全PASS |
| ARCHIVED→RELEASED | 可核成功release_id、具体环境及本变更版本覆盖 | 归档、版本号或失败部署不能替代；预发不冒充生产 |

3. **分类、批准与版本不改绑（R8-002/003/006/007）。** 按R8-A05已决映射，提供方MR/PR标签committee-review或当前head的proposal正向标记「需委员会确认：是」任一个即为委员会范围；完整读取证明两者皆无才走普通路径。平台不从高风险、作者、平台角色或路径推断。标记读取失败不是普通变更，任一正向标记也不被另一标记缺失/否定覆盖。审计保存分类依据与其来源/版本、所需审阅策略、每人批准所指完整SHA；GitHub/工蜂的实际审阅策略和撤回/过期字段在R8-A02核实。

   普通范围只核当前MR head所需批准＋当前PM明确回应，不依赖R7服务；委员会范围在二者之外加核同head的R7有效确认。旧SHA批准不能算当前head批准，R6/R7实质修改策略用于原审阅的过期/待核对判定，不把“无实质修改”解释为批准或确认改绑到新SHA。head、标签、proposal、所需审阅人与批准有效性均在推进提交时重核。执行/受检commit可以不同于目标规格版本，但需到固定编号的适用证明（R8-A03），不能按同编号无条件复用。保留历史批准和阶段，不生成伪造当前批准。

4. **PM只消费事实（R8-002/007）。** 从R9读取完整当前决策点及有效明确回应；零项须有完整集合证明。不同意/需修改仍保留原意见，不变成“同意”；是否据此改规格由既有决策/委员会流程处理，R8不替PM裁决。涉及改规格的新目标需当前head的MR批准及PM回应，委员会范围另需当前R7确认，旧回应/旧内容不自动沿用。R9未就绪则相关事实不可验证，不由R1知悉或默认值补齐。R8-A05已按平台架构组2026-11-01T03:1xZ裁定冻结；普通MR不新增重复Console确认动作，委员会标记与MR/PM/附加R7分别核验。
5. **场景四态与修正链（R8-004/006/008）。** 固定目标的适用Scenario全集来源于该变更增量及明确引用的基线，解析/分页不完整失败关闭；新增/删除/重命名需核映射，不能把缺编号当无场景。每条记录关联受检commit和适用目标、状态、证据、可信记录人/UTC及跳过理由。PASS/FAIL链接运行或手工报告；未执行/不适用链接说明记录，不造运行ID。修正追加引用旧记录，保留当时FAIL；当前有效结果选择规则与并发在实施设计冻结。开发自测与QA独立验收分别归因，不能冒认QA。
6. **一致性推进（R8-007/009）。** 一次操作带明确目标/预期前态与幂等关联，提交边界重核权/版本/全部守卫并同事务保存状态与依据审计。重复操作返回原事实，冲突不覆盖；依赖失效则保持真实状态并显示阻塞，不产生新成功阶段。不在此虚构具体HTTP状态码、DDL或跨系统锁，事务/引用有效期机制依R8-A01～04核实，类别映射依已决R8-A05。
7. **发布是另一事实（R8-005/009）。** 发布记录由可信发布方提供成功release_id与环境，并证明覆盖本变更目标版本；实现commit可能与规格commit不同，不按同分支名猜覆盖。多环境记录逐项展示；RELEASED显示其实际环境和依据，不能笼统将预发当生产。保留未执行/不适用，即便有真实release也不改成测试PASS。
8. **界面与权限（R8-009）。** 展示完整SHA、七阶段、显式类别与MR所需审阅/批准、适用的委员会确认、缺项/未知、前提引用、逐场景证据及具体发布环境；仓库权限沿GitHub/工蜂提供方逐主体核实，缓存不带来授权，提供方迁移不自动转移记录。敏感外链仅坐标/报告位置，按既有安全策略主动打开，不代理抓取源码或泄漏其它仓库摘要。

## Risks / Trade-offs

- “未执行但可归档”易被误读：强制显示数量/理由，不用绿色“全部通过”概括；稳定期验收是否通过仍由QA九项结论判定。
- R7/R9等外部事实与状态事务存在竞争：读后提交必须重核，一致性契约未核前不开放推进。
- 全量tasks/Scenario集合或适用映射不可信：不能以空集合、旧编号、旧Spec final补齐；保持阻塞待核，源材料修正走Git。

## Migration Plan

按已决R8-A05，先核R8-A01～04及两种提供方MR审阅/显式分类实际字段、权限和一致性、引用有效性→另派实现→各边正反矩阵及并发/缺依赖测试→隔离GitHub/工蜂真实事实集成与QA独立验收→另申请预发。原旧Spec状态不迁成新事实，无状态/证据/发布账批量回填，无部署或冻结开关授权。

## Open Questions

R8-A05已决，不再挂起类别映射；真实提供方当前head/所需审阅/标签/批准等接口仍待核。普通变更不因R7默认未装配而被误加门，委员会范围仍需真实R7；R9未实现/发布事实未核不能因planningComplete被视为可用。回退/跳步例外若需新增，应另行决策，不在本单悄悄开放。
