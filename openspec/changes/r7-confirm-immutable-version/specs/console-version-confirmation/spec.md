## ADDED Requirements

### Requirement: R7-001 确认永久绑定完整坐标
平台 MUST 将每次确认记录为受控仓库身份、规范变更目录、完整 commit SHA、可信确认人、服务端 UTC 时刻和明确确认含义的不可变事实。坐标必须指向该仓库该 commit 下存在的变更目录；不接受可变 ref、短 SHA、任意 URL 或缺失含义的确认，不从 Git 作者推导确认人。

#### Scenario: R7-001-S01 完整确认可追溯
- **WHEN** 获权委员会成员确认仓库 A 的变更 X 在完整 commit C 的明确范围
- **THEN** 记录含 A、X 目录、C、实际成员、UTC 时刻和确认含义，重读保持原值

#### Scenario: R7-001-S02 不完整或伪造坐标不得产生确认
- **WHEN** 仅提交分支或短 SHA、跨仓 commit、缺失目录/含义、路径穿越或客户端冒填确认人
- **THEN** 拒绝并且无有效确认写入，不补用当前 HEAD 或 Git 作者

### Requirement: R7-002 委员会确认与 MR 审阅分开
Console MUST 将确认动作仅提供给有确认资格且当前有仓库 read 的研发管理委员会主体；资格、权限或坐标无法验证时拒绝写入；普通变更以 MR 审阅为准。界面与记录必须区分「委员会确认」和「MR 审阅」，不得以 MR 通过生成委员会确认，也不得要求普通变更多走一次 Console 确认。

#### Scenario: R7-002-S01 合格成员执行委员会确认
- **WHEN** 有仓库 read 和委员会确认资格的成员执行确认
- **THEN** 生成标为委员会确认的记录，与同页 MR 审阅分别呈现

#### Scenario: R7-002-S02 越权和重复审阅门均被识别
- **WHEN** 普通审阅者尝试委员会确认、委员会成员仓库权限已撤销、资格/ACL/commit 查询失败，或普通变更只有 MR 通过
- **THEN** 前述越权/无法验证格均拒绝且不写记录；只有 MR 通过格仅显示 MR 结果，不自动生成或要求补点委员会确认

### Requirement: R7-003 实质修改使原确认失效
需求、场景、范围或任务实质修改后，平台 MUST 按已批准 R7-PM01 A 保守文件变化策略（仅 tasks.md 勾选、tasks.md 的「交接记录」节变化与内容不变 archive 移动豁免）使原确认对当前版本失效并显示「针对旧版本」。保留原确认和所指 commit，不覆盖、不自动复制到新版本；不涉及该变更的提交不得仅因仓库 HEAD 改变而失效。非实质修改也不得改变原确认的绑定 SHA。

#### Scenario: R7-003-S01 四类实质修改逐项触发失效
- **WHEN** C 已确认后，C2 分别改变需求约束、验收场景、适用范围或任务内容（四格独立执行）
- **THEN** 四格原确认均显示针对旧版本且不计作 C2 的有效确认，需要针对 C2 再确认

#### Scenario: R7-003-S02 无关提交不得误失效或迁移
- **WHEN** C2 分别仅改变其它能力代码、tasks.md 勾选、交接记录节，或只移动到 archive 且文件集合/内容不变（四格独立执行）
- **THEN** 不标成因实质修改失效；确认仍明确绑定 C，不改成 C2，界面说明当前版本与所确认版本的关系；若任一豁免夹带任务文字/需求/场景/范围实质修改，仍判实质变化并标旧版本

### Requirement: R7-004 不确定比较与并发不产生假有效
平台 MUST 留下用于版本比较的两端 SHA、策略版本与判定依据；策略未裁定、文件不可读或比较失败时显示「待核对」，不得宣称旧确认覆盖新内容。确认提交与版本推进并发时，记录只能对应实际审看的 commit；若当前版本已变，重新比较并提示旧版本或待核对，不得静默确认最新 HEAD。

#### Scenario: R7-004-S01 并发推进仍只确认所读版本
- **WHEN** 成员读取 C 后提交确认，同时目标已推进到有实质修改的 C2
- **THEN** 如保存只保存 C 的历史确认，C2 未获有效确认，显示旧版本并提示重新确认

#### Scenario: R7-004-S02 比较失败不得复用绿标
- **WHEN** C2 无法读取、策略未定或比较器错误
- **THEN** 显示待核对及原因，留原 C 记录，不将缓存的有效结论用于 C2

### Requirement: R7-005 强推及不可读历史不转移确认
平台 MUST 以原仓库与完整 SHA 读取确认，不以分支名、目录名或同名仓库重新绑定。force push、删分支、重建分支或历史 commit 不可读时，保留原确认坐标并如实提示可读性/比较状态；强推后实质修改仍按 R7-003 失效。分支保护不代替平台验证。

#### Scenario: R7-005-S01 强推后新内容没有继承确认
- **WHEN** 分支从已确认 C 强推至不同内容 C2，变更目录仍同名
- **THEN** 原记录仍指 C，C2 不继承确认；可比较的实质变化标旧版本，不可比较标待核对

#### Scenario: R7-005-S02 历史缺失不得悄悄改指当前版本
- **WHEN** C 被清理不可读，或同名路径在另一仓库出现
- **THEN** 显示原仓库/C 与不可读原因，不显示替代仓库或 HEAD 内容为已确认内容

### Requirement: R7-006 Console 可见确认版本与含义
Console MUST 在确认前、确认结果和历史记录持续显示仓库、变更、所确认完整 commit、确认人、时刻、含义与当前有效性；当前浏览 commit 与所确认 commit 不同时分别标明，不得只展示短 SHA、分支或「已确认」绿标。记录读取也必须逐主体核仓库权限，失败不暴露私库记录或正文。

#### Scenario: R7-006-S01 浏览新版本仍看得见旧确认坐标
- **WHEN** 用户有权浏览 C2 并查看 C 的确认历史
- **THEN** 可核到完整 C、C2、身份/时刻/含义及旧版本或比较结果，MR 与委员会标签分开

#### Scenario: R7-006-S02 撤权后缓存不泄露确认记录
- **WHEN** 当前用户仓库权限被撤销或无法验证，再访问历史记录（含缓存命中）
- **THEN** 拒绝读取，不返回记录/正文，不用服务账号或上次授权兜底

### Requirement: R7-007 新确认不抹历史且不等于发布
平台 MUST 使针对新 commit 的再确认成为独立记录，保留旧确认与失效依据；重复提交同一确认操作不得制造重复确认事实。委员会确认、MR 通过、tasks 勾选或 archive 均不得在本能力中产生验收完成或发布事实。

#### Scenario: R7-007-S01 再确认有独立历史
- **WHEN** C2 实质变化后获权成员完成新确认，并重试同一操作
- **THEN** 存在 C 旧记录与一条 C2 新确认，重试不增加重复事实；无自动发布记录

#### Scenario: R7-007-S02 通过和勾选不得伪造完成
- **WHEN** 仅收到 MR 通过或仓内 tasks 全勾选/archive，且未有人执行有效委员会确认
- **THEN** 不生成委员会确认，也不宣称验收或发布完成
