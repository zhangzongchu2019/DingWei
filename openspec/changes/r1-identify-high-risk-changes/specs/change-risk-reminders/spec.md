## ADDED Requirements

### Requirement: R1-001 七类风险按三路并集识别
平台 MUST 覆盖资金、权限、数据删除、对外接口或协议、SLA、数据迁移、个人数据与隐私（含跨境）七类；使用 risk:funds、risk:permission、risk:data-delete、risk:api-contract、risk:sla、risk:migration、risk:privacy。标签、改动路径、diff 新增行关键字任一路命中即纳入结果，并保留全部命中依据；无命中不生成风险提醒。路径读取各仓 openspec/risk-paths.yaml 与平台默认表，规则组合纳入版本，不由未匹配的其它路线否决命中。

#### Scenario: R1-001-S01 七类三路各自能触发
- **WHEN** 对冻结规则为七类分别仅提供标签、路径或新增行关键字命中（七类×三路共21格，逐格执行），以及多路同时命中同一类
- **THEN** 各格都返回对应类别和来源依据，多路结果取并集并去重，不因另外两路未命中而漏报

#### Scenario: R1-001-S02 无命中和近似样本不误报
- **WHEN** 对七类三路分别提供按同一规则明确不满足的近似/无命中对照（21格），且其它路线均无命中
- **THEN** 结果无风险类别、MR和Console都无风险提醒；任何漏报或错报都使相应用例FAIL，不凭无日志判PASS

### Requirement: R1-002 判定纯函数与输入完整性
判定 MUST 为纯函数：输入仅含带固定仓库/base/head SHA的完整 diff、标签快照与已解析不可变规则版本；规则版本包含默认表、仓库规则blob及匹配语义。输出为类别、规则编号与标签/路径/新增行号依据或明确无法判定；相同输入结果稳定，不依赖网络、时钟、全局可变表或投递状态。关键字仅检查文本新增行，不检查删除行、上下文行和diff头；不完整/截断输入不得报告无风险。

#### Scenario: R1-002-S01 重放输入得到同一并集
- **WHEN** 使用同一diff/标签/规则版本重复调用，改变运行时刻或投递是否成功
- **THEN** 得到相同排序/去重后的类别和依据；新增行命中可定位head行号，判定不产生网络、存储或评论副作用

#### Scenario: R1-002-S02 存量内容和取件失败不伪判
- **WHEN** 关键字只在删除/上下文行或+++文件头，或diff/规则缺页、截断、坐标不符（各格执行）
- **THEN** 前一组不产生关键字命中；后一组显示无法判定及原因，不冒充完整无风险或成功检查

### Requirement: R1-003 两种提供方的可信仓库输入
diff/标签/评论与合并事实 MUST 经仓库托管提供方接口取得，支持 GitHub 的 dingwei 与工蜂业务仓；标识包含提供方/实例、稳定仓库/MR身份和完整commit。服务端核当前主体读取权限及受控来源、指定版本完整性，评论另核写权限；拒绝任意URL、跨仓替换和不可验证权限。迁移不自动转移权限、坐标或缓存，所有旧事实保留原提供方身份。

#### Scenario: R1-003-S01 两种托管来源采用同一判定契约
- **WHEN** 在分别获权的GitHub与工蜂测试仓取得同等规范化diff/标签/规则
- **THEN** 相同规范化输入判定一致，提醒指向各自真实仓库/commit，读取与评论权限分别可核

#### Scenario: R1-003-S02 提供方混淆和越权不泄露
- **WHEN** 仅服务账号有权、用户撤权、评论缺写权限、同名仓库迁移或返回错误commit（各格执行）
- **THEN** 不跨主体返回私库结果，不向错误MR写评论；评论失败如实留待处理，不以另一提供方/HEAD/文件服务补源码

### Requirement: R1-004 命中在MR与Console双端可追溯提醒
每次完整命中 MUST 在该MR评论与获权Console各形成一条汇总提醒；同commit标签/规则变化依R1-006更新原提醒并追加修订，不另建独立提醒。提醒含七类中实际命中类别、规则版本、依据（标签、路径、关键字规则及新增行号）、负责人和完整commit。两个渠道分别记录提醒ID、服务端UTC时刻、投递结果及MR评论位置；同一判定输入重试幂等，部分失败只补缺失渠道，不将受理/失败当双端送达。不转发源代码行、补丁、秘密或可授予仓库读取的链接。

#### Scenario: R1-004-S01 双端提醒完整且重复调度不刷屏
- **WHEN** 一个commit命中多类/多路并重复调度同一输入
- **THEN** MR和Console各仅一条汇总，全部命中依据和完整commit可核，负责人一致，无源代码正文或凭据外发

#### Scenario: R1-004-S02 缺端和未知送达不得记成功
- **WHEN** 任一渠道写失败/超时未知，或已有MR评论后Console重试（各格执行）
- **THEN** 各端保留真实结果，只补未完成端，不复制成功评论；缺一端时不能显示双端提醒完成，也不由提醒故障阻断MR合并

### Requirement: R1-005 负责人知悉与合并时刻留痕
平台 MUST 让可信变更负责人对指定提醒修订/commit执行“已知悉”，记录其身份、服务端UTC时刻和原命中依据；重复知悉不产生矛盾事实，其他人不得冒认。合并时刻来自提供方可信合并事件并记录来源与接收时刻；未收到事实时如实未知，不用知悉或评论时刻代替合并。已知悉不是MR通过、委员会确认或PM回应。

#### Scenario: R1-005-S01 负责人知悉并可追溯实际合并
- **WHEN** 负责人知悉C的提醒，随后提供方报告该MR已合并
- **THEN** 可分别核负责人、提醒/知悉/合并时刻、来源与C；重试知悉不改原时刻，不生成审批通过

#### Scenario: R1-005-S02 冒认知悉和伪合并被拒
- **WHEN** 他人冒认负责人、只回消息ACK，或MR未合并但有人知悉（各格执行）
- **THEN** 不产生负责人的有效知悉或虚构合并时刻，不把知悉当PM同意/委员会确认

### Requirement: R1-006 追加命中commit重新提醒与同commit修订
追加commit C2命中时 MUST 对C2重新生成双端提醒，即使C已知悉或MR已合并；C的知悉不覆盖C2。无命中的C2不生成风险提醒，C历史保留；同一固定判定输入的重复事件不重复提醒。按已决R1-PM01 A，同commit标签或规则变化 MUST 更新双端原提醒并追加可追溯修订，记录前后输入版本、命中集合、修订身份与UTC，保留历史修订及知悉。命中集合变化时重置该修订的「已知悉」，旧知悉不覆盖新集合；集合未变化不因该变化重置知悉。同一输入重放不重复追加修订或重置知悉；取件失败不冒充集合变化或清零风险。

#### Scenario: R1-006-S01 已合并后追加命中也再提醒
- **WHEN** C已知悉且MR合并后，关联变更又出现命中的C2，并重复接收C2事件
- **THEN** C2在双端各有一次新提醒且待知悉，C记录仍绑定C；重复事件不再产生额外提醒

#### Scenario: R1-006-S02 新版本无命中不沿用旧风险
- **WHEN** C命中但C2完整判定无命中，或同C2原事件重放
- **THEN** 不因C旧命中给C2造提醒，不迁移C的知悉；重放不刷屏，历史仍能查看

#### Scenario: R1-006-S03 同commit标签或规则改变并产生不同命中集合
- **WHEN** C的原提醒已知悉，标签变化或规则版本变化使完整判定的命中集合增加、减少或归零（两种变化来源×三种集合变化逐格执行）
- **THEN** MR与Console更新各自原提醒并追加可追溯修订，展示新集合/无命中，重置该修订知悉；不新建独立提醒，旧修订及其知悉身份/时刻仍可核

#### Scenario: R1-006-S04 同集合与重复事件不误重置或刷屏
- **WHEN** C标签或规则改变但完整命中集合未变，随后重放新输入，或命中集合已变并被负责人知悉后再重放（逐格执行）
- **THEN** 首次输入变化仅更新原提醒并追加一次修订，集合未变不重置知悉；重放不追加修订、不重置已知悉、不另发独立提醒

#### Scenario: R1-006-S05 不完整判定与迟到旧知悉不能掩盖新风险
- **WHEN** 同C的新标签/规则读取失败、diff截断，或集合变化后旧修订的知悉请求才到达（逐格执行）
- **THEN** 前组显示无法判定并保留最后完整修订，不伪造无命中/集合变化；迟到旧请求不知悉新修订，新修订仍待负责人知悉，双端失败依R1-004保留真实投递结果

### Requirement: R1-007 风险提醒不阻塞合并
风险命中、负责人未知悉、部分投递失败或规则检查不可用 MUST NOT 成为本能力新增的合并/状态推进审批门；不得新增签核表单、要求别人确认或自动关闭MR。Console如实显示风险及检查/送达状态，不将“未阻塞”伪装成无风险。其它既有CI、权限或R8/R9独立前提不因本能力被绕过。

#### Scenario: R1-007-S01 命中但未知悉仍不新增门禁
- **WHEN** 高风险命中未知悉，且MR原有独立条件已满足
- **THEN** 提醒保留可见，合并不因R1而被阻止；知悉后也不要求第二人签核

#### Scenario: R1-007-S02 提醒故障不能创建阻塞或假绿
- **WHEN** 规则读取未知或评论失败，或R9仍有未回应决策点
- **THEN** 前两格不生成R1合并阻塞也不显示无风险成功；R9未回应不因R1不阻塞而被伪造成已满足

### Requirement: R1-008 PM决策边界独立
proposal存在“待PM决策”事项时 MUST 由独立R9决策流程处理；R1只提供风险/版本引用，不能替R9发送决策请求、采纳回应或宣告PM闭环。普通风险知悉不能清除决策点，也不能推进依赖PM的SPEC_APPROVED。R9未接入时明确显示其依赖未就绪，不能悄悄视为无需PM。

#### Scenario: R1-008-S01 风险与PM事项分别呈现
- **WHEN** 同一变更既有风险命中又有待PM决策点
- **THEN** 风险提醒引用固定版本，PM事项交R9独立记录，负责人知悉风险后PM仍保持其真实状态

#### Scenario: R1-008-S02 不能以知悉替代决策
- **WHEN** 负责人点击已知悉或R9尚未装配，但尚无有效PM回应
- **THEN** 不自动生成PM回应、外发PM消息或标决策完成，不因此宣称SPEC_APPROVED前提已满足
