### 0.2 冻结锚上的机器派生实算值〔判据以 checker 现算为准，本合同不写手写分母〕

`§23–§24 heading = 14` · `owner_sp 含 SP8 的 E 行 = 36（E.1=25 · E.3=5 · E.4=6）` ·

🔴 **同域两个 SP 的派生规则**：`GOV` 域由 **SP0（定义层 §1–§4）** 与 **SP8（治理面 §23–§24）** 共用，
架构的域列**无法**区分两者。故原型入口集合采**差集派生**：
`架构 §13 主责域含 GOV 的入口`（9） **减去** `已收口 SP0 正文 COVERAGE 中【完整认领】的入口`（5） ＝ **4**（`s1` / `s8` / `s8r` / `s8h`）。

🔴 **减数按【完整认领】取，部分认领的入口不得整块扣除**〔首轮评审阻断①的闭法，取方案 B〕：
SP0 认领 `#s1` 的原文是「typed 待决队列**中的** `spec_fix`/`spec_claim`」——**它认的是入口内的一个切片，不是整屏**。
若按入口 ID 整块扣，`s1` 上**批准/待决决策**那一片就两边都不认领，而双方各自的 checker 仍报未知 0 ——
**分母短在减数粒度上，不是短在集合上**。故：
- 判据：SP0 认领单元格中 id 之后带「中的／仅／部分／两类／之一」等限定词者 ＝ **部分认领**，**不参与扣除**；
- `check.sh` 有硬断言：任一部分认领入口若被扣掉，直接 exit 2（报「切片之外将无人认领」）；
- 另有正交反测：把 SP0 那行的限定词去掉，`s1` 才会被整块扣——证明该守卫是**吃劲的**，不是装饰。
⇒ **`s1` 整块留本件**；SP0 已认领的 `spec_fix`/`spec_claim` 两类由本件**只读消费、不改其语义**（`AC-SP8-04`）。

## 1. 六个必备面

### ① 系统对接

SP8 设计 `GOV` 治理面的授权两轴、spec 预授权与失效、渠道授权分级、平台域基线变更范围与审批形态、
紧急件通道与分发面校验，并细化既有接口：

- `GOV-CMD-IssueEffectGrant`（本件主责：签发、范围、时限、消费与吊销）；
- `GOV-CMD-DecidePending`（治理面消费：批准/拒绝落账与二次签）；
- `GOV-CMD-SubmitSpec`、`GOV-QRY-ResolveGateSet`（**只写 seam**：授权判据如何引用其产物，不改其定义层语义）。

不新增架构接口 ID，不新增事件 ID。GOV 消费 AccessCtx 与 principal；向各 effect owner 输出 grant 与批准结论。

### ② 运行约束

- **两轴并存取严**：审批的两个轴同时成立才放行，任一不足即拒；不得以一轴覆盖另一轴；
- **spec 预授权**：授权来自 spec 版本与其锚，spec 一改锚即变；预授权范围不得越出 spec 声明；
- **失效由机制触发**：不靠人记得——收口、版本变更、时限到期均自动触发失效并落账；
- **上线后由运维预案承接**：上线后的访问授权依据是运维预案条目，不是临时口头许可；
- **渠道授权分级**：按渠道 assurance 分级授权，弱渠道不得承载高危 effect；
- **平台域基线变更**：范围以 §24.1 为准；**批次签数由批内最高危项决定**，不得按平均或多数稀释；
- **紧急通道只允许单调收紧**：任何执行后会扩大任一主体权限或可达范围的动作，**不得走紧急路径**；
- **分发面必须校验批准**：分发侧独立校验 approval，不以"上游说批了"为准；
- 所有批准与 grant 走受控 transaction、幂等键与 generation，审计不可改。

### ③ 预计数据

只定义测量出口：grant 签发/消费/吊销/过期数、二次签等待与超时数、预授权失效触发数（按触发源分）、
渠道分级拒绝数、基线变更批次数与批内最高危档分布、紧急件使用数与事后补审完成率、分发面校验拒绝数、
批准链审计量。每项须带依据与复核点，无实测写 `unknown`。

### ④ 环境要求

- 设计只读冻结件，不接生产、不签发真实 grant、不改数据库、不执行真实审批；
- 不新增外部依赖；复用既有 repository/outbox/audit seam 与 Go 标准库；
- 实现须在 SP1 AccessCtx 与 SP7a 受控 transaction 内；缺任一前置 fail-closed；
- fixture 不含 secret、真实企业授权数据、真实凭据或个人可识别事故。

### ⑤ 设计约束

1. **范围不扩**：仅设计 §23、§24；SP0 定义层、SP1 身份、各 effect owner 业务语义只写 seam。
2. **不改上游已收口件**：与 SP0/SP1/SP2/SP3 seam 对撞一律停路径并登记交裁，不单方给上游产物加必填字段。
3. **主体只认 principal**：批准方、二次签方、紧急件申请方均为 verified principal；Agent 只入 audit provenance。
4. **按 effect 判不按名判**：紧急通道准入只看「执行后是否存在任一主体的权限或可达范围被扩大」。
5. **取严不取宽**：两轴、批次签数、渠道分级、继承关系一律取严；任何"取宽"路径须显式登记为例外并落账。
6. **失效是机制不是提醒**：预授权失效必须由收口/版本/时限事件驱动，不得只写"应当及时清理"。
7. **分发面独立校验**：批准结论在消费侧必须可独立复算，不接受调用方自述已批准。
8. **代际与幂等**：grant 与批准记录带 generation 与幂等键；迟到的批准/吊销按 generation 栅栏丢弃。
9. **不新增依赖**：不引入新数据库、新中间件、新架构接口或事件 ID。
10. **SP7b 随本域交付**：本件定义 GOV 治理面 schema/migration/cutover/rollback 合同。

### 4.1 评审协议

- verdict 词表仅 `PASS/NO/INCONCLUSIVE`；任一阻断未闭即 NO；
- **最多 4 轮**：每轮全文一次性给全量阻断，作者一次性整改，不逐条往返；
- 第 3 轮仍有范围/语义争议交 coordinator/业主裁定，第 4 轮只签最终 verdict；
- 三位评审者须对同一 commit 独立 PASS（3/3），不以多数票替代；
- 只判本轮阻断，不翻旧账；旧问题仅在直接破坏本设计时入阻断。
