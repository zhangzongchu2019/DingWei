# 批准记录的【授权根】—— 谁能证明一条批准确实出自门方

> 🔴 **本件当前【没有任何 ACTIVE 后端】。这是实况，不是没写完。**
> ⇒ 任何**已登记的受控例外**当前一律判 **UNKNOWN（exit 2）**；
> 🔴 **例外本身、以及依赖该例外的那个闸，都不得报 PASS。**

## 一、为什么需要它

乙域 terra 的两个变异（判于 `fix/e-registry-and-18-1` @ `434b8fe`）证明：
只要「批准」是一次**字符串比对**，它就不是批准 ——
例外栏填字面 `terra`（仓内并无其批准记录）放行；`AUTHOR_SESSION` 由环境变量覆盖后执笔方自批放行。

⚠️ 第二版把批准记录放在**工作区文件**里，仍未解决根：
**那份文件在执笔方的写权范围内** —— 证据仍落在被判方可改的面上。

## 二、机制 ＝ 丙（门方独占件），精确版〔乙域 terra 收尾裁定 2026-08-26〕

| # | 条款 |
|---|---|
| 1 | 批准记录落 **reviewer-owned 独占件 / 独占受保护分支** |
| 2 | `approval_ref` 解析到 **不可变 commit ＋ 记录 ID**，形如 `<门方会话>@<40位 commit>#<记录ID>` |
| 3 | 记录逐项绑定 `claim_id · 被抑制对象 · 件 · 行指纹 · 理由码 · 批准人 · UTC` |
| 4 | **CI 从远端受保护 ref 验其可达**（`merge-base --is-ancestor`），且**批准人 ＝ 该记录 owner／门方** |
| 5 | 执笔方**无写权、无自批权**（执笔方会话名写死在 `specs/gates/lib/exceptions.sh`，不读环境变量）|
| 6 | 🔴 **ACTIVE 后端缺失 / 不可取 / 验证失败 ＝ UNKNOWN（exit 2）**，一律不得 PASS |

🔴 **用「不可变 commit」而不是「读工作区台账」的理由**：
**指到一个 commit，就把证据钉在了历史里，改不动也删不掉**；
而工作区那份文件，执笔方随时可写。

### 另两条候选的处置（同一裁定）

| 候选 | 裁定 |
|---|---|
| 甲：`git blame` 作者 | ❌ **只是元数据，不是授权** —— 不作后端 |
| 乙：GPG 签名台账 | ⚠️ 可**日后叠加**在丙之上；🔴 **无密钥信任根 / 撤销根时，不可单独作后端** |
| 丙：门方独占受保护 ref | ✅ **采用**，即上表六条 |

## 三、启用方式（🔴 由门方或 coordinator 加，不由执笔方加）

```
ACTIVE: reviewer-owned-protected-ref
REF: <门方会话名> <远端受保护 ref> <记录在该 ref 内的路径>
```

例（**示例，当前未启用**）：

```
REF: zzc-chatgpt56terrazhangzongchu-2642 refs/remotes/origin/review/approvals-terra approvals/terra.approvals
```

记录行格式（TAB 分隔八列）：

```
<记录ID> <claim_id> <被抑制对象> <件> <行指纹> <理由码> <批准人> <批准时刻UTC>
```

门方名册取自**同一 commit** 内的 `reviewers.txt`（不取工作区那份 —— 同上一条理由）。

**本件当前的 ACTIVE 行：无。REF 行：无。**

## 四、能力边界（写明不假装）

⚠️ 本机制在**仓侧保护尚未授权**（CODEOWNERS / 保护分支 / 必过状态检查，属业主件）时，
仍挡不住「有人把 ACTIVE / REF 行直接写进本件」这一类 —— 挡它的是那条受保护分支本身的写权。
🔴 **不得因为本机制存在，就宣称「例外已受控」**；当前只做到了
「例外的**形状**受控、且在授权根落地前**一律不放行**」。
