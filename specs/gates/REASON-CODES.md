# 抑制/豁免的【受控理由码】与其机器可判后置条件

> 🔴 **立本件的直接原因**（乙域裁定归执笔方实现，2026-08-26）：
> 豁免理由此前是**自由文本**，闸只校「非空」。
> **执笔方曾以「跨行误命中」为由，压住两处【行内就有】的过期口径断言，而闸照旧返回 0。**
> ⇒ **理由无人核 ＝ 闸有一个没人看的后门。**
>
> **本件把「理由是否属实」从语义问题降为形状问题**：
> **判据交给码，叙述留给人。** 码不在表内即拒；码在表内则跑其后置条件。

## 〇、🔴 判据的来源：**豁免有两种，此前被同一个标记同时承担**

> **丙域原话（2026-08-26）**：
> **「`style-ok` 的本义是『指出了问题的那句话不算问题』，而这两处用它给真正的过期断言发了通行证 —— 【豁免代替修复】。」**

| | 性质 | 应有处置 |
|---|---|---|
| **标注豁免** | 评审标注里**引述**了旧断言 —— 那句引述不该被判成旧断言本身 | ✅ **自动**：剥离标注后判剩余，**无需登记、无需批准** |
| **内容豁免** | 正文里**真有**过期断言，拿理由把它挡住 | 🔴 **须结构化登记 ＋ 人工批准 ＋ 逐处绑定** |

🔴 **旧机制的错，不在于「有豁免」，而在于用同一个 `style-ok` 同时承担这两件事** ——
于是**第二种搭了第一种的便车**。
⚠️ **执笔方那两处「跨行误命中」的压制，正是【内容豁免伪装成标注豁免】。**

### 由此直接推出（归口方的推论，执笔方认为成立并已实现）

> **内容豁免的定义里就含「人工批准」；批准不成立则豁免不成立。**
> ⇒ **闸不校验批准方，就等于承认了一种「无批准的内容豁免」，而按定义它不存在。**

⇒ 本机制的三个维度**不是三条独立要求，是同一个定义的三个面**：
**逐处绑定**（是哪一处）· **受控码 ＋ 后置条件**（凭什么）· **人工批准**（谁准的）。
**缺任一个，它就不再是「内容豁免」，而是又一次「豁免代替修复」。**

## 一、格式

例外条目第 4 列写作 `<code>` 或 `<code>：<补充说明>`。
· **`<code>` 参与判定**，须在下表内；
· 🔴 **`<补充说明>` 只给人读，不参与判门** —— 它可以自由写，但**不承担判据职能**。

## 二、码表与后置条件（**逐码可判**）

| code | 语义 | 🔴 机器可判后置条件 |
|---|---|---|
| `cross-line-false-positive` | 命中来自跨行拼接，非本行 | **该行【行内不得】含被抑制短语**<br>⚠️ **执笔方那次编造的理由正是此码，会被本条当场拆穿** |
| `historical-narrative` | 沿革叙述，描述旧状态 | 该行须含**明确时点表述**（`vX.Y` / 日期 / 「之前」「当时」「原」）<br>🔴 **且不得含现在时标记**（「现有」「现为」「目前」）—— 见沿革通则 |
| `rv-annotation` | 评审方标注中引述旧断言 | 该行须落在 `【RV…】` 标注段内 |
| `is-current-rule` | 词面误命中，本行实为现行规则 | 被抑制短语须**同时出现在权威定义节**（`〔权威定义〕` 标记所在节）内 |
| `evidence-of-absence` | 断言内容本身就是「该对象不存在」 | 该行所指对象**确实不存在**（可实查）<br>⚠️ 在**路径锚闸**上此条**天然成立**（闸只在路径确实不存在时才走到判码这一步）⇒ 该通道的判断量全在 approval，码只挡「选了个不相干的码」|
| `mention-not-assertion` | 该行只是**提及**旧措辞，并非断言现状 | 被抑制短语须落在**引号内**（`「…」` / `『…』` / `"…"`）<br>🔴 自由文本写「这只是提及」谁都会写；**引号是形状，形状可判** |
| `normative-not-process` | 该行是**规范内容**，不是评审过程叙述（体例闸通道）| 后置条件限制**它能用在哪类命中上**，不去判语义：<br>· 命中若是**版本戳更正 / 沿革自述 / 过程叙述**形态 ⇒ **一律拒**（那正是本闸要拦的，用本码即豁免代替修复）<br>· 只有命中落在**角色/评审方词**上才许用（规范里确实有「关于这些角色的规定」）<br>⚠️ **判不了这一句究竟是不是规范内容** —— 判断量在 approval |

🔴 **未列入本表的码一律拒**（不做「未知即放行」）。
🔴 **空码一律拒**（空码 ＝ 没码，与空理由同性质）。

## 二之二、🔴 **`approval_ref`：批准必须是一条可解析的记录，不是一个名字**

> **立本节的直接原因**（乙域 terra 复验 `fix/e-registry-and-18-1` @ `434b8fe`，两个变异实测）：
> ① 例外「批准方」栏填字面 `terra`，而仓内**并无 terra 的任何批准记录** ⇒ 旧实现 rc=0；
> ② `AUTHOR_SESSION` **可由环境变量覆盖**，改个名字执笔方即可自批 ⇒ 旧实现 rc=0。
>
> 🔴 **「批准方」是一次字符串比对，不是一次批准核验。字符串不是证据。**

**例外键（六列）**：`claim_id` ＋ `被抑制对象` ＋ `件` ＋ `行指纹` ＋ `理由码` ＋ `approval_ref`
（terra 定的最小键是前者去掉「被抑制对象」的五元组；本实现多带对象列，因为一行可能有**多个**命中，
而**例外的粒度必须是短语，不是行** —— 否则第二个命中会搭第一个的便车。）

| 情形 | 判 |
|---|---|
| `approval_ref` 缺失 / 空 | **拒（exit 1）** |
| 含未决词（待 / 未 / pending / TODO） | **拒** |
| 形状不是 `<门方会话名>#<台账号>` | **拒** |
| 台账不存在 / 台账内无此号（**不可解析**）| **拒** |
| 台账行的 `claim_id` `件` `行指纹` `理由码` 任一不符（**失配**）| **拒** |
| 台账 `# OWNER:` ≠ 批准方，或批准方不在 `specs/gates/reviewers.txt` | **拒** |
| 批准方 ＝ 执笔方 | **拒**（🔴 执笔方会话名在库内**写死**，不读环境变量）|
| 以上全过，但**授权根无 ACTIVE 后端** | 🔴 **UNKNOWN（exit 2）**，不是 PASS |

实现：`specs/gates/lib/exceptions.sh`（三闸共用）；授权根：`specs/gates/approvals/TRUST-ROOT.md`。

## 二之三、🔴 三类抑制**统一**走本机制（乙域全闸契约）

> terra 原话：「`style-ok` / `status-ok` / `path-ok` 等抑制均属**特权例外**；每个例外须**精确绑定**
> 被豁免对象、理由、reviewer approval，**不能由执笔自由文本生效**。
> 每闸反测必须**同时**有『真实违规＋行内编造抑制＝拒』和『经受控例外的合法对象＝过』；
> **例外缺失 / 失配 / 未知不得 PASS**。」

| 通道 | 闸 | 旧机制 | 现机制 |
|---|---|---|---|
| `style-ok` | `superseded-claims-gate.sh` | 整行跳过 → 结构化登记（v2 校「批准方」字符串）| 受控例外 v3 ＋ `approval_ref` |
| `style-ok` | `prose-style-gate.sh` | `grep -v` **整行跳过** ＋ 只校理由非空 | 受控例外（同一套库）|
| `path-ok` | `path-anchor-gate.sh` | `grep -v` **整行跳过** ＋ 只校理由非空 | 受控例外（同一套库）|
| `status-ok` | `status-consistency-check.sh` | `grep -v` **整行跳过** ＋ 只校理由 ≥8 字 | 受控例外（同一套库）|

🔴 **注意第一、二行：同一个 `style-ok` 标记被【两个闸】各自解释。**
RV-乙18 只改了已撤销断言闸那一个，体例闸这一个原封不动 ——
**「改了三类抑制里的一类」这句话本身还说宽了：连那一类都只改了一半。**
⚠️ 记此一笔：**判「某个规则改完了没有」，要按【使用点】数，不是按【规则名】数。**

🔴 **「只校理由非空 / 够长」是长度，不是批准。**
⚠️ **上一版只改了三条通道里的一条** —— 写下「三类抑制均属特权例外」的那个人只改了 `style-ok`。
**这正是「改了规则未同步引用点」的自指形态**，记在此处备忘。

### 迁移期的【冻结基线】

统一之日仓内已有 4 处旧抑制（`path-ok` 1 处、`status-ok` 2 行共 3 处短语命中、`style-ok`（体例闸）1 处），
而**有效批准现在拿不到**（授权根待门方裁定）。一刀切等于用「全仓红」代替治理，
故按乙域给 ㉙ 的同一口径立**棘轮**：

| 规则 | |
|---|---|
| 基线按**行指纹**绑定 | 该行内容一改即掉出基线，必须走批准 |
| 基线**不可新增** | 不在基线内的新抑制一律拒（fail-closed，**天然单调**，不靠计数比大小）|
| 每次运行打印 | 基线数 / 当前数 / 增减 |
| 基线的**理由码列只是备注** | 🔴 基线条目**不跑**后置条件（它本就不是受控例外）；写在那里只为让人看懂债务是什么 |

🔴 **基线不是批准**，是「已知未治理」的可见化；输出里必须与 PASS 分开写
（`PASS WITH REGISTERED DEBT`）。授权根落地后须逐条补批准并从基线删除。

## 三、能力边界（写死，勿读成更宽）

⚠️ 本机制判**【理由码与行形态是否相符】**。
🔴 **判不了【这条豁免该不该给】** —— 那是门方的判断。**闸过 ≠ 豁免正当。**
⚠️ 亦**判不了码选得对不对**：选了一个后置条件恰好满足、但语义不符的码，机器看不出来 —— 归门方。
🔴 **也判不了「这条批准该不该批」**：`approval_ref` 核验的是「这条批准**记录存在、且与这一处逐项对得上**」，
不是「门方的判断正确」。**闸过 ≠ 豁免正当。**
🔴 **更挡不住「直接改判据文件本身」**（改台账 / 改名册 / 改授权根）—— 挡它的是**仓侧保护**
（CODEOWNERS ＋ 保护分支 ＋ 必过状态检查），该项**尚未授权**，属业主件。
⇒ 故当前对「授权根是否成立」的默认答案是 **UNKNOWN，不是 PASS**。
