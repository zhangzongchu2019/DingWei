## 1. 六个必备面

### ① 系统对接

本任务交付一份新的平台架构件，内部同时承载：

1. 目标态分域定义；
2. 域内、跨域及平台边界接口契约；
3. 逻辑、运行、部署、数据、安全、可靠性、可观测与迁移架构。

架构件须对接新版 SpecDoc 的 SP0–SP8、附录 E 约束与原型可达入口。接口设计不另立第四件，
但必须在架构件内成为可独立审查的完整部分，不能散落在组件说明中。

### ② 运行约束

- 不以未经实测的 TPS、Agent 数、数据量或延迟作为选型结论；未知量明确列为待测参数。
- 身份链未就绪时，mutating 操作与状态观测 fail-closed。
- 企业隔离、人层隔离、幂等、代际、outbox、封存与紧急面均须给失败行为，不只写正常路径。
- 任何“高可用、低延迟、可扩展”表述必须同时给测量出口或降为目标，不得写成现状事实。

### ③ 预计数据

本合同不编造规模数。架构正文须建立“已知值 / 未知值 / 复核点”表，至少覆盖：

- 企业数、每企业 principal 数、项目/任务/node 数；
- 在线 Agent、同 principal 并发 consumer、帖子与通知 fanout；
- 知识条目、附件、审计与 outbox 增长；
- 峰值读写、批处理窗口、保留期与恢复目标。

未知量不得阻止逻辑边界设计，但凡影响容量、分片、池大小或部署形态的结论，必须标明验证时点与 owner。

### ④ 环境要求

- 设计环境：当前 Git 仓与冻结输入，不接生产、不改数据库、不改部署。
- 目标环境至少区分平台域、企业域以及研发测试 / preprod / prod；环境属性来自受控部署源，不信请求自述。
- 凭据、真实企业数据、主机地址与 secret 不进入架构正文或测试夹具。
- 涉及真实 PG、备份/恢复、RLS、故障切换的运行证据由相应交付验证门取得，本合同只定义被测对象与期望。

### ⑤ 设计约束

以下约束在本任务中不可由执笔方自行放宽：

1. **重新设计**：不得复制旧 A§ 结构、编号、域表或结论后改名；旧架构不是新结论的证据。
2. **目标域先于代码包**：先按业务责任、权威数据、事务边界和策略边界定域，再映射现有包；不得把目录树直接当领域模型。
3. **接口随域带出**：每个域定义同时给 commands / queries / events / capabilities；跨域调用必须有明确方向。
4. **单一权威**：同一概念、接口、枚举、错误码或状态机只设一个权威定义，其余位置引用，不复述第二份。
5. **身份不可降级**：可信主体为 `principal`；`agent` 仅溯源，永不参与授权或门判定。
6. **企业与人分轴**：企业决定库边界，人决定 `owner_principal` 与责任；不得再用一个含糊 tenant 字段承载两层。
7. **读写路径收敛**：领域数据访问经受控仓储接口；旁路、迁移、报表与紧急面均须显式列出，不把例外藏在“内部调用”。
8. **接口设计并入架构件**：不新增独立接口文档，但接口章节必须可独立验收。
9. **不扩施工范围**：本任务只产设计件及其验证材料，不实现代码、schema、部署或 cutover。
10. **依赖不增**：新增外部依赖须逐项给必要性、替代方案与退出成本，否则默认不引入。

## 3. 目标态分域合同

### 3.1 定域判据

一个目标域必须能回答以下问题，缺一项不得成域：

1. 它对哪类业务结果负责？
2. 哪些数据由它唯一权威维护？
3. 哪些不变量必须在它的事务边界内成立？
4. 哪些策略由它判，哪些只能消费上游判定？
5. 它向外暴露什么，明确不暴露什么？
6. 它失效时影响什么，是否允许降级？
7. 它依赖谁，谁依赖它，是否形成环？

### 3.2 覆盖主题而非预设域

新设计至少须覆盖下列责任主题，但允许基于上述判据合并或拆分；本表不是目标域清单：

- 企业、人、渠道、会话与可信 principal；
- spec、规则、审批与平台治理；
- 项目、任务、node、门、发版与复盘；
- 上下文、知识、visibility 与生命周期；
- skill、MCP、provision 与资源目录；
- 帖子、通知、摘要、附件与封存；
- Agent 管理、渠道接入、运行资源与紧急面；
- 受控仓储、企业库路由、迁移与审计。

### 3.3 分域完备性

- 每个 SpecDoc 章节必须有且仅有一个主责域，可有协作域；无人认领数为 0。
- 每项权威数据必须有唯一 owner；“多个域共同维护”不成立，须改为一主多消费者。
- 跨域同步必须标权威方向、延迟容忍、重复/乱序处理和修复方式。
- 依赖图须可计算；同步调用环为 0。确需反馈环时，须通过事件/任务表达并给终止与幂等条件。
- 当前 `internal/`、`cmd/` 包须全部映射到目标域或横切层；映射完整不等于目录结构就是目标域。

## 4. 接口设计合同

### 4.1 接口分层

| 层 | 范围 | 最低要求 |
|---|---|---|
| **平台边界** | IM/HTTP/WebSocket、Agent、ops、对象存储、Git、LLM、PG | 协议、认证、信任边界、版本、限流、失败与审计 |
| **跨域** | 目标域之间的 command/query/event/capability | owner、调用方向、schema、幂等、超时、错误、可观测与兼容 |
| **域内稳定 seam** | 需隔离存储/策略/外部 SDK 的内部接口 | 允许实现替换，但不得绕过域不变量 |

普通函数调用不因“存在”自动成为架构接口；只有跨越责任、信任、事务、进程或替换边界者进入接口目录。

### 4.2 每个接口的必填字段

每项接口须有稳定 ID，并填齐：

`owner_domain`、`consumer`、`transport`、`operation/effect`、`request/event schema`、`response/result schema`、
`principal source`、`AccessCtx`、`authorization point`、`idempotency key`、`generation/version`、`transaction boundary`、
`timeout/cancel`、`retry/dedupe`、`error taxonomy`、`audit event`、`compatibility`、`negative cases`。

不适用字段必须写理由，不能留空。

### 4.3 强制接口族

架构正文至少逐族建立目录并指向权威定义：

1. 认证器 → 连接 → 信封 → Receiver 的可信主体传播；
2. `principal → enterprise database` 注册映射与 `AccessCtx`；
3. 项目/任务/node 与 board/mcsd 的命令、查询、事件；
4. 门结果、待决队列、发版与回滚 capability；
5. 受控仓储 API、企业库事务包装与 RLS 上下文；
6. 上下文/知识 ingest、query、visibility 与运行态 MCP；
7. skill/MCP catalog、push/pull、provision、ack 与卸载；
8. 帖子/通知/outbox/cursor/digest/附件；
9. Agent 生命周期、渠道接入、环境供给与紧急 sidecar；
10. 管理、审计、指标、健康与恢复接口。

### 4.4 接口级红线

- `agent` 不进入授权输入；授权唯一主体为经验证的 `principal`。
- enterprise/org 不取自请求字段；由服务端可信主体映射得出。
- 跨企业无自由 capability；企业内跨人能力须显式列资源、目的、时限与审计。
- 领域 SQL 不暴露裸连接，不允许调用方绕过受控事务包装。
- 外部副作用必须有授权、幂等、审计与结果引用；不得借“模板/数据”跳过契约门。
- 错误不得用成功空集掩盖拒绝；拒绝前不得先查询敏感数据。

## 5. 技术架构合同

新版架构正文至少含以下视图，且视图之间必须使用同一组受控 ID：

1. **上下文视图**：平台边界、外部主体、系统与信任边界；
2. **目标域视图**：职责、权威数据与依赖；
3. **组件视图**：域内组件及其接口实现责任；
4. **运行视图**：进程、并发、队列、定时器、连接池与故障传播；
5. **部署视图**：edge、平台服务、sidecar、平台库、企业库及外部依赖；不写真实地址和凭据；
6. **数据视图**：一平台库 + N 企业库、表 owner、RLS、归属快照、digest、outbox 与迁移边界；
7. **安全视图**：principal 链、AccessCtx、PEP/PDP、预授权、break-glass、secret/redaction；
8. **可靠性视图**：幂等、代际、CAS、outbox/ACK、重放、封存、恢复与降级；
9. **可观测视图**：结构化日志、指标、trace、审计、告警及每项 SLO 的数据源；
10. **迁移视图**：现状 → 过渡 → 目标，双写/回填/验证/cutover/rollback 与不可逆点；
11. **容量视图**：只采用有依据的规模值，未知量列 benchmark/压测计划；
12. **决策记录**：备选、取舍、被拒方案、假设与复核触发条件。

## 6. 现状映射与迁移合同

### 6.1 证据规则

- 代码搜索范围必须与断言作用域一致；按概念搜索，不只搜字面关键词。
- “未找到”只能支撑所声明范围内的缺证，不能直接推出全系统不存在。
- 每项现状结论附源码/配置/脚本证据；运行行为若未实测，标 `unverified`。
- 旧架构件中的现状数字、包数与部署结论一律重新实取，不继承。

### 6.2 映射表

每个现有包、进程、持久化对象至少归为：

- `retain`：语义与边界均可保留；
- `adapt`：保留实现但加受控接口/上下文；
- `rewrite`：现有模型中心与目标责任冲突；
- `retire`：目标态无可达入口或被新能力替代。

每行须给目标域、迁移责任 SP、前置、兼容窗口、回滚点与验收门。

## 7. 追踪与一致性合同

### 7.1 双向追踪

- `SpecDoc requirement → domain → interface → component/data → acceptance`
- `prototype reachable entry → user action → interface → domain → result/error state`
- `package/process/table → target domain → migration state`

正向无落点、反向无来源均为阻断；不能用“见全文”作锚。

### 7.2 受控标识符

域、组件、接口、事件、数据对象、部署单元分别使用不同前缀；同一 ID 只允许一个权威定义。
引用须可解析，枚举须逐项一致，图与表不得各自发明别名。

### 7.3 冲突处置

- SpecDoc 与原型冲突：登记冲突，不由执笔方静默选择；交 coordinator/业主裁。
- 目标约束与代码现状冲突：目标不降级，记录迁移差距。
- 两条安全约束不可同时满足：fail-closed，进入评审，不以“更易实现”裁断。

### 8.2 语义验收

- [ ] 接口设计没有把外部副作用藏进“数据/模板”以规避审查。

### 8.3 证据验收

- [ ] 所有现状断言带搜索范围或运行证据；未实测项不写成事实。
- [ ] 输入指纹、文件规模、版本与评审锚实算一致。
- [ ] 追踪矩阵双向无断链；计数由脚本/查询生成，不手写总数作为权威值。

### 8.4 门结果

评审方按全文一次性给完整 findings，不逐点往返；最多三轮。任一阻断未闭合则 NO。
执笔方自检、lint、脚本全绿只作旁证，不能替代 opus50 与 deepseek 的独立 verdict。
