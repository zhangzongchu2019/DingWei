## 使用与治理

1. **持有**：本清单由门方持有与维护；作者（opus50）不得修改（§4.1、§7.2——与「implementer 不能自签门 PASS」同一条纪律）。
2. **打勾即门**：`[x]` 只由门方打；每项须附证据坐标（文件 · 行 · 命令 · 输出），空勾无效。
3. **演进**：本清单自身的修订走「提案 → 门方批准」；作者在评审中发现的漏项（如丙域各轮的实证）以「候选增补」提交，门方定收不收。
4. **与机器分工**：speclint / arch-refcheck 已覆盖的形状项（§N 存在性、计数写死、表格完整、符号混用）**不再人工复核**；本清单只承担机器判不了的实质（E.3 #47c：lint 能力边界）。
5. **生效联动**：本清单（三域合并版）首次用于架构评审，即 SpecDoc §0.4 第 2 项生效前置的闭合证据之一；闭合前 SpecDoc 不得被任何子 spec 引用为依据（§0.4）。

## 附：裁断（任务 2）——8-24 三域架构评审无 checklist 完成并 PASS，是否须重走

**结论：不须重走。但 PASS 的效力边界必须钉死。**

1. **对象不同**。§0.4 第 2 项的 checklist 是「SpecDoc 生效为规范」的前置，服务的是**以 SpecDoc 为依据的后续评审**（子 spec、SP7a、实现门）。8-24 三域评审的对象是 **SpecDoc 文本本身**（文档一致性核验），不是 §0.2 分级所指的「目标工程」的架构评审——该工程尚未开工，其架构评审尚未发生。
2. **循环依赖防护**。checklist 的候选输入是 E.4，而 E.4 的正确性（计数、互引、覆盖）正是 8-24 评审的审查内容。要求「评审规范文本前先有从该文本派生的 checklist」是循环依赖——checklist 不可能先于被评审件存在。「架构评审开始时生成」只能合理读为「**首个以本件为依据的**架构评审开始时」。
3. **效力边界（必须钉死）**。8-24 三域 PASS = **文本一致性 PASS**，不等于 SpecDoc 生效、不等于施工放行。SpecDoc 现为草案（生效前置 #1 Spec Kit 结构、#2 checklist 未闭）。任何人引用 8-24 PASS 作为施工依据 = 误读，属 E.1 可登记违规。
4. **衍生命题同答**。架构设计 v0.7 的三域评审同样是文本评审（其 A§0.0 自标「已过的门：无、不得作为施工依据」），不须重走。真正的架构评审（首个应为 SP0 / SP1 或 SP7a）开始前，本 checklist 必须已就位并由门方持有——**那是红线，不是建议**。
5. **落账建议**：本裁断记评审台账；checklist 三域合并版落成即报 coordinator 归口，作为 §0.4 第 2 项的闭合证据链起点。
