# spec 起草自查件（产品方用）

> 🔴 **本件不判门。** 硬门是 §4.6.2，人审是 §4.6.4。
> **本件全过 ≠ 可进待认领池** —— §4.6.4 明写「不得因『机器项全过』而免人审」。
>
> 🔴 **本件不是 checklist。** checklist 是 **reviewer-owned**（§4.1 · §7.2：只有 reviewer 能打 `[x]`，
> 执笔方不得代写、不得代勾）。**故本件通篇不使用 `[ ]` 形态** ——
> 起草方自备一份带勾选框的表自己勾，形式上就与自签门 PASS 无法区分。
>
> ⚠️ **本件是 DingWei 侧的附加件，不是 Spec Kit 的模板。**
> Spec Kit 及其模板属 immutable 名单第一批（§4.2 要求 2 · §16.5），**不得改、不得提案改**。
> 本件叠加在其之上，只补 DingWei 特有的属性头块（§5.2）与内容五面（§4.7.1）。

## 第一部分 · 骨架（照此填，缺项写「无」，不留空）

🔴 **§4.7.1 铁律：允许声明「无」，不允许不提。**
留空会让「漏写」与「确实没有」在机器侧无法区分 —— 这是本件全部"缺什么"判据的根。

### 1.1 属性头块（§5.2 七项）

⚠️ **七项不是产品方一个人填的**，§5.2 定了三方分填。
**产品方只填自己那格，其余照填「待 tech 填」/「待 ops 填」** ——
**「待填」本身是合法取值，留空不是。**

| 类 | 属性 | 取值域 | 填写方 | 本 spec 取值 |
|---|---|---|---|---|
| A | `外部契约变更` | 无 / 兼容新增 / 破坏性 | **业务语义层＝产品方**；接口层＝tech | |
| A | `数据模型变更` | 无 / 加列加表 / 改列删列改语义 | tech | |
| A | `影响范围` | 单模块 / 跨模块 / 跨服务 | tech | |
| B | `在产影响` | 不影响 / 灰度可回滚 / 直接影响在产 | ops / owner | |
| B | `回滚成本` | 重启即回滚 / 需回滚数据 / 不可回滚 | ops / owner | |
| B | `安全面` | 否 / 是 | ops / owner | |
| C | `预估节点数` | 数字 | tech | |

### 1.2 内容五面（§4.7.1）

| 面 | 写什么 | **不**写什么 | 主要填写方 | 本 spec 内容 |
|---|---|---|---|---|
| **① 系统对接** | 外部契约：接口 · 数据格式 · 依赖方与被依赖方 · 兼容性承诺 | 内部模块间调用 | 业务语义＝产品方；接口层＝tech | |
| **② 运行约束** | 并发量 · 数据量 · 时限 · SLO · **降级与超时行为** | 「高性能」「响应快」等不可验表述 | 业务期望＝产品方；SLO 须 tech 确认 | |
| **③ 预计数据** | 预计用户规模 · 工作时段 · 并发量约定 | —— | **产品方主场**（§4.7.2 业主定） | |
| **④ 环境要求** | 依赖的外部系统与版本 · 必需的隔离域 · 所需凭据级别（§22.4） | 部署步骤、安装手册 | tech / ops | |
| **⑤ 设计约束** | **限定解空间的决策**：不引入 X / 必须复用 Y / 不得新增某类路径 | 类图 · 表结构 · 时序 · 算法选择（属 §25.3） | 产品方可填 | |

## 第二部分 · 缺什么（完备性自查）

**逐条自问，答"否"即为缺项。这一部分是形状判据，可机器化。**

| # | 自问 | 依据 |
|---|---|---|
| 1 | 属性七项**每一项都有取值**（含「待 tech 填」）？ | §5.2 · §4.7.1 铁律 |
| 2 | 五面**每一面都出现**（含写「本 spec 无外部对接」）？ | §4.7.1 |
| 3 | ③ 里**每一个预计值**都带 `依据`？（类比系统实测 / 业务方给定 / 历史数据外推 / **明确标「无依据，暂定」**） | §4.7.2 #1 |
| 4 | ③ 里**每一个预计值**都带 `复核点`？（上线后 N 周 / 达到某使用量 / 某里程碑） | §4.7.2 #2 |
| 5 | ④ 中若含**跨边界访问**，是否已按 §23.2 预授权格式写（**范围 / 用途 / 时限三字段非空**）？ | §4.7.1 ④ 连带 |
| 6 | ② 中是否写了**降级与超时行为**（不只是正常路径）？ | §4.7.1 ② |
| 7 | ② 中的表述**能否由产物反证**？（出现「高性能」「响应快」即为不可验表述） | §5.1 判据二 |

## 第三部分 · 哪里逻辑不对（内部自相矛盾自查）

🔴 **本部分只查【你自己写的两处是否打架】，不查【业务逻辑对不对】。**
后者本件判不了，见第四部分。

| # | 若…… | 则必须…… | 打架的样子 | 依据 |
|---|---|---|---|---|
| 1 | `外部契约变更 = 破坏性` | 承认要过**架构评审 ＋ 用例评审 ＋ 交付验证** | 同时写「本次走轻量流程 / 不需要评审」 | §5.4a `R-CON-01` |
| 2 | `数据模型变更 = 改列删列改语义` | 承认要过**架构评审 ＋ 交付验证（含回滚演练）** | 只写"加个字段而已" | §5.4a `R-DM-01` |
| 3 | `安全面 = 是` | 承认**代码评审门方必须是安全角色** | 因「才改五行」而略过 | §5.4a `R-SEC-01` · §5.8 |
| 4 | `在产影响 = 直接影响在产` | 承认要过**交付验证 ＋ 执行结果评审** | 写「灰度就行」而属性仍取该档 | §5.4a `R-PROD-01` |
| 5 | `回滚成本 = 不可回滚` | 承认须**架构评审 ＋ 业主签署** | 无业主签署位 | §5.4a `R-RB-01` |
| 6 | `预估节点数 = 大` | **先做拆分设计** | 未拆而直接进实现 | §5.2 C 类 · §4.4 |
| 7 | ⑤ 里写了某条约束 | 用 §4.7.1 判据自问：「**这东西变了，要不要重新评审 spec？**」<br>**要 ⇒ 留在 ⑤；不要 ⇒ 它是设计**，该搬去 §25.3 架构设计文档 | 把表结构 / 时序 / 算法选择写进了 ⑤ | §4.7.1 ⑤ 判据 |
| 8 | 任一属性取了值 | 自问「**事后拿什么产物能证伪它？**」答不上来 = 不可验证声明 | 声明「数据模型变更＝无」而交付物 diff 里会出现 migration | §5.2 硬性纪律 2 |
| 9 | 任一面写了「无」 | 自问是「**确实没有**」还是「**还没想**」 | 用「无」代替"还没想清楚" | §4.7.1 铁律 |
| 10 | 想因「改动小」把 `安全面` 从「是」调到「否」 | **不可以** —— 安全面是独立维度，**不得被「改动小」稀释** | 「五行改动而已」 | §5.2 硬性纪律 1 |

> ⚠️ **第 1–5 条是同一个动作**：§5.3「每属性独立映射到必须加哪些门 → 取并集」，
> **禁止先算总级别再查门**。产品方在此只需承认并集，不需自己定级。

## 第四部分 · 本件判不了什么（照实写，免得被当成门）

| 判不了 | 归谁 |
|---|---|
| **业务逻辑对不对** —— 需求本身是否成立、是否该做 | §4.6.4 人审 |
| **填进去的值真不真** —— 预计用户规模拍得合不合理 | §4.7.2 #3：实测偏离超阈值 ⇒ 触发 spec 复核 |
| **两处各自合法但互不一致**的枚举 | 门方（附录 E.4 #60 ②）|
| **引用存在但语义不符**（引对号引错义） | 门方（附录 E.4 #60 ①）|
| **是否可以进待认领池** | §4.6.2 硬门 ＋ §4.6.4 人审，**本件不参与** |

🔴 **本件全部答完，只说明"形状齐了、自己没跟自己打架"。**
**它不构成任何门的通过依据。**
